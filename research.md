# Research: Layered architecture (domain/services/coordinator/compute/view) vs strict MVVM for a Qt6+VTK+CUDA desktop app

## Summary
Official Qt guidance favors **MVP over MVVM** for QML; MVVM is described as a "misnomer" in the Qt context because QML binds C++ QObjects directly. Nokia's public "Core UI Architecture" (Neptune 3 UI) mandates a store/worker QObject layer that is the *only* entity allowed to talk to service instances, kept view-free and headless-testable — the closest published analog to this repo's coordinator+services split. In QML terms a separate ViewModel class is usually redundant state: a coordinator QObject exposing Q_PROPERTY/slots to QML already *is* the "view model."

## Findings
1. **Qt/QML recommends MVP, not MVVM.** The Qt blog series "Qt Widgets to Qt Quick" describes the legacy Qt Widgets "MVC with a twist" as a code-reuse problem and recommends moving to a clean **MVP** — freeing business logic from widget controllers into a proxy/controller layer. Qt's Model/View documentation likewise treats MVC/MVVM as "varying implementations" sharing one principle: separate the code that displays data from the code that reads/modifies it. [Qt.io: Qt Widgets to Qt Quick, part 2](https://www.qt.io/blog/qtwidgets-to-qtquick-application-journey-part2); [Felgo: Separation of Model, View and Logic Code](https://felgo.com/doc/apps-howto-model-view-separation/)
2. **A coordinator / QObject mediator is a recognized Qt idiom.** Official **Neptune 3 UI Core UI Architecture** documents a `store` layer that is the only entity allowed to talk to service instances; views only reference stores; panels/controls have no store dependency. Stores expose an interface so views bind to a mock/simulated store, enabling harness tests without services. This is the closest published analog to a 5-layer domain/services/coordinator/view split. [doc.qt.io: Neptune3UI Application Architecture](https://doc.qt.io/Neptune3UI/neptune3ui-application-architecture.html)
3. **Non-UI QObject coordinators (state machines) are common and headless-testable.** The SO answer pattern "your app is a state machine: transitions between stages dictate a UI change, not a UI driving logic" matches the "controller must not inherit QWidget" rule seen in real Qt codebases (e.g. vnote's `controllers/AGENTS.md`: controllers are QObject mediators, MUST NOT inherit QWidget, translated into service calls/UI feedback in one direction only). Qt's State Machine framework provides the API for this. [vnote controllers/AGENTS.md](https://github.com/vnotex/vnote/blob/master/src/controllers/AGENTS.md); [Qt State Machine Overview](https://doc.qt.io/qt-6/qtstatemachine-overview.html)
3. **CUDA/GPU-backed ViewModels stay headless via injected cost/executors.** Teams keep the compute boundary testable by injecting the GPU cost function / executor (e.g. a `std::function` into a pure optimizer) so unit tests never touch CUDA; the QObject view-model is a thin proxy into a service layer. The NVIDIA omniverse Qt/Vulkan example shows GPU-backed golden tests must run under a display or offscreen path. ParaView's Offscreen rendering docs confirm VTK can render without a display (pvserver/pvrenderserver), which is the VTK answer to headless render tests. [ParaView: Offscreen Rendering](https://www.paraview.org/paraview-docs/latest/cxx/Offscreen.html); [Qt Testing Guide (QTest signals/models/viewmodels)](https://helpmetest.com/blog/qt-testing-guide/)
4. **Coordinator vs ViewModel is mainly a lifetime/ownership choice, not two clean, separately-documented patterns.** An MVP-in-QtQuick writeup (mimec.org) shows the presenter is a QML component wiring view+model with bindings; a separate ViewModel class is not needed because QML binding to C++ QObject props IS the role MVVM would assign to a ViewModel. When the model is GPU/optimizer-backed, the cost runs on a worker QObject whose signals marry UI-thread to worker-thread — the coordinator's job is exactly this headless QObject worker. [mimec.org MVP in QtQuick](https://www.mimec.org/blog/model-view-presenter-in-qtquick)

## Recommendations
1. **Keep the 5-layer split (MVP-flavored), do NOT add a separate ViewModel layer.** Treat `jtml_domain`/`jtml_services`/`jtml_coordinator` as the store/worker/controller layers that never inherit QWidget; `view` + thin `app` stay the only true GUI. This gives headless tests of the coordinator as a QObject/QThread state machine, matching the "Neptune store layer" official guidance.
2. **Pit MVC and use MVP-appropriate naming:** `coordinator` is the QObject that QML binds to; it exposes Q_PROPERTY and slots but holds no UI/window logic, owns the worker-thread lifecycle, and re-emits signals on the main thread (QTBUG-2842).
3. **Keep the CUDA seam injected** (cost function/executor as `std::function` into the pure DIRECT optimizer), so the GPU boundary is a host-side seam and headless tests never touch CUDA. Optionally run a golden path offscreen via VTK offscreen/`Offscreen` for a single oracle.
4. **Headless-render boundary:** keep compute (DIRECT) in a worker-thread service with status callbacks; render only the VTK canvas, and give tests an offscreen VTK mode as the golden-test surface instead of the real display.

## Clarification questions for planner
- Is a coordinator per top-level screen (screen-switch + vertical slice) enough, or do you want a single global coordinator? (Neptune 3 uses per-app "Main/store." The choice drives WHERE the state machine lives.)
- Should the coordinator own the DIRECT lifecycle & worker thread (headless QObject/QThread workers, per job) or should a lightweight QObject be given a ready-to-use controller handle for the view? (Determines whether coordinator is thin or fat.)
- Strictly: is MVVM demanded by anyone, or is the real goal "testability + decoupling"? If the latter, MVP / store-split is cheaper and matches Qt guidance exactly.
- Which VTK test surface do you require — offscreen rendering (ParaView pattern) or an injected stub/fake render? If offscreen, note it may require a display on CI unless the offscreen renderer is used.

## Gaps / unverified
- **No verified public full "CUDA + DIRECT + Qt6 desktop" precedent found** (network may have dropped mid-run; likely). The strongest analogs: ParaView offscreen + QML-VTK integration (john-stone-ics) + Neptune store pattern.
- The precise "coordinator lifetime ownership" tradeoffs aren't pinned by a single authoritative Qt doc; they derive from combining the Store pattern with MVP guidance.
