# moc signals: section mid-class turns accessors into signals (duplicate definitions)

## Problem

A `signals:` section inserted in the **middle** of a Q_OBJECT class (before the
accessor declarations, with no access specifier after it) makes moc treat
everything after it as signals — it generated `QMetaObject::activate` emitter
bodies for plain accessors like `hasCalibration()`, `selectedModels()`,
`frameCount()`, colliding with their `.cpp` definitions at link time.

## Symptoms

- `multiple definition of StudyBridge::hasCalibration() const` across
  `StudyBridge.cpp.o` and `mocs_compilation.cpp.o` (same for
  `selectedModels()`, `frameCount()`).
- No source-level error — only the link error, appearing right after the new
  signal landed.

## What Didn't Work

Chasing it as a pose-sync/linkage issue — the duplicate-definition error was
initially blamed on the pose-sync change. It was a distinct build-only trap
caused purely by the new signal's placement.

## Solution

Keep `signals:` sections **last** in the class (or follow them with an explicit
access specifier):

```cpp
class StudyBridge : public QObject {
    Q_OBJECT
public:
    // accessors / Q_INVOKABLEs FIRST
    bool hasCalibration() const;
    // ...a signals: section must never sit before these...
signals:
    // signals LAST — everything after "signals:" is a signal until the
    // next access specifier
    void poseAdjusted(int, double, double, double, double, double, double);
};
```

The new signal was moved into the existing signals section.

## Why This Works

moc's contract: `signals:` opens a signals region that extends until the next
access specifier. A signal declaration gets an emitter body
(`QMetaObject::activate`) generated by moc; any plain accessor falling inside
that region also gets a generated body, duplicating the `.cpp` definition.
Signals-last (or an immediate `public:`/`private:`) keeps the regions disjoint.

## Prevention

- Keep `signals:` sections last; if one must appear mid-class, immediately
  follow with `public:`/`private:`.
- On `multiple definition of <Class>::<accessor>` between a `.cpp.o` and
  `mocs_compilation.cpp.o`, suspect a mis-scoped `signals:` region before
  suspecting the linker/CMake.
- This is **distinct** from the AUTOMOC header-in-source-list gotcha
  (`docs/solutions/conventions/jtml-testability-and-cmake-conventions-2026-08-07.md`
  §2): that one is headers never being moc'd at all (undefined symbols); this
  one is moc generating **too much** (duplicate symbols).
