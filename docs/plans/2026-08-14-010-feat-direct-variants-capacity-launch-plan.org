** Overview
:PROPERTIES:
:CUSTOM_ID: overview
:END:
Two workstreams land on the seams plan 008 built (stage-graph container,
=DirectOptimizer::Options= slot, =BuildGpuCostAdapter=):

1. *The algorithm plan the Options stubs point at* (plan 008 U8: "the divergence branches
   land with the algorithm plan (R9)"; the origin's Phase 3). The literature's
   highest-evidence upgrade --- *1-DTC-GL-gb* (synthesis Finding 3) --- becomes real
   variant semantics behind the existing fail-fast =Options= surface: GL two-step Pareto
   selection, globally-biased (gb) phase switch, faithful 1-DTC least-split rule, ε
   refinement control, and the DIRECT-GLh hidden-constraint surrogate. The stage graph
   grows a per-stage optimizer slot (=StageSpec.options=), a new stage runner
   *=RunOptimizedStage=* replaces the pure-DIRECT =RunDirectStage= call sites in the loop,
   and a new high-level graph *=jtml-gl-gb=* is registered as the scoring candidate.
   Promotion stays harness-arbitrated (R9): =jtml-production= remains the default,
   bit-identical.

2. *A capacity-based kernel launch service for cost queries*, shaped as the owner asked:
   /outside/ the optimization graph. A compute-layer service (=CostCapacityService=) owns
   device-capacity knowledge --- SM count, per-kernel occupancy, the SAFE_CAP ceiling, and
   the runtime-derived eval-bank count N --- and the optimizer /sends cost queries to it/.
   The capacity answer sizes kernel launches ("when available": capacity-derived config,
   today's sizing as fallback) and, through the origin's batch seam (R12), executes POH
   batches N-way when capacity allows. The stage graph, the stage loop, and
   =DirectOptimizer= stay launch-agnostic --- no launch machinery enters the coordinator
   or domain layers.

** Problem Frame
:PROPERTIES:
:CUSTOM_ID: problem-frame
:END:
The repo's current DIRECT configuration --- original selection, ε=0, all hull ties,
one-side trisection on the largest /denormalized/ side, L2 size --- sits in the worst
local-refinement regime the literature documents for a 20k--35k-budget 6-DOF search
(synthesis Finding 3; Stripinis & Paulavičius 2022: GL selection beats IO/IA by ~60--72%
on n>4 problems, with the budget crossover far below the 20k trunk). Plan 008 built the
container for this: =Options= exists with bit-identical defaults, but every non-default
field is a fail-fast stub awaiting this plan (see origin: R3, R9;
=docs/plans/2026-08-12-008-refactor-optimizer-graph-container-plan.md= U8).

Meanwhile each cost evaluation launches ~15 kernels with fixed or sqrt-heuristic sizing
(=include/compute/launch_config.cuh=, =include/compute/cuda_launch_parameters.h=), zero
occupancy awareness, and one pose per round trip. The GPU is under-occupied per kernel
(origin R11). The owner's shape for fixing that: a capacity-aware launch service the
optimizer queries, so launch policy never mucks up the optimizer. This resolves the
origin's deferred N-bank question at the same time: the bank count is /runtime,
capacity-derived/ --- not a compile-time constant.

Plan-local requirements (the capacity-launch shape is an owner decision beyond the
origin's letter; it implements the origin's R11 intent):

- P1. The capacity/launch machinery lives in a compute-layer service; the coordinator and
  domain layers never see CUDA launch types.
- P2. Capacity-based launch is used *when available*: a successful capacity query yields
  the launch config; otherwise today's sizing runs unchanged (fail-safe fallback, never a
  crash).
- P3. A capacity-derived launch never computes less work than the exact launch would: the
  work-coverage invariant is =grid × block ≥ work items= and SAFE_CAP is the ceiling. The
  service never produces a grid larger than the minimal covering grid (exact-grid-wins
  below resident capacity --- see Key Technical Decisions; over-launching fully-guarded
  kernels only schedules no-op blocks). Bit-identity follows from verified PER-KERNEL
  full-body =if (i < total)= guards + int-atomic reductions (deep-dive R2-3) --- the guard
  premise is verified per kernel, never assumed globally (U10's per-kernel policy;
  =DistanceMapMetric_Kernel= lacks it and is excluded).

** Key Technical Decisions
:PROPERTIES:
:CUSTOM_ID: key-technical-decisions
:END:
- *Landing variant = 1-DTC-GL-gb, ε=0, L2 kept* (synthesis Finding 3): GL selection beats
  IO/IA by ~60--72% on n>4; the 20k trunk lives far above the ≥4000-eval GL crossover; -gb
  is the only restriction that never hurt and is best on expensive objectives (GPU
  silhouette renders qualify).
- *Guarded divergence, per field.* Every variant branch guards on "different from default"
  before diverging (plan 008 U8's proof strategy); defaults stay bit-identical by
  construction, and each field's fail-fast stub flips to "implemented" independently.
- *gb semantics: canonical + code-as-shipped arm.* The DIRECTGO reference code inverts the
  phases vs two papers (synthesis Finding 9). Implement the canonical prose semantics
  (local phase while improving + on every-5th security iterations; global-only beyond 5
  stagnant iterations; Yaro_epsilon 0.01; numbers 5 / every-5th from Gb-DISIMPL) and carry
  a flag for the inverted code-as-shipped arm so the battery records which semantics it
  measured (AE3).
- *Faithful 1-DTC requires the least-split rule.* The studied 1-DTC splits the least-split
  dimension in /unit/ space (global split counter, lowest-index tie-break); the repo
  splits the largest denormalized side. They coincide on the trunk and diverge
  deterministically on the first branch/leaf split (repo picks Z, study picks X). The new
  split rule lands as a non-default =SplitRule= value --- a real behavior change, but only
  ever inside the new graph, scored on the anisotropic-range probe and the staged battery
  before promotion (synthesis Finding 10).
- *GLh at selection time, over feasible f_min only* --- φ = f_min + d(x_min,x), d̄ = d/√n,
  f̄ = (f−f_min)/(f_max−f_min), sentinel 10^9, re-tag when x_min moves ≥ 1e-6 in unit
  coords (paper Eqs. 3--6, verified Round 3). It hooks the existing non-finite eval
  chokepoint; DIRECT_DILATION cannot emit NaN, so production's active cost never triggers
  it --- it is insurance for the NaN-emitting variants (Mahfouz, pole-constraint,
  sym-trap) and for hidden-constraint battery problems.
- *=RunOptimizedStage= replaces the pure-DIRECT call sites; it does not fork the loop, and
  it does not duplicate the runner.* The stage loop calls one function per stage;
  =RunOptimizedStage= computes the stage's effective options and calls the existing
  PRIVATE =RunDirectStage= runner once --- the runner gains an =Options= parameter
  (defaulted to classic for today's call shape), so its entire wiring (adapter, call
  offset, improvement/iteration callbacks, cooperative stop, error path, writeback) stays
  single-sourced and the default path is diff-untouched. Extending the private runner's
  signature is NOT the executor extraction origin R4 forbids --- the runner is private;
  the oracle and probe converge on =BuildGpuCostAdapter=, never on the runner, so the
  signature change is invisible to them.
- *Per-stage options live on =StageSpec=, selected atomically* (resolves the origin's
  deferred "final StageSpec field set" question): ={kind, range, budget, repeat,
  cfm_index, options}=. The precedence is one exact per-stage rule:
  =effective_options(stage) = spec.options if any field differs from classic, else
  direct_options_, else classic= --- where the run-level =direct_options_= originates at
  =OptimizerRunLaunch.direct_options= (plan 008 U8) forwarded through =Initialize=.
  Selection is ATOMIC --- never per-field merged --- so the battery manifest always
  records a variant that actually ran (AE3 determinism). Accepted corollary for v1: a
  default =spec.options= means "inherit run-level", so a graph cannot force classic over a
  non-default run-level slot; no merge. The runner needs an Options field-wise equality
  (is-classic) helper --- a U1/U6 deliverable (no operator== exists today).
- *Capacity is a compute-layer service the optimizer queries* (owner's shape; P1).
  =CostCapacityService= answers: device snapshot, per-kernel occupancy, SAFE_CAP-clamped
  grid sizing, and =EvalBankCount()=. The coordinator owns no buffers and no streams
  (deep-dive R2-4's contract).
- *Capacity-based launch = host-side sizing only, and never a larger grid than the work
  requires* (P3, deepened): the invariant is work coverage --- =grid × block ≥ work
  items=, SAFE_CAP the ceiling --- and the capacity-derived grid is =ceil(work / B_opt)=
  for the kernel's occupancy-optimal block size =B_opt=. *Exact-grid-wins below resident
  capacity*: over-launching fully-guarded kernels only schedules no-op blocks (a
  guaranteed regression at any workload --- the deepening audit's blocker), so the service
  never produces a grid larger than the minimal covering grid. Where capacity sizing
  actually pays is the /reduction/ of overshooting launch formulas (the 2D-sqrt render
  grids overshoot up to ~100% for non-square work) toward the minimal grid, under a
  per-kernel policy: fill kernels are block-pinned at 256 (stride-prefix architecture),
  halo metric kernels are excluded, and =DistanceMapMetric_Kernel= is EXCLUDED from
  reshaping until its missing full-body =i < total= guard lands in its own scoped,
  oracle-gated kernel unit --- its only guard today is a derived-location bound (=orig_loc
  < width*height=) that overshoot threads can pass, so a minimal-grid reshape can change
  scores (the review-verified guard hole; U10's per-kernel policy carries the full table).
  Overflow beyond SAFE_CAP keeps today's synchronous fallback; bit-identity rests on
  per-kernel VERIFIED full-body =if (i < total)= guards + int-atomic reductions (synthesis
  Finding 5 determinism doctrine) --- verified per kernel, never assumed globally.
- *The bank count N is runtime, MEMORY-bounded* (resolves the origin's deferred R11
  question): =EvalBankCount()= = =min(⌊device free memory ÷ per-bank footprint⌋, N_MAX)=,
  floored at 1 --- memory, not occupancy, is the binding constraint for buffer banks
  (occupancy bounds concurrent kernels, not allocations). The per-bank footprint is the
  per-eval WRITE-SET (the 40 MB stride-prefix buffer and the per-triangle arrays dominate
  --- not the image + score ints), counted across BOTH cameras in biplane; read-only
  buffers stay shared. =EvalBankCount()= (the pool size) is decided in =Initialize= after frame dims are known and BEFORE
  the first GPUModel ctor; the service owns the bank POOL (render outputs + per-eval score buffers + pinned twins), checked out per-pose by the greedy feeder and returned on recycle --- RenderEngine/GPUMetrics render/score into a caller-supplied pool buffer set rather than an N-fixed internal. N=1 means "serial path, allocates nothing new".
- *The batch seam follows R12 exactly*: optional sibling =std::function=, replay-ordered
  bookkeeping (calls, optimum, callback order identical whether the cost layer batches or
  not), no CUDA types in the domain header, Tier-0 replay test as the contract's
  executable spec.

- *Final StageSpec field set* (origin deferred-to-planning): ={kind, range, budget,
  repeat, cfm_index, options}= --- the options slot defaults to the bit-identical classic
  search; registry graphs carry non-default options per stage.

  memory-bounded via =CostCapacityService::EvalBankCount()= = =min(⌊device free memory ÷
  per-bank write-set footprint⌋, N_MAX)=, floored at 1. The ceiling formula is fixed (Key
  Technical Decisions); only the numeric =N_MAX= and the per-bank write-set enumeration
  are implementation-time.
- *What "capacity-based launch" sizes* (resolved by the deepening audit): NOT up-clamped
  grids --- over-launching fully-guarded kernels is a guaranteed regression, so the
  service never produces a grid larger than the minimal covering grid. Capacity sizing
  means occupancy-optimal block sizes, the reduction of overshooting launch formulas
  toward the minimal covering grid (per-kernel policy table in U10), SAFE_CAP as the
  ceiling, and the runtime memory-bounded bank count N for the batch path.
- *Which gb semantics*: canonical prose semantics as the default arm; the inverted
  code-as-shipped behavior rides as an explicit battery arm with a recorded semantics pin
  (synthesis Finding 9).
- *New graph name*: =jtml-gl-gb= (registry naming convention next to =jtml-production=;
  not a reserved stub name).
- *How the new graph runs before plan 009 lands*: the battery drives it headlessly through
  =StageGraphByName("jtml-gl-gb")= + the stage runner directly --- no =Initialize= change
  needed for scoring. Production consumption waits on plan 009 U1+U2.
- *Epsilon shape*: =Options.epsilon= (exists) + a floored-form flag (Gablonsky
  =max(10⁻⁴|f_min|, 10⁻⁸)=) so the battery's ε-arm {0, 1e-7, 1e-4} can express both the
  pure ε|f_min| filter (inert at f_min=0 by Definition 4.1) and its documented mitigation.

kernel's occupancy-optimal block size =B_opt=, never exceeding the minimal covering grid and
never below it (exact-grid-wins below resident capacity), never above SAFE_CAP threads, and
never above the guide's grid-dimension ceiling =maxGridDim= (2²¹−1 per axis, CC 3.0+ --- a
pathological 1-elem/block config must not overflow the grid). -
=EvalBankCount()=: MEMORY-bounded --- =min(⌊device free memory ÷ per-bank footprint⌋,
N_MAX)=, floored at 1, where the per-bank footprint is the per-eval write-set (U12
enumeration) counted across both cameras in biplane. Occupancy is a grid-sizing input only
--- it bounds concurrent kernels, not buffer allocation. - Construction-order invariant: =EvalBankCount= (the pool size) is computed once in =Initialize= after frame dims are known and BEFORE the first GPUModel ctor. The service owns the POOL of buffer sets (render outputs + score buffers + pinned twins); RenderEngine/GPUMetrics render/score into a caller-supplied buffer set. Single-eval consumers (oracle twin, z-profile probe, =EvaluateCostFunctionAtPoint=) always target the bank-0 set the engine already owns (no allocation; N=1 identity). - No streams, no buffers, no allocation in the service itself ---
it is pure knowledge + sizing math. Buffer/stream ownership lands with U12 where the
deep-dive pinned it (RenderEngine/GPUMetrics internals).

*Patterns to follow:* =include/compute/launch_config.cuh= (the builder shape it supersedes
--- keep it for non-cost callers until a follow-up migrates them); =gpu_metrics.cu='s
pinned-buffer ownership style.

*Test scenarios:* - Happy path (headless): with injected fake props (80 SMs, 2048
threads/SM), =CapacityGrid= for work ≤ resident capacity returns EXACTLY the minimal

(headless): work = 0 → minimal launch (1 block); work = SAFE_CAP exactly → unchanged;

Edge case (headless): =EvalBankCount= floors at 1 when the per-bank write-set footprint

- [ ] U12. *N-way eval banks + streams, sized by capacity (gated)*

*Goal:* When the capacity service says N > 1 fits, the POH batch runs N-way: N banks of
eval state (render output + score buffers), N CUDA streams, capacity-sized launches per
bank --- the origin's streamed N-way target (R11) with the bank count resolved at runtime.

*User Note*: I'm not sure that this is exactly what I mean, though maybe it is. I'm
suggesting that you can basically queue up one pose at a time into the system until it's
full, and then just greedily evaluate as space becomes available. The kernel launch itself
doesn't have to be N-way by design, but it would occur, because of available capacity,
that you would have N running concurrently. I'm not suggesting that you have to queue up N
at the beginning, and then launch them at the same time, I'm saying that if you're just
feeding the GPU one at a time based on capacity, and the kernel launching parameters
allowed it, you would see better overall utilization.

*Requirements:* R11, R12, R13, R10, P1

*Dependencies:* U10 (capacity launches), U11 (the batch seam); *external:* the Cut-0
instrumentation verdict from the measurement workstream must exist, EXTENDED with CPU host
time per cost call (R10: no perf claim without measured numbers; the band-reachability
condition is =GPU_active_per_eval ≥ CPU_host_per_eval= --- if CPU overhead dominates, no N
reaches the band; and if GPU-active > 1 ms falsified the sync-bound model, this unit's
premise is re-reviewed before execution)

*Files:* - Modify: =src/compute/cost_capacity_service.cuh/.cu= (owns the bank POOL ---
pool init = min(EvalBankCount, |batch max|) at Initialize; per-pose =CheckoutBank()= /
=RecycleBank()= on the greedy feeder's capacity probe; =RunCostBatch= N-way: per-bank
stream assignment, per-bank capacity launches, deterministic combine --- the pose→score
result order stays input order) - Modify: =src/compute/render_engine.cu= (render INTO a
caller-supplied output pointer instead of the single internal =renderer_output_= --- the
per-bank output lives in the pool, the engine writes to a passed-in device buffer; the
internal buffer stays as bank-0 / single-eval default so N=1 allocates nothing new) -
Modify: =src/compute/gpu_model.cu= (render-output passed in per call, not owned
internally; N-free --- the engine no longer takes an N ctor param, the pool holds the
buffer sets) - Modify: =src/compute/gpu_metrics.cu= (score into a caller-supplied
score-buffer bank; pinned twins move into the pool; =SetActiveBank= drops to a pool-index
passthrough --- pinned situs gpu_metrics.cu:7-65) - Modify: =src/coordinator/optimizer_manager.cpp=
(the service owns the pool; constructed in =Initialize= with the rest of the GPU object
graph --- the manager owns the graph, compute owns the state, the coordinator owns
neither) - Test: GPU-labeled (the Tier-0 replay test's GPU twin + the bit-identity diff +
the meter band)

*Approach:* - Pool size = =EvalBankCount()= at Initialize --- AFTER frame dims are
known, BEFORE the first GPUModel ctor; the POOL owns =max(EvalBankCount, needed)= buffer
sets (render outputs + per-eval score buffers + pinned twins), each checked out per-pose by
the greedy feeder and returned on recycle (the user's service-owned lazy-pool model).
N=1 keeps the U11 serial execution (allocates nothing new beyond the bank-0 set the
engine already owns). Gate before executing: =pool × per-bank footprint ≤ 50%= of device
free memory, measured. - Per-bank write-set enumeration (the binding audit): every per-eval-
WRITTEN device buffer is a pool resource --- the 40 MB stride-prefix buffer,
projected/snapped/bbox triangle arrays, vertex-z, backface/ tangent, z-line values, CUB
scratch storage, renderer output, score buffers + pinned twins (~75 MB/bank at a
300k-triangle implant); read-only buffers (triangles, normals) stay explicitly shared.
Sharing any write buffer across concurrent banks is a data race that fails the
bit-identity gate nondeterministically. - Two migration levers, not one: (1) the
platform's per-thread default stream (compile with =--default-stream=per-thread= or
define =CUDA_API_PER_THREAD_DEFAULT_STREAM=) makes the legacy implicit-sync hazard
vanish for any poorly-specified call, AND (2) stream-explicit variants for every cost-path
CUDA call (=cudaMemsetAsync=, stream-parameterized CUB scan, =cudaMemcpyAsync= into pinned
buffers on the bank stream, structural syncs as per-bank =cudaStreamSynchronize=), pinned
by a grep-gate test asserting zero default-stream launches/copies in the bank path. The
guide: the legacy default stream implicitly synchronizes with every other stream --- one
unmigrated synchronous call serializes all banks even after (1). - Executor structure
(band reachability): the greedy feeder checks out a free bank per pose as capacity allows
(=cudaStreamQuery= / =cudaEventQuery= as the non-blocking capacity probe), rendering the
WHOLE batch round-robin across checked-out banks BEFORE any fill drain; then per pose in
input order: per-bank stream sync (cheap --- N−1 evals old), fill config from the pinned
fragment_fill copy, fill + metric launches, score reads deferred to bank recycle (the
user's single-pose-at-a-time greedy model, now with the pool making it possible). A
naive launch-sync-fill-next loop serializes the host on each render phase and caps
throughput at ~1/render-time (Flood parity, not above it). - Determinism doctrine
(synthesis Finding 5): per-pose reductions stay int-atomic within a bank; banks never
share a reduction target; the batch result vector is assembled in input order ---
bit-identity vs the serial path is diffable. - Streams are the service's (compute-owned);
the coordinator still only registers the callback (deep-dive R2-4). - All bank allocation
at =Initialize= / =CheckoutBank= pool --- the eval path still allocates nothing per call.

*Test scenarios:* - Covers AE2. Integration (GPU): pose→score sequence bit-identical to
the serial path over the oracle frames (empty diff) with N ≥ 2. - Covers R13. Integration
(GPU): the fixed meter (when landed by the measurement workstream) shows evals/s inside
the pre-registered band (1,000--5,000; Flood 3,000 parity line recorded) --- and the
revert rule applies: no improvement over 3 runs ⇒ abandon the jj change, keep serial. -
Edge case (GPU): a POH batch smaller than N --- only the needed banks launch; results
still input-ordered. - Error path (GPU): any CUDA error inside the batch executor aborts
the stage through the existing error path (error_occurrred_ + OptimizerError; no silent
partial batch, no silent per-point fallback). - Edge case (GPU): determinism stress ---
the bit-identity diff runs with a multi-bank batch whose adjacent poses schedule on
different banks, repeated ≥ 3× to catch interleaving-dependent races.

*Verification:* oracle green, replay green, bit-identity diff empty, measured band
recorded in the run's result doc; or the unit is reverted per R13 and recorded as a
measured no-go.

** System-Wide Impact
:PROPERTIES:
:CUSTOM_ID: system-wide-impact
:END:
- *Interaction graph:* =Optimize()= loop → =RunOptimizedStage= → =DirectOptimizer=
  (variant options) → injected cost (single or batch sibling) → =CostCapacityService= →
  capacity-sized launches / N banks. The =UpdateDisplay=/=UpdateOptimum=/=OptimizerError=
  signal contract is untouched --- the iteration/improvement callbacks fire from the same
  places they fire today, in the same order (under the batch path, replayed fires occur
  back-to-back at batch return; order identical, wall-clock timing may differ). The
  options precedence chain (=OptimizerRunLaunch.direct_options= → Initialize →
  =direct_options_= → =RunOptimizedStage='s atomic selection over =spec.options=) is the
  plan-009 handoff contract: named-graph consumption must route through the same rule,
  never re-derive one.
- *Error propagation:* unimplemented variant options fail fast at stage start (never
  mid-search); capacity-query failures fall back to today's sizing silently-by-design (P2)
  with the unavailability observable via the service; batch-size contract violations fail
  fast in the replay loop; ANY error inside the batch executor (v1 serial or U12 N-way)
  aborts the stage through the one existing error path (=error_occurrred_= +
  =OptimizerError=) --- never a partial batch, never a silent per-point fallback.
- *State lifecycle risks:* the N-way banks are the one new allocation surface ---
  allocated once in =Initialize= (N decided after frame dims, before the first GPUModel
  ctor), freed with the GPU object graph (service destruction sequenced with the models
  and GPUMetrics in the manager's destructor), never per-call; the ceiling formula =N_MAX
  ≤ ⌊(device memory − fixed allocations) / per-bank write-set footprint⌋= bounds
  worst-case VRAM growth (numeric value measured at U12). The gb phase state is
  per-=DirectOptimizer=-instance (per-stage), never shared across stages.
- *API surface parity:* =BuildGpuCostAdapter= has three consumers (production runner,
  Tier-2 oracle, z-profile probe) --- this plan never changes its body; the batch sibling
  is additive and the oracle keeps the single-eval path.
- *Integration coverage:* the multistage oracle on the GPU machine is the arbiter for
  every Phase-A landing (driven through the named graph once plan 009 lands) and for
  U10/U12 bit-identity; the headless suite cannot see launch behavior by design.
- *Unchanged invariants:* =jtml-production='s shape, the cumulative caps [20000, 25000,
  30000, 35000], the four lineage invariants (group-once dilation, per-repeat re-seed,
  asymmetric z-leaf, frame-to-frame seed chaining), the Sym_Trap =[{Leaf, repeat=0}]=
  script, the domain layer's zero-CUDA contract, and the reserved stub graph names.
