* Purpose

Reference for replacing the C++ DIRECT core (=DirectOptimizer=) with the Rust
implementation in =rust/direct-rs=, keeping the C++ coordinator
(=OptimizerManager=, =CostFunctionManager=, GPU cost) intact. This is a
*handshake spec* — the concrete FFI boundary Rust and C++ must agree on — not a
full implementation plan. It records every option considered so the reader can
choose deliberately.

** Contract at a glance (the C++ engineer's two-minute read)

- **Rust side owns the search.** =rust/direct-rs= exposes =DirectOptimizer=
  via the bridge; C++ owns cost + lifecycle + the worker thread.
- **Cost crosses one way.** An opaque =CppCost= handle (wrapping a
  =std::function=) is passed INTO Rust; Rust calls =evaluate6(x,y,z,xa,ya,za)=.
  No =std::function= crosses the ABI; the seam is opaque + method.
- **The boundary surface** (bridge, verbatim at "Rust bridge"):
  =new_direct_optimizer(range,start,budget,mode) -> Box<DirectOptimizer>=,
  =run_ffi(&self, cost: &CppCost) -> RunOutcome=, =request_stop(&self)=.
- **=RunOutcome=** = { best: Pose, best_cost: f64, calls: u32, ok: bool, error: u32 }.
- **Four truths that must survive any backend** (see Contract): cumulative
  =calls+offset= budget; SAME optimum per cost sequence (Tier-3 is the gate);
  eval ordering = calls++ → non-finite → optimum → storage → improvement
  callback; =evaluate= is serial on one worker thread.
- **Never let Rust panic across the boundary** — a panic =abort()=s the whole
  process. Errors become =ok:false= + =error:= code, never a thrown exception.
- **Lifetime rule:** =CppCost= handle must out-live =run_ffi()=.

That's the agreement. Everything else in this doc teaches /why/ or fills a
detail. Re-check the verbatim bridge + call-site sections before coding.

Coming from **Python**: ch 3-8 is mostly review (variables, functions,

* Toolchain first — make the compiler your tutor

You cannot learn Rust by reading. The borrow checker is the teacher and it only
speaks when you compile. Before Milestone 0, build a loop where you can ask the
compiler a question and get an answer in under three seconds. Everything below
this section assumes that loop exists.

#+begin_src text

  src/

Why split it this way: =lib.rs= holding *only* the bridge is FFI containment —
the unsafe surface is one file you can audit. Every other module is ordinary
safe Rust, unit-testable with no C++ and no GPU in the room. **If a module
can't be tested headlessly, FFI has leaked into it.** (The one structural exception: `CppCostHandle`'s `Cost` impl in `cost.rs` links against the C++ static lib — that is by design, not leakage.) That single rule is worth
more than any diagram in this doc.

** Read the error, not the code

A rustc error has four parts: the code (=E0502=), the one-line claim, the
annotated span, and a =help:= line that is usually the literal fix. Beginners
stare at the span. The fastest learners read the =help:= first, then
=rustc --explain=, and only then look at their own code. Appendix A's table and
the glossary's error lookup are the project-specific version of that habit.

* Learning Roadmap (plan it, then fill it)

This doc is big enough that the order you read it *is* a learning path. Use
this roadmap as your map; the section headings are the terrain. Each milestone
ends with a self-check you should be able to answer without looking before
moving on.

** Milestone 0 — why this is a two-language project

Goal: before any Rust, understand the split. The C++ side owns the cost and
lifecycle; Rust owns the search algorithm. Everything else is plumbing between
two runtimes.

- Read: =Purpose=, =Contract being filled=, =One-picture flow=.
- **Book**: none — orientation. Return to it after every milestone; the
  handshake diagram is the anchor.
- Self-check: state which side owns (1) the cost function, (2) the optimizer's
  search loop, (3) the worker thread, (4) the UI progress, and (5) the
  cumulative budget.

** Milestone 1 — value types: Pose + Hyperbox

Goal: model the data before any algorithm. Internalize =Copy= vs =Clone= vs
move, and why small POD structs cross FFI by value.

- Concept: =#[derive(Copy, Clone)]= on small structs; what a value is in Rust.
- **Book**: ch 04-01 (moves), ch 05-01 (structs), ch 06 (enums for =Direction=).
- **rust-skills**: =own-copy-small=, =own-move-large=, =type-enum-states=.
- Self-check: explain why =Pose= is =Copy= but a =Hyperbox= whose center is a
  =Pose= stays =Copy= (small POD), vs one that wraps a =Vec= which isn't — i.e.
  what makes a type =Copy=-eligible and what =Copy= costs you.

** Milestone 2 — the BTreeMap design

Goal: the central data-structure decision, and the most Rust-flavored one in
the doc. Learn =Ord=-based containers and the =OrderedFloat= wrapper.

- Concept: =f64= is not =Ord=; =BTreeMap= needs a total order; wrapping floats.
- **Book**: ch 08 (collections) + the =ordered_float= crate docs (the Brown
  book has no =OrderedFloat= section — this is where you learn to read a
  dependency's docs).
- **rust-skills**: =coll-map-choice=, =coll-set-membership=, =num-float-compare=.
- Self-check: why can't you put =f64= directly as a =BTreeMap= key, and what is
  the minimum wrapper that fixes it?

** Milestone 3 — the gather (read-only borrow)

The first actual pass over the tree. Internalize *read-only borrow* = a =&self=
pass with no mutation and no clone.

- Concept: =iter()=, =first_key_value()=, projecting =(size, cost)= without
  touching the box.
- **Book**: ch 04-02 (borrowing), ch 13-02 (iterator adapters).
- **rust-skills**: =own-borrow-over-clone=, =perf-iter-over-index=.
- Self-check: why does the gather take =&self= (not =&mut=), and what would
  break in the type system if you tried to =.clone()= the box out?

** Milestone 4 — POH selection (pure transform)

Goal: =convex_hull(&[PohPoint]) -> Vec<PohPoint>= as a pure function. Internalize
value-in/value-out and the absence of side effects.

- Concept: mapping (size, cost) pairs through a hull algorithm; returning owned
  =Vec<PohPoint>=.
- **Book**: ch 10-02 (traits) + ch 13 (closures as data).
- **rust-skills**: =anti-vec-for-slice=, =perf-collect-once=.
- Self-check: if =convex_hull= is pure, what do you pass in and what comes out,
  and how do you know the tree wasn't touched?

** Milestone 5 — trisection + the ownership dance

The crown jewel of the doc and the deepest borrowing lesson: take = move,
trisect = owned transform, reinsert = move back.

- Concept: =pop_first()= returns owned; =&mut self= is exclusive.
- **Book**: ch 04 (ownership) — the payoff milestone; re-read it.
- **rust-skills**: =own-move-large=, =mem-take-replace=, =own-arc-shared=.
- Self-check: why must you pop/remove the winner OUT of the map before
  trisecting it, and why can't you mutate a map-resident box in place?

** Milestone 6 — cost injection + the trait

Goal: the =Cost= capability; batch-vs-serial; the one-FFI-hop idea.

- Concept: =trait Cost=, =impl Fn= vs =Box<dyn Cost>=.
- **Book**: ch 10-02 (traits), ch 17 (trait objects), ch 13 (closures).
- **rust-skills**: =trait-dyn-vs-generic=, =closure-fn-trait-bounds=.
- Self-check: why is =Cost= a trait and not a concrete struct field, and when
  would you prefer =impl Fn= vs =Box<dyn Cost>=?

** Milestone 7 — the FFI boundary (cxx)

Goal: see your Rust reach into C++. Own =#[cxx::bridge]=, opaque types, shared
structs/enums, the no-panic rule.

- Concept: =extern "Rust"= vs =extern "C++"=, =Box<DirectOptimizer>= on C++ side,
  shared enum => wildcard =_= arm.
- **Book**: ch 19 (unsafe/FFI), ch 16 (threads for Send/Sync).
- **rust-skills**: =unsafe-safety-comment=, =err-no-unwrap-prod=.
- Self-check: what two things can never cross a cxx boundary, and why does that
  force the status-struct + ProgressSink shapes?

** Milestone 8 — errors + status (the gate)

Goal: the error story inside (=Result= + =?) vs at the edge (status struct).

- Concept: two-tier errors; Result in, status out; panic never crosses.
- **Book**: ch 09 (all of it).
- **rust-skills**: =err-result-over-panic=, =err-thiserror-lib=, =err-question-mark=.
- Self-check: converting =OptimizerError= to a =RunOutcome.ok= — what is lost
  and what is kept, and why is that acceptable at the FFI edge?

** Milestone 9 — assemble the loop + A/B

The finish: wire gather → POH → trisect → reinsert into one =run()= behind the

- Concept: glue, ownership flow end-to-end, the =ok= gate.
- **Book**: ch 04 + ch 13 once more (full recap).
- Self-check: walk the ownership of ONE hyperbox from insertion to trisection

* Contract being filled

The C++ =DirectOptimizer::Run()= contract, from =include/domain/direct_optimizer.h=:

| Method                            | Signature             | Semantics                                          |
|-----------------------------------+-----------------------+----------------------------------------------------|
| =Run()=                           | =bool Run()=          | false=error; loop guard =(calls+offset)<budget && !stop= |
| =GetCostFunctionCalls()=          | =unsigned int=        | =cost_function_calls_ + call_offset_=              |
| =GetNonFiniteCount()=             | =unsigned int=        | count of non-finite evals                          |
| =GetOptimumLocation()/Value()=    | =Point6D / double=    | denormalized physical best / best cost             |
| =Stop()=                          | =void=                | cooperative, checked between iterations            |
| =SetCallOffset(u)=                | =void=                | cumulative offset; canonical caps trunk 20k → 2x branch 25k/30k → leaf 35k |
| =SetIterationCallback(f)=         | =void=                | after each ConvexHull+Trisect, ~30fps              |
| =SetImprovementCallback(f)=       | =void=               | on new best (emits UpdateOptimum)                  |
| =SetBatchCost(f)=                 | =void=                | optional U11 batch sibling                         |

=Options= struct (8 fields, all fail-fast unless default):
=selection= (SelectionMode=Original), =epsilon=0.0, =delta_limit=bool(false),
=size_measure=SizeMeasure=L2, =split_rule=SplitRule=OneSide,
=ties=TieSelection=All, =hidden_constraints=bool(false),
=globally_biased=bool(false).

Truths that must survive any backend:

- cumulative =calls+offset= budget semantics (canonical caps: trunk 20k → 2x branch 25k/30k → leaf 35k, per direct_optimizer.h)
- the SAME optimum for the same cost sequence (Tier-3: parity replay over recorded C++ cost sequence is the actual gate; Tier-1 headless golden validates shape)
- eval ordering: calls++ → non-finite → optimum update → storage → improvement callback
- =evaluate= executed **serially** on one worker thread (GPUModel pose is mutated per call)

*** Rust learning — "options as data" vs the god object

The C++ =Options= struct is already *value-shaped* (a struct passed by value)
— a good instinct. The normie-from-C++ error is to treat it as a bag of
bools/enums read by =if= inside =Run()=. Rust nudges you to make the impossible
state *unrepresentable* rather than merely checked.

- **Book**: ch 05 (structs), ch 06 (enums + exhaustive =match=),
  ch 10-02 (traits).
- **rust-skills**: =type-enum-states=, =type-newtype-validated=,
  =api-parse-dont-validate=, =api-common-traits=, =num-float-compare=,
  =anti-over-abstraction=.

Normie (a loose struct with raw codes; callers must remember valid values):

#+begin_src rust
pub struct Options { pub selection: u8, pub epsilon: f64, pub delta_limit: bool }
// a caller writing selection: 8 compiles fine and is wrong at runtime
#+end_src

Idiomatic (a named enum + derive so invalid values can't exist):

#+begin_src rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum SelectionMode { Original }      // only one legal value today
#[derive(Debug, Clone, Copy, Default)]
pub struct Options { pub selection: SelectionMode }  // Default == the C++ default
#+end_src

Why =epsilon=, =size_measure=, =split_rule=, =ties=, =hidden_constraints=,
=globally_biased= are *absent* above: the C++ side fails-fast on any
non-default value. The idiomatic Rust is to **not declare the knob until you
implement it** (=anti-over-abstraction=). Declaring a field you cannot honor
is a promise the type system can't keep; dropping it entirely is a
=compile-time= guarantee that beats the run-time =ValidateOptions()=.

The cumulative budget caps (trunk 20k → 2x branch 25k/30k → leaf 35k) are
better as **data** than scattered literals — a single =Budget= newtype
(=type-newtype-ids=) and the ladder defined once, used everywhere. If you ever
*compute* a budget, reach for =num-overflow-explicit= (checked/saturating
arithmetic) rather than letting a += overflow wrap.

* Designing DIRECT from scratch, step by step

This is the procedural heart. Forget the FFI and options for a moment: here we
derive the Rust DIRECT data model and loop *one step at a time*, in the order
you'd discover them while porting. Each step introduces exactly one idea,
usually one type, and checks itself before moving on. This is where the
"normie → idiomatic" comparisons get their teeth — each step is a real decision,
not a style preference.

Throughout, "deduce" means *let the compiler + the borrow checker teach you*,
not just copy a pattern. The Brown Book's ch 4 is the reference for steps 3-5;
re-open it when a step feels abstract.

** Step 1 — model a point: `Pose` (value type)

The whole algorithm is a search over 6-D poses. First question: what is a pose
*on its own*? A bundle of six =f64= whose identity is its contents. That is a
value type — and in Rust the first reflex is to ask: should this be =Copy=?

Normie-from-C++ (a class with methods + hidden members):
#+begin_src cpp
class Pose { double x,y,z,xa,ya,za; /* getters, setters... */ };
#+end_src

Idiomatic (a plain value struct, =Copy=, fields public):
#+begin_src rust
#[derive(Clone, Copy, PartialEq, PartialOrd)]
pub struct Pose { pub x:f64, pub y:f64, pub z:f64, pub xa:f64, pub ya:f64, pub za:f64 }
#+end_src

Why: =Pose= is 6×=f64= = 48 bytes — genuinely small — and its equality/order are
meaningful (=PartialEq=, =PartialOrd=). =Copy= is right for a small plain-data
value (rust-skills =own-copy-small=): passing it around copies 48 bytes (cheap),
and =Copy= lets you read it out of a map key without =.clone()= ceremony.

- **rust-skills**: =own-copy-small=, =type-enum-states=.
- **Book**: ch 04-01 (Copy vs move), ch 05-01 (structs).

Stop. **Check** — is a =Pose= a thing you own or a thing you copy? It is both —
=Copy= is the honest label for "duplicating it is cheap and preserves meaning,"
which tells the compiler it may copy at will.

** Step 2 — model an axis: `Direction` (enum, not ints)

DIRECT trisects along one of six axes. The normie input is ints 0..5 or named
constants; Rust has a better tool: =Direction= as an =enum=.

#+begin_src rust
#[derive(Clone, Copy)] // tiny tag — keep it Copy
pub enum Direction { X_DIR, Y_DIR, Z_DIR, XA_DIR, YA_DIR, ZA_DIR }
#+end_src

An =enum= buys three things the normie approaches lack:
1. no invalid value (no "axis 7") — =type-enum-states=;
2. exhaustive =match= — the compiler forces all six cases; and
3. it pairs with an index into =depths: [u32; 6]= via a small const mapping
   array instead of a cast. You already have `const DIRECTIONS: [Direction; 6]`.

- **rust-skills**: =type-enum-states=, =pat-exhaustive-enum=.
- **Book**: ch 06 (enums + match).

** Step 3 — model a box: `Hyperbox`

Now the atom of the search. A hyperbox has a center (=Pose=), a per-axis depth
=depths: [u32; 6]= (how many times each axis has been trisected), and a cost at
that center (=Option<f64>= — we'll see why).

Normie-from-C++ (a class with a =size()= method + friends):
#+begin_src cpp
class HyperBox6D { /* ... */ double GetSides(); /* ... */ };
#+end_src

Idiomatic (a plain struct + a method on an =impl=):
#+begin_src rust
#[derive(Clone, Copy)]
pub struct Hyperbox {
    pub cost_at_center: Option<f64>,
    pub center: Pose,
    pub depths: [u32; 6],
}
impl Hyperbox {
    /// L2 norm of box extent from depths — the "size" used by POH.
    pub fn size(&self) -> f64 {
        self.depths.iter()
            .map(|e| 3f64.powf(-2.0 * (*e as f64)))
            .sum::<f64>()
            .sqrt()
    }
}
#+end_src

Two Rust habits to internalize here:

- **=Option<f64>= for "not scored yet."** The center box inherits its parent's
  cost; the two shifted boxes don't exist yet — pending a batch eval. =Option=
makes "not yet known" an explicit state instead of a magic =DBL_MAX=/=-1=
sentinel. This is =type-option-nullable= + =api-parse-dont-validate=: represent
  the absence; don't smuggle a fake number.
- **A method computes what isn't stored.** =size()= is derived from =depths=
every time; you don't cache it in the struct. Fewer fields = fewer places to be
inconsistent. (Add a cache only if it shows up in the profiler =
=perf-profile-first=.)

- **rust-skills**: =type-option-nullable=, =api-parse-dont-validate=,
  =own-copy-small=, =perf-profile-first=.
- **Book**: ch 05-01 (structs), ch 06 (Option), ch 13-02 (iterators — the =sum=
  is already an iterator pipeline).

Stop. **Check** — why =Option<f64>= for cost rather than =f64= with =-1=
"meaning missing"? Because =-1= might be a valid cost that gets silently used;
=None= is a kind the compiler forces you to handle before you can use the box.

** Step 4 — the two-level `BTreeMap` (the Ord problem)

The heart of the data model is a container of hyperboxes keyed by size (outer)
then cost (inner). The moment you reach for a sorted map you hit a very
Rust-specific wall: **=f64= is not =Ord=.**

Why: =BTreeMap= (and =BTreeSet=, =BinaryHeap=, sort) needs a *total order* — the
=Ord= trait. But =f64= has =NaN=, which compares "not equal to everything,
including itself," breaking total-order. So the standard library deliberately
refuses =f64= as a map key / in =Ord= contexts.

Normie-from-C++ (map on =std::map<double,...>= — C++ lets you, NaN foot-gun
later):
#+begin_src cpp
std::map<double, std::vector<Box*>> columns;  // NaN quietly poisons comparisons
#+end_src

Idiomatic (wrap the float + add an id for ties):
#+begin_src rust
use ordered_float::OrderedFloat;             // newtype: f64 that IS Ord
pub type SizeKey = OrderedFloat<f64>;
pub type CostKey = (OrderedFloat<f64>, u64); // (cost, unique id) so equal costs don't collide
#+end_src

=OrderedFloat<f64>= is a newtype that implements =Ord= by asserting the value is
never =NaN=. It's the idiomatic escape hatch when you know your floats are total
(your sizes/costs are never NaN). The =u64= tiebreak makes the inner key injective.

- **rust-skills**: =num-float-compare=, =type-newtype-ids=, =coll-map-choice=.
- **Book**: the =ordered_float= crate isn't in the Brown book — this is your
  first "read a dependency's docs" moment. The concepts (traits, newtype, =Ord=)
  are ch 10-02 + ch 08.

Stop. **Check** — why is the inner key =(cost, u64)= rather than just =cost=?
Because two boxes can have the same cost; a =BTreeMap= keyed by cost alone
would let the second silently overwrite the first. The monotonically increasing
=u64= box id breaks the tie so both survive — =type-newtype-ids= in a container.

** Step 5 — the gather (read-only pass)

Now the first read over the tree: collect, for every size-row, the min-cost
box's (size, cost) pair — the input to POH. This is a **read-only borrow** pass
= =&self=, no mutation, no clones.

Normie-from-C++ (a =const&= method that iterates + copies minima out):
#+begin_src cpp
std::vector<std::pair<double,double>> gather(const std::map<...>& rows) {...}
#+end_src

Idiomatic (read-only =iter()= + =first_key_value()=, projecting two numbers):
#+begin_src rust
fn gather_poh(&self) -> Vec<PohPoint> {
    let mut rows = Vec::new();
    for (size_key, cost_val) in self.boxes.iter() {          // &, immutable
        if let Some((key, _box)) = cost_val.first_key_value() {  // &, immutable
            rows.push(PohPoint {
                size: (*size_key).into_inner(),   // copy the f64 out of the key
                cost: (key.0).into_inner(),       // copy the cost, not the box
            });
        }
    }
    rows
}
#+end_src

The teaching gold is *what did NOT happen*: we never =.clone()= a =Hyperbox=,
we never mutated the tree, so =gather_poh= is =&self= and it's callable while
other borrows are live. If the normie version cloned boxes into a
=Vec<Hyperbox>=, it'd be forced into =&mut self= (or fight the borrow) and carry
the whole box when only two numbers were needed. The borrow checker *points to*
the leaner shape.

- **rust-skills**: =own-borrow-over-clone=, =perf-iter-over-index=,
  =own-slice-over-vec=.
- **Book**: ch 04-02 (borrowing — the whole step), ch 13-02 (iterator
  adapters), ch 04-01 (Copy — why =*size_key= is a copy, not a move).

Stop. **Check** — why does the gather return =Vec<PohPoint>= (owned copies of
(size, cost)) instead of =Vec<Hyperbox>= or borrows into the map? Because POH
only needs two numbers; borrowing into the map would ripple =&mut self= rules;
and owned small copies are cheap. Return /values/, not /references/ into
yourself — the whole point of value types.

** Step 6 — POH selection (pure transform)

POH (potentially-optimal hyperboxes) — convex hull / pareto over the =PohPoint=
list. This is a **pure function**: =convex_hull(&[PohPoint]) -> Vec<PohPoint>=. It
touches no tree, borrows nothing lasting, allocates only its own return.

Normie-from-C++ (a method that pushes/pops a member list):
#+begin_src cpp
void convexHull() { m_poh.push_back(...); m_poh.pop_back(); }  // mutates THIS
#+end_src

Idiomatic (pure: takes a slice, returns an owned Vec):
#+begin_src rust
fn convex_hull(poh: &[PohPoint]) -> Vec<PohPoint> {  // &[T], not &Vec<T>
    let mut hull: Vec<PohPoint> = Vec::new();
    for p in poh.iter() {
        while hull.len() >= 2
              && cross(hull[hull.len()-2].size, hull[hull.len()-1].size, p.size) <= 0.0 {
            hull.pop();
        }
        hull.push(*p);
    }
    hull
}
#+end_src

Why does it feel cleaner than the C++? No side channel — input is a slice of
points, output is an owned =Vec=, nothing else changes. The absence of side
effects is not a preference; it's what lets you call it headlessly in a unit
test with a stub cost (=test-mock-traits=) with no GPU or UI. (The =&[T]= habit
= =own-slice-over-vec= also makes it FFI-ready.)

- **rust-skills**: =anti-vec-for-slice=, =own-slice-over-vec=, =perf-collect-once=,
  =test-mock-traits=.
- **Book**: ch 10-02 (pure funcs over traits), ch 13 (iterators), ch 04 (why an
  owned =Vec<PohPoint>= return is fine — it's moved out, not copied out).

** Step 7 — trisection + the ownership dance (THE lesson)

The step that ties the room together: take a selected box out, trisect it into
center + two shifted boxes, reinsert them. This is where Rust's ownership model
forces a structurally correct design that C++ lets you violate.

Normie-from-C++ (mutate the box in place, resize a vector):
#+begin_src cpp
void trisect(HyperBox &b, std::vector<...> &out) { /* mutate b, push children */ }
#+end_src

Idiomatic (consume the parent, return the children):
#+begin_src rust
fn trisect(mut parent: Hyperbox) -> (Hyperbox, [Hyperbox; 2]) {  // take = move
    let (min_idx, _) = parent.depths.iter().enumerate()
        .min_by_key(|&(_, v)| *v).expect("6-element array");
    parent.depths[min_idx] += 1;
    // center keeps parent's cost; two shifted children get cost_at_center: None
    // ... (build pos/neg shifted boxes)
    (parent, [pos, neg])
}
#+end_src

and the caller re-inserts:
#+begin_src rust
let (center, [pos, neg]) = Hyperbox::trisect(winner);  // winner moved OUT
// batch-eval pos/neg's new centers first, then reinsert with costs
#+end_src

Why does Rust force "take it out, transform, put it back"?

1. **The map key is the size.** =BTreeMap<SizeKey, ...>= — if you mutated a
   map-resident box's =depths=, its =size()= changes, so its =SizeKey= would be
   wrong and the map corrupted. Rust's borrow rules make this hard to even
   express.
2. **=pop_first()= returns /owned/.** On the inner map it gives you the winner
   as an owned =Hyperbox= — no lifetime to fight, free to move/transform. That's
   =mem-take-replace= in the wild.
3. **Reinsert = move=.** =boxes.entry(new_key).or_default().insert(id, child)=
   moves the child in. The tree *owns* it now; your Rust code no longer does.

This is the single most important ownership lesson in the doc. Carry this:
**the three phases map to three ownership states — borrow to gather, own to
transform, move to store — and the borrow checker keeps them honest.**

- **rust-skills**: =own-move-large=, =mem-take-replace=, =own-copy-small=,
  =api-builder-must-use=.
- **Book**: ch 04 (all of it); ch 15 (why =Box= fits =unique_ptr=-shaped
  ownership); ch 08 (BTreeMap entry/remove API).

Stop. **Check** — why can't you just mutate a box inside the map and "put it
back in place"? Because its size (the map key) changed, and Rust won't give you
an =&mut= into a container while you're keyed by its value (the map re-balances
on =insert=/=remove=, not in place).

That is the whole algorithm core in seven steps. What remains — cost injection,
batching, FFI, errors — is scaffolding around this loop, which is why the
Roadmap routes you back to Steps 5-7 the most.

** Reconciliation note — the pedagogical depths model vs the shipped C++

Steps 3–7 model a box as =depths: [u32; 6]= with size derived via
=3f64.powf(-2.0 * depth)= and trisection on the minimum-depth axis. This is a
teaching simplification. The real C++ =DirectOptimizer= tracks per-axis side
lengths (=SetSides= / =TrisectSide=, dividing one side by 3.0), computes size as
the L2 norm of current sides, and splits on the **largest denormalized** axis
(=DenormalizeRange(sides).GetLargestDirection()=, first-max tie-break in x..za
order, per =SplitRule::OneSide=). For anisotropic ranges the chosen axis differs
from the depth-minimum choice.

When you implement for real: re-anchor on the actual state (per-axis sides or
depths + the range vector), match =HyperBox6D::SetSides= bit-for-bit, select the
split axis as the largest denormalized side, and shift children by the current
side length — not =3^-(depth)=.

*** Rust learning — what does "shared struct" mean, and why does cxx care?

The `struct Pose { x: f64, ... }` inside `#[cxx::bridge]` is a **shared
struct** — one definition, two languages, byte-identical layout. cxx
generates a C++ `struct Pose` with the same fields in the same order, so a
`Pose` can be passed *by value* across the boundary with zero serialization.

- **Book**: ch 05-01 (defining a struct), ch 19 (unsafe/FFI — how a `#[repr]`
  ties layout).
- **rust-skills**: =api-non-exhaustive=, =name-acronym-word= (name it `Pose`,
  not `POSITION6D`), =own-copy-small=. `Pose` is 6×f64 = 48 bytes — small and
  `Copy`-able, so passing it by value is cheap (normie-from-Python would
  over-use references/boxes worried about cost; here by-value is the fast
  choice).

Normie-from-C++ (reach for a smart pointer / reference everywhere):

#+begin_src rust
fn run(&mut self, cost: &CppCost, point: &Pose) -> f64   // borrow of a 48-byte POD
#+end_src

Idiomatic (small value types cross by value):

#+begin_src rust
fn evaluate6(&self, x: f64, y: f64, z: f64, xa: f64, ya: f64, za: f64) -> f64
#+end_src

Notice the doc chose the *six-double* scalar form for the hot path, not the
`&Pose`. That's a deliberate cxx/layout decision — a bare `Pose` by value
would also work, but six scalars make the ABI trivially C-compatible and dodge
any implicit padding question. The takeaway: **at an FFI boundary, prefer the
simplest ABI (plain doubles / POD struct) so both compilers agree on layout
without you reasoning about padding.** Brown Book ch 19-04 explains why layout
matters for FFI.

A shared `enum PohMode` becomes a C++ `enum class PohMode` on the other side.
Because a C++ `enum class` can legally hold an out-of-list value, every =match=
on a shared enum in Rust must include a wildcard `_` arm — cxx cannot prove
C++ will only send a listed discriminant. This is a genuinely Rust-flavored
~normie= trap: in C++ you never match exhaustively; in Rust the compiler
*forces* the `_` anyway.

#+begin_src rust
let mode = match mode {
    ffi::PohMode::ConvexHull => ...,
    ffi::PohMode::Pareto     => ...,
    ffi::PohMode::Aggressive => ...,
    _ => Err(UnknownPohMode),   // cxx shared enums can't be trusted to be in-list
};
#+end_src

(**Book ch 06**, exhaustive matching; this is exactly why Rust prefers exhaustiveness.)

* Options & landmarks

** backend selection — A/B switch mechanics

1. *Runtime C++ virtual interface*: define an =IOptimizer= abstract seam that a
   wrapper around the existing C++ =DirectOptimizer= AND the Rust backend both
   implement; select at runtime (via the =OptimizerRunController= factory)
   without touching the stage loop. Cleanest long-term (one objective seam the
   whole app uses); more moving parts up front. cxx opaque types compose with
   C++ inheritance (move-only smart-ptr-handled structs).
2. *Compile/link-time toggle* (CMake): =option(JTML_USE_RUST_OPTIMIZER ...)=;
   conditionally =target_link_libraries(... direct-rs-lib)= + define
   =JTML_USE_RUST_OPTIMIZER=. Pick at build; zero runtime divergence; requires
   rebuild to toggle.
3. *Direct single-branch swap* in =RunDirectStage= (the flow above): least
   injection; both implementations coexist behind =optimizer_backend=. Fastest
   to A/B; coordination layer still knows Rust directly.

Recommend for expedient A/B: **#3 first**, then promote to a runtime interface
(#1) if you want a settings toggle without recompiling.

** Milestones — run-to-completion vs live progress

- =M1 (recommended first)=: =run(&mut self, cost) -> RunOutcome= — run to
  completion, no live UI progress. Shortest to a compilable A/B.
- =M2 (live progress)=: cxx CANNOT take a C++ std::function callback into Rust
  (C++→Rust fn pointers unimplemented). Reverse the wiring: an opaque C++
  =ProgressSink= with methods =on_iteration(calls)/on_improvement(best)= that
  Rust *calls out to* (Rust→C++ methods — supported) and C++ re-emits the
  coordinator's =UpdateDisplay /= UpdateOptimum=. Must match C++ ordering exactly (30fps
  iteration, on-improvement) or the UI regresses.
- =M3 (per-step from C++)=: expose =step()= that C++ drives in a loop; keeps
  progress control in C++ but diverges from the C++ Run structure. Not
  recommended for a drop-in.

*** Rust learning — callbacks, and why cxx flips the direction

M2's =ProgressSink= may look odd if you come from C++/Python where a callback
is just "a function you pass in". Rust draws a sharp line between *callable
you can hand out* and *callable you can accept*, which explains the whole M2
shape.

- **Book**: ch 13-01 (closures), ch 13 (Fn-traits), ch 16 (message
  passing/threads — the UI-pacing side).
- **rust-skills**: =closure-fn-trait-bounds= (=FnOnce= ⊇ =FnMut= ⊇ =Fn=;
  request the *least* restrictive), =closure-move-capture=,
  =api-builder-must-use=.

The `Fn`/`FnMut`/`FnOnce` hierarchy is Rust's way of saying *how many times
and with what exclusivity* a closure may run:

- =FnOnce= — may be called once.
- =FnMut= — may be called repeatedly, may mutate captured state.
- =Fn= — may be called repeatedly, captures immutable (can be shared).

Normie-from-C++ (the host passes a =std::function= into Rust for progress):

#+begin_src cpp
// CANNOT work in cxx: C++->Rust fn pointers aren't implemented
opt.setProgressCallback([](int iter, double best){ ... });
#+end_src

Why cxx forbids it: function pointers in cxx flow **Rust→C++** only. So the
idiomatic M2 is the reverse — Rust calls a method on an opaque C++ object:

#+begin_src rust
// Rust holds an opaque C++ ProgressSink and calls OUT (supported direction)
run_with_sink(&mut sink);          // sink.on_iteration(calls) etc.
#+end_src

The teaching moment: in C++/Python a callback is ambient (implicit, whatever
the caller wants). In Rust a callback is a *first-class value/contract* with
well-defined effects. When the boundary forbids one direction, you invert the
ownership — the "sink" pattern (Rust owns a handle to the host and pokes it)
is the idiomatic Rust way to express "the host wants progress while I run".

M1's simpler shape (run-to-completion, return =RunOutcome=) skips callbacks
entirely — which is why it's the recommended first milestone: it lets you get
the algorithm + the cost crossing right before adding the progress-inversion
complication. This sequencing — get the pure path correct, then layer the
callback inversion — mirrors how Rust itself decouples pure logic from IO.

** Cost invocation

- *Serial per-point*: keep scalar =evaluate6(x,6doubles)= in a tight loop. Works,
  but crosses the cpp boundary per point (~20k–30k total evals).
- *Batch query* (matches C++ =BatchCostFunction=): collect new centers → one
  =&[Pose]= → =Vec<f64>= in input order. Recommended for real runs; maps onto
  cxx slices.
- *Slices*: cxx supports slices of shared structs (=Pose=) and primitives, NOT
  opaque types. =&[Pose] ↔ C++ =rust::Slice<const Pose>=. Prefer =&[Pose]=
  over a flat =Vec<f64>= for clarity.

*** Rust learning — slices, iterators, and "one FFI hop"

The batch-vs-serial decision is a place where idiomatic Rust and performance
agree, and it teaches two habits: **slices over references-to-Vecs**, and
**iterator pipelines over index loops**.

- **Book**: ch 04-03 (slices — `&[T]` is a fat pointer: pointer + length),
  ch 13-02 (iterators), ch 13-04 (lazy iterators; collect only when needed),
  ch 08 (Vec).
- **rust-skills**: =own-slice-over-vec=, =perf-iter-over-index=,
  =perf-iter-lazy=, =perf-collect-once=, =anti-vec-for-slice=,
  =anti-index-over-iter=, =coll-map-choice=.

Normie-from-C++/Python (loop by index, pass =&Vec<f64>=):

#+begin_src rust
fn batch_cost(costs: &Vec<f64>) -> Vec<f64> {   // &Vec is a smell
    let mut out = Vec::with_capacity(costs.len());
    for i in 0..costs.len() {                    // indexing = bounds checks
        out.push(costs[i] * 2.0);
    }
    out
}
#+end_src

Idiomatic (slice + iterator; accept `&[f64]`, chain lazily):

#+begin_src rust
fn batch_cost(costs: &[f64]) -> Vec<f64> {      // &[T], not &Vec<T>
    costs.iter().map(|c| c * 2.0).collect()      // lazy, no manual push
}
#+end_src

Why this matters for the BUFFER seam specifically:

- **`&[Pose]` vs empty-receiving `Vec`** — a slice is a /view/ over contiguous
  memory; cxx maps `&[T]` to C++ `rust::Slice<const T>`, which lets the C++
  host pass a contiguous `std::vector<Pose>` without copying. That's the
  "zero-copy batched eval" you wanted.
- **One FFI hop beats many** — each scalar `evaluate6` crossing is a boundary
  transit; a batch collects ~hundreds of new centers into one `&[Pose]` and
  makes **one** call. For 20k-30k evals this is the difference between 20k
  crossings and a handful. The =BatchCostFunction= sibling in C++ exists for
  precisely this.
- **Iterator pipelines compose with your BTreeMap** — the POH gather you
  already wrote (`self.boxes.iter()...first_key_value()`) is a READ-ONLY
  borrow pipeline; the trisection (`remove`/=pop_first=) is the MUTATING side.
  Slice-vector-boundary habits keep the borrows straight.

Reading tip: Brown Book ch 4-03's slice diagram (the fat-pointer of ptr+len)
is the exact mental model for `rust::Slice<const Pose>`.

** Cost injection — Arg-time vs constructor-time

- =A (cost via method arg)=: =DirectOptimizer= { =boxes, current_best = } and
  =run(&mut self, cost: &CppCost) -> RunOutcome=. Cost flows in at call time.
- =B (cost stored in struct)=: constructor takes the handle; Rust owns it;
  =run(&mut self)= alone. Matches the C++ constructor shape.

Both work; A keeps the optimizer pure and the FFI thin.

*** Rust learning — the =Cost= capability as a trait (not a class)

Option A (cost via method arg) is the idiomatic one, and it's worth
understanding *why*: =DirectOptimizer= becomes a **pure data + algorithm**
object and the cost is a small **capability** it knows how to call, injected
per-call. In Rust that capability is best expressed as a **trait** — a
contract, not a base class.

- **Book**: ch 10-02 (traits), ch 17-02 (trait objects =dyn Trait=),
  ch 13 (closures — the cost is eventually a closure over GPU state).
- **rust-skills**: =trait-dyn-vs-generic=, =trait-object-safety=,
  =closure-fn-trait-bounds=, =closure-impl-fn-return=, =test-mock-traits=.

The normie-from-C++ approach (a base class =Cost= with virtual =eval()=, or a
=std::function= alias) reads as a concrete =CppCost= dependency everywhere:

#+begin_src rust
// normie: hard-code the concrete handle into the optimizer
struct DirectOptimizer { cost: CppCost /* concrete */ }
#+end_src

Idiomatic (a trait that *both* a test stub and the real C++ handle implement):

#+begin_src rust
trait Cost {
    fn eval(&self, poses: &[Pose]) -> Vec<f64>;   // batch shape, needed later
}
struct CppCostHandle(/* cxx opaque */);   // impl Cost by calling evaluate6
struct AnalyticCost;                       // test stub for headless Tier-1
#+end_src

Making =Cost= a trait vs. a concrete =CppCost= dependency is what lets you run
the SAME algorithm against a **test stub** and the **real GPU cost** — that's
=test-mock-traits=, and it's exactly why the scaffold already sketches a
=trait Cost= next to =CppCost=. Then the two shapes differ only by dispatch:

- **=impl Fn= (generics)** — zero-cost, monomorphized, great for a hot
  per-call closure. Use when the cost really is a closure.
- **=dyn Fn=/trait object (=Box<dyn Cost>=)** — one vtable, needed when the
  concrete cost is selected/stored at runtime. Your A/B already implies runtime
  selection.

The A/B switch is literally this: two backends are two implementations of one
contract. Whether that contract is Rust's =Cost= trait (inside the crate) or
C++'s =IOptimizer= virtual interface (across the boundary) is the same idea in
two languages — which is what the =IOptimizer= option is pointing at.

** Outcome/error channel — Result vs status

- cxx =Result= → C++ throws =rust::Error= (std::exception). In a Qt/CUDA
  pipeline, exceptions-on is uncertain → prefer **explicit status**:
  =RunOutcome { ok: bool (or code), best, best_cost, calls }=.
- Never let Rust panic across FFI (panic logs+aborts). Represent all error
  paths in the status struct / error enum; never unwrap across the boundary.

*** Rust learning — errors as values, not as side effects

The whole =Result= vs status-struct decision is a Rust-native philosophy: Rust
has **no exceptions**. Errors are just values returned from functions. This
changes the normie-from-C++/Python default dramatically.

- **Book**: ch 09-01 (panic), ch 09-02 (=Result= + =?=),
  ch 09-03 (=unwrap= vs =expect= — when each is honest).
- **rust-skills**: =err-result-over-panic=, =err-thiserror-lib=,
  =err-anyhow-app=, =err-no-unwrap-prod=, =err-question-mark=,
  =err-context-chain=, =err-lowercase-msg=.

Normie-from-C++ (bool return + out-param, or throw an exception):

#+begin_src cpp
bool Run(/* out */ double& best_cost);
#+end_src

Normie-from-Python (rely on =raise= and =try/except=):

#+begin_src python
def run(...):
    if bad: raise OptimizerError("bad")
#+end_src

Idiomatic Rust (return a =Result= / explicit status; the *caller* decides):

#+begin_src rust
type RunResult<T> = Result<T, OptimizerError>;

#[derive(thiserror::Error, Debug)]

    #[error("all-zero range {range:?}")]
    ZeroRange { range: Pose },
    #[error("non-finite cost {cost}")]
    NonFiniteCost { cost: f64 },
    #[error("poisoned executor")]
    Poisoned,
}
#+end_src

Why the doc chose an **explicit status struct** (=RunOutcome{ ok: bool, error: u32, ... }=)
rather than Rust's =Result= for the FFI boundary specifically: cxx can map a
Rust =Result= to a C++ `rust::Error` exception — but that requires C++
exceptions to be **enabled**, which is uncertain in a Qt/CUDA toolchain, and a
Rust panic crossing an FFI boundary is *undefined behavior* (it =abort()=s the
whole process). So:

- **Inside** the Rust crate, use =Result<T, OptimizerError>= freely (=?
  everywhere) — that's idiomatic and safe.
- **Across** the cxx boundary, return a plain status struct, and map the inner
  =Result= to it as the last step (`out.ok = result.is_ok()`). This keeps the
  Rust-side ergonomics and the C++-side safety.

This two-tier pattern — rich errors inside, flattened explicit status at the
FFI edge — is the idiomatic way to bridge Rust's error values to a C++ caller:

the boundary is the ONE place you convert, and you never let a panic or a
=rust::Error= exception escape across it.

*** Rust learning — ownership is the point (not a speed bump)

This whole section is Brown Book ch 4 made concrete. The normie-from-C++
reaction is "why do I need =Box<DirectOptimizer>=", but in Rust =Box= is not a
pointer-with-extras; it's the *ownership* model made explicit.

- **Book**: ch 04-01 (what is ownership), ch 04-03 (slices),
  ch 15-01 (=Box= "for having a value on the heap"), ch 15 (smart pointers).
- **rust-skills**: =own-borrow-over-clone=, =own-copy-small=, =own-move-large=.

Normie-from-C++ (=unique_ptr= everywhere because it's the default):

#+begin_src rust
fn make() -> Box<DirectOptimizer> { Box::new(DirectOptimizer::default()) }
#+end_src

...is actually fine *here* — because the C++ side owns the handle move-only, and
=Box= is Rust's =unique_ptr=-equivalent. The lesson: =Box= isn't wrong because
it's a pointer; it's wrong to reach for it when you only need to /borrow/. The
doc's =&self= / =&mut self= receivers are the borrow side.

Normie-from-Python mistake: passing =self= by value everywhere. cxx forbids
`self` by value for opaque types — and that's not a limitation, it's Rust
refusing to let you silently /duplicate/ something you can only own once. The
distinction the section hammers (Brown ch 4-01):

- =T= (by value): I *move* it — I alone own it now.
- =&T=: I *borrow* it to read; others can too.
- =&mut T=: I *borrow* it to mutate; exclusive.

There is no "copy" in that list for a non-=Copy= type. That absence is the
point. The rule "=CppCost handle must out-live the run call=" is likewise an
ownership statement: C++ holds the =std::function=+GPU captures; Rust borrows
it for the duration of =run=. The borrow ends when =run= returns, so the handle
stays alive — the whole lifetime idea in one sentence.

* Appendix A — deep dive: borrowing and the DIRECT loop

If you only read one appendix, make it this one: it's ownership/borrowing made
concrete against the exact shapes this project uses. The Brown Book ch 4 is the
source; here we map it onto =boxes: BTreeMap<SizeKey, BTreeMap<CostKey,
Hyperbox>>= and the run loop.

** The four borrow flavors and when the loop uses each

Re-read this table whenever a borrow error confuses you. Every one of these is
deliberately exercised by the DIRECT loop.

| Rust expression            | borrow kind          | in this project                                  |
|----------------------------+----------------------+--------------------------------------------------|
| =&self= / =&T=             | shared (read-only)   | =gather_poh= over the whole tree                  |
| =&mut self= / =&mut T=     | exclusive (write)    | =trisect_and_reinsert= (it removes + inserts)     |
| =T= by value               | move (ownership)     | =pop_first()= giving you the owned winner        |
| =&[T]=                     | slice (a window)     | =convex_hull(&[PohPoint])= — a borrowed view      |

The rule that governs almost every error here: **you can have many =&T= or one
=&mut T=, never both for the same data at the same time.** (Brown ch 4-02.)

** The borrow dance, zoomed to one iteration

Walk the loop and name the borrow at each breakpoint (this is Milestone 9's
self-check, but written out):

#+begin_src rust
// 1. GATHER — shared borrow: many readers, no writer
let mut candidate_points = self.gather_poh();     // &self
let selected = make_hull(&candidate_points);       // &[PohPoint]

// 2. TRISECT — here we switch from &self to &mut self
//    `self` was &self during gather; now we need &mut self to mutate the map.
for point in &selected {
    // 3. TAKE — move ownership OUT of the map (needs &mut)
    let winner: Hyperbox = {
        let row = self.boxes.get_mut(&OrderedFloat(point.size)); // &mut row
        let (_key, hb) = row.expect("selected row exists").pop_first()
            .expect("non-empty row");
        hb                                          // moves the Hyperbox out
    }; // row borrow ends here

    // 4. TRANSFORM — we OWN `winner` now; no borrow at all
    let (center, [pos, neg]) = Hyperbox::trisect(winner);

    // 5. REINSERT — move the children BACK in (&mut)
    self.insert_box(center);   // insert as known-cost
    // pos/neg: batch-eval their centers, then insert with scores
}
#+end_src

The borrow transitions are the *spine* of the method:

- =&self→&mut self= happens by *method signature*, not by hand — a method
either takes =&self= or =&mut self=, so the compiler forces gather and
trisect to be separate methods with different receivers. That's why you can't
have one giant =&mut= method that gathers and mutates at once and expect the
borrow rules to stay sane.
- The =row= borrow in step 3 is **scoped to the block**: the =&mut row= dies
at the closing brace, so =hb= (owned) can be returned out of it. This block-
scoping is exactly the =mem-take-replace= / last-use pattern; the compiler ends
the borrow at the winner's last use.

** The three errors you will actually hit (the canon)

These are the borrow-error codes you'll encounter in this project, mapped to
the /cause/ and the /fix/:

| Error   | What it means                                  | How it bites here                 | The fix                           |
|---------+------------------------------------------------+-----------------------------------+-----------------------------------|
| =E0382= | use of a moved value: you moved it away        | reusing a =Hyperbox= after        | don't reuse after move; or        |
|         | then used it again                             | =pop_first()= moved it out        | reorder so last use comes first   |
| =E0502= | cannot borrow as mutable because it's also     | =&mut self= while a =&self=       | scope the shared borrow so it ends|
|         | borrowed as immutable (two borrows, wrong way) | borrow of the map is still alive  | before the =&mut= begins          |
| =E0499= | two mutable borrows at once                    | two live =&mut= into the tree     | never hold two =&mut= into the    |
|         |                                                | (e.g. nested =get_mut= loops)     | same map; restructure              |
| =E0505= | cannot move a value out of a borrow            | =&self= row then trying to        | pop/remove /out/ via =&mut= or     |
|         |                                                | return an owned =Hyperbox=        | clone only the fields you need    |

- **Book**: the Brown Book has a whole chapter (ch 4) that animates these,
  with an interactive "editor" where you drag borrows around.
- **rust-skills**: =own-borrow-over-clone=, =own-move-large=,
  =mem-take-replace=, =anti-index-over-iter=.

* Appendix B — deep dive: ownership, lifetimes, and Send/Sync

This appendix is for the moments when value/move/borrow isn't enough — when you
need =Box=, when a lifetime shows up in a signature, and when the compiler
starts asking about =Send= and =Sync= because of the worker thread + GPU cost.

** Lifetimes: what they really are (and aren't)

A lifetime is not a value you pass around; it's the compiler's label for "how
long a borrow is valid". You mostly write =&T= and let Rust elide lifetimes; an
explicit lifetime (=<'a>=) appears when a return type borrows from an argument.

Normie-from-C++ confusion: "=&Point6D= is a const reference, why do I need a
lifetime?" The answer: the returned value's lifetime is tied to the borrow's
origin. In this project you rarely write explicit lifetimes because you /own/
the values. The one place they appear is cxx opaque types and =&CppCost=
borrows — which cxx manages for you.

- **Book**: ch 10-03 (lifetimes), Brown ch 4-02 (the borrow table).
- **rust-skills**: =own-lifetime-elision=, =type-phantom-marker=.

** =Box=: only when you need a stable address or heap

Recall =rust::Box<DirectOptimizer>= on the C++ side. Box is one specific tool,
not a default. You reach for =Box<T>= when:

- T is recursive (a tree node) — not here.
- T is huge and you want to move a pointer instead — your =Hyperbox= is tiny.
- you need heap because of a trait object =Box<dyn Cost>= — only if you pick
  runtime dispatch for the cost (Milestone 6).
- FFI wants a stable pointer (cxx =Box<DirectOptimizer>=) — THIS is your case.

Normie mistake: =Box= every struct "just in case". Stop — value =Hyperbox=`s by
default; box only the FFI boundary object. =own-move-large=, =mem-box-large-
variant=.

** Send and Sync: why the GPU cost blocks one thread

This is where =Send= and =Sync= finally matter. The worker thread (on the C++
side) calls =run= synchronously; the GPU cost (:CppCost=) mutates =GPUModel=
pose state on each =evaluate=. So:

- =Send= means "value can be transferred to another thread." =CppCost= wraps
  a =std::function= + GPU captures — Rust can't prove it's thread-safe, so it
  won't be auto-=Send=.
- =Sync= means "&T can be shared across threads." Same story.

Rather than fight that, the design keeps everything on ONE worker thread and
calls =run= to completion (M1). That sidesteps =Send= / =Sync= entirely — you never
move =CppCost= between threads because the C++ side owns the thread and the
handle. This is why the doc's threading rule is "serial, one thread" and why
=M1 (run-to-completion) is recommended before M2 (which needs care about which
thread calls into the sink).

- **Book**: ch 16 (concurrency — Send/Sync are the runtime of fear =free=
  threading; =Rc= vs =Arc=).
- **rust-skills**: =own-arc-shared= (when you DO need shared ownership across
  threads, upgrade =Rc=→=Arc=), =conc-thread-local=, =unsafe-send-sync-manual=.

** =Rc=/=Arc=/=RefCell=: the "when you DON'T need them" warning

If you find yourself reaching for =Rc=, =Arc=, or =RefCell= in DIRECT, pause
hard. They are for /shared/ or /interior/ ownership, and the whole design avoids
both:

- =Rc/Arc= for shared ownership — you never share a =Hyperbox=; the map owns it
  and you move it in/out. You don't need shared pointers at all.
- =RefCell= for interior mutability — you mutate through =&mut= methods, not
  through interior mutation. If you're grabbing =RefCell=, you've probably
  mis-structured a method's receiver (should be =&mut self=, not =&self= + a
  hidden =RefCell=).

Intro Section n/a; see Interior Mutability appendix.

Stop. **Check** — why is =CppCost= not auto-=Send/Sync=, and how does keeping
the run on one thread dodge that (instead of adding =unsafe impl Send=)? Because
Rust can't verify the captured GPU state is thread-safe; single-threading makes
the question moot without any unsafe.

* Appendix C — interior mutability: when you do NOT need it

Interior mutability (=Cell=, =RefCell=, =Mutex=, =RwLock=, =Atomics=) lets you
mutate through a shared reference. It is a *workaround for a borrow it gives
up*, and DIRECT's design exists largely to not need it. This appendix helps you
recognize the moment you're reaching for it and whether that's a real need or a
sign you've mis-structured.

** The honest use case

You need interior mutability when: a value must be mutably changed, but you
only have =&self=/=&= access, and you can't re-structure to =&mut=. Classic
examples: caches, counters behind an API that only hands out =&self=, or raw
pointer mutation like GPU buffers owned by C++ and visible to Rust as =&T=.

In DIRECT, the places you might 'tempt' reach for it:

- a =cost_function_calls_= counter you bump in =&self= methods;
- a cache of computed =size()= values;
- the =CppCost= handle that mutates GPU state but comes in as =&CppCost=.

** Why DIRECT mostly dodges it

1. **The counter.** In the C++ it's a member bumped by all methods. The Rust
   idiomatic move is to make =&mut=-taking methods the ONLY mutators, and keep
   the counter next to =boxes= behind =&mut self=. If a counter needs to be
   readable from =&self= AND written from elsewhere, =Cell<u32>= is legitimate
   — but only because you've proven =&self= must observe it while =&mut=
   writes elsewhere. Often you can reorder so a single =&mut self= method owns
   the bump and the read, and =Cell= never appears.
2. **The cache.** =perf-profile-first=: don't cache until the profiler says so.
   And even then, a =RefCell= cache turns every read into a potential panic
   (.borrow() twice = panic) — you trade one class of bug for another.
3. **The GPU =CppCost=.** This is the real one. On the C++ side, =evaluate()=
   mutates =GPUModel= pose via a mutable closure, but to Rust it arrives as
   =&CppCost=. If Rust needed to /store/ that handle and call it from multiple
   places, you might reach for =RefCell<&CppCost>=. But the design passes =
   &CppCost= /in to run/=/batch= and finishes the call synchronously, so the
   C++ side alone owns mutation — no interior mutability needed in Rust.

** The "is it a real need?" checklist **

Ask, in order, before introducing =RefCell= / =Cell=:

1. Can I change a =&self= method to =&mut self=? If a mutator touches state,
   it should /take/ =&mut= — that's the honest signal.
2. Can I return data instead of mutating in place? (gather returns =Vec<PohPoint>=;
   it doesn't scribble a member.)
3. Is this genuinely shared mutable state visible across & reads and &mut
   writes? Only /then/ is =Cell=/=RefCell=/=Mutex= justified, and pick =Mutex=
   if it crosses threads.

If the answer to #1 or #2 is yes, you don't need interior mutability — you need
a better method signature. Reaching for =RefCell= early is the "masturbatory
types" spike this project wants to avoid (see =anti-over-abstraction= and the
Options-as-data block).

- **Book**: ch 15-05 (=RefCell= "interior mutability"), ch 16 (threads =
  =Mutex= vs =RwLock=), rust-skills =own-refcell-interior= =
=own-mutex-interior=.
- **rust-skills**: =own-refcell-interior=, =own-mutex-interior=,
  =own-rc-single-thread=, =anti-over-abstraction=.

Stop. **Check** — you're about to add =RefCell<u32>= for a call counter. Run
the checklist: can the bumping method take =&mut self=? If yes, drop the
=RefCell=. Only keep it when =&self= readers MUST see the current count while
another object owns mutation — which, in DIRECT, the =&mut self=-run loop
handles without interior mutability.

* Appendix D — =Option= and =Result= in practice (the Python jump)

Coming from Python, this is the appendix that will save you the most time.
Python has =None= and exceptions and they're *ambient*: any value might be
=None=, any call might raise. Rust makes both into ordinary types you must open
before use. =Option<f64>= is not "an f64 that might be missing" — it is a
different type from =f64=, and the compiler will not let you add 1.0 to it.

This is exactly the =cost_at_center: Option<f64>= field from Step 3, so every
example below is real.

- **Book**: ch 06-02 (=match= + =Option=), ch 06-03 (=if let=),
  ch 09-02 (=Result= + =?=), ch 18 (patterns in depth).
- **rust-skills**: =type-option-nullable=, =err-question-mark=,
  =err-no-unwrap-prod=, =pat-exhaustive-enum=.

** The four ways to open an =Option= (in order of preference)

#+begin_src rust
// 1. match — when both arms do real work
match hb.cost_at_center {
    Some(c) => record(c),
    None    => queue_for_eval(hb),
}

// 2. if let — when only one arm does work
if let Some(c) = hb.cost_at_center { record(c); }

// 3. let-else — when None means "bail out of this function" (the flattener)
let Some(c) = hb.cost_at_center else { return Err(OptimizerError::Unscored) };
// `c` is a plain f64 from here down — no nesting, no indentation creep

// 4. combinators — when you're transforming, not branching
let doubled: Option<f64> = hb.cost_at_center.map(|c| c * 2.0);
let shown:   f64         = hb.cost_at_center.unwrap_or(f64::INFINITY);
#+end_src

=let-else= (option 3) is the one C++/Python developers never discover on their
own and then use constantly. It is the idiomatic early-return: the happy path
stays un-indented, the failure path is one line. Reach for it whenever your
=match= has a =None= arm that just leaves.

** The combinator cheat-sheet

These are the =Option=/=Result= methods worth memorizing. Every one of them
replaces an =if= you'd have written in C++.

| Call                        | Means                                          | Use here                             |
|-----------------------------+------------------------------------------------+--------------------------------------|
| =.map(f)=                   | transform the inside, keep the wrapper          | scale a cost, keep "unscored"-ness    |
| =.and_then(f)=              | =map= where =f= itself returns Option/Result    | chained lookups (row → box)           |
| =.unwrap_or(v)= / =_else(f)=| supply a default                                | treat unscored as =INFINITY= for sorts |
| =.ok_or(e)= / =_else(f)=    | =Option= → =Result= (attach a reason)           | "selected row missing" → error        |
| =.ok()= / =.err()=          | =Result= → =Option= (throw the reason away)     | the FFI-edge flatten                  |
| =.filter(p)=                | keep =Some= only if predicate holds             | "scored AND finite"                   |
| =.take()=                   | move the value out, leave =None= behind         | claim a pending cost exactly once     |
| =.as_ref()= / =.as_mut()=   | =&Option<T>= → =Option<&T>=                     | peek without moving out of =&self=     |
| =.is_some_and(p)=           | test the inside without unwrapping              | guards in =if=                        |
| =.zip(other)=               | pair two =Some= into one =Some((a,b))=          | need both center costs or neither     |

=.take()= deserves a flag: it is =mem-take-replace= in miniature and it's how
you move a non-=Copy= value out of a struct field you only have =&mut= to.
When the borrow checker says "cannot move out of =self.field=", =.take()= is
usually the answer.

** =?= — the operator that makes =Result= bearable

Normie (Python habit: let it raise, or C++ habit: check every return):

#+begin_src rust
let row = match self.boxes.get_mut(&key) {
    Some(r) => r,
    None => return Err(OptimizerError::MissingRow { key }),
};
let (_k, hb) = match row.pop_first() {
    Some(p) => p,
    None => return Err(OptimizerError::EmptyRow { key }),
};
#+end_src

Idiomatic (=?= = "unwrap or return the error to my caller"):

* Appendix E — the run loop assembled (contract-faithful)

Milestone 9 says "wire it together" and the doc never shows the wiring. Here it
is, and the reason it's worth spelling out is that **the eval-ordering contract
from "Contract being filled" lives in exactly one function** — get it wrong and
the Tier-3 parity golden diverges in a way that's miserable to bisect.

Re-read the contract line first:

> eval ordering: calls++ → non-finite → optimum update → storage → improvement callback

** The struct

#+begin_src rust
pub struct DirectOptimizer {
    tree: BoxTree,                 // the two-level BTreeMap (Step 4)
    budget: u32,                   // cumulative cap: trunk 20k → branch 25k/30k → leaf 35k
    call_offset: u32,              // SetCallOffset — cumulative across stages
    calls: u32,
    non_finite: u32,
    best: Pose,
    best_cost: f64,
    stop: Arc<AtomicBool>,         // cooperative Stop(), set from the C++ thread
    improved_this_iter: bool,      // tracks whether best changed this iteration
    range: Pose,                   // for the ZeroRange error payload
}
#+end_src

That =Arc<AtomicBool>= is the *one* honest interior-mutability case in the
whole design, and it's worth pausing on — Appendix C told you to be suspicious
of =RefCell=, and this is the exception that proves the rule. =Stop()= is
called from a different thread than =run()=, so there is no way to restructure
it into =&mut self=: the checklist's question 3 ("genuinely shared mutable
state across threads?") answers *yes*. =AtomicBool= not =Mutex<bool>= because
it's one bit and never needs to be read-and-written atomically together with
anything else. Everything else in the struct stays behind =&mut self=.

** The eval helper — where the contract is enforced

#+begin_src rust
/// Evaluate a batch and fold the results into optimizer state.
/// Returns costs in INPUT ORDER (the contract the C++ BatchCostFunction keeps).
fn eval_batch(&mut self, cost: &dyn Cost, poses: &[Pose]) -> Vec<f64> {
    let costs = cost.eval(poses);            // ONE FFI hop for the whole batch
    debug_assert_eq!(costs.len(), poses.len(), "batch cost must preserve length");

    for (pose, &c) in poses.iter().zip(costs.iter()) {
        self.calls += 1;                     // 1. calls++  (counts non-finite too)
        if !c.is_finite() {
            self.non_finite += 1;            // 2. non-finite
            continue;                        //    a non-finite eval never becomes best
        }
        if c < self.best_cost {              // 3. optimum update
            self.best = *pose;
            self.best_cost = c;
            self.improved_this_iter = true;  // 5. deferred — see below
        }
    }
    costs                                    // 4. storage is the caller's job (reinsert)
}
#+end_src

The subtle bit: the contract puts **storage before the improvement callback**,
but the improvement is *detected* here during the eval. So you don't fire the
sink here — you set a flag and fire it after reinsertion. Firing early is the
classic port bug: the UI shows a new optimum for a box that isn't in the tree
yet, and if anything downstream reads the tree on that signal, it races.

** The loop

#+begin_src rust
pub fn run(&mut self, cost: &dyn Cost, sink: Option<&mut dyn ProgressSink>) -> RunResult<()> {
    if self.tree.is_empty() { return Err(OptimizerError::ZeroRange { range: self.range }); }

    while (self.calls + self.call_offset) < self.budget
          && !self.stop.load(Ordering::Relaxed)
    {
        self.improved_this_iter = false;

        // GATHER — &self borrow, no mutation (Step 5)
        let points   = self.tree.gather_poh();
        let selected = convex_hull(&points);          // pure (Step 6)
        if selected.is_empty() { break; }             // nothing left to split

        // TRISECT — &mut self; take out, transform, put back (Step 7)
        let mut pending: Vec<(Pose, PendingSlot)> = Vec::new();
        for point in &selected {
            let winner = self.tree.take_min_of_row(point.size)?;   // owned
            let (center, [pos, neg]) = Hyperbox::trisect(winner);
            self.tree.insert_scored(center);                       // cost inherited
            pending.push((pos.center, PendingSlot::Pos(pos)));
            pending.push((neg.center, PendingSlot::Neg(neg)));
        }

        // ONE FFI hop for every new center this iteration
        let poses: Vec<Pose> = pending.iter().map(|(p, _)| *p).collect();
        let costs = self.eval_batch(cost, &poses);

        // STORAGE — then and only then, the callbacks
        for ((_, slot), c) in pending.into_iter().zip(costs) {
            self.tree.insert_with_cost(slot.into_box(), c);
        }
        if let Some(s) = sink.as_deref_mut() {
            s.on_iteration(self.calls + self.call_offset);   // ~30fps pacing is C++'s job
            if self.improved_this_iter { s.on_improvement(self.best, self.best_cost); }
        }
    }
    Ok(())
}
#+end_src

And the FFI edge — the one place =Result= becomes status (M8):

#+begin_src rust
pub fn run_ffi(&mut self, cost: &CppCost) -> ffi::RunOutcome {

    ffi::RunOutcome {
        best:      self.best,
        best_cost: self.best_cost,
        calls:     self.calls,

    }
}

** Three things this skeleton exposes that the prose didn't

1. **Batch granularity is per-iteration, not per-box.** All the new centers
   from one POH round go in one =&[Pose]=. That's the "one FFI hop" claim made
   concrete: ~2×|hull| poses per crossing instead of one.
2. **The budget can overshoot.** =eval_batch= evaluates the whole batch, so the
   final iteration may push =calls= past =budget=. The C++ checks the guard
   *between* iterations too — so this matches — but confirm it against
   =direct_optimizer.h=, because if C++ truncates mid-batch and Rust doesn't,
   the golden diverges on call count. **This belongs in "Remaining open
   questions".**
3. **=sink= is =Option<&mut dyn ProgressSink>=.** M1 passes =None= and the
   whole progress path costs nothing; M2 passes =Some=. One signature, both
   milestones — this is =trait-dyn-vs-generic= paying off.

** Tier 3 — parity against the C++ (the actual gate)

The contract says the judge is "the SAME optimum for the same cost sequence".
So make the cost sequence the artifact:

1. Instrument the C++ =DirectOptimizer= to dump, per eval: index, the 6 doubles
   in, the cost out. Run one fixture. That file is your golden.
2. In Rust, implement =Cost= as a *replay* over that file: it asserts the
   incoming pose matches the recorded pose and returns the recorded cost.
3. Any divergence fails at the *first differing eval*, with an index — instead
   of you comparing two final optima and having no idea where they split.

#+begin_src rust
struct ReplayCost { records: Vec<(Pose, f64)>, cursor: Cell<usize> }
// eval(): for each pose, assert_relative_eq! against records[cursor], return cost
#+end_src

**Capture contract (read before writing the recorder):**

- **Record SERIAL, judge SERIAL.** During capture, force the C++ serial
evaluate path — do NOT install =SetBatchCost= (the U11 batch adapter). Batch
capture can carry numerically different costs than serial replay (bank-batched
kernels vs scalar), so a batch-produced golden is a different function than the
serial replay you'll judge against.
- **ReplayCost advances the cursor by =poses.len() per batch.** Rust consumes
BATCHES (~2×|hull| poses per iteration through one eval() call); the cursor
must advance by the incoming slice length, matching positionally within the
batch.
- **Exhausted tape = a divergence signal, not a panic.** When Rust requests more
evals than recorded, return a distinct error ("requested eval N > recorded M")
and let it float up as =ok:false= — do not index-panic on the =Vec=. A raw
panic here masks the first-divergence index you actually want.
- Re-record whenever the admission/cost-execution path changes.

This is the single highest-leverage test in the port, and note what it needs:
=Cost= being a trait, and the batch/serial distinction being a detail the trait
hides. Two design decisions from M6 exist mostly to make this test possible.

(=Cell<usize>= for the cursor is legitimate here — Appendix C's checklist,
question 3, with =&self= forced on you by the trait signature. A test is also
the one place a =RefCell= panic is acceptable: it fails the test, which is the
point.)

** The panic firewall (do this once, in =lib.rs=)

Because a panic crossing FFI is undefined behavior and the design says "never
let Rust panic across FFI", make that structural rather than aspirational:

#+begin_src rust
pub fn run_ffi(&mut self, cost: &CppCost, sink: Option<&mut dyn ProgressSink>) -> ffi::RunOutcome {
    // Canonical: run_ffi is the FFI wrapper around run().
    // M1 passes sink=None; M2 passes Some(&mut sink).
    let handle = CppCostHandle(cost);
    let result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
        self.run(&handle, sink)
    }));
    match result {
        Ok(()) => ffi::RunOutcome { best: self.best, best_cost: self.best_cost,
                                     calls: self.calls + self.call_offset, ok: true, error: 0 },
        Err(_) => ffi::RunOutcome { best: Pose { x:0.0,y:0.0,z:0.0,xa:0.0,ya:0.0,za:0.0 },
                                     best_cost: 0.0, calls: 0, ok: false, error: 1 },
    }
}
#+end_src

Caveats worth understanding rather than copying blindly: =catch_unwind= does
nothing under =panic=abort=, and =AssertUnwindSafe= is you promising the state
isn't left half-mutated. It's a net, not a design. The design is =Result=
everywhere inside (Appendix D) — this catches the bug you didn't predict, on a
customer's machine, instead of aborting the whole application.

- **Book**: ch 09-01 (panic and unwinding), ch 19-01 (=unsafe=/FFI).
- **rust-skills**: =err-no-unwrap-prod=, =unsafe-safety-comment=.

Stop. **Check** — the C++ side reports a plausible optimum but =out.ok == false=
every run. Where do you look first? (The =Result=→=ok= flatten in =run_ffi=:
something inside is returning =Err= *after* best was already updated — which is
exactly the information the flatten throws away. Log the =OptimizerError=
on the Rust side before you drop it; this is the "what is lost at the edge"
from M8, biting.)
