* The problem, repo-grounded
- JTML does 2D-3D registration of knee implants (Lima KR femur/tibia) against
  single-plane fluoroscopy: DIRECT global optimizer over a GPU cost function.
- The user's topic: near-symmetric implants (hip/shoulder) give weak signal
  about the symmetric axis to the current cost functions; curvature heatmaps
  were attempted and "still not great".
- Recon correction: the curvature metric was NEVER functionally implemented —
  it is a stub returning constant 0.0 (curvature_hausdorf_metric.cu:70-71),
  never registered in listCostFunctions(), never called. The CPU-side pipeline
  (curvature_utilities.cpp: Menger curvature, inflection keypoints, per-keypoint
  distance-transform heatmaps) worked; the GPU port was abandoned by the owner
  (2023-11-27 commit: "Most likely a dud. Going to deprecate for now"), and the
  2026-08-12 deep-dive disposition is "explicitly DE-SCOPE, don't implement"
  (undefined semantics, per-stage allocation leak DIRECT_DILATION.cpp:42-43,
  silent cudaMalloc(0) error path). "Not great" = never finished, not tried-and-failed
  as a metric. The CPU utilities (curvature_utilities.cpp, generate_curvature_heatmaps)
  still exist and work.

* Cost-function invariance (the core fact)
- All 7 registered cost variants (DIRECT_DILATION default, DIRECT_DILATION_T1,
  DIRECT_DILATION_SAME_Z, DIRECT_DILATION_POLE_CONSTRAINT, DD_NEW_POLE_CONSTRAINT,
  sym_trap_function, DIRECT_MAHFOUZ) compute silhouette/contour-projection terms
  (FastImplantDilationMetric overlap, DistanceMapMetric edge-to-template, Mahfouz
  intensity+contour) plus translation-only pole/z priors.
- Result: EVERY image term is invariant under rotation about the implant's
  symmetry axis. The only rotation-sensitive term in the repo is sym_trap_function's
  varus/valgus penalty vv = asin(fem2tib[2][1]) (sym_trap_function.cpp:132-134),
  which breaks the rotation-degenerate basin. Pole terms depend only on
  translations — they cannot disambiguate rotation.
- Two distinct features share the name "sym trap": (1) the DOMAIN sym-trap
  directive (CalculateSymTrap sweep, optimizer_manager.cpp:1324+; mirror-pose
  detection via Crane-Duffy dyad construction in src/domain/sym_trap_functions.cpp:
  compute_mirror_pose — the Jensen-2024-style dual-pose geometry); (2) the
  COMPUTE sym_trap cost variant (pole distance + varus/valgus penalty).
  Librarians must not conflate them.

* What was tried before (do-NOT-re-suggest list)
1. Curvature-Hausdorff heatmap cost — failed twice (2023 GPU port abandoned;
   2026 de-scope verdict). CPU utilities live; metric semantics undefined.
2. In-engine ML classifier for tibial mirror disambiguation — NO-GO on data
   scale (only 3 labeled frames); the published route (Jensen 2024) is external
   Python/scikit-learn post-processing (dyad generation + SVM-RBF, 94% F1).
   The cheap transfer is the dyad psi/continuity MEASUREMENT, not retraining in C++.
3. "Add a SymTrap seam" — already exists (Directive::SymTrap → Sym_Trap leaf-only
   script → CalculateSymTrap sweep; pins landed: relay=61, tibia costCalls=0).
4. SAME_Z / pole priors at weight 1 — inert (~0.01-0.3% of base cost); sym_trap's
   75/500 weights are the only calibrated priors.
5. Treating monoplane z-weakness as a new-algorithm problem — the z axis is
   structurally weak (Yamazaki 2004; measured 6.31 mm gap; jtml.z_profile
   instrument exists: 31-render Delta-z sweep, valley_depth/argmin_offset/
   plateau_halfwidth/noise_floor). Biplane (Subject0) is the documented z ceiling.
6. Curvature de-scope completion is PENDING (remove AllocateCurvatureHausdorfScore
   at DIRECT_DILATION.cpp:42-43 + add de-scope banner) — a live hygiene item.

* Integration seams for a new approach
- Optimizer: DirectOptimizer::Options (direct_optimizer.h:47-72) — defaults
  bit-identical; non-default fields are fail-fast stubs awaiting plan 010
  (DIRECT 1-DTC-GL-gb variant engine, active, unimplemented).
- Stage graph: StageScript/StageGraph registry (optimizer_stage_script.cpp) —
  only jtml-production registered; StageGraphByName consumption awaits plan 009
  (stage-graph selection, active, unimplemented).
- Cost variant: CostFunctionManager registry (7 variants, register-by-interface
  pattern, "DO NOT EDIT" banners with documented exceptions) + per-variant .cpp
  in src/compute + explicit CMakeLists entry (GLOB trap).
- Verification: two-tier oracle — Tier-1 analytic (CI, quadratic), Tier-2
  appearance (IoU > 0.85 gate, measured 0.9936; pose GT is self-referential —
  labels generated from the same STL at the fitted poses, so silhouette IoU is
  the trustworthy gate, not absolute pose). jtml.oracle_multistage (production
  shape, caps 20k/25k/30k/35k), jtml.z_profile (weak-axis instrument).
- Measured: ~7,000 evals/s, ~15 s whole multistage run, ~143 us/eval (derived),
  RTX 3090 Ti, CUDA 12.4. Per-eval: ~15 kernels + 5 sync D2H copies — sync-latency
  bound, not kernel bound (prior architecture-grounding run, synthesis.org).
