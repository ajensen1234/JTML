#+TITLE: Front-End Architecture: QML vs QWidgets for JTML
#+DATE: 2026-08-11
#+PANOPTES_ANGLE: qml-vs-widgets
#+PANOPTES_RUN: please-look-through-all-the-plans-that-we-ve-done-and-the-co-msope0fc1x2q

* Summary

VTK 9.3's QML integration is real and the repo's own pinned VTK build already compiles and installs it (libvtkGUISupportQtQuick-9.3.so sits in _deps/vtk/install, unlinked by anything), but the honest verdict from a 10-year Qt/VTK architect's seat is: a full QML front-end for JTML is a plan-005-scale project that replaces ~1,600 lines of view content, re-plumbs every QItemSelectionModel call site, reworks the interactor.h globals around QQuickVTKItem's render-thread ownership model, and rides the bug tail of a young integration — all to buy styling/declarative-layout benefits nothing in the current roadmap needs. The ecosystem evidence is unambiguous: the two flagship VTK apps (ParaView, 3D Slicer) and the medical-imaging stack (MITK, ImFusion's QtDisplayWidget) are QWidgets-first, and Slicer's maintainer explicitly warns that QML+VTK "you may need to invest time... and plan extra time for testing and development at each Qt or VTK release." Recommendation: NO-GO on a full QML front-end now; keep the seams QML-ready (they already are), sharpen the "QML-swappable later" comment into an explicit "not now" decision, and if QML is ever pursued, gate it behind an xcb QQuickVTKItem spike and start with QQuickWidget islands, not a rewrite.

* Key Findings

** The repo's pinned VTK 9.3.0 has the new QML API (QQuickVTKItem) and it is already compiled in this repo's build — nothing links it
- VTK 9.3.0 release notes, Qt section: "QML integration support has been upgraded to allow a vtkRenderWindow per QQuick item." [Source: https://docs.vtk.org/en/v9.4.1/release_details/9.3.html]
- Confidence: high
- Relevance: this is exactly the "vtkRenderWindow per QQuick item" premise; it is not marketing — the class exists in the pinned source tree.
- The pinned source _deps/vtk/source/GUISupport/QtQuick/ contains QQuickVTKItem alongside the OLD stack, and the old stack (QQmlVTKPlugin, QQuickVTKRenderWindow, QQuickVTKRenderItem, QQuickVTKInteractorAdapter, QQuickVTKInteractiveWidget) is wholesale marked VTK_DEPRECATED_IN_9_3_0("Use QQuickVTKItem instead"). VTK 9.3's own QML examples (Examples/GUI/QML/QtQuickBoxWidget, QtQuickCone, QtQuickChartsOn3DScene, QtQuickProperty) all use the new API: subclass QQuickVTKItem, override initializeVTK(vtkRenderWindow*), call QQuickVTKItem::setGraphicsApi() before QGuiApplication, qmlRegisterType into a QML module. [Source: repo — _deps/vtk/source/GUISupport/QtQuick/CMakeLists.txt; _deps/vtk/source/GUISupport/QtQuick/QQuickVTKItem.h; _deps/vtk/source/Examples/GUI/QML/QtQuickBoxWidget/main.cpp]
- Confidence: high (repo-local, read directly)
- Relevance: a QML front-end would NOT be built on a dead/deprecated API; it would use the API VTK itself recommends. But the deprecation churn itself (whole old QML stack deprecated in 9.3.0) is a signal of how fast this surface moves.
- The repo's VTK install contains lib64/libvtkGUISupportQtQuick-9.3.so.9.3 and include/vtk-9.3/vtkGUISupportQtQuickModule.h (built via VTK_GROUP_ENABLE_Qt=YES in vtk_installer.sh). src/view/CMakeLists.txt links jtml_view against VTK_LIBRARIES but nothing references GUISupportQtQuick or Qt6::Quick/Qml. [Source: repo — _deps/vtk/install/lib64/, vtk_installer.sh, src/view/CMakeLists.txt]
- Confidence: high (repo-local)
- Relevance: a QML spike costs zero VTK rebuild; it only needs CMake link additions (VTK::GUISupportQtQuick + Qt6::Quick + Qt6::Qml + vtk_module_autoinit) and the pixi env already ships the full QtQuick/QtQuickControls2/QtQml headers (include/qt6/QtQuick*, QtQuickControls2* present under .pixi/envs/default; pixi.lock pins qt6-main 6.7.2 + qt6-wayland).
- QQuickVTKItem's contract is the architectural crux: "All VTK objects are owned by and run on the QML render thread!! This means you CAN NOT touch any VTK state from any place other than in this method, in destroyingVTK or in your dispatch_async() functions!!"; "At the time of this method execution, the GUI thread is blocked"; and "At any moment the QML SceneGraph can decide to delete the underlying QSGNode... you must be prepared to reset all the VTK state associated with any QML property you have attached to this node." [Source: repo — _deps/vtk/source/GUISupport/QtQuick/QQuickVTKItem.h (VTK 9.3.0 tag, verbatim doc comments); mirrored at https://vtk.org/doc/nightly/html/classQQuickVTKItem.html]
- Confidence: high (primary source, both local and upstream)
- Relevance: this is a different threading/lifetime model than QVTKOpenGLNativeWidget. Every VTK actor/renderer/mapper JTML touches from C++ (Viewer, MainScreen slots, interactor.h styles) must be reachable only through initializeVTK/destroyingVTK/dispatch_async — a structural constraint on the whole view layer, not a swap of one widget.

** The QML integration is young, with a documented bug tail — including bugs in exactly the areas JTML cares about (mouse picking, interactor styles, image rendering)
- Kitware (Mathieu Westphal), Feb 2022 on the VTK discourse: "Your analysis is correct, QtQuick support is very new and will be improved over time." [Source: https://discourse.vtk.org/t/qml-rendering-problem/7820]
- Confidence: high (direct quote, VTK maintainer)
- Relevance: temper any expectation that the QML path is as hardened as the QVTKOpenGLNativeWidget path that JTML's render smoke test already depends on.
- Practitioner experience in the same thread (Michael Jackson, building a VTK+QML desktop app): "There will also be conflicts between the Vtk render thread, the gui Main thread and the QML rendering thread which need to be managed by you, the developer. One must be extremely careful about managing these threads or you will be artifacts and crashes in your application." And: "If I had to do things over I never would have selected QML. I would absolutely [have] stuck with QWidgets for a desktop application." [Source: https://discourse.vtk.org/t/qml-rendering-problem/7820]
- Confidence: high (direct quotes, multiple posts)
- Relevance: the three-thread problem (VTK render thread, GUI thread, QML render thread) is precisely the interaction surface JTML lives on (progress/render interleave during segmentation, interactor.h mouse-state globals, processEvents loops).
- Reported bugs against the 9.3-era QQuickVTKItem path: (1) mouse positions mis-translated due to devicePixelRatio not set on QVTKInteractorAdapter inside QQuickVTKItem — reproduced with VTK 9.3 + Qt 6.5.3 using the official QtQuickBoxWidget example (user shipped a patch; upstream fix release not confirmed); (2) vtkInteractorStyleRubberBandPick and any style that draws a selected area (e.g., vtkInteractorStyleDrawPolygon) fail with QQuickVTKItem — exactly the draw-pick family JTML's DRR tool / pickers touch; (3) scatter-plot markers do not render; (4) vtkResliceImageViewer (2D DICOM slice viewer) does not work with QQuickVTKItem; (5) "Cannot assign object to list property data" when instantiating QQuickVTKItem on Windows; (6) older QQuickVTKRenderWindow-era limitations (VTK renders below all QtQuick elements; background-color control broken; item-in-Rectangle and visible-toggle bugs). [Sources: https://discourse.vtk.org/t/mouse-position-qt-vtk-9-3/13260 ; https://discourse.vtk.org/t/vtkinteractorstyles-that-draw-selected-area-fail-with-qquickvtkitem/15798 ; https://discourse.vtk.org/t/scatter-plot-markers-not-rending-in-qquickvtkitem-in-qt-qml-application/16018 ; https://discourse.vtk.org/t/vtkresliceimageviewer-doesnt-work-with-qquickvtkitem/10739 ; https://discourse.vtk.org/t/qml-integration-issue-cannot-assign-object-to-list-property-data/14634 ; https://discourse.vtk.org/t/qml-rendering-problem/7820 ; https://discourse.vtk.org/t/some-bugs-when-use-vtk-in-qml-use-the-official-way/9650 ; https://discourse.vtk.org/t/background-color-always-black/7516]
- Confidence: medium (community reports, unpatched status per-thread; dates 2022–2024)
- Relevance: JTML's interaction surface (picking, drag modes, viewport text, coronal plane) overlaps several of these bug reports. A spike must specifically test mouse picking at DPR=1 and the custom interactor styles before any commitment.
- The QtVtk community project (Qt Quick Controls 2 + VTK) works with VTK 8.2/Qt 5.15 but "works fine with vtk8 in rendering" and broke on vtk9 — the community had to rewrite the integration (john-stone-ics/QuickVtk and QML-VTK-Examples forks exist precisely for this). [Source: https://discourse.vtk.org/t/qml-rendering-problem/7820 ; https://github.com/nicanor-romero/QtVtk ; https://github.com/john-stone-ics/QML-VTK-Examples]
- Confidence: medium
- Relevance: "it exists in the tree" ≠ "it works out of the box for our feature set"; the community has needed bespoke rewrites at each VTK major.

** On the xcb-only render environment: QML does not fix it, it inherits it — and the DPI bug is platform-relevant
- The app and its render smoke both force QT_QPA_PLATFORM=xcb because "the Wayland/EGL stack on this box cannot give QVTKOpenGLNativeWidget a GL context (blank render) - the app's historical working platform is xcb" (test/CMakeLists.txt sets ENVIRONMENT QT_QPA_PLATFORM=xcb on jtml.render_smoke and jtml.probe_vtk; render_smoke.cpp mirrors the app mechanism QVTKOpenGLNativeWidget + vtkGenericOpenGLRenderWindow). [Source: repo — test/CMakeLists.txt, test/oracle/render_smoke.cpp]
- Confidence: high (repo-local)
- Relevance: a QML front-end runs on the same Qt platform plugin (xcb); the Wayland blank-render risk is orthogonal and inherited, not removed. QT_QPA_PLATFORM=xcb will still be the only working platform.
- QQuickVTKItem::setGraphicsApi() "sets the graphics API to OpenGLRhi and sets up the surface format for intermixed VTK and QtQuick rendering" — i.e., the Qt Quick scenegraph renders via the same OpenGL stack the app already uses under xcb; no separate window needed (unlike the deprecated QQuickVTKRenderWindow plugin). No xcb-specific QQuickVTKItem failure was found in the discourse/GitHub trail; the relevant platform-sensitive bug is the devicePixelRatio/mouse-position one above (DPR matters most in mixed-DPI X11 setups). [Source: repo — _deps/vtk/source/GUISupport/QtQuick/QQuickVTKItem.h; https://discourse.vtk.org/t/mouse-position-qt-vtk-9-3/13260]
- Confidence: medium (no direct xcb+QQuickVTKItem confirmation found; "should work under xcb" is an inference from the shared GL stack, to be proven by spike)
- Relevance: the xcb-only constraint is not a QML blocker, but it also means QML cannot be sold as "fixes our render environment."

** The ecosystem speaks with one voice: medical-imaging/VTK desktop apps are QWidgets-first; QML+VTK production cases are rare and the flagship maintainers say so
- Andras Lasso (3D Slicer core developer), Jan 2021: "Classic widgets are guaranteed to work, because both major projects that use VTK with Qt (Paraview and 3D Slicer) use those. However, Qt essentially stopped development of classic widgets years ago and they just do minimal bugfixes, if even that. You can customize classic widgets with stylesheets to get modern look and feel, but it is easier to create custom GUIs (that does not resemble native controls) using QML. However, I'm not sure how many projects use VTK with Qt QML - you may need to invest time into making the VTK renderer work in QML and plan extra time for testing and development at each Qt or VTK release." [Source: https://discourse.vtk.org/t/vtk-9-pyqt-application/5079]
- Confidence: high (verbatim quote from the Slicer maintainer)
- Relevance: the two anchors of this app's own stack (VTK + Qt for 2D-3D registration) are maintained in widgets; the "extra testing at each Qt or VTK release" cost is precisely what a small lab/research repo cannot absorb quietly.
- 3D Slicer community thread on a custom-app QML redesign: "Based on our prior experience, if the whole application is written in QML, the challenge was the integration with VTK viewers (it is related to sharing of OpenGL context)." [Source: https://discourse.slicer.org/t/using-external-qml-for-slicer-custom-application/5325]
- Confidence: high (Slicer community, quoted)
- Relevance: OpenGL context sharing between the VTK viewport and a QML scene is the known hard seam; JTML's whole UI is built around two VTK viewports.
- MITK (the other major medical-imaging toolkit) ships its rendering UI as Qt widgets: QmitkRenderWindow and friends (group QmitkModule "Basic Qt widgets and classes for MITK"); its rendering concept is VTK-derived via a vtkMitkRenderProp. [Source: https://docs.mitk.org/latest/group__QmitkModule.html ; https://docs.mitk.org/latest/QVTKRendering.html]
- Confidence: high
- Relevance: two independent medical-imaging toolkits chose widgets for VTK viewport hosting.
- ImFusion (commercial medical imaging SDK, Munich): the primary Qt embed point is ImFusion::GUI::QtDisplayWidget, a "Specialization of a QOpenGLWidget" (i.e., widgets), with the whole ImFusionGUI layer being a platform-agnostic abstraction "previously, our visualization stack relied on Qt for input event handling and embedding into a OpenGL-enabled display surface"; separately they ship a QMLRendererDemo "to natively integrate the ImFusionLib rendering stack into a QML application." [Sources: https://docs.imfusion.com/cppsdk/group___im_fusion_g_u_i_qt.html ; https://docs.imfusion.com/cppsdk/_im_fusion_g_u_i_migration.html ; https://github.com/ImFusionGmbH/public-demos]
- Confidence: high
- Relevance: the commercial-medical pattern is widgets-first core with optional QML *surfaces* — not a wholesale QML rewrite — which is exactly the hybrid option below.
- Qt's own product positioning: "Qt Quick is for creating dynamic and fluid user interfaces. ... Qt Widgets are for creating complex desktop applications." Community thumb-rule repeated across forums for scientific desktop apps: widgets; QML when targeting touch/mobile or designer-heavy custom UIs. [Sources: https://doc.qt.io/QT-6/topics-ui.html ; https://forum.qt.io/topic/34048/scientific-application-with-qt ; https://forum.qt.io/topic/86914/qml-or-widgets]
- Confidence: high (vendor docs + forum consensus)
- Relevance: nothing about JTML (two VTK viewports, lists, dialogs, progress) is touch-first, animation-heavy, or design-reskin-driven; it is the canonical "complex desktop application" Qt positions for widgets. Counter-consideration: Lasso's point that Qt Company invests in Qt Quick, not widgets, is the one structural argument for QML — but it argues for QML readiness, not an immediate migration (see Recommendations).

** For THIS app, a QML front-end reuses the seams and replaces the view content — the reuse matrix is concrete
- Reused as-is (zero change): FrameListModel / ModelListModel (both QAbstractListModel — the QML-native model interface; ListView renders QAbstractListModel directly), SessionState, SessionController, SettingsService, SegmentationController, EdgeProcessor, coordinator (OptimizeCoordinator), domain + compute layers — all widget-free by design (plan 004). [Source: repo — include/view/frame_list_model.h, include/view/model_list_model.h, include/view/mainscreen.h role comment]
- Confidence: high (repo-local)
- Relevance: the "seams are ready" claim in the project's prior answer is structurally true — the model and service layers would survive a QML front-end untouched.
- Reused with significant rework: Viewer. It owns renderer/actor/mapper management (load_3d_models_into_actor_and_mapper_list, change_model_opacity_to_*, set_model_position_at_index, background switches) that maps naturally onto initializeVTK's "create pipeline and attach to the window" — but its render-window attachment is QVTKOpenGLNativeWidget-specific (load_render_window(ui.qvtk_widget->renderWindow()), get_interactor(), set_render_window_and_display) and all VTK state would have to live inside a vtkUserData object owned by the QML render thread. Under QQuickVTKItem the render window is created by the QML item, not by the app. [Source: repo — include/view/viewer.h, src/view/mainscreen.cpp:341-344]
- Confidence: high (repo-local)
- Relevance: Viewer is the single biggest "reuse with rework" item; its ~60-method surface mostly survives, but its window/interactor plumbing does not.
- Replaced, not reused (~1,600 lines of view-only content per project recon; independently confirmed blocks): ArrangeMainScreenLayout (mainscreen.cpp:375–~1050, ~675 lines of code-driven layout/geometry that QML anchors/layouts would replace entirely); display-mode radios (original/inverted/edges/dilation), model radios (original/solid/transparent/wireframe), edge controls (aperture spin, thresholds, apply/reset), menu bar + all action slots, key handling (QKeyEvent → QML Keys/Shortcut), and the four dialogs (SettingsControl, DRRTool, Controls, About). [Source: repo — include/view/mainscreen.h slot list; src/view/mainscreen.cpp]
- Confidence: medium (line-count proportions from recon + spot verification of the layout block; exact replacement-line total not re-derived)
- Relevance: this is the honest cost anchor: the QML work is a UI rewrite of the biggest TU in the repo, not a re-skin.
- The progress/render interleave (segmentation loops calling processEvents + render per frame; mainscreen.cpp segmentation slots) stays C++ and stays in the view — in QML it becomes the same C++ loops emitting progress signals into QML bindings. Neither framework removes the processEvents hazard; the interleave is orthogonal to widgets vs QML. [Source: repo — include/view/mainscreen.h SegmentationController comment]
- Confidence: high (repo-local)
- Relevance: don't expect QML to fix the UI-hang/repaint behavior during long segmentation runs; that risk is unchanged.

** The QItemSelectionModel wiring does NOT map to QML ListView — the models survive, the selection machinery does not
- Qt ships an ItemSelectionModel QML type ("Instantiates a QItemSelectionModel to be used in conjunction with a QAbstractItemModel and any view supporting it") — but the only Qt Quick view that supports it is TableView, which gained cell selection in Qt 6.3 (selectionBehavior in 6.4). QML ListView has no selectionModel property at all; its selection idiom is delegate-based (ListView.isCurrentItem / currentIndex) or manually tracked model state. [Sources: https://doc.qt.io/QT-6/qml-qtqml-models-itemselectionmodel.html ; https://www.qt.io/blog/item-views-in-qt-quick ; https://forum.qt.io/topic/98184/listview-qml-and-qitemselectionmodel-c]
- Confidence: high (Qt 6.11 docs + Qt blog + forum)
- Relevance: the repo's U2 selection semantics are QWidgets-specific by construction: 30+ call sites of ui.model_list_widget->selectionModel()->selectedRows() and ui.image_list_widget->currentIndex().row(); setCurrentIndex(idx, SelectCurrent|Rows) for default-select-first; select(idx, Select|Rows) / Deselect|Rows / ClearAndSelect|Rows for swap-principal and empty-selection fallback; selectionChanged connections into the two list slots; SyncSessionState() pulling widget selection into SessionState (mainscreen.cpp:96-168, 2422-2425, 2571-2575, 3199-3202, 3358-3368, 3481-3484, 3169-3171). [Source: repo — src/view/mainscreen.cpp]
- Confidence: high (repo-local, grepped)
- Relevance: every one of those call sites re-plumbs in a ListView world. The models are reused, but the selection state moves into either (a) model-level roles (add a selected/current flag to FrameListModel/ModelListModel and re-emit dataChanged), or (b) a C++-owned QItemSelectionModel kept in sync with delegate clicks. Both are rewrites of behavior the oracle/headless tests currently pin via "model + selectionModel together are the headless-testable unit."
- Pitfalls in the mapping: QItemSelectionModel::SelectionFlags batching (SelectCurrent/ClearAndSelect semantics, per-item unbatched Deselect/Select with R13-visible intermediate states) has no QML equivalent — delegate-based selection cannot reproduce intermediate selectionChanged emissions without manual state management; selectedRows() returns rows in row order while QML currentIndex + delegate clicks give press-order; ListView delegate recycling means selection visuals must live in the model, not the delegate; and the multi-selection model-list (SelectCurrent with arrow keys deliberately NOT connected — currentChanged disconnected) is bespoke and must be re-specified in QML terms. [Sources: repo — src/view/mainscreen.cpp:157-168, 3344-3368 ; https://doc.qt.io/QT-6/qml-qtqml-models-itemselectionmodel.html]
- Confidence: high
- Relevance: this is the "selection wiring is QWidgets-specific" cost made concrete and quantified; it is mechanical but touches the most behavior-pinned code in the view layer.

** Honest migration shape: three viable paths, one cheap hedge, and the conditions under which QML is worth it
- Path A — full QML front-end (plan-005-scale): (1) spike gate — minimal QML window hosting two QQuickVTKItems rendering the main + coronal viewports under QT_QPA_PLATFORM=xcb with this repo's VTK build; verify blank-render-free output, mouse pick at DPR=1, custom interactor styles, one segmentation progress pass; (2) composition-root swap (src/app/main.cpp QApplication → QGuiApplication + QQmlApplicationEngine + qmlRegisterType for the VTK item); (3) list surfaces via existing models + re-plumbed selection; (4) dialogs + menus in QML; (5) interactor.h rework into initializeVTK/dispatch_async discipline (highest-risk step — the file-scope globals interactor_calibration/speed/mouse state and the one-TU constraint were designed for widgets); (6) render regression parity (QQuickVTKItem has no widget->grab(); capture via vtkWindowToImageFilter or QQuickWindow::grabWindow, and offscreen/headless testing moves to QQuickRenderControl — the ctest -L render contract changes). [Sources: repo — src/app/main.cpp, include/view/interactor.h, test/oracle/render_smoke.cpp, test/CMakeLists.txt ; https://doc.qt.io/qt-6/qquickrendercontrol.html ; https://doc.qt.io/QT-6/qml-qtqml-models-itemselectionmodel.html]
- Confidence: high (shape grounded in repo files)
- Relevance: every phase above is checkable and independently shippable, which is exactly why the spike gate should be phase 1 and the decision point should be after it.
- Path B — hybrid QQuickWidget islands: embed QML surfaces (the two study lists, dialogs) inside the existing QMainWindow via QQuickWidget, keep QVTKOpenGLNativeWidget for the viewports. QQuickWidget "acts as a true QWidget and supports, among others, better clipping and stacking, as expected from a true QWidget." Caveats: "One top-level window can only use one single graphics API for rendering" (both paths would be OpenGL here, so OK), and QQuickWidget renders into FBOs with a "minor performance hit" and "disables the threaded render loop on all platforms." [Sources: https://doc.qt.io/qt-6/qquickwidget.html ; https://doc.qt.io/qt-6.8/qtquick-quickwidgets-qquickwidgetversuswindow-opengl-example.html ; https://forum.qt.io/topic/58716/qquickwidget-vs-qquickview ; https://www.qt.io/blog/qt-quick-and-widgets-qt-6.4-edition]
- Confidence: high (official docs)
- Relevance: Path B captures the two genuinely attractive QML properties for JTML (declarative list delegates, easier custom dialogs) with zero VTK-in-QML risk and no selection-machinery rewrite — the lists keep QListView+QItemSelectionModel or expose models to QML delegates via QQuickWidget as a bounded experiment.
- Path C — stay QWidgets, harvest the migration literature's lesson that the hard 80% is already done: the canonical widgets→QML migration playbook (Qt blog "An Application Journey"; KDAB MuseScore) is (1) pin behavior with introspection-based tests, (2) refactor "MVC with a twist" to MVP by freeing logic from controllers, (3) replace the view per surface. JTML's plan 004 already executed steps 1–2 (headless-testable models+services, SessionState as single source of truth); step 3 is the only remaining cost, and it is not on the roadmap. [Sources: https://www.qt.io/blog/qtwidgets-to-qtquick-application-journey-part2 ; https://www.kdab.com/breathe-new-qml-life-into-a-qwidget-based-app-from-the-2000s-video/]
- Confidence: high
- Relevance: the repo is in the rare position of being migration-ready with zero migration pressure; that is an option, not an obligation.
- Conditions under which QML becomes worth it for JTML (all are currently absent): (1) a concrete UI need QWidgets cannot deliver cheaply (custom-drawn overlays on the VTK viewport, animated workflow UI, tablet/touch OR surfaces); (2) the QML integration matures — QQuickVTKItem's bug reports (DPI, draw-pick styles, markers) thin out across Qt 6.8+/VTK 9.4+; (3) a designer-driven reskin becomes a product requirement (single-sourcing the look). None of these are on the current research-tool roadmap; the honest prior answer ("seams ready, ~1,600 lines replaced, selection wiring QWidgets-specific, xcb risk") survives this research with the added evidence that the module is already built and the ecosystem is widgets-first.
- Confidence: high
- Relevance: this is the go/no-go basis below.

Only a spike (phase 1 of Path A) can verify — including the DPR bug's status at Qt 6.7.2 (the report was Qt 6.5.3, with a user-supplied patch).
- Whether the devicePixelRatio/mouse-position fix landed in a VTK 9.3.x point release: the discourse thread's patch was user-authored; upstream merge/release could not be confirmed from available sources.
- The exact total of "view-only content replaced" (~1,600 lines): layout block (~675 lines) and selection call sites (30+) verified directly; the total figure comes from project reconnaissance and was not fully re-derived.
- Whether Qt's "widgets are in maintenance mode" claim (Lasso, 2021) still holds for Qt 6.8+: Qt 6 does continue shipping and fixing QWidgets, but no authoritative statement on relative investment was found; treated as a directional concern, not a fact.
- Whether any major production medical-imaging product runs a full QML UI with VTK viewports: none found; Luma Vision/Globus/Augmedics Qt case studies confirm Qt in medical imaging but do not disclose framework split; ImFusion's QML demo is an SDK demo, not its flagship app.

* Recommendations for JTML

1. GO/NO-GO: NO-GO on a full QML front-end for now. It is a plan-005-scale rewrite (Path A) whose only confirmed payoff is styling/declarative layout — none of the current problems (VTK binding fragility, interactor.h globals, xcb-only rendering, progress interleave) are QML problems, and the ecosystem + VTK maintainers put the QML+VTK burden on the adopter ("plan extra time for testing and development at each Qt or VTK release"). The decision is not permanent: it is "not now, with a cheap option preserved."
2. Sharpen the "QML-swappable later" comment (src/view/CMakeLists.txt:6): replace it with an explicit, dated decision record — "QML-ready seams (models/services/domain are widget-free; VTK 9.3 GUISupportQtQuick is already built in-tree); QML front-end deferred (angle 04, 2026-08-11); revisit on a concrete UI need or Qt 6.8+/VTK 9.4+ maturity." This turns an aspirational comment into a tracked decision and prevents a future contributor from reading it as a promise.
3. If QML is ever pursued, spend the first increment on the spike gate only (Path A phase 1): one QML window, two QQuickVTKItems (main + coronal viewports), QT_QPA_PLATFORM=xcb, this repo's VTK build (libvtkGUISupportQtQuick is already installed — no VTK rebuild), exercising mouse pick at DPR=1 and the custom interactor styles. Go/no-go restarts on the spike result. Add Qt6::Quick/Qt6::Qml + VTK::GUISupportQtQuick to a scratch target with vtk_module_autoinit; do not touch jtml_view yet.
4. If a QML showcase is needed sooner (designer demos, grant visuals), use Path B — QQuickWidget islands for the two study lists and a dialog or two, keeping QVTKOpenGLNativeWidget viewports. This is the commercial-medical pattern (ImFusion ships widgets-first + a QML demo) and it exercises the seams without the VTK-in-QML risk, selection rewrite, or interactor rework.
5. Do NOT speculatively rework interactor.h (file-scope globals, one-TU constraint) into QQuickVTKItem's render-thread discipline: it is the highest-risk, zero-current-payoff item, and the known draw-pick-style failures under QQuickVTKItem suggest the port may require behavior changes, not just relocation.
6. Treat the render regression contract (ctest -L render, widget->grab() PNGs under forced xcb) as a QML front-end's most expensive hidden cost: QQuickVTKItem has no grab() equivalent, and headless/oracle testing would move to QQuickRenderControl/vtkWindowToImageFilter — any QML plan must budget for a new golden-image pipeline, not reuse the existing one.
