#+TITLE: Compute Architecture & Performance Profiling — Implementation-Level Findings (jtml_compute)
#+DATE: 2026-08-11
#+PANOPTES_RUN: jtml-research-horizons
#+PANOPTES_ANGLE: 05-compute-architecture

* Summary

The merged jtml_compute SHARED lib is a single-stream, default-context CUDA pipeline: one silhouette/DRR render (8 kernels) plus 2-3 metric kernels per cost evaluation, all serialized by 2-5 synchronous D2H cudaMemcpy's *per evaluation*. Per-frame cost budgets of 20k→35k evaluations therefore imply ~500k kernel launches and ~150-175k pipeline drains per frame — the pipeline is sync-bound, not kernel-bound. The silhouette+DIRECT_DILATION path is value-deterministic on a given machine (all its reductions are int atomics, which are order-independent); the only genuinely order-nondeterministic production reduction is the float atomicAdd in the DRR line-integral fill (render_drr_engine.cu), which the DIRECT cost path never calls. The doc claim "CUDA reductions/atomics are not bit-reproducible" (jtml-testability-and-cmake-conventions §6) is therefore imprecise for the DIRECT_DILATION oracle path: the observed 6.31 mm z_trans gap (test/golden/baseline.json) is better explained by cross-hardware float divergence (FMA contraction, arch differences) amplified by DIRECT's discrete trisect decisions, plus a production-vs-oracle backface-culling config difference (ON in OptimizerManager, OFF in oracle_test). Several real defects lurk in the live cost path: a broken pixel-index formula in DistanceMapMetric_Kernel, a pointer-vs-value check in ImplantMahfouzMetric, a curvature metric that returns 0 without launching its kernel, and an in-place metric that mutates the render output.

* Key Findings

** Per-evaluation data flow: 15 launches + 5 synchronous D2H copies for one DIRECT_DILATION eval
- Monoplane DIRECT_DILATION cost (src/compute/DIRECT_DILATION.cpp:63-105) = RenderPrimaryCamera → FastImplantDilationMetric → DistanceMapMetric. Each eval runs:
  - Render() (src/compute/render_engine.cu:701-860): cudaMemset of the full w×h image (line ~723), ResetKernel<<<1,1>>>, WorldToPixelKernel (3×triangles), BoundingBoxForTrianglesKernel (4×triangles), BoundingBoxSizesKernel (triangles), CUB DeviceScan::ExclusiveSum, PrepareLaunchPacketKernel<<<1,1>>>, StridePrefixKernel, FillTriangleKernel — then **two synchronous D2H cudaMemcpy's** (bounding box 4 ints + fragment_fill 1 int, lines ~815-821) because the host must decide the fill launch size and check overflow.
  - FastImplantDilationMetric (src/compute/fast_implant_dilation_metric.cu:157-290): 4 launches (reset, edge, dilate, difference) + 1 D2H sync (line ~285).
  - DistanceMapMetric (src/compute/distance_map_metric.cu:58-111): 3 launches (2 resets + main) + **2 D2H syncs** (lines ~102-107).
  - Total per monoplane eval: ~15 kernel launches, ~5 blocking D2H copies, 2 cudaMemset's. Biplane (DIRECT_DILATION.cpp:88-100) roughly doubles it (2 renders + 2 metrics). DIRECT_MAHFOUZ eval = render + ImplantMahfouzMetric = ~17 launches + 6 D2H syncs (implant_mahfouz_metric.cu does 4 syncs alone, lines ~326/347/444/465).
- Every D2H copy on the default stream is an implicit full pipeline drain. With 35,000 evals/frame (golden_oracle.org:79-81) that is ~175k host-GPU sync round-trips per frame; at ~10-20 µs each that is on the order of seconds of pure serialization per frame. This is the single most defensible "where does the time go" answer: the kernels are tiny image ops; the syncs dominate.
- Confidence: high. Source: repo paths above.
- Relevance: any compute-architecture change (kernel fusion, stream rework, async copy-back) that removes per-eval syncs attacks the measured bottleneck directly.

** All GPU allocations are hoisted out of the hot path; zero cudaMalloc churn per eval
- RenderEngine::InitializeCUDA (render_engine.cu:243-316) allocates all buffers once (triangles, normals, projected, snapped, bboxes, prefix, stride_prefixes = 10M ints ≈ 40 MB, z-line-values, CUB temp storage) and copies the mesh to the device once. CUB storage size is queried once via DeviceScan::ExclusiveSum(nullptr,...) (lines ~295-300).
- GPUMetrics ctor (gpu_metrics.cu:22-110) allocates the pinned score buffers once; AllocateCurvatureHausdorfScore does one cudaMalloc per stage init (called from initializeDIRECT_DILATION, DIRECT_DILATION.cpp:49).
- Per-eval memory traffic: 1 MB memset + ≤ bbox-area fills + cropped metric reads/writes + 5 ints D2H. All small.
- The churn lives per-FRAME, not per-eval: (a) GPUImage::UploadImageToGPU frees and re-allocates the device buffer and pinned bounding_box on every upload (gpu_image.cu:106-193); (b) torch segment path does a torch::zeros placeholder allocation per call and — explicitly — c10::cuda::CUDACachingAllocator::emptyCache() after every frame (services/segmentation_controller.cpp:25-27), which defeats the caching allocator so the next frame's tensors re-cudaMalloc from the driver.
- Confidence: high. Source: repo paths above.
- Relevance: "cudaMalloc churn in the hot path" is NOT present per eval — the allocator churn is per frame (segmentation). The per-eval cost is launch overhead + sync latency + memory bandwidth of re-zeroing the full image each eval.

** Determinism audit: the DIRECT_DILATION path is value-deterministic; only the DRR fill is order-nondeterministic
- Every reduction in the cost path uses int atomics: WhitePixelSum atomicAdd (gpu_metrics.cu:125-127), FastImplantDilationMetric_DifferenceKernel atomicAdd/Sub (fast_implant_dilation_metric.cu:137-145), DistanceMapMetric_Kernel atomicAdd (distance_map_metric.cu:36-40), IOUKernel atomicAdd (iou.cu:47-54), L1,1 difference kernel (l_1_1_matrix_diff_norm.cu:34-41), Mahfouz kernels (implant_mahfouz_metric.cu:95-116, 145-180). Integer addition is commutative and exact, so atomic ORDER does not change the VALUE: these reductions are bit-reproducible across runs on the same GPU.
- The one float reduction — DRR_FillTriangleKernel's `atomicAdd(&dev_z_line_values[pixel], (tvz1*tvz2*tvz3*denominator)/(...))` with the sign flipped for backface triangles (render_drr_engine.cu:328-352) — is order-nondeterministic: the per-pixel accumulation of float line-integrals varies run to run in the last ULPs. This is the only production reduction matching the docs' "not bit-reproducible" claim. The DRR path is used only by view/drr_tool.cpp (interactive tool), never by the DIRECT cost functions.
- The silhouette render itself is deterministic per thread: WorldToPixelKernel and the barycentric fill test are pure float math on fixed inputs (render_engine.cu:397-482, 616-700). The bbox atomicMin/atomicMax are int → order-independent.
- The ~6.3 mm z_trans gap (test/golden/baseline.json "observed_max_gap_vs_golden") is therefore NOT explained by atomic ordering in the DIRECT_DILATION path. Plausible sources, in order: (1) float FMA-contraction / arch divergence in the render+fill math across machines and nvcc versions (direct evidence: CMAKE_CUDA_ARCHITECTURES=native, CMakeLists.txt:58-59, so binaries are arch-specific); (2) DIRECT's discrete ConvexHull/Trisect decisions amplifying 1-ULP cost differences into different trisect trajectories (src/domain/direct_optimizer.cpp:143-201); (3) a real config difference: production OptimizerManager constructs GPUModel with use_backface_culling=true (optimizer_manager.cpp:716-722), while the oracle runs with backface culling OFF "to match label generator Study2Grid" (oracle_test.cpp:190-197; baseline.json run_config) — the silhouette itself differs between production and oracle.
- Docs-vs-code contradiction, flagged: jtml-testability-and-cmake-conventions-2026-08-07.md:143 states "CUDA reductions/atomics are not bit-reproducible" as the reason the Tier-2 gate must be tolerance-based. The code shows the gate could be much tighter on a single machine (int reductions deterministic; silhouette deterministic), and that the true cross-machine noise is float ISA/FMA divergence plus DIRECT chaos, which tolerance-gating handles fine either way. The tolerance philosophy is correct; the stated mechanism is not.
- Confidence: high (mechanism), medium (attribution of the 6.31 mm gap — not measurable from source alone).
- Relevance: determinism work should target (a) DRR float atomics if DRR ever enters the cost path, (b) a pinned --fmad=false / fixed-arch build for reproducible traces, NOT a rewrite of the int reductions.

** Live bugs in the active cost path (not doc'd anywhere)
- DistanceMapMetric_Kernel index formula is wrong: `int i = (blockIdx.y + gridDim.x + blockIdx.x) * blockDim.x + threadIdx.x;` (distance_map_metric.cu:20) — should be `blockIdx.y * gridDim.x`. The + instead of * shifts every y-block's sampling window by one extra row of threads, leaving a 256-thread gap between y-blocks and reading pixels OUTSIDE the intended dilated crop (guarded only by `orig_loc < width*height`, so reads stay in-image but at the wrong offsets). DIRECT_DILATION calls this every eval (DIRECT_DILATION.cpp:80), so the trunk cost is subtly biased; the appearance gate tolerates it (measured IoU 0.9936) but the metric is not computing what the comment says.
- ImplantMahfouzMetric guards the divide with `if (pixel_score_ != 0)` — a pointer check, not a value check; the pointer is always non-null so a zero denominator divides by zero → ±inf score (implant_mahfouz_metric.cu:346, 464). Also `atomicAdd(&result[0], 2.55 * pixel)` passes a double into an int atomic — implicit truncation, non-obvious quantization (lines 96, 115).
- CurvatureHeatmapMetric is a stub: it launches only the reset kernel and returns 0.0 — the CurvatureHausdorfMetric_Kernel body is defined but never launched (curvature_hausdorf_metric.cu:41-76), and there is an off-by-one in its crop width (`right_x - left_x - 1`, line 63). Not called by any cost function today, so the breakage is latent.
- Backface triangles get bounding-box size forced to 1 ("In theory should be 0, but this leads to fragments so make 1", render_engine.cu:551-558) and are still run through the fill test at their bbox corner pixel; when that pixel center falls inside the backface triangle it writes a spurious 255 pixel. Masked in practice (same value as legit fills; silhouette is binary), but it means backface culling is not exact.
- DistanceMapMetric's return divides an int score by `edge_pixels_count_[0] + 0.1` (double) — fine numerically, but the +0.1 hack to avoid singularity silently distorts the metric at low edge counts (distance_map_metric.cu:110).
- Confidence: high (all directly from source).
- Relevance: these are "what the code does that docs don't mention" items for the R15 black-box trust; the first two affect the live trunk/leaf costs.

** Launch configs: hardcoded 256 threads, square grids, one dead config builder
- include/compute/cuda_launch_parameters.h: `threads_per_block = 256; maximum_stride_size = 10000000;` — globally hardcoded. Fragment cap = 10M × 255 ≈ 2.55B fragments (the "2.56B cap"); overflow prints to stderr and aborts the render with cudaErrorMemoryAllocation (render_engine.cu:826-836).
- Grids are 2D-square `ceil(sqrt(n/256))` shapes (constructor, render_engine.cu:186-210) — a 1D grid-stride would be simpler and avoids the sqrt rounding; for small n the square grid wastes blocks (e.g. n=1000 → 2×2=4 blocks for 3×1000 vertices → 6×256=1536 threads vs 1024 needed... actually ceil(sqrt(3000/256))=4 → 4×4×256=4096 threads for 3000 items; 24% waste).
- FillTriangleKernel uses a two-level binary search (StridePrefixKernel over every 256th fragment + per-block shared-memory prefix slice of 256 ints, render_engine.cu:568-613, 637-656) — a reasonable design for fragment→triangle lookup, but the per-fragment binary search on shared memory is ~8 iterations of divergent branching per fragment; a precomputed per-pixel triangle list (classic rasterizer "tile lists") would remove it entirely.
- include/compute/launch_config.cuh (LaunchConfigBuilder) is dead code — defined, never called; RenderEngine computes its own dims. Another unbuilt path alongside shape_sensitivity (src/CMakeLists.txt has add_subdirectory(shape_sensitivity) commented out; art.cu uses float atomicAdd for moments and ART features).
- Occupancy is never queried; the only shared memory in the hot path is the 256-int prefix slice (1 KB/block) and the 16×16 dynamic uchar tiles (256 B) in the two edge kernels (fast_implant_dilation_metric.cu:205-211, implant_mahfouz_metric.cu:397-403).
- Confidence: high.
- Relevance: kernel-level tuning (grid-stride loops, tile-based fill, occupancy) is all greenfield; nothing is tuned today.

** The metrics mutate the render output in place — the "render then score" contract is not read-only
- FastImplantDilationMetric runs EdgeKernel then DilateKernel on the SAME buffer as the rendered silhouette (fast_implant_dilation_metric.cu:218-273) — the render output is overwritten with EDGE_PIXEL/DILATED_PIXEL values. DistanceMapMetric then reads EDGE_PIXEL out of that same mutated buffer (distance_map_metric.cu:33-38) — i.e., the composition only works because of the mutation ordering. ImplantMahfouzMetric does the same (inverse-scale dilation writes gray ramp values, implant_mahfouz_metric.cu:264-340). Any code path that reuses a rendered image for two metrics (or for display) would see corrupted pixels; Render()'s leading cudaMemset is what hides this.
- Confidence: high.
- Relevance: kernel-fusion work and any "cache rendered frame" optimization must respect (or fix) this in-place contract; a copy-on-score or separate metric scratch buffer is the cheap fix.

** Torch inference: per-frame, allocator-hostile, and now inside jtml_services (004 U8)
- segment_image (src/compute/machine_learning_tools.cpp:7-72): square-pad + resize on host, then per call: torch::zeros placeholder (CUDACachingAllocator), raw cudaMemcpy into data_ptr, .to(kFloat) device copy, flip({2}) copy, jit forward, threshold, toByte, flip — then D2H. The raw cudaMemcpy on data_ptr bypasses torch's stream semantics (fine on the default stream, but it pins the tensor's lifetime assumptions).
- SegmentationController::SegmentFrame then calls c10::cuda::CUDACachingAllocator::emptyCache() after EVERY frame (services/segmentation_controller.cpp:25-27, deliberately, for RTX 4070 VRAM). Consequence: the next frame's tensor churn re-allocates from the driver instead of the cache — a documented, deliberate performance/allocator trade-off that is exactly the "CUDACachingAllocator calls" pitfall.
- ImplantEstimator::EstimateImplantPose (services/implant_estimator.cpp:27-150): per estimate — one torch forward (orientation), 2 GPU silhouette renders, 2 full-image synchronous D2H copies (w×h bytes each, lines 82-83, 113-114), and host-side OpenCV phaseCorrelate (a full FFT, line 132). The z estimate is area-ratio `z = -pd * sqrt(sum_proj/sum_seg)` with a clamp to principal distance.
- Layer character: src/services/CMakeLists.txt (004 U8 comment) — jtml_services now links ${TORCH_LIBRARIES} + ${JTA_LIBS}; jtml_compute itself PUBLIC-links torch (src/compute/CMakeLists.txt) — so torch is in the compute lib's ABI surface and every services TU that links jtml_compute pulls CUDA+torch. The app executable also links torch directly (src/app/CMakeLists.txt). This is the "services-layer GPU-link character change": the headless services layer is now GPU-dependent by link, even though headless tests compile layer .cpps directly and never link the lib (the CMake comment says this is why tests still pass).
- Confidence: high.
- Relevance: "moving torch out of services" = moving SegmentationController/ImplantEstimator call sites (currently view/mainscreen.cpp:1708-1737, 1914-1920) back into an app-layer seam, and dropping torch from jtml_compute's PUBLIC link (segment_image could move with it). The emptyCache-per-frame policy is the first cheap win (keep tensors pooled, clear only on OOM).

** Orchestration: single worker thread, cooperative stop, budgets cumulative — no GPU-side parallelization anywhere
- OptimizerManager::RunDirectStage (src/coordinator/optimizer_manager.cpp:1225-1293) binds DirectOptimizer (pure host loop, include/domain/direct_optimizer.h) to the GPU cost lambda; SetCallOffset(cost_function_calls_) implements cumulative budgets (trunk 20k → +branch 5k×2 → +leaf 5k = 35k, golden_oracle.org:78-81).
- The DIRECT loop is strictly sequential: each ConvexHull+Trisect iteration evaluates 2 new points per potentially-optimal box in a serial for-loop (src/domain/direct_optimizer.cpp:143-201). The evaluations within one iteration are independent — this is the natural (only) parallelism seam for multi-GPU/batched evaluation, but nothing exploits it; everything runs on the default stream with zero cudaStream usage anywhere in src (grep for cudaStreamCreate: none).
- Biplane passes the SAME cuda_device_id for both cameras (optimizer_manager.cpp:765-796), so GPUModel's two-RenderEngine multi-device plumbing is vestigial — multi-GPU is not exercised in production.
- The app's live "ms/call" display divides `clock() - start_clock_` by call count (optimizer_manager.cpp:1274-1281) — `clock()` is process CPU time, which excludes GPU kernel time and driver-wait wall time, so the meter structurally under-reports per-eval cost. It measures host overhead, not GPU time.
- Confidence: high.
- Relevance: multi-GPU today = batch the per-iteration DIRECT evaluations or split cameras; not a drop-in flag.

** Profiling readiness: Nsight-compatible env, nvtx dependency present but ZERO instrumentation in source
- pixi.toml declares nvtx and passes -DLIBNVTOOLSEXT to CMake (pixi.toml:75); grep for nvToolsExt/nvtx3/nvtxRange across src/: no hits. The scaffolding exists; no markers exist.
- CUDA 12.4 toolkit, CMAKE_CUDA_ARCHITECTURES=native (CMakeLists.txt:58-59) — binaries are machine-specific (perf and float behavior both arch-dependent).
- test/oracle/oracle_test.cpp already exercises the full GPU pipeline headlessly (BuildFramePipeline + DirectOptimizer + IoU gate) and prints cost-call counts — the natural harness for timing instrumentation (cudaEvent or std::chrono around callActiveCostFunction). Its oracle budget is a flat 3000 (few minutes), per oracle_test.cpp:236.
- Confidence: high.
- Relevance: methodology answer: Nsight Systems (trace of the default-stream sync pattern + torch) + Nsight Compute on FillTriangleKernel/DRR fill, wrapped by adding nvtx3 ranges around Render()/metrics/torch per eval — the deps are already installed.

** Dead, unbuilt, and app-only paths (the "black-box" is smaller than it looks)
- registration_metric.cu and metric_toolbox.cu: every kernel commented out (dead by construction).
- IOU and L1,1 metrics: not called by any production cost function — used by the oracle test only (oracle_test.cpp:247-249, 318-319).
- CurvatureHeatmapMetric: stub returning 0 (above). gpu_image_functions.cu (ConvolutionKernel etc.), EdgeDetectRenderedImplantModel, DilateEdgeDetectedImage: reachable only from the Study2Grid tool (app/Study2Grid/main.cpp:341-343).
- RenderDRR: only view/drr_tool.cpp (interactive DRR preview with UI bounds; downloads the full image per draw, drr_tool.cpp:128-146).
- shape_sensitivity (ART/IARTD): excluded from the build (src/CMakeLists.txt comment), float atomicAdd inside (art.cu:48-49, 77-92) — a second non-deterministic reduction if ever resurrected.
- Confidence: high.
- Relevance: the maintainable surface that matters for performance work is ~8 files: render_engine.cu, render_drr_engine.cu, the 6 metric TUs, gpu_metrics.cu, machine_learning_tools.cpp, and the DIRECT_* cost bodies.

* What Could Not Be Verified

- Actual kernel/launch/sync timing: no profiling data exists in-repo (no Nsight traces, no event timing); per-eval sync-cost estimates are derived from CUDA driver behavior and launch counts, not measurement. The "sync-bound" hypothesis needs a 30-minute Nsight Systems capture to confirm.
- The exact attribution of the 6.31 mm z_trans gap: source alone cannot prove whether it is FMA divergence, DIRECT chaos, or the backface-culling config difference (all three are consistent with the code; only an A/B experiment isolates them).
- Whether DRR float atomicAdd noise is visible in practice in the drr_tool (drr_tool renders single poses interactively; run-to-run ULP differences would be invisible at uchar quantization — untested).
- Whether the DistanceMapMetric index bug measurably biases the recovered pose vs the correct formula (would need a fixed-kernel A/B on the oracle).
- Torch jit forward latency and cuDNN/cuBLAS algorithm selection (nondeterministic-algorithm state is never queried/set in-repo — grep for at::globalContext/deterministic: none).
- GPUImage::GetDeviceImagePointer's error path frees device memory as a side effect (gpu_image.cu:155-161) — observed but never triggered in tests.

* Recommendations for JTML

1. Measure before restructuring (cheapest, highest value). Add nvtx3 ranges around the per-eval segments (Render / FastImplantDilationMetric / DistanceMapMetric / per-stage) and capture with Nsight Systems; also add cudaEvent timing around costFunctionDIRECT_DILATION in test/oracle/oracle_test.cpp. The nvtx dep and LIBNVTOOLSEXT are already wired (pixi.toml:75) — the instrumentation is the missing piece. Expect to confirm: ~5 syncs × 35k evals ≈ 175k pipeline drains per frame dominate.
2. Remove the per-eval syncs from Render(): replace the two D2H cudaMemcpy's (render_engine.cu:815-821) with a single cudaMemcpyAsync on a side stream, or compute the fill grid from a device-side upper bound (allocate dev_stride_prefixes for the worst case and skip the host round-trip; the overflow check can be a device flag copied back once per stage). This is the single highest-leverage kernel-level change and is orthogonal to the appearance gate.
3. Fix the three live cost-path bugs first (they poison every downstream measurement): DistanceMapMetric_Kernel index formula (distance_map_metric.cu:20), the pointer-vs-value denominator check (implant_mahfouz_metric.cu:346/464), and either implement or delete CurvatureHeatmapMetric (returning 0 today is a trap for future leaf costs). Pin each with a headless unit test before the fix (R15: pin the quirk, then normalize).
4. Make the metric pipeline read-only: give FastImplantDilationMetric/ImplantMahfouzMetric a scratch buffer instead of mutating the rendered image (fast_implant_dilation_metric.cu:218-273). This unblocks image caching, metric reuse, and a CPU-fallback comparison (the metric would then be a pure function of two images).
5. Determinism: do NOT rewrite the int reductions (they are value-deterministic; the docs' claim to the contrary is imprecise). Instead (a) document the real noise sources in golden_oracle.org (float FMA/arch divergence + DIRECT chaos + backface config), (b) optionally add a reproducibility build flag (--fmad=false + pinned arch) for trace debugging, and (c) if DRR ever joins the cost path, convert its float atomicAdd to a per-block shared-memory partial + deterministic tree (render_drr_engine.cu:328-352). The appearance gate stays tolerance-based; determinism is a debugging aid, not a gate.
6. Reconcile the production-vs-oracle backface setting: production uses backface culling ON (optimizer_manager.cpp:716-722), the oracle runs OFF to match labels (oracle_test.cpp:190-197, baseline.json). Either document why production's silhouette may differ from the label generator's, or align them; this is a real, unexamined divergence in the load-bearing gate.
7. Torch in services (004 U8): keep the layer change but (a) stop calling CUDACachingAllocator::emptyCache() per frame — pool the placeholder tensor and clear only on OOM (segmentation_controller.cpp:25-27), and (b) prefer jit-model warmup + preallocated output tensors to cut the per-call tensor churn in segment_image/EstimateImplantPose. Moving torch out of jtml_services entirely (back to an app-level seam) is defensible but secondary; the emptyCache policy is the actual perf bug.
8. Multi-GPU/parallelism: the only safe seam is the DIRECT iteration — evaluate the 2 points per potentially-optimal box concurrently (direct_optimizer.cpp:183/198) or split biplane cameras across devices; do not attempt data-parallel DIRECT. This is a research item, not a near-term change; single-GPU sync removal (item 2) yields most of the win.
9. CPU fallback for debug/headless: the silhouette+DIRECT_DILATION pipeline is trivially portable — the host already computes Canny/dilate/distance maps in OpenCV (frame.cu), and the render is a software rasterizer (project + polygon fill + binary metric); a cv::fillPoly-based CPU render + OpenCV dilate/IoU reproduces the DIRECT_DILATION cost with no CUDA. DRR (z line-integrals) would need a small CPU rasterizer — defer. This gives a true Tier-1-GPU parity path and makes the oracle runnable on non-GPU CI for the cost pipeline (not the gate).
10. Kernel consolidation, scoped: merge the 3 reset kernels and the metric resets into the consuming kernels (each `<<<1,1>>>` reset is a launch round-trip per eval: render_engine.cu:722, fast_implant_dilation_metric.cu:170, distance_map_metric.cu:72-73, iou.cu:65), and switch the square grids to 1D grid-stride loops (render_engine.cu:186-210). Leave FillTriangleKernel's two-level binary search alone unless Nsight Compute shows it hot — replacing it with per-pixel tile lists is a bigger rewrite than the current sync problem justifies.
