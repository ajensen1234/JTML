* Summary

The two-tier oracle is correctly framed as a behavior-preservation gate (R1/R2/R15) and is exemplary for a research tool — but it currently gates ONE case (Kneel_1 femur, 1 of 3 frames, monoplane, single trunk stage at flat budget 3000) and its 0.85 IoU threshold sits far below the measured 0.9936, so gate sensitivity is unknown. The highest-leverage moves are: (1) close the production-oracle divergence by adding an oracle variant that drives the real cumulative stage loop (20k→25k→30k→35k, dilation 6/4/1) — the leaf z-refinement stage is exactly the weak axis (documented 6.31mm z_trans gap) the current oracle never exercises; (2) validate the oracle itself with a mutation/perturbation suite (the literature calls this oracle-quality testing); (3) treat the oracle as verification and build a separate accuracy-evidence trail, because the repo's own published lineage (Jensen et al., "Joint Track Machine Learning," the DIRECT-JTA paper) already reports the validation design and numbers (sub-mm in-plane, <1.8mm out-of-plane, per-DoF RMS vs human-supervised/RSA/mocap) that this tool would need to reproduce. Regulatory reality: AGPL does not exempt anything — under MDR 2017/745 and FDA SaMD frameworks, intended purpose decides device status, and a 2D-3D registration tool that processes images fails the FDA CDS exclusion. The honest "research only" boundary is a written intended-purpose statement, not the license.

* Key Findings

** Golden-master at scale: behavior-preservation is the right frame, but single-fixture coverage caps its power
- Characterization/golden-master testing verifies observed behavior, not correctness — exactly the repo's R1/R2 "behavior-preservation, not correctness" framing; it is the standard technique for pinning legacy/imaging behavior during refactor. [Source: https://qaskills.sh/blog/approval-testing-golden-master-guide ; http://blog.ansuz.nl/index.php/2023/01/25/characterization-testing/]
- Confidence: high
- Relevance: confirms the crown-jewel stance is sound; the weakness is coverage (1 case) and sensitivity (see oracle-of-the-oracle finding), not the technique.
- Mature imaging projects scale golden images with a triage service: Skia Gold manages baselines outside git, diffs every commit's rendered output (>500k images per commit for Skia), and requires explicit human triage of each diff as positive/negative before it becomes a new baseline. This is the mature pattern for multi-fixture, multi-frame appearance gates. [Source: https://docs.skia.org/docs/dev/testing/skiagold/ ; https://chromium.googlesource.com/chromium/src/+/main/docs/gpu/gpu_pixel_testing_with_gold.md]
- Confidence: high
- Relevance: JTML's single Catch2 IoU assertion per fixture will not scale to a fixture matrix (3 frames × femur/tibia × biplane × 2nd subject) without a baseline-triage convention — a "render diff review" step (render-smoke-output/ already exists as the seed of this).
- Golden references must be compared against a tolerance band sized to the metric's own noise, never an exact line — the video-encoding world's VMAF golden-reference practice. [Source: https://www.forasoft.com/learn/video-quality/articles-vqm/regression-testing-golden-references]
- Confidence: high
- Relevance: JTML's IoU>0.85 threshold (measured 0.9936) was apparently not calibrated from renderer noise; the threshold should be set from the measured noise floor across GPUs (RTX 3090 + one other) plus margin, and the informational per-px L1 (0.0207) promoted to a secondary banded gate.
- Property-based and example-based tests are two orthogonal specification axes, not flavors of the same activity: examples pin intent, properties pin invariants; a suite with only one axis is incompletely specified. [Source: https://www.tddbuddy.com/blog/properties-pin-the-invariants/ ; https://fast-check.dev/docs/introduction/why-property-based/ ; https://increment.com/testing/in-praise-of-property-based-testing/]
- Confidence: high
- Relevance: JTML already follows this (13 hegel PBT targets each with a deterministic twin — "PBT complements, never replaces"); at scale the PBT layer should grow optimizer invariants (budget bookkeeping, range clipping, denormalize round-trip) while fixtures stay example-based.

** The oracle itself needs testing: mutation/perturbation analysis of the gate
- Oracle quality is a recognized, measurable problem: "checked coverage" (which statements actually influence an oracle) is a stronger indicator of oracle quality than mutation testing; weak oracles fail to reveal faults. [Source: https://www.st.cs.uni-saarland.de/publications/files/schuler-stvr-2013.pdf ; https://nmaguirre.github.io/assets/pdf/ase2025a.pdf]
- Confidence: high
- Relevance: the 0.85 gate with 0.9936 measured means we do not know what regressions would trip it. A perturbation suite (pose perturbed by the documented z_trans gap 6.31mm, ±1mm/±1°, dilation schedule broken, cost variant swapped) that asserts the gate trips would measure gate sensitivity — cheap, GPU-only, no new fixtures.
- Metamorphic testing is the standard answer to the oracle problem in scientific software, including numerical/optimization code where exact outputs are unavailable: check relations among outputs of related inputs instead of asserting a single expected output. [Source: https://dl.acm.org/doi/10.1145/3143561 ; https://pmc.ncbi.nlm.nih.gov/articles/PMC7252536/ ; https://homepages.uc.edu/~niunn/papers/SE4Science18.pdf]
- Confidence: high
- Relevance: the two-tier oracle is already one metamorphic relation (render-at-recovered-pose ≈ Labels); cheap additional MRs: known-pose recovery from synthetic renders (non-circular, pose known by construction), equivariance under rigid perturbation, IoU monotonicity under increasing pose perturbation.

** Multi-stage shared-loop gap: what practice says, and what it costs
- The production and oracle stage shapes genuinely diverge. Production (include/domain/settings_constants.h): trunk range ±35 all, budget 20000, dilation 6; 2 branches range (15,15,25,25,25,25), 5000 each; leaf/z-search range (3,3,15,3,3,3) (z opened to ±15), 5000, dilation 1 — cumulative 20k→25k→30k→35k via SetCallOffset. Oracle (golden_oracle.org): single trunk stage, flat budget 3000, range (12,12,15,15,15,15), flat dilation 6. The oracle therefore never exercises the branch stages, the leaf z-refinement, the tibia-after-femur ordering, or sym_trap disambiguation — and the documented 6.31mm z_trans gap vs 15mm tolerance is precisely the weak axis the leaf stage exists to refine. [Source: repo — include/domain/settings_constants.h, golden_oracle.org, src/coordinator/optimizer_manager.cpp]
- Confidence: high (repo-internal, verified by grep/read)
- Relevance: a regression in stage-loop bookkeeping, dilation scheduling, or tibial ambiguity handling would pass the oracle. This is the single most valuable oracle expansion.
- General practice is not "end-to-end vs per-stage" but both, at different layers: unit-test pipeline components and budget/range bookkeeping per stage; integration-test between components; a few expensive E2E gates at the top (test pyramid). ML pipeline guidance is explicit that integration between pipeline components must be tested in addition to component quality. [Source: https://beyond.minimumcd.org/docs/testing/ ; https://developers.google.com/machine-learning/crash-course/production-ml-systems/deployment-testing ; https://docs.gitlab.com/development/testing_guide/testing_strategy/]
- Confidence: high
- Relevance: JTML's per-stage unit surface (optimize_intent, coordinator seam) exists but nothing E2E drives the production stage loop against appearance ground truth.
- For global optimizers, budget-vs-tolerance "data profiles" are the standard way to characterize how much budget a solver needs to reach a tolerance τ — the direct frame for choosing an oracle budget shape that is both fast and representative of production. [Source: https://epubs.siam.org/doi/10.1137/080724083 (Moré & Wild, SIAM J. Optim. 2009)]
- Confidence: high
- Relevance: instead of the ad hoc 3000-budget reduction, measure the smallest cumulative budget shape whose recovered pose stays above IoU≈0.98 on Kneel_1, then use that shape for CI.
- The repo's own published lineage validates the staged optimizer end-to-end: DIRECT-JTA (trunk/branch/leaf with decreasing dilation, tibia-after-femur, varus/valgus penalty) was evaluated against human-supervised kinematics, an RSA study, and a motion-capture-tracked sawbones phantom — not per-stage. [Source: https://ar5iv.labs.arxiv.org/html/2205.00057]
- Confidence: high
- Relevance: E2E (staged, production-shaped) validation is the published norm for this exact algorithm family; per-stage-only oracle coverage is the outlier.

** Biplane validation: what Subject0 needs and what accuracy the field reports
- Biplane model-based registration accuracy in the field: contour-based biplane tracking vs marker-based gold standard (cadaveric knees, 6 specimens) showed bias/precision of 0.01±0.65° (rotations) and 0.01±0.59mm (translations) — sub-mm/sub-degree across walking, extension, and drop-landing. [Source: https://pubmed.ncbi.nlm.nih.gov/23021610/ (Giphart et al., J Biomech 2012)]
- Confidence: high
- Relevance: these are realistic TRE/precision targets for a biplane appearance gate and for any clinical-accuracy claim.
- A cadaveric comparison of model composition × number of views (single vs biplane): biplane configurations kept mean absolute errors below 0.3mm and 0.9° per motion component regardless of bone-model type; radiodensity-model single-plane (RS) ≈ homogeneous biplane (HB); radiodensity biplane (RB) most accurate and most robust to fast motion. [Source: https://www.jstage.jst.go.jp/article/jbse/16/3/16_21-00105/_article/-char/en (J Biomech Sci Eng)]
- Confidence: high
- Relevance: justifies the biplane gate (camera-B) as the accuracy-dominant configuration, and sets tolerance expectations (<0.3mm/<0.9° is what the field achieves biplane).
- Gold-standard methodology for 2D-3D registration validation: fiducial-based ground truth (cadaver specimens with attached fiducials, multiple modalities) and, more recently, uncertainty-modeled ground truth where fiducial-derived transforms are jointly optimized with noisy 3D fiducial locations (MPPC criterion) — the field's answer to "how do we know the ground truth is right." [Source: https://pmc.ncbi.nlm.nih.gov/articles/PMC3091017/ ; https://pmc.ncbi.nlm.nih.gov/articles/PMC9290855/ ; https://pubmed.ncbi.nlm.nih.gov/16192053/]
- Confidence: high
- Relevance: Subject0's ground truth does not require clinical imaging — render-at-known-pose from both cameras (the existing Study2Grid label generator) is the same flat-shaded-projection ground truth the JTML lineage used for segmentation labels; but the camera-B calibration (Camcal1/2.txt) must be independently verified (fiducial or render-self-consistency check) because R2 anti-circularity forbids re-deriving ground truth from the tool itself.
- What Subject0 additionally needs: (1) Labels/ for camera B (currently absent — the recon lists no Labels/ for Subject0); (2) a machine-checkable frame↔label mapping (the monoplane correspondence 1024/2806.tif↔AT_K1_V1_0160_label_fem.tif was resolved empirically — that hazard must not repeat per fixture); (3) the TIFF y-flip convention recorded per camera; (4) per-frame pose ground truth if TRE, not just IoU, is to be reported. [Source: repo — example_studies/Subject0/, golden_oracle.org]
- Confidence: high (repo-internal)
- Relevance: these are the concrete acceptance criteria for "biplane appearance gate" deferred work.

** Clinical accuracy evidence for TKA implant registration: the published numbers
- The closest published evidence for this exact tool is the UF/Denver lineage paper (Jensen, Flood, Palm-Vlasak, Burton, Rullkoetter, Banks): CNN segmentation → NFD shape library → DIRECT-JTA (three-stage trunk/branch/leaf Lipschitzian optimization with decreasing dilation and L1 cost). Reported: RMS differences vs human-supervised kinematics sub-mm for in-plane translations, <1.8mm out-of-plane (ML translation), rotations ≤4° inside the tibial ambiguous zone and <1.7° outside; independent RSA validation (113 single-plane lateral TKA images): RMS 0.8mm AP, 0.5mm SI, 2.6mm ML, 1.0° FE, 1.2° AA, 1.7° IE; independent instrumented-sawbones + motion capture (45 images): RMS 0.72mm AP, 0.31mm SI, 1.82mm ML, 0.56° FE, 0.63° AA, 0.84° IE. Blunders: 1 femoral, 43 tibial of 392 test images, 66% of tibial blunders due to symmetry ambiguity; ambiguous zone = apparent tibial varus/valgus <3.6°. [Source: https://ar5iv.labs.arxiv.org/html/2205.00057]
- Confidence: high
- Relevance: this is the accuracy evidence the tool would need to reproduce, and the per-DoF RMS table (not IoU) is the reporting template. The repo's DIRECT_DILATION cost, dilation schedule, tibia-after-femur ordering, and sym_trap disambiguation are all in this paper.
- Field context for single-plane implant registration: in-plane accuracy is typically ~0.1-1mm while depth (out-of-plane translation) is the known weak axis because silhouette changes little with depth — the exact failure mode JTML documents as the 6.31mm z_trans gap. [Source: https://orthoarchives.com/en/orthoscience/article/W2120883230 ; https://iopscience.iop.org/article/10.1016/j.medengphy.2020.01.002]
- Confidence: medium (secondary summaries for the depth-position paper; Hannan et al. abstract confirms <1mm in-plane)
- Relevance: the leaf stage's z-opened range (±15) and the oracle's z tolerance (15mm) are the field's known weak axis; clinical TRE targets should be in-plane sub-mm, out-of-plane ≤1.5-2mm.
- The credibility ladder for this tool's accuracy evidence is the same one its lineage used: in-silico known-pose recovery (synthetic DRR renders) → phantom (sawbones + markers + motion capture) → cadaver (marker-based gold standard) → clinical (vs human-supervised expert or RSA). [Source: https://ar5iv.labs.arxiv.org/html/2205.00057 ; https://pubmed.ncbi.nlm.nih.gov/23021610/]
- Confidence: high
- Relevance: a phantom study (replicating the 45-image sawbones design) is the cheapest non-circular accuracy evidence and directly answers "what accuracy evidence would matter."

** Regulatory framing: when this tool becomes a device, and what evidence that implies
- EU: software with a medical purpose is a medical device (MDR Art. 2(1), recital 19: general-purpose software is not a device even in healthcare settings); qualification and classification are decided by the manufacturer's intended purpose — "Software must have a medical purpose on its own to be qualified as MDSW." Classification rule 11 puts information-providing MDSW at class IIa (higher if decisions risk serious deterioration). [Source: https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX%3A32017R0745 ; https://health.ec.europa.eu/system/files/2020-09/md_mdcg_2019_11_guidance_en_0.pdf ; https://health.ec.europa.eu/latest-updates/update-mdcg-2019-11-rev1-qualification-and-classification-software-regulation-eu-2017745-and-2025-06-17_en]
- Confidence: high
- Relevance: the moment this tool is intended to inform individual-patient diagnosis/treatment (e.g., "measure TKA kinematics for patient management"), it is MDSW; a kinematics-measurement tool for clinical decision-making is class IIa at minimum. "Research only" is a statement of intended purpose, not a default.
- FDA: intended use is determined by labeling, marketing, and representations (21 CFR 801.4); SaMD = software intended for medical purposes without being part of a hardware device; the 21st Century Cures Act CDS exclusion requires the software NOT be intended to acquire/process/analyze medical images — a 2D-3D registration tool processes images, so the CDS exclusion does not apply. RUO labeling does not exempt: "mere placement of an RUO or IUO label... does not render the device exempt," and FDA looks at how it is marketed. [Source: https://www.govinfo.gov/content/pkg/FR-2019-09-27/pdf/2019-20965.pdf ; https://www.thefdalawblog.com/2019/10/fda-issues-a-second-draft-guidance-for-clinical-decision-support-software/ ; https://www.mintz.com/insights-center/viewpoints/2146/2024-04-03-fda-warning-letter-stark-reminder-if-you-claim-your ; https://imdrf.org/sites/default/files/docs/imdrf/final/technical/imdrf-tech-131209-samd-key-definitions-140901.pdf]
- Confidence: high
- Relevance: "research tool" status is protected by what the project says and distributes, not by AGPL or by absence of a clearance sticker.
- IEC 62304 evidence for an optimizer + appearance gate: verification ("did we build it right" — unit/integration/system test records, which is where the oracle lives) is distinct from validation ("did we build the right thing" — clinical accuracy per intended use). The documentation package maps to specific clauses (requirements, architecture, detailed design, test records, problem resolution, configuration management) and feeds MDR Annex II §6.1. All third-party components (VTK, torch, OpenCV, Eigen, Qt, hegel) are SOUP under IEC 62304, requiring functional/performance specification, failure-mode analysis, and config management (clauses 5.3.3, 5.3.4, 7.1.3, 8.1.2). [Source: https://mdregulatory.com/iec-62304-software-verification/ ; https://zechmeister-solutions.com/en/blog/software-documentation-package-iec-62304 ; https://zechmeister-solutions.com/en/blog/open-source-software-medical-devices ; https://aptskillmedtech.com/soup-assessment-iec-62304-guide/]
- Confidence: high
- Relevance: the two-tier oracle is literally a verification artifact for a design input like "shall register within stated accuracy"; the accuracy evidence (phantom/cadaver/clinical) is the validation layer. A SOUP inventory is cheap to write now and painful to reconstruct later.
- Open-source publication does not exempt: "The regulatory requirements do not depend on whether software is placed on the market as open source" — university-published open-source medical software can still be a medical device with liability exposure. [Source: https://blog.johner-institute.com/regulatory-affairs/open-source-software-as-a-medical-device/]
- Confidence: high
- Relevance: the AGPL research-tool skepticism is correct in spirit but wrong as a shield; the honest boundary is a written intended-purpose statement plus distribution/claims discipline.

** CI/GPU runners and oracle-label discipline
- GitHub-hosted GPU runners (T4) are GA (July 2024): Linux 4-core GPU = $0.052/min, Windows 4-core GPU = $0.102/min; larger runners are not free for public repos and included minutes do not apply; they require GitHub Team/Enterprise. A 60-minute oracle run (TIMEOUT 3600) would cost ~$3.12/run hosted; a calibrated 10-15 min reduced-budget run ~$0.5-0.8. [Source: https://docs.github.com/en/billing/reference/actions-runner-pricing ; https://github.blog/changelog/2024-07-08-github-actions-gpu-hosted-runners-are-now-generally-available/]
- Confidence: high
- Relevance: self-hosted runners on the lab's existing GPU machines (U2/U6, already named in test/CMakeLists.txt) are the zero-marginal-cost path; a gpu label + nightly full oracle + per-PR reduced oracle is the standard shape.
- Self-hosted GPU runner practice: register the runner with a custom gpu label, target runs-on [self-hosted, gpu], verify with nvidia-smi, prefer persistent over ephemeral runners for CUDA driver stability. [Source: https://latchkey.dev/learn/ci-how-to/build-on-self-hosted-gpu-runner-github-actions ; https://blog.scientific-python.org/scikit-learn/gpu-ci/]
- Confidence: high
- Relevance: concrete implementation pattern for the deferred "no GPU CI job" item.
- Mature image-diff tooling: pytest-mpl (RMS tolerance + explicit baseline update) and pixelmatch (perceptual diff) are the reference patterns for tolerance-based image comparison; Skia Gold shows the triage workflow at scale. [Source: https://pytest-mpl.readthedocs.io/en/stable/image_mode.html ; https://pypi.org/project/pixelmatch/ ; https://docs.skia.org/docs/dev/testing/skiagold/]
- Confidence: high
- Relevance: even in C++/Catch2, the pattern transfers: baseline PNGs stored as fixtures, diffs reviewed and approved explicitly, tolerance per metric not per test.
- Oracle label discipline hazards found in the repo: labels are "oracle" and "oracle;render" (no standalone gpu label); empirical frame↔label correspondence; TIFF y-flip convention; oracle WORKING_DIRECTORY = repo root; TIMEOUT 3600 (a 1-hour gate is a smell for per-PR gating). [Source: repo — test/CMakeLists.txt, golden_oracle.org]
- Confidence: high (repo-internal)
- Relevance: each new fixture should ship with a machine-checkable manifest (frame↔label mapping, y-origin, calibration hash, render-at-jts IoU≈1.0 self-consistency check on ingest) so the "empirically resolved" correspondence never silently misaligns a new subject.

* Recommendations for JTML

** Close the multi-stage divergence first (highest value, one fixture)
- Add an oracle variant that drives the production stage loop on Kneel_1 frame 0: cumulative budgets 20k→25k→30k→35k, ranges 35/15/3 (z ±15 in leaf), dilation 6/4/1, tibia-after-femur ordering with sym_trap disambiguation, same IoU>0.85 appearance gate. Assert it passes at the same ~0.99 IoU level as the current single-stage run. A regression in SetCallOffset bookkeeping, dilation scheduling, or the leaf z-refinement is currently invisible to the oracle; this closes that hole.
- Use a Moré & Wild data-profile analysis on Kneel_1 to pick a reduced budget shape (e.g., 5k/2k/2k/2k) whose recovered pose stays above IoU≈0.98, and run THAT shape per-PR in CI and the full production shape nightly. This replaces the ad hoc 3000-budget reduction and the 3600s TIMEOUT with a defensible number.
- The shared stage-loop refactor (production Optimize() and oracle driving one routine) is exactly right (R15); the oracle variant above is its acceptance test.

** Validate the oracle itself (cheap, no new fixtures)
- Add a perturbation/mutation suite on the GPU runner: perturb the starting pose by the documented z_trans gap (6.31mm) and by ±1mm/±1° per DoF, break the dilation schedule, swap the cost variant — and assert the IoU gate trips. This measures gate sensitivity (checked-coverage/oracle-quality literature) and answers "would this gate catch a real regression?"
- Calibrate the IoU threshold: measure renderer noise floor across RTX 3090 and one other GPU; set threshold = noise floor + margin instead of the ad hoc 0.85; promote per-px L1 (measured 0.0207) to a banded secondary gate.

** Expand fixtures in cost order, with a fixture manifest
- (1) remaining 2 Kneel_1 frames; (2) tibia golden (tib.jts + Labels/tib exist — needs an oracle run and a documented z-axis expectation; tibial symmetry ambiguity is the known blunder source, 66% of tibial blunders in the lineage paper); (3) Subject0 biplane: render Labels for camera B (and A) at known poses via Study2Grid, verify Camcal1/2.txt self-consistency (render-at-jts IoU≈1.0), and add a machine-checkable manifest (frame↔label mapping, y-origin, calibration hash) so the empirically-resolved monoplane correspondence never silently misaligns; (4) a second subject.
- Ingest gate for every new fixture: render-at-known-pose IoU ≈ 1.0 self-consistency check, per R2 (never re-derive ground truth from the tool being tested).

** Build the accuracy-evidence trail separately from the oracle (verification vs validation)
- The oracle is verification. For accuracy evidence, follow the lineage paper's own ladder: (1) in-silico known-pose recovery from synthetic renders (non-circular — poses synthetic); (2) sawbones phantom + markers + motion capture, replicating the 45-image design; (3) cadaver with marker-based gold standard; (4) clinical comparison vs human-supervised or RSA. Report per-DoF RMS/MAE + bias + blunder rate in the lineage paper's Table II format.
- TRE targets to design against (field-reported): sub-mm in-plane translation, ≤1.5-2mm out-of-plane (depth is the known weak axis — the 6.31mm z gap is exactly this), sub-degree rotations, with the tibial ambiguous zone (<3.6° apparent varus/valgus) documented as a limitation.

** GPU CI and labels
- Add a standalone gpu label; wire a self-hosted runner on U2/U6 (runs-on [self-hosted, gpu], nvidia-smi probe) — zero marginal cost vs $0.052/min hosted. Nightly: full oracle (production-shaped) + render smoke; per-PR: reduced-budget oracle + headless suite. Target <15 min oracle runtime so the gate is actually run, not tolerated.
- Adopt a Skia-Gold-style triage step for baseline images (render-smoke-output/ is the seed): diffs reviewed and approved explicitly before baselines move.

** Regulatory posture (cheap now, expensive later)
- Write the intended-purpose statement into the repo (README or docs/): either explicit research-only scope (no individual-patient use, no clinical claims, no distribution for diagnosis) or a device-development roadmap. AGPL does neither.
- Build a SOUP inventory now (VTK, torch, OpenCV, Eigen, Qt, hegel: functional purpose, failure modes, version) — it is cheap today and is required content for any IEC 62304/MDR Annex II package later.
- If the clinical trajectory is pursued (the lineage paper explicitly anticipates it: "will soon be practical to perform these measurements in a clinical setting"), the phantom→cadaver→clinical evidence above is the same evidence IEC 62304 validation and MDR Annex II would require — starting the evidence trail is not regulatory overhead, it is the product's scientific core.
