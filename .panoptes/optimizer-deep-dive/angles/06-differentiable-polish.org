#+TITLE: Differentiable Polish — gradient-based local refinement after DIRECT, the z-signal, and what is actually transferable to a hand-written CUDA stack
#+DATE: 2026-08-12
#+PANOPTES_ANGLE: differentiable-polish

* Summary

A gradient-polish stage after DIRECT is feasible in this stack, but only if it optimizes a *smooth surrogate* — the production DIRECT_DILATION cost is a piecewise-constant function of pose (binary silhouette + int-atomic reductions), so its gradient is zero almost everywhere and undefined at pixel flips. The surrogate already exists in the codebase: the chamfer distance-map term (DistanceMapMetric), whose gradient is the standard analytic-silhouette-gradient: Σ over rendered edge pixels of ∇D(p)·(projection Jacobian). That Jacobian needs only the per-pixel triangle-ID + barycentrics that FillTriangleKernel already computes and throws away. The depth channel is the angle's main myth to puncture: a front-surface z/w buffer is 80% machinery-present (the DRR fill already interpolates perspective-correct z), but a depth channel does *not* make z observable in single-plane fluoro — the 6.31 mm z gap is the magnification limit, and the only real z-fixes are biplane (already supported) or a known-geometry prior. Verdict: GO for a budget-accounted polish stage (chamfer surrogate, analytic Jacobian, ~2-3 weeks) scored by angle 03's harness as a DIRECT-only vs DIRECT+polish ablation arm; NO-GO for the photometric DRR-gradient and torch-bridge routes.

* Key Findings

** The production cost is piecewise-constant in pose — the gradient of the existing cost is not a usable signal, and this is the load-bearing constraint on everything else
- FastImplantDilationMetric reduces with int atomicAdd over binary comparisons (DILATED_PIXEL/EDGE_PIXEL vs WHITE in the dilated comparison) and DistanceMapMetric sums int distance values over a *discrete* edge-pixel set; both change only when a rendered pixel flips 0↔255 as vertices cross pixel centers. The render itself (RenderEngine::Render) writes a binary silhouette. [Source: repo — src/compute/fast_implant_dilation_metric.cu, src/compute/distance_map_metric.cu, src/compute/DIRECT_DILATION.cpp:58-92]
- Consequence: finite-difference on the production cost gives zero or garbage Jacobians for any step not straddling a flip boundary; there is no gradient to "polish" through the production metric. Any polish stage must (a) optimize a smooth surrogate, and (b) verify the result with the production cost — the surrogate is a *search* objective, the production cost stays the *arbiter* (same relationship as angle 03's appearance gate vs cost math).
- Also note the existing metric's int reduction truncates (double→int atomicAdd truncation is already listed as bug 6 in the local recon) — a polish surrogate must use float accumulation.
- Confidence: high (source-verified)
- Relevance to this project: kills option (b) of accountable question 1 (finite-difference on the existing cost) before it starts; forces the surrogate architecture that the harness can actually measure.

** The smooth surrogate already exists: DistanceMapMetric is a chamfer loss, and its gradient is the standard analytic silhouette gradient
- DistanceMapMetric = Σ_{rendered edge pixels} distance_map[p] / (count+0.1) — a mean-chamfer of the rendered silhouette edge to the target (fluoro) edge; the distance transform makes it Lipschitz with an image-space gradient ∇D computable numerically from the distance map itself. [Source: repo — src/compute/distance_map_metric.cu; include/compute/frame.h (SetDistanceMap)]
- The standard differentiable-registration gradient is dL/dθ = Σ_{p ∈ E(θ)} ∇D(p)·(dp/dθ) + a boundary term from pixels crossing the edge set; the boundary term is what analytic AA (Modular Primitives) or soft coverage (SoftRas/DIB-R) smooths, and it is small relative to the ∇D term inside the DIRECT basin (few flips per step at convergence). Published relatives of exactly this gradient: "Analytical Derivatives for Differentiable Renderer: 3D Pose Estimation" (arXiv:1906.07870) and "3D/2D Registration of Angiograms using Silhouette-based Differentiable Rendering" (arXiv:2501.14918). [Source: https://arxiv.org/abs/1906.07870; https://arxiv.org/html/2501.14918]
- dp/dθ is analytic for a rigid body: projected p = (fx·X/Z + cx, fy·Y/Z + cy) with (X,Y,Z) affine in the pose θ (R·v + t), so the 2×6 projection Jacobian is a ~50-line kernel. This is the "Modular-Primitives-style analytic silhouette gradient" in its minimal form — no soft rasterizer, no AA pass required for the MVP.
- Confidence: high (the math is standard; the codebase already contains both ingredients)
- Relevance: this is the minimal viable gradient signal (accountable question 1): analytic projection Jacobian + numerical ∇D from the existing distance map, at 1 render per step. The honest baseline to implement *first* (measurement-first) is forward/central differences on this same surrogate (6-12 renders/step, zero new rasterizer code) — it establishes whether gradient polish wins at all before the analytic investment.

** FillTriangleKernel already computes the per-pixel triangle-ID + barycentrics that the gradient needs — and discards them
- FillTriangleKernel computes the unnormalized barycentrics (a, b, c, denominator) for the inside test and only writes 255 to the image. Writing (triangleIndex, a, b, c) out for filled pixels is the Modular-Primitives per-pixel output minus the NDC z: exactly the (ID, u, v) tuple the backward pass consumes. The renderer also knows the projected positions and (in the DRR twin) per-vertex camera z, so the un-projected 3D source point of each edge pixel is recoverable. [Source: repo — src/compute/render_engine.cu FillTriangleKernel; Modular Primitives rasterizer outputs (ID, u, v, zc/wc) + 2×2 barycentric Jacobian per https://ar5iv.labs.arxiv.org/html/2011.03277]
- Cost: one extra device buffer (float4 per filled pixel) + ~10 lines in the fill kernel. The stride/prefix/bounding-box launch scheme is untouched.
- Confidence: high (source-verified)
- Relevance: this is what makes the analytic route cheap — the rasterizer is already 80% of a differentiable rasterizer; only the output staging and the backward scatter-add are missing.

** The depth channel: machinery is 80% present, but a depth channel does NOT fix the z-weak axis in single-plane fluoro — the honest finding this angle exists to deliver
- Where z comes from today: the silhouette path (Render) computes per-vertex camera z (tZ) in WorldToPixelKernel and *discards it*; the DRR path stores it (dev_transf_vertex_zs_) and DRR_FillTriangleKernel interpolates per-pixel perspective-correct z via the rational formula (tvz1·tvz2·tvz3·denominator)/(a·tvz2·tvz3 + b·tvz1·tvz3 + c·tvz1·tvz2) — which is exactly 1/(λ1/z1 + λ2/z2 + λ3/z3), i.e. the perspective-correct interpolated camera z at the pixel. There is no z-testing anywhere (all triangles draw; backfaces are sign-flipped in the DRR accumulation). A front-surface NDC-style depth buffer (this stack's "z/w" ≡ −tZ_cam, positive toward the detector) needs only a min-z test in the fill + a float buffer — and dev_z_line_values_ (width×height float) is already allocated and reusable. [Source: repo — src/compute/render_engine.cu:430-520, src/compute/render_drr_engine.cu DRR_WorldToPixelKernel + DRR_FillTriangleKernel, include/compute/render_engine.cuh dev_z_line_values_/dev_transf_vertex_zs_]
- Why it does not fix z: (a) there is *no target depth* in a single-plane fluoro to compare a rendered depth against — a depth-difference term only exists in synthetic self-supervised ablations (render at known pose → optimize), against a registered bone model / known-geometry prior, or in biplane; (b) the observed z gap is the magnification limit — z-translation is only observable through scale (6.31 mm z gap vs 0.16/0.08 in-plane in baseline.json; angle 03's probe arithmetic: <1% scale change over ±15 mm at ~1.1 m), and no gradient changes what is observable; (c) NVDiffrast — the reference implementation of Modular Primitives — intentionally does *not* backprop through the z/w channel (issue #70: the z/w output's gradients are not propagated; the meaningful gradients are the vertex-position ones). [Source: repo — test/golden/baseline.json tolerances.observed_max_gap_vs_golden; https://github.com/NVlabs/nvdiffrast/issues/70 (search-verified content, page fetch failed); https://nvlabs.github.io/nvdiffrast/]
- What the depth machinery IS worth: (i) occlusion-aware visibility gradients — Modular Primitives' premise "a 3D primitive with no effect on the image receives zero gradient" requires knowing which triangle owns each pixel (z-test), which the renderer lacks today; (ii) a synthetic-depth loss in the harness's self-supervised arm (a genuine z test *when a target depth exists*); (iii) the z-line-integral (dev_z_line_values_) is a stronger quantitative z signal than front-depth (it shifts by ≈Δz·path-length under z-translation) but is an X-ray-attenuation proxy — unobservable for a saturated metal implant and only useful in the ML/DRR pathway (DiffDRR-style).
- The real z-fixes: biplane (the codebase already has it — calibration_.convert_Pose_A_to_Pose_B and a biplane branch in DIRECT_DILATION) and the known-geometry prior (implant constrained to a registered bone). This matches the prior-run ML angle's finding 8 ("if the ML pathway is to beat the monoplane z gap, biplane is the evidence-backed direction").
- Confidence: high on the machinery facts (source-verified + NVDiffrast issue); high on the observability argument (analytic); medium on the exact clinical z-benefit of biplane/prior until measured
- Relevance: answer to accountable question 2 — the depth channel is a *gradient-quality and ablation-signal* feature, not a z fix; the harness should test it as such (self-supervised depth arm), and the z-profile probe (angle 03) should first confirm the chamfer surrogate's valley is deeper than the dilated-overlap valley — that is the precondition for any polish z-win.

## Round 2 — Executable MVP Spec for the Polish Stage (differentiable-polish)

### Summary

This round converts Round 1's verdicts into an executable MVP spec, from the differentiable-rendering/CUDA seat, with every number grounded in the verified repo: (1) the precondition gate is now measurable — a term-decomposed z-profile probe (chamfer-only vs dilated-overlap-only valley depths from the *same* 31-render sweep) with pre-registered thresholds (valley_depth ≥ 0.10, chamfer − dilated ≥ 0.05, |argmin_offset| ≤ 2 mm, evaluated at the leaf dilation 1 over the ±15 mm sweep) that gates the arm's **z-claim**, never the arm itself; #### R2-3 — What "staging the barycentrics FillTriangleKernel already computes" means as a concrete kernel refactor: a sibling kernel, a 16 MB buffer, and the last-writer pairing argument
- Current state (verified by direct read): FillTriangleKernel (render_engine.cu) computes the unnormalized barycentrics a, b, c and denominator for the inside test — a = (y2−y3)(px−x3) + (x3−x2)(py−y3), b = (y3−y1)(px−x3) + (x1−x3)(py−y3), c = denominator − a − b, with the two-branch inside test (denominator > 0 and < 0) — and writes only 255 to dev_image[(py)*width + px]. The stride/prefix/bounding-box launch scheme is untouched. [Source: repo — src/compute/render_engine.cu (InitializeCUDA/FreeCuda/Render), include/compute/render_engine.cuh (dev_z_line_values_ precedent)]
- The consistency argument that makes this correct WITHOUT atomics: the current fill is last-writer-wins in the deterministic fragment-stream order (no atomics in FillTriangleKernel; thread i of the fill grid owns fragment i, and the stream order is fixed by the prefix sums). Writing the image byte and the attribute float4 from the SAME thread preserves the pairing: at any pixel, the attribute (triangle, u, v) belongs to the same triangle that produced the silhouette value there. The render stays bit-deterministic, and the attribute buffer is bit-deterministic with it (the ablation runner's run_hash/re_reruns_identical discipline carries over). #### R2-4 — The analytic projection Jacobian + gradient-of-distance-map kernel (1 render/step): the math, the kernel structure, float-accumulation rules, production-parity matching, and the FD-twin gate

#### R2-5 — The ablation arm that arbitrates contradiction 6: THREE arms at equal cumulative budget, the B-arm budget-gift control, the IoU gate, per-axis gaps, and the sample size that makes it conclusive
- The round-1 two-arm design had a confound this round's redesign removes: DIRECT-only@B vs DIRECT@(B−B_p)+polish@B_p cannot separate "polish added quality" from "the 1000 evals were spent better by polish than DIRECT would have spent them" — the budget gift itself is the alternative explanation.
