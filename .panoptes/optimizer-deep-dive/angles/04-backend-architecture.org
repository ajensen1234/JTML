#+TITLE: Backend Architecture — the minimal surface for swappable parameters + cost + backend
#+DATE: 2026-08-12
#+PANOPTES_ANGLE: backend-architecture

* Summary

The optimizer "backend" is already a stack of three seams — the run-level
OptimizerRunDriver (plan 006 U5), the stage loop inside OptimizerManager::Optimize,
and DirectOptimizer's injected cost boundary. This session's job is to make the
*middle* seam data-driven, not to add layers. Target shape: OptimizerRunLaunch stays
the single by-value payload, additively gaining the DIRECT Options struct; the stage
sequence (trunk → branch×N → leaf) becomes a StageScript (a vector of StageSpec) that
the same Optimize() executor consumes; the dilation/dark-silhouette derivation and the
GPU cost-adapter construction become named, unit-pinned pure functions; the
DirectOptimizer boundary stays exactly std::function<double(const Point6D&)>. The
"backend" is deliberately NOT an enum or interface: run-level backend = the injected
driver (the fake driver already proves it), stage-level backend = the future StageKind
switch, and a gradient-polish stage is one more script entry with its own runner — all
in the same seam. Explicit non-moves: the frame loop, session state, and the 7+1 signal
surface stay in the manager; the GPU cost path stays in compute; no new CMake target;
no headless executor extraction until the multi-stage oracle (angle 03) demonstrates the
driver seam insufficient.

* Key Findings

** Target shape: one by-value payload, three conceptual sections, the stage loop as data (Q1)

- The current payload already separates most of the wanted surfaces: OptimizerSettings
  (budgets/ranges/enables, include/services/optimizer_settings.h) is the optimizer-side
  config and the three CostFunctionManagers (active variant + parameter values per stage,
  include/compute/CostFunctionManager.h) are the cost config — both already travel by
  value in OptimizerRunLaunch (include/coordinator/optimizer_run_driver.h). What is
  missing is (a) the stage *sequence* as data, (b) a slot for the DIRECT variant Options,
  and (c) a named derivation for the cost-derived loop inputs (dilation, dark silhouette).
  [Source: include/coordinator/optimizer_run_driver.h; include/services/optimizer_settings.h]
- Confidence: high. Relevance: the "RunSpec" the handoff deferred is mostly *naming and
  flow*, not new structure — the three-way split (optimizer config / cost config /
  backend) maps onto fields that already exist.
- StageSpec data model: {StageKind kind, Point6D range, unsigned int budget,
  unsigned int repeat, unsigned int cfm_index}, where repeat materializes
  number_branches. The branch group dilates ONCE and emits UpdateDilationBackground once,
  then re-seeds + budget-accumulates per repeat (optimizer_manager.cpp:1036-1080) — so
  `repeat` is a property of the stage *group*, not per-iteration dilation, and the data
  model must carry it that way or the emission sequence drifts. BuildStageScript(settings)
  → {trunk(range, trunk_budget, 1, cfm 0), branch(range, branch_budget, number_branches,
  cfm 1) if enable_branch_ && number_branches > 0, leaf(range, leaf_budget, 1, cfm 2) if
  enable_leaf_}. [Source: src/coordinator/optimizer_manager.cpp:940-1215]
- Confidence: high. Relevance: this is the single structural change that makes budget-shape
  ablations (5k/2k/2k/2k from synthesis item 3) and dilation-schedule ablations (item 7)
  a payload change instead of an editor session on Optimize().
- Dilation stays COST-owned: today the manager reads the stage dilation ints and dark-
  silhouette bools from each CFM's active cost-function parameters (the "Dilation" /
  "dark_silhouette" name scan, optimizer_manager.cpp:237-345). The target keeps that
  direction — cost config → DeriveStageCostParams(cfm) → loop — rather than moving
  dilation into optimizer config, because the CFM parameter IS the single source of truth
  (switch the active variant and the dilation follows). Moving it would fork the truth.
  The seam is the named pure function, called once in Initialize, with the derived values
  stored in the manager members exactly as today. [Source: src/coordinator/optimizer_manager.cpp:237-345]
- Confidence: high. Relevance: answers the dispatch's "dilation under optimizer
  configuration" framing with a deliberate counter: dilation is a *derived cost property*,
  exposed to the optimizer loop through a pinned seam.
- DIRECT Options placement: domain/direct_optimizer.h, next to the engine (domain is
  Qt-free; the Options struct is plain data). Constructor evolution is additive —
  `DirectOptimizer(cost, range, start, budget, Options opts = {})` — so the Tier-1 golden
  call sites (test/unit/test_direct_optimizer.cpp) compile and behave unchanged; the
  default must reproduce today's epsilon=0 / L2 size-measure / center-sampling behavior
  bit-identically (R13, synthesis item 5's own requirement). Flow:
  launch.direct_options → manager member → RunDirectStage → DirectOptimizer. Angle 01 owns
  the struct's *contents*; this session owns where it lives and how it flows.
  [Source: include/domain/direct_optimizer.h; .panoptes/jtml-research-horizons/synthesis.org item 5]
- Confidence: high (mechanics), medium (future defaults — 01 owns them).
- Backend selection: deliberately NO RunBackend enum on the spec today. The run-level
  backend is already the driver — injected per run, and the fake driver in the lifecycle
  test is proof it is swappable (test/lifecycle/optimizer_run_controller_test.cpp:51+).
  The stage-level backend is the future StageKind switch inside the runner. An enum with
  one value is exactly the speculative abstraction the stance rejects; the extension

  docs/solutions/conventions/jtml-shared-vm-layer-2026-08-11.md item 1]
- Confidence: high. Relevance: keeps the "no new layer / maximal reuse" leanings intact.

** The stage loop stays in Optimize() but becomes script-driven; the injection boundary stays a std::function, its construction factored out (Q2)

- Optimize() (L883-1215) interleaves three kinds of work per frame: session/GPU state
  (seeding from pose storage or previous optimum, non-principal pose updates, CFM frame-
  index, OpenCV dilation restores), the stage script (trunk → branch×N → leaf with per-
  group CFM init/dilate/emit and per-iteration re-seed/range/budget accumulation), and
  signal emission (UpdateDilationBackground, UpdateDisplay, UpdateOptimum, OptimizedFrame).
  Only the middle one is algorithm policy; the other two are the manager's job and stay.
  [Source: src/coordinator/optimizer_manager.cpp:883-1215]
- Confidence: high. Relevance: answers "where does the stage loop move" — it does not
  leave the manager; it becomes data-driven in place. The executor IS Optimize(), and it
  stays the only executor (see non-goals on extraction).
- Script-driven loop shape, preserving today's semantics exactly: `for (const StageSpec& s
  : stage_script_) { CFM init + dilate + emit UpdateDilationBackground; for (i < s.repeat)
  { re-seed from current_optimum_location_; SetSearchRange(s.range); budget_ += s.budget;
  RunDirectStage(s); } CFM destruct; }` with the counters reset before the loop (today's
  trunk preamble: budget_ = trunk_budget, cost_function_calls_ = 0 — i.e., the reset is a
  loop-start property, not a per-kind special case; branch/leaf accumulate by design).
  [Source: src/coordinator/optimizer_manager.cpp:976-1145]
- Confidence: high (relocation claim; equivalence is pinned by parity + oracle, see the
  pin gap below). Relevance: this is Cut B of the migration.
- RunDirectStage (L1225-1296) stays the stage runner. Its injected lambda — set the GPU
  principal-model pose from the denormalized physical point, biplane-convert via
  calibration, call the stage manager's active cost — becomes a named adapter factory
  (working name BuildGpuCostAdapter(principal_model, calibration, stage_manager)) in
  coordinator. Three consumers converge on it: the production runner, the z-profile probe
  (synthesis item 2 explicitly cites the injected-cost boundary at :1225-1246), and
  oracle_test's hand-rolled twin (oracle_test.cpp:286-291, which today re-implements the
  lambda with a comment "exactly as OptimizerManager::RunDirectStage does"). [Source:
  src/coordinator/optimizer_manager.cpp:1225-1296; oracle/oracle_test.cpp:286-291;
  .panoptes/jtml-research-horizons/synthesis.org item 2]
- Confidence: high. Relevance: the "injection boundary becomes" answer — DirectOptimizer's
  CostFunction stays std::function<double(const Point6D&)> with SetCallOffset, Stop, and
  the iteration/improvement callbacks (include/domain/direct_optimizer.h); only the
  construction of the GPU-bound lambda moves into the named adapter.
- Future gradient-polish stage (angle 06): one StageSpec with a new StageKind, its own
  runner branch (gradient optimizer over a DRR/differentiable silhouette cost), its own
  cost adapter, same callbacks, same loop, same driver. No StageRunner interface is built
  now — there is one runner today; the switch statement is the extension point.
  [Source: .panoptes/jtml-research-horizons/synthesis.org item 3 (R15 stage-loop refactor
  go/no-go), item 10 (differentiable refinement as nearest learned-refinement horizon)]
- Confidence: high (design), medium (06's exact runner shape). Relevance: this is the
  "multi-stage oracle + gradient polish plug into the same seam" requirement, satisfied
  with the script + driver, not a plugin architecture.

### Key Findings

#### R2-1 — Cut E's deferral gate made falsifiable: one named perturbation, three named gates, decided by the oracle's perturbation suite

- The gate is now a decision procedure, not a vibe. The multi-stage oracle (angle 03) gains a perturbation arm: inject a wrong-stage dilation emit into the production stage loop — the branch group dilates its comparison image with `trunk_dilation_val_` instead of `branch_dilation_val_` at the branch transition (optimizer_manager.cpp:1040-1058), or equivalently swap the branch/leaf group order in the script. The trigger fires iff ALL of the driver-seam-observable gates stay green: (a) per-frame IoU ≥ 0.85, (b) costCalls() landing on 20k/25k/30k/35k (the stage-bookkeeping gate), (c) qml_parity IoU unchanged. If any gate trips → the seam is sufficient at stage granularity → Cut E stays deferred and the trip is recorded as checked-coverage evidence (angle 03's oracle-of-the-oracle). If none trips → the driver seam is demonstrated insufficient for the measurement mission → StageKind dispatch + headless executor are sanctioned, and the multi-stage oracle moves to the headless executor.
- Why the failing class is exactly the emission/dilation class — structural, source-verified: the controller's observation channel is entirely counter-derived. `stageText()` = `StageLabel(ProgressBudgets, calls)` is a pure function of the cumulative call count (optimizer_run_controller_core.h:159-165,189-192); `UpdateDisplay(double,int,double,unsigned int)` (optimizer_manager.h) carries ms/calls/minimum/model-index but NO stage identity; the OptimizerRunDriver interface (include/coordinator/optimizer_run_driver.h) exposes Manager/ThreadActive/Initialize/Start/Stop/Wait and nothing mid-run. A wrong-dilation emit changes no counter, no pose value that the 0.85-vs-0.9936 band can see, and no relay payload. Cost-budget breaks, by contrast, ARE caught (costCalls on caps) — they are the perturbation suite's negative control, proving the seam can see the counter class and is blind specifically to the emission class.
- Why the wrong dilation plausibly passes (the hypothesis the suite must measure): branch dilation (4 or 3 per contradiction 1) is ≤ trunk (6), so the branch's dilated comparison image is a strict subset of the trunk's — the dilated-overlap family is near-flat in z and wide in-plane (angle 03's magnification arithmetic), so the recovered optimum and its IoU are nearly unchanged; the flat-3000 oracle never even reaches branch/leaf today, so no existing pin covers this class (Round 1's recorded R13 gap, now given a concrete instrument).
- Explicit non-triggers (the negatives matter as much as the positive): the z-profile probe does NOT demonstrate insufficiency — after Cut D it consumes BuildGpuCostAdapter directly in its own test process, never through the driver seam; and the stage-bookkeeping gate's existence means the oracle already covers the budget class through the seam. Only the emission/dilation perturbation can fire the trigger.
