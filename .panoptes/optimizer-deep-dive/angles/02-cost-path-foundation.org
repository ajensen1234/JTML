The dilation contradiction resolves to code = 6/4/1 (settings_control.cpp:1201-1206 sets branch=4, leaf=1; settings_constants.h 6/−2/1; the 6/3/1 claim lives only in golden_oracle.org prose + baseline.json and is never exercised by the oracle's flat trunk-only budget). * Key Findings

** Bug 1 — DD_NEW_POLE_CONSTRAINT.cpp:134: uninitialized min_dist (UB read)

- Failure mode: `double min_dist;` is declared uninitialized; the accumulation is +=-only inside `if (x_tran/y_tran/z_tran)` guards; the value is unconditionally read at `return metric_score + min_dist;` (line 159). The registry defaults for all three flags are false (CostFunctionManager.cpp listCostFunctions: X_TRANS/Y_TRANS/Z_TRANS false), so the += never executes and the return reads a fully-indeterminate double — UB ([basic.indet]). In practice the stack residue can be a signalling NaN → cost NaN → DIRECT's comparisons all false → optimizer misbehaves silently. Even with a flag true, += starts from garbage.
- Pin (Tier-0 pure, via extraction): extract the accumulation into a pure helper `double PolePenalty(x_dist, y_dist, z_dist, bool x_t, bool y_t, bool z_t, double weight)` that initializes `min_dist = 0.0` and sums only enabled axes. Spec test: `REQUIRE(PolePenalty(1.0,2.0,3.0,false,false,false,75.0) == 0.0)` (no flags → exactly 0 contribution) and `REQUIRE(PolePenalty(1,2,3,true,false,false,75) == 75.0)`. Today the code has no such pure surface and the cost returns `metric + garbage`, so the spec test fails by construction against the current implementation (cannot link a correct helper, and the Tier-2 variant below observes the garbage).
- Pin (Tier-2 GPU-labeled, fails today): at any fixed pose with PoleWeight=0 and all flags false, `costFunctionDD_NEW_POLE_CONSTRAINT()` must equal `white_sum_A + FastImplantDilationMetric(...)` (the chamfer-only term, computable directly in the test via GPUMetrics). Today the return additionally carries whatever the uninitialized stack slot held. [Source: src/compute/DD_NEW_POLE_CONSTRAINT.cpp:134-159]
- Fix: `double min_dist = 0.0;` (line 134).
- Oracle impact: none — DIRECT_DILATION never calls this function. Confidence: high.

** Bug 2 — DD_NEW_POLE_CONSTRAINT.cpp:117-120: Y_dist ≡ X_dist, Y_TRANS a no-op

- Failure mode: the Y-axis projection reuses the X-axis vector: `y_delX = s_x * Δx; y_delY = s_y * Δy; y_delZ = s_z * Δz;` with Δ = np−p (lines 117-119), byte-identical to the X_dist block (112-115). The Y axis of the non-principal frame is r = R·{0,1,0} = (r_x, r_y, r_z), computed at lines 93-95 and used only for alpha. Consequence: Y_TRANS toggles a duplicate of the X_TRANS term; the y-axis separation between femur and tibia is never penalized. If a user enables Y_TRANS expecting a y constraint, they silently get a double-counted x constraint.
- Pin (Tier-0 pure): with identity rotation (all angles 0): r=(0,1,0), s=(1,0,0), a=(0,0,1); pure y-offset Δ=(0,5,0) gives X_dist=|s·Δ|=0, correct Y_dist=|r·Δ|=5, buggy Y_dist=|s·Δ|=0. Spec test on the extracted PolePenalty: `REQUIRE(PolePenalty(0, 5, 0, false, true, false, 1.0) == 5.0)`. Additionally a pure characterization on the vectors: for any pose where the s and r axes differ, `Y_dist != X_dist` must hold — today they are equal by construction. Tier-2 behavioral pin: at a pose offset purely in the non-principal y direction, toggling Y_TRANS must change the cost by `pole_weight * |r·Δ|`; today it changes nothing (Δ⊥s ⇒ X_dist=0) — fails today. Note the Tier-2 variant must run after Bug 1's fix (else min_dist garbage contaminates the delta).
- Fix: line 117-119 use r_x/r_y/r_z: `double y_delX = r_x * (np.x_location_ - p.x_location_);` etc.
- Oracle impact: none. Confidence: high.

** Bug 3 — CostFunctionManager.cpp:46-48: always-true stage guard collapses every stage to Trunk

- Failure mode: `if (stage_ != Stage::Trunk || stage_ != Stage::Branch || stage_ != Stage::Leaf) stage_ = Stage::Trunk;` is a tautology — no value can equal all three enum members, so the condition is always true and `stage_` is forced to Trunk after any constructor call (the Branch/Leaf constructors at settings_control.cpp:1198-1199 and any future stage-conditional logic). Live consequence today: DIRECT_DILATION_T1 (the only stage_ consumer, DIRECT_DILATION_T1.cpp:64,89) always takes its "trunk" branch and dilates the render to 1 px — its branch/leaf behavior is unreachable. DIRECT_DILATION (the oracle's cost) never reads stage_, so the oracle is unaffected.
- Pin (Tier-0, requires one test-support addition): `CostFunctionManager(Stage)` performs no GPU work in the constructor (only listCostFunctions + pointer-null init, CostFunctionManager.cpp:22-53), so a headless test can construct it and assert the stage is preserved — but `stage_` is private with no accessor (CostFunctionManager.h:147). Add `Stage getStage() const` (pure, behavior-neutral) and pin: `REQUIRE(CostFunctionManager(Stage::Branch).getStage() == Stage::Branch); REQUIRE(CostFunctionManager(Stage::Leaf).getStage() == Stage::Leaf);` — fails today (both return Trunk). Caveat: the test target must compile CostFunctionManager.cpp, which pulls CUDA headers (gpu_metrics.cuh); that is a compile-time CUDA dependency, not a runtime-GPU one — a deliberate, flagged relaxation of the "CUDA-free" headless convention for this one target (or gate the target behind JTML_BUILD_TESTS as usual, since the project already requires the CUDA toolkit to build).
- Fix: `||` → `&&` on line 46 (intent: force Trunk only for invalid values; with a 3-value enum the guard is then dead but harmless — or delete it).
- Oracle impact: none. Confidence: high.

** Bug 5 — distance_map_metric.cu:27: wrong grid→pixel index formula (LIVE in the oracle)

- Failure mode: `int i = (blockIdx.y + gridDim.x + blockIdx.x) * blockDim.x + threadIdx.x;` — the block row must multiply, not add: correct is `(blockIdx.y * gridDim.x + blockIdx.x)`. Concrete failure for a 64×64 crop with threads_per_block=256 (16×16 blocks, gridDim=(4,4)): correct block (bx,by) covers crop rows by*4..by*4+3; the buggy formula maps block (0,0) to i∈[1024,1280) ⇒ rows 16-19 instead of 0-3, block (0,1) to rows 20-23, block (1,0) ALSO to rows 20-23 — crop rows 0-15 are never visited and rows 20-23 are visited by two blocks. The only guard is `orig_loc < width*height` (line 38), so reads stay in-image but at wrong offsets (and for crops smaller than 256·gridDim rows the mapping leaves the crop entirely). Both atomicAdd counters (edge_pixel_count, distance_map_score) therefore accumulate at wrong pixels: the metric `score/(count+0.1)` is deterministic but wrong. Because DIRECT_DILATION calls DistanceMapMetric every evaluation (DIRECT_DILATION.cpp:80), the oracle's cost landscape — and hence the IoU 0.9936 measurement — includes this corruption. This is the single bug that directly undermines the baseline.
- Pin (Tier-0 pure): extract the mapping into a pure function `int CropIndexToGlobal(int blockIdxY, int gridDimX, int blockIdxX, int blockDimX, int threadIdxX)` and pin full-coverage invariants over a 64×64 crop (gridDim=(4,4), 256 threads): every crop pixel visited exactly once, none outside [0, cw*ch). The correct formula satisfies; the buggy one fails (enumerate both in the test; the failing assertion documents the bug, the passing one pins the fix). Also a Tier-2 GPU-labeled differential: DistanceMapMetric vs the CPU reference on a small synthetic image with a known edge pattern must agree; today they disagree wherever blockIdx.y > 0.
- Fix: line 27 → `int i = (blockIdx.y * gridDim.x + blockIdx.x) * blockDim.x + threadIdx.x;` (this matches the pattern already correct in every other metric kernel, e.g. iou.cu:37, l_1_1_matrix_diff_norm.cu:24, fast_implant_dilation_metric.cu:129).
- Oracle impact: HIGH — changes the distance-map term of every oracle cost evaluation; expect the recovered pose / IoU / L1 / the 6.31 mm z gap to move. Must be followed by an oracle re-run and a baseline.json re-baseline (measured IoU 0.9936, per-px L1 0.0207 are informational, gate is IoU > 0.85). Confidence: high.

** Bug 6 — implant_mahfouz_metric.cu:324/446 pointer guard + :93/122 double→int truncation

- Failure mode (guard): `if (pixel_score_ != 0) intensity_score = intensity_score / static_cast<double>(pixel_score_[0]);` (324) and the same at 446 for contour_score — `pixel_score_` is host-pinned memory allocated once in the GPUMetrics constructor (gpu_metrics.cu ctor cudaHostAlloc), so the pointer is never null and the guard always passes; when the denominator kernel counts zero pixels (e.g. an extreme pose with an empty silhouette crop during DIRECT exploration), the division is by 0 → ±inf/NaN cost. The intent was a value check `pixel_score_[0] != 0`.
- Failure mode (truncation): `atomicAdd(&result[0], 2.55 * pixel)` at 93 (EdgeMahfouzNumerator) and 122 (EdgeMahfouzDenominator) — `result` is `int*`, and atomicAdd(int*, int) converts the double 2.55·pixel to int with truncation toward zero (per-pixel error up to 2.55). Both the contour numerator and denominator are quantized, biasing the ratio; the intensity branch (line 153) is integer-valued already, so it is unaffected. The host then multiplies the contour numerator by 255.0 (line ~420) while the kernels' internal scale is 2.55 — a scale inconsistency that should be pinned as current spec (kernel-as-spec) and reconciled against the Mahfouz 2003 paper before "fixing".
- Pins: Tier-0 CPU reference replicates both accumulation semantics on small synthetic images — (a) the intended float/double accumulation of 2.55·pixel vs (b) the actual int-truncated accumulation, asserting they differ (documents the quantization as current behavior); Tier-2 GPU-labeled: with a rendered image whose bbox crop contains no qualifying pixels (denominator 0), `ImplantMahfouzMetric` must return a finite value (guard works) — today it can return ±inf.
- Fix: `if (pixel_score_[0] != 0)` at 324 and 446 (unambiguous bug). Truncation: default to keep-and-pin (kernel-as-spec) unless the Mahfouz paper dictates float accumulation, in which case switch the accumulators to float/double and the CPU reference becomes the spec test. Also note the final combination `contour_score * (-2.67) + intensity_score * (-1)` (line ~465) is an unnormalized weighted sum — pin as-is.
- Oracle impact: none (DIRECT_MAHFOUZ is not the oracle's cost; DIRECT_MAHFOUZ.cpp:38,50 are its only consumers). Confidence: high.

- Pin: trivial characterization — `CurvatureHeatmapMetric` returns exactly 0.0 for any input (passes today; documents the stub). ** Metric-math CPU-reference test inventory (Tier-0, headless; feeds 03's harness)

Where the math is ambiguous the CURRENT KERNEL CODE is the spec; the CPU references below encode that spec so future kernel changes are diffable. File targets: new test/unit/test_metric_semantics.cpp (+ hegel twin test_metric_semantics_properties.cpp) registered as explicit .cpp-list targets in test/CMakeLists.txt (jtml_test_metric_semantics / jtml_test_metric_semantics_props, headless label, mirroring the house pattern at test/CMakeLists.txt:239-276). The GPU-vs-CPU differential comparisons belong to 03's harness (oracle label); the Tier-0 files define the reference values it compares against.

- Chamfer — FastImplantDilationMetric (src/compute/fast_implant_dilation_metric.cu): semantics to pin: (a) edge detection = 8-neighbor boundary of WHITE(255) against BLACK(0) → EDGE(100), interior/exterior untouched; (b) dilation = for each EDGE pixel, offsets (±j, ±k) with j,k ∈ [1, dilation] write DILATED(99) only over WHITE/BLACK pixels — EDGE and already-DILATED pixels are never overwritten, and the axial cross (j=0 or k=0) is never dilated (quadrant-only morphology — spec quirk, verified in DilateKernel lines 83-118); (c) difference = +1 per dilated/edge pixel where comparison==WHITE(255), −1 otherwise (lines 120-145); (d) return −1·score; (e) cost composition = comparison_white_sum + chamfer ⇒ 0 at perfect overlap; (f) NO normalization — the chamfer term is absolute pixel counts, so its weight scales with silhouette size (relevant for the z-sensitivity analysis: this is the only z-sensitive term per the synthesis). Pin each stage as a pure function over small uchar images (32×32, 64×64) plus the composed minimum-at-match property.
- Distance map — DistanceMapMetric (src/compute/distance_map_metric.cu): semantics to pin: sum of distance_map values at pixels where projected_image == EDGE(100) within the bbox±dilation crop, divided by (count + 0.1) (the +0.1 singularity hack distorts low-count cases — pin it as spec, flag for review); the crop grid mapping must use the CORRECTED index formula (Bug 5); and the composition quirk: the input buffer arrives already mutated by FastImplantDilationMetric (edge/dilated values in place), so only the surviving EDGE(100) ring is sampled — DILATED(99) pixels are not counted (kernel line 34: `projected_image[orig_loc] == EDGE_PIXEL`).
- Mahfouz ratios — ImplantMahfouzMetric (src/compute/implant_mahfouz_metric.cu): intensity ratio = Σ(comparison-white-silhouette intensity · rendered-white) / Σ(rendered-white) (kernels 129-155, guard bug at 324); contour ratio with the 2.55·pixel int-truncation (93/122) and the host's 255.0 scale + final −2.67·contour − intensity (line ~465). Pin both the intended float math and the actual truncated math; assert they differ; document the scale chain.
- IoU — IOU (src/compute/iou.cu): intersection/union over the UNION of the two bounding boxes, pixel-nonzero criterion (A>0 || B>0), not ==255; IoU(A,A)=1 for non-empty A; region-restricted (pixels outside both bboxes excluded). Trivial CPU reference; PBT properties: range [0,1], symmetry, reflexivity.
- L1 — L_1_1_MatrixDifferenceNorm (src/compute/l_1_1_matrix_diff_norm.cu): Σ|A−B| over the union-bbox crop (NOT the full frame); PBT properties: symmetry, L1(A,A)=0, non-negativity.
- ComputeSumWhitePixels (src/compute/gpu_metrics.cu:134): count of pixels == WHITE(255).
- PBT invariants for the hegel twin: IoU ∈ [0,1]; IoU(A,B)=IoU(B,A); IoU(A,A)=1; L1(A,B)=L1(B,A); L1(A,A)=0; chamfer(A,A)=0 after adding the comparison white sum; distance-map score ≥ 0; Mahfouz ratios ≥ 0. Use small synthetic uchar images (sampled 16×16 / 32×32), mirroring the typed round-trip PBT style in test_cost_function_properties.cpp.

** Backface divergence — reconciliation with evidence

- Production: monoplane OptimizerManager constructs GPUModel with use_backface_culling=true (optimizer_manager.cpp:716,721 — 6th constructor arg true); biplane true/true (765,788). Oracle/parity paths all use false: oracle_test.cpp:207, qml_parity_check.cpp:238, segmentation_oracle_test.cpp:173, MlBridge.cpp:336.
- Label generator: Study2Grid uses false with the in-source comment "BACKFACE CULLING APPEARS TO BE GIVING ERRORS" (src/app/Study2Grid/main.cpp:263-277).
- Renderer mechanics: there is no z-buffer — backface triangles get zero rasterization size (BoundingBoxSizesKernel skips dev_backface[i]==true, render_engine.cu:534-566) and the fill is a point-in-triangle shade (FillTriangleKernel, render_engine.cu:616+). So culling OFF paints front AND back faces; for a closed manifold viewed from outside the outlines coincide (back faces project inside the front outline), but for concave/self-occluding geometry (femoral condyle undercuts) or an OPEN segmentation-derived STL, culling ON can drop visible pixels and change the silhouette boundary.
- Which is correct for the appearance oracle: OFF, and it is load-bearing. The labels were generated with OFF (Study2Grid), and the oracle's frame↔label correspondence is pinned EMPIRICALLY by start-pose render IoU == 1.0 (oracle_test.cpp diagnostic + golden_oracle.org/baseline.json) — that correspondence only holds under the same OFF convention. Switching the oracle to ON would change the rendered silhouette where the STL is open/concave and break the gate against OFF-generated labels. The measured 0.9936 is an OFF-vs-OFF number and is self-consistent.
- For production (ON): defensible for a closed opaque implant fitting real x-rays, but it renders a different silhouette convention than the labels. Recommended evidence before deciding: (a) headless STL manifoldness check on KR_right_7_fem.stl (count boundary edges: closed ⇒ 0), (b) GPU-labeled ON-vs-OFF silhouette IoU at the golden pose: ≈1.0 ⇒ the divergence is immaterial for this model and production ON can stay; measurably < 1 ⇒ production and the oracle render different silhouettes and the two paths must be reconciled deliberately (either both OFF to match the label convention, or regenerate labels under ON). My recommendation: keep the oracle OFF (pinned), run the two evidence checks, and only then touch production. Confidence: high on "oracle must stay OFF"; medium on the production-correct answer until the checks run.

** NaN/Inf emission audit — DIRECT_DILATION cannot emit NaN; GLh's trigger lives in three other variants

- The oracle cost composition is `white_sum_A + FastImplantDilationMetric + DistanceMapMetric` (src/compute/DIRECT_DILATION.cpp:72-99). Every intermediate is an int: `ComputeSumWhitePixels` returns an int count (gpu_metrics.cu:134-170), the chamfer is `-1 * pixel_score_[0]` (int, fast_implant_dilation_metric.cu:289-290), and the distance map is `distance_map_score_[0] / (edge_pixels_count_[0] + 0.1)` (distance_map_metric.cu:125-126) with a numerator that is a sum of uchar values (0-255) and a denominator ≥ 0.1 (the count is atomicAdd-only, non-negative). No float division, no sqrt, no asin, no uninitialized read in this path. Maximum possible accumulation 255·1024² ≈ 2.55e8 ≪ 2³¹, so int overflow is unreachable. **Verdict: the DIRECT_DILATION return value is a finite double for every pose, including empty silhouettes, degenerate projections, and behind-camera poses.** Confidence: high.
- The DIRECT-GLh NaN trigger therefore resolves to three other variants, all production-reachable: (1) DIRECT_MAHFOUZ — `if (pixel_score_ != 0)` tests the pinned pointer, never the value (implant_mahfouz_metric.cu:324, 446); with `pixel_score_[0] == 0` (empty rendered silhouette or no qualifying edge pixels) the division `intensity_score / 0` and `contour_score / 0` yield 0/0 = NaN (DIRECT_MAHFOUZ is selectable in production and forces dilation to 3, optimizer_manager.cpp:252-253/270-271/288-289); (2) DD_NEW_POLE_CONSTRAINT — the UB `min_dist` read (round-1 Bug 1) can surface a NaN payload from stack residue; (3) sym_trap — `float vv = asin(fem2tib[2][1])` (sym_trap_function.cpp:129) is NaN for any |entry| > 1, reachable through FP rounding of the rotation product even with an orthonormal R; the α/β denominators are provably 1.0 (r·r = s·s = 1 for 312 rotations), so no division risk there. Confidence: high (structural), except the DD UB payload which is compiler-dependent (medium).
- **Correction to angle 01/synthesis "NaN poisons hull slope comparisons"**: the data storage sorts each size-column by value descending with the true minimum at the back, and `ConvexHull` reads only the back (GetMinimumHyperboxValue returns `minimum_value_columns_[col_id]` = the back, direct_data_storage.cpp:107/165/184-190; HyperBoxLessThanValue sorts descending so push_back appends the new minimum). A NaN box fails every comparison and is inserted at the column FRONT, where it is never selected, never popped by DeleteHyperBoxes (which pops the back), and never read by the hull. The actual NaN behavior is: (a) `result < current_optimum_value_` is false, so a NaN eval never updates the optimum (direct_optimizer.cpp:210-213); (b) the NaN box accumulates as dead weight in its size-column; (c) the column minimum only becomes NaN after ALL finite boxes in that column have been trisected away — a delayed, conditional poisoning, not immediate hull corruption. The finite-check design below should be motivated by (a)+(b) (lost evals, unbounded dead-weight growth) rather than the round-1 "silent hull-slope corruption" claim. Confidence: high on the storage mechanics (read verbatim), medium on the exact runtime effect (needs the Tier-0 probe to observe).
- **Where the finite-check wraps**: `DirectOptimizer::EvaluateCostFunction` (src/domain/direct_optimizer.cpp:203-213, the `double result = cost_(denormalized_point);` at :205) is the single chokepoint shared by production (`RunDirectStage` constructs DirectOptimizer with the injected lambda, optimizer_manager.cpp:1234-1248), the oracle (oracle_test.cpp:286-291), and the coordinator (OptimizeWorker, optimize_coordinator.cpp:12-17).
