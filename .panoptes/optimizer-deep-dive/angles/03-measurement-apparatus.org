#+DATE: 2026-08-12

* Summary

The measurement doctrine is already written into plan 006: *no algorithm deltas before the measurement apparatus exists* — the current oracle (test/oracle/oracle_test.cpp: 3 Kneel_1 frames, trunk-only, flat budget 3000, backface OFF, IoU ≥ 0.85) cannot see the z-weak axis, and DIRECT numeric convergence is too noisy for raw-pose gates (docs/plans/2026-08-11-006-refactor-shared-vm-layer-extraction-plan.md "Follow-On Optimization Phase"). This angle specs the apparatus in four instruments that reuse existing seams rather than new infrastructure: (1) a headless Tier-0 CPU metric reference (the per-metric semantics that 02 pins, consumed as test-only math); (2) a manifest-driven Tier-2 GPU ablation runner over the 7 registered cost variants × budget shapes × dilation schedules, writing test/golden/ablation.json; (3) a z-profile probe that sweeps z_trans through the RunDirectStage injected-cost lambda (optimizer_manager.cpp:1225+) — the cheapest instrument that can see the z-weak axis; (4) a production-shaped multi-stage oracle (20k→25k→30k→35k cumulative, per-stage dilation, tibia-after-femur, sym_trap) driven through the plan-006 OptimizerRunDriver seam with appearance-only gates (per-frame IoU ≥ 0.85, per-px L1 and z recorded against baseline.json bands), plus a CI shape (new gpu label, self-hosted RTX 3090 runner, data-profile-reduced per-PR budget) that leaves the headless suite untouched.

* Key Findings

** The ablation runner is a two-tier split: a headless CPU metric reference (Tier-0) and a GPU per-variant scorer (Tier-2), joined by a manifest — never hand-written per-variant tests
- Tier-0 (headless, CI, CPU): reference implementations of the metric semantics — overlap count + comparison-white-sum normalization (FastImplantDilationMetric), mean-chamfer on the L1 distance map (DistanceMapMetric), IoU, L1,1, Mahfouz intensity ratio — on synthetic binary images, in test/unit/. The headless Frame twin already provides edge/dilation/distance-map via pure OpenCV (test/unit/frame_headless.cpp implements Canny/dilate/invert/distanceTransform against the same include/compute/frame.h), so every input the metrics consume is producible CPU-side. The metric contracts are documented in include/compute/gpu_metrics.cuh (IOU = intersection/union of white spaces; L_1_1 = summed abs diff; FastImplantDilationMetric = overlap normalized by the comparison white-pixel sum). These are test-only reference implementations (R13: no production edits); 02-cost-path-foundation owns the per-metric semantics tests and this tier consumes them.
- Tier-2 (GPU, gpu label): run each variant on Kneel_1 (3 frames) under the production budget shape with the oracle's appearance gate (silhouette IoU ≥ 0.85 vs Labels/fem — independent of all cost math; the R2 guardrail "never validate a metric by its own optimum"). Record recovered pose per axis, IoU, per-px L1, z-gap vs fem.jts, and cost-call count into ablation.json. The compute-only shape (DirectOptimizer bound to the real GPU cost, exactly oracle_test.cpp's BuildFramePipeline + cost lambda pattern) is the Tier-2 workhorse; the app-wiring shape is the multi-stage oracle below.
- Per-variant configuration surface (the matrix the manifest must encode): variant name ∈ the 7 registered costs (CostFunctionManager::listCostFunctions: sym_trap_function, DD_NEW_POLE_CONSTRAINT, DIRECT_DILATION_POLE_CONSTRAINT, DIRECT_DILATION_SAME_Z, DIRECT_DILATION_T1, DIRECT_DILATION, DIRECT_MAHFOUZ — src/compute/CostFunctionManager.cpp:344-423); per-stage budget shape (production 20000/5000/5000/5000 cumulative 20k→25k→30k→35k, reduced data-profile shape, flat 3000 oracle shape — baseline.json budget_per_stage/budget_cumulative_effective); per-stage dilation schedule (6/3/1 per golden_oracle.org prose vs 6/4/1 per TRUNK_DILATION 6 + BRANCH_DILATION_DECREASE 2 + Z_SEARCH_DILATION 1 in include/domain/settings_constants.h — the contradiction is itself an ablation axis; each variant's own registered Dilation int param per src/compute/CostFunctionManager.cpp); ranges (trunk ±35, branch (15,15,25,25,25,25), leaf (3,3,15,3,3,3) — settings_constants.h); backface ON (production) vs OFF (oracle/label-generator); frame set {0,1,2}.
- Cost profile that makes this tractable: the flat-3000 oracle run takes "a few minutes" on the RTX 3090 (qml_parity_check.cpp kRunTimeoutMs = 30 min watchdog) ⇒ roughly 20–60 evals/s ⇒ the 35k production shape is ~10–30 min/frame, and the full matrix (7 variants × 3 frames × production shape) is hours — which is why the manifest is required (selectable subsets), a reduced shape is CI-default, and the full shape is nightly. [Source: repo — test/oracle/oracle_test.cpp, test/oracle/qml_parity_check.cpp:124-126, test/golden/baseline.json, src/compute/CostFunctionManager.cpp:344-423, test/unit/frame_headless.cpp, include/compute/gpu_metrics.cuh]
- Confidence: high (repo-internal, source-verified)
- Relevance to this project: this is the missing decision tool — the 7 registered variants have never been compared head-to-head (test/unit/test_cost_function.cpp covers only the parameter registry), and every algorithm claim in the run's papers (DIRECT-GLh hidden constraints, refinement control) needs this harness before it can be judged.

** The multi-stage oracle drives the REAL Optimize() stage loop through the OptimizerRunDriver seam — OptimizerRunLaunch is the payload, the controller relays are the observation channel, and the gates stay appearance-based
- The seam is ready and green: include/coordinator/optimizer_run_driver.h defines OptimizerRunLaunch (calibration, camera_a/b frames, models, selected_model_indexes, primary_model_index, pose_matrix LocationStorage, OptimizerSettings, the three CostFunctionManagers by value, directive, iter_count) and the OptimizerRunDriver interface (Manager/ThreadActive/Initialize/Start/Stop/Wait) with the production adapter CreateOptimizerManagerRunDriver wrapping OptimizerManager untouched (src/coordinator/optimizer_run_driver.cpp: a fresh manager + QThread per run, finished-before-Initialize bind, H3 destructor contract). OptimizerRunController::start() drives the sequence (save-last-pose mirror → gate → seed → driver → 8 binds → Initialize → thread start) and re-emits by-value relays on the controller thread; the core exposes the oracle seam's observation channel directly: costCalls(), stageText(), progress() (optimizer_run_controller_core.h:154-165, "calls vs cumulative budget — the oracle seam, M12").
- What the oracle must therefore do: construct OptimizerRunRequest{ directive, save-last-pose mirror args, gate inputs, LocationStorage seeded from fem.jts frame 0, launch{ production OptimizerSettings, three CFMs with DIRECT_DILATION + per-stage dilation params, frames built at Canny 3/0/150 + dilation 6, models = femur (primary) + tibia (non-principal) } }, call start(), wait for runState == Completed, then run the appearance comparator (GPUModel backface OFF + GPUMetrics::IOU vs the vertically-flipped label TIFF — the exact oracle mechanics) at the pose relayed by optimizedFrameRelayed. The real stage loop runs unmodified inside OptimizerManager::Optimize(): trunk budget 20000 → 2×branch 5000 each (budget_ accumulates 25k/30k) → leaf 5000 (35k), each stage a fresh DirectOptimizer with SetCallOffset(cost_function_calls_) so the loop guard is cumulative (optimizer_manager.cpp:1031, 1087-1093, 1142-1146; DirectOptimizer::SetCallOffset in include/domain/direct_optimizer.h), per-stage re-dilate of the comparison image to the stage's dilation value, and per-stage CFM Initialize/Destruct.
- The gates (per baseline.json tolerances): (a) HARD — per-frame silhouette IoU ≥ 0.85 vs the empirically pinned label (baseline.json silhouette_iou_threshold; measured 0.9936 — the IoU gate stays the appearance arbiter, never raw pose); (b) BANDED-RECORD — per-px L1 vs the baseline 0.021 informational threshold (measured 0.0207; promote to a banded assert only after the cross-GPU noise floor is calibrated — prior-run angle 06 finding, https://www.forasoft.com/learn/video-quality/articles-vqm/regression-testing-golden-references); (c) BANDED-INFORMATIONAL — z-gap vs baseline.json pose_per_axis_informational z_tran = 15.0 (observed 6.31) — recorded per frame into ablation.json and asserted only inside the band, because DIRECT z convergence is noisy by design; (d) STAGE-BOOKKEEPING — the controller's costCalls() at each stage transition must land on the cumulative caps 20k/25k/30k/35k (± the seed eval), and per-stage CFM Dilation parameters must match the manifest — this is the regression the flat-3000 oracle is blind to (a SetCallOffset or dilation-scheduling regression passes today).
- Tibia-after-femur + sym_trap: the production workflow is sequential runs — femur as primary (tibia pinned non-principal from tib.jts via LocationStorage, which Optimize() reads for the pole/sym_trap costs at optimizer_manager.cpp:937-947), then tibia as primary with the femur pose fixed at the recovered value. The QML bridge's SingleModelOnly pre-check would reject the two-model launch, so the oracle drives OptimizerRunController directly (the widgets' full surface), not the bridge stack — qml_parity_check.cpp remains the proven harness template for the single-model case. The Sym_Trap string directive (optimizer_manager.cpp:177-185 → CalculateSymTrap) is NOT in the controller's typed Directive enum (Single/All/Each/From/… — optimizer_run_controller_core.h:58-62), so the tibia-ambiguity pass needs a small seam addition (a typed Directive::SymTrap mapped to the manager string) — the one concrete seam gap this spec found.
- Confidence: high (repo-internal, source-verified; the seam behavior is pinned by the green jtml.optimizer_run_controller lifecycle suite per the plan-006 record)
- Relevance: this is synthesis roadmap item 3 (production-shaped multi-stage oracle) — the highest-leverage expansion, and the acceptance test for any future shared-stage-loop refactor (plan 006 explicitly shapes the run controller as its future seam: "the multi-stage oracle consumes the OptimizerRunDriver seam from U5").

** The z-profile probe reuses the RunDirectStage injected-cost boundary — sweep z_trans with all other axes pinned at fem.jts truth and read the cost curve; it is the cheapest instrument that sees the z-weak axis
- The entry point is optimizer_manager.cpp:1225+ — RunDirectStage's injected lambda takes the denormalized physical Point6D, sets the GPU model pose (primary + biplane secondary via calibration convert), and scores stage_manager.callActiveCostFunction(). The probe replicates exactly that lambda body (or, for the driver-seam variant, drives a controller run with leaf-like settings), looping Δz ∈ {-15,-14,…,+15} mm around the fem.jts z at fixed truth for the other 5 axes, recording cost(Δz) per variant per dilation level.
- Why it exposes the z-weak-axis signal directly: the dilated-overlap family is nearly flat in z because a z shift is pure magnification — at ~1.1 m source distance a ±15 mm shift changes scale by <1%, inside the 6 px dilation tolerance — so the probe's diagnostic is the normalized depth of the cost valley: valley_depth = (max_{Δz} cost − cost(0)) / (max − min over the sweep). A healthy z signal shows a deep, centered valley; a z-blind metric shows a flat curve (or worse, an off-center one). Per-variant ranking (chamfer-heavy DIRECT_DILATION ≥ Mahfouz ≥ pure overlap) is exactly what this instrument measures — prior-run angle 01 hypothesis (repo .panoptes/jtml-research-horizons/angles/01-cost-function-landscape.org, the magnification arithmetic derived from baseline.json z_tran ≈ -1022.93 and pitch 0.373).
- Cost: 31 cost calls per (variant, dilation, frame) ≈ 31 renders — milliseconds each at ~20-60 evals/s ⇒ the whole 7-variant × 3-dilation × 3-frame probe is on the order of a couple of minutes on the RTX 3090. It needs no production changes (the boundary already exists) and no new fixtures. As a metamorphic-relation bonus it asserts cheap oracle-quality invariants: cost(0) is the sweep minimum within noise, and valley depth > a noise floor — a variant that fails this is z-blind by measurement, not by argument.
- Headless Tier-0 analog: the CPU metric reference can run the same sweep on synthetic silhouettes scaled by the magnification factor, giving a no-GPU z-sensitivity estimate; the GPU probe remains authoritative because it exercises the real render + metric path (this is 05-compute-perf's boundary: the probe consumes timing, it does not own instrumentation).
- Confidence: high on the probe mechanics (the lambda boundary is source-verified); medium on the per-variant valley-depth ranking until the probe runs (it is a measurement instrument by design, not a claim).
- Relevance: the z-weak axis is the run's load-bearing research problem (prior-run synthesis finding, converged from 5 independent literature sources + the 6.31 mm measured z gap); this probe is the instrument that turns the argument into data and gates every z remedy (SAME_Z weight calibration, chamfer reweighting, leaf refinement).

** ablation.json schema — variant × budget shape × dilation schedule × metric → per-frame IoU / per-px L1 / z-gap, plus the run hash (determinism record)
- Concrete schema (test/golden/ablation.json, sibling of baseline.json):

  {
    "schema_version": 1,
    "runner": {
      "gpu": "RTX 3090", "cuda": "12.4", "timestamp": "...",
      "run_hash": "sha256(variant|budget_shape|dilation_schedule|frames|start_pose_source|backface|edge_config)"
    },
    "variants": [
      {
        "name": "DIRECT_DILATION",
        "cost_path": "src/compute/DIRECT_DILATION.cpp",
        "params": {"Dilation": 6, "Black_Silhouette": null},
        "dilation_schedule": {"trunk": 6, "branch": 3, "leaf": 1},
        "budget_cumulative": [20000, 25000, 30000, 35000],
        "ranges": {"trunk": [35,35,35,35,35,35], "branch": [15,15,25,25,25,25], "leaf": [3,3,15,3,3,3]},
        "backface": false,
        "edge_config": {"canny": [3, 0, 150]},
        "results": [
          {"frame": 0, "recovered_pose": [x,y,z,xa,ya,za],
           "iou": 0.9936, "l1_per_px": 0.0207, "z_gap_mm": 6.31,
           "cost_calls": 35000, "elapsed_s": 1234.0,
           "gate": {"iou_pass": true, "l1_band_pass": true, "z_band_pass": true}}
        ],
        "determinism": {"seeds": [], "note": "no RNG in DIRECT or the int-atomic cost path; run_hash is the determinism twin",
                        "re_runs_identical": true}
      }
    ],
    "z_profiles": [
      {"variant": "DIRECT_DILATION", "dilation": 6, "frame": 0,
       "sweep_mm": [-15,-14,...,15], "costs": [ ... ],
       "valley_depth_norm": 0.42, "argmin_mm": 1.0}
    ]
  }

- Determinism semantics (the seeds column is honest about being empty today): DIRECT is RNG-free (pure convex-hull/trisection bookkeeping — src/domain/direct_optimizer.cpp) and every active cost-path reduction is an int atomicAdd, which is order-independent and therefore value-deterministic run-to-run on a machine (prior-run angle 05 finding; the only float-atomic reduction, render_drr_engine.cu's DRR fill, is not in the DIRECT cost path). So the determinism twin is: same run_hash ⇒ bit-identical output on the same GPU; the runner asserts it by running the flagship variant twice. The seeds array is reserved for future stochastic variants (e.g., multistart) and for cross-GPU noise-floor trials.
- The run_hash (not a seed) is the schema's regression tripwire: any change to variant/budget/dilation/frame-set/start-pose-source/backface/edge-config that forgets to update the manifest changes the hash and fails the diff review.
- Confidence: high (schema is a proposal grounded in the verified repo fields: baseline.json's budget_cumulative_effective/tolerances/measured block is the template; the 7 variants' registered params are source-verified)
- Relevance: ablation.json is the decision record the harness produces — the per-variant z-gap table is what the DIRECT variant switch (01-direct-variants) and the weight calibrations (02) get judged against; it lives next to baseline.json so the golden spec and the ablation data are one directory.

** CI integration — a new gpu ctest label, a self-hosted RTX 3090 runner, a data-profile-reduced per-PR budget shape, and nightly full shape; the headless suite is untouched by construction
- Current state: the headless suite is `ctest -L headless` (pixi.toml test task, --timeout 600) and is the only thing GitHub Actions runs (workflows/cmake.yml); GPU tests carry labels "oracle" (TIMEOUT 3600) and "oracle;render" (TIMEOUT 120) and are never in the default run — the split is already load-bearing. New tests must follow the same registration recipe (repo-root WORKING_DIRECTORY, xcb env for renderers, explicit labels).
- New targets and labels:
  - jtml.metric_reference — Tier-0 CPU metric reference + z-profile Tier-0 analog. LABELS "headless", TIMEOUT 120-300. Zero GPU, zero impact on the existing 46 headless tests beyond a new green target.
  - jtml.z_profile — GPU probe. LABELS "gpu;oracle", TIMEOUT 600 (a couple of minutes of renders). This is the per-PR z-health check.
  - jtml.ablation — manifest-driven runner. LABELS "gpu", TIMEOUT sized to the manifest's budget shape (reduced shape ≤ 30 min per PR; the full production shape is NOT a ctest case — it is a nightly job with a job-level timeout, because 7 variants × 3 frames × 35k evals is hours).
  - jtml.oracle_multistage — the driver-seam multi-stage oracle. LABELS "gpu;oracle", TIMEOUT 3600 for the reduced budget shape (mirrors jtml.oracle's convention); nightly full shape.
- Why the headless suite is untouched: the pixi test task filters `-L headless` only, so any gpu-labeled test is invisible to CI by construction; the new gpu label is additive (existing oracle tests can gain a second label "oracle;gpu" without changing `-L oracle` behavior). GPU tests run `ctest -j1` (one GPU, one runner) — serialization is the runner's job, not ctest's.
- Runner: self-hosted on the lab's existing RTX 3090 box (the U2/U6 machines named in test/CMakeLists.txt), registered with a custom gpu label, runs-on [self-hosted, gpu], nvidia-smi probe on job start; GitHub-hosted GPU runners cost ~$0.052/min (Linux 4-core) so self-hosted is the zero-marginal-cost path (https://docs.github.com/en/billing/reference/actions-runner-pricing, https://latchkey.dev/learn/ci-how-to/build-on-self-hosted-gpu-runner-github-actions). Schedule: per-PR = headless (existing) + jtml.z_profile + reduced-budget jtml.oracle_multistage; nightly = full jtml.oracle_multistage + jtml.ablation (full shape) + render smokes.
- The reduced budget shape must come from a Moré & Wild data-profile measurement, not another ad hoc number: for each candidate cumulative shape, measure the smallest total budget whose recovered pose stays above IoU ≈ 0.98 on Kneel_1, and use that for per-PR CI (https://epubs.siam.org/doi/10.1137/080724083; prior-run angle 06 finding). The existing 3600 s TIMEOUT on jtml.oracle is the smell this replaces: a gate that takes an hour is tolerated, not run.
- Gate-sensitivity companion (oracle-of-the-oracle): the 0.85 IoU gate sits far below the measured 0.9936, so we do not know what regressions trip it; the apparatus includes a perturbation suite on the gpu runner — perturb the start pose by ±1 mm/±1° per DoF and by the documented 6.31 mm z gap, break the dilation schedule, swap the variant — and assert the gate trips (checked-coverage oracle-quality practice, https://www.st.cs.uni-saarland.de/publications/files/schuler-stvr-2013.pdf). This is cheap (a handful of extra runs) and calibrates the gate's sensitivity.
- Confidence: high on the CI mechanics (labels/timeouts/registration verified in test/CMakeLists.txt + pixi.toml + workflows/cmake.yml); medium on the wall-clock estimates (no per-eval timing data for the 35k shape — the 20-60 evals/s figure is derived from the flat-3000 run's "a few minutes").
- Relevance: this closes the last gap in the measurement loop — the instruments exist (Tier-0/ablation/oracle/z-probe) AND they run on a schedule, so the measurement-first doctrine has teeth: a PR that regresses SetCallOffset bookkeeping, dilation scheduling, or z-refinement fails loudly before the algorithm work even starts.

** The z-profile probe and the multi-stage oracle both consume — never re-own — the sibling angles' outputs (non-overlap boundary)
- 02-cost-path-foundation owns the per-metric semantics tests and the 7-bug fixes with pin-first tests; the Tier-0 reference in this angle is the harness those semantics tests plug into (a test-only CPU mirror of the documented GPU metric contracts), and the Tier-2 ablation runs re-verify after 02's fixes land (bug-4's always-Trunk guard means DIRECT_DILATION_T1's paper-style path is currently unreachable — the ablation of the symmetric-vs-asymmetric dilation schedule is gated on that fix).

- Confidence: high (boundaries are the dispatch contract, grounded in the plan-006 recommended sequence: bugs → multi-stage oracle → ablation harness)
- Relevance: prevents three angles from spec'ing the same binary three ways; the driver seam, the injected-cost lambda, and baseline.json remain the single shared vocabulary.

* What Could Not Be Verified

- The effective branch dilation at runtime: settings_constants.h implies 6/4/1 (TRUNK_DILATION 6, BRANCH_DILATION_DECREASE 2 → 4, Z_SEARCH_DILATION 1) while golden_oracle.org prose says 6/3/1; the actual value is read from each CFM's registered int "Dilation" parameter at runtime and could not be verified without a running session. The ablation manifest must treat the schedule as data, not assume either value.
- Whether the tibia golden (tib.jts + Labels/tib present in example_studies/Kneel_1/Labels/tib) passes the same IoU gate — no tibia oracle run is on record; the tibia-after-femur pass of the multi-stage oracle is specified but its thresholds are uncalibrated until the first run.
- The cross-GPU IoU/L1 noise floor — only the RTX 3090 has measured numbers (0.9936 / 0.0207); the per-px L1 banded gate and any IoU threshold retune are deferred until a second GPU is measured.
- Per-eval wall-clock for the production 35k shape — no timing data exists; the 20-60 evals/s and resulting 10-30 min/frame estimates are derived from the flat-3000 run's "a few minutes" and are exactly what 05-compute-perf's instrumentation will replace.
- The per-variant z-sensitivity ranking (chamfer-heavy ≥ Mahfouz ≥ pure overlap) is a hypothesis until the z-profile probe runs; the probe is specified here precisely because the claim was never measured.
- The exact Magnification arithmetic behind the "dilated overlap is flat in z" mechanism (6.31 mm at ~1.1 m source distance → <1% scale) is derived, not measured — the probe measures the true profile directly.
- Whether the Sym_Trap manager string can be driven through OptimizerRunController today: the typed Directive enum (optimizer_run_controller_core.h:58-62) does not include it, so the tibia-ambiguity pass needs a small seam addition; the manager-side path (CalculateSymTrap at optimizer_manager.cpp:1294+) is verified, the controller-side mapping is not.
- The gate-sensitivity of IoU ≥ 0.85 (what size of regression trips it) is unknown until the perturbation suite runs — the 0.85 vs 0.9936 gap makes the gate's checked coverage an open question.

## Round 2 — Executable Specifications (measurement-apparatus)

### Summary

This round turns Round 1's sketches into executable specs from the test-infrastructure seat: (1) the perturbation suite that calibrates the IoU 0.85 gate's checked coverage — a per-variant IoU-vs-Δ transfer-function grid plus targeted regression injections, whose deliverable is the minimal-detectable-regression table per axis; (2) the z-profile probe as a runnable spec — 31-render Δz sweep on the verified RunDirectStage injected-cost lambda (optimizer_manager.cpp:1235-1246), valley-depth metric, and the chamfer-heavy ≥ Mahfouz ≥ pure-overlap ranking mapped onto the verified metric composition of the 7 variants; (3) a Round-1 correction with source proof: the Directive::SymTrap seam addition ALREADY EXISTS in the current tree (optimizer_run_controller_core.h:60-63 → "Sym_Trap" → optimizer_manager.cpp:177-185), so the work is now pins and the tibia-after-femur drive sequence, not a code change; (4) the complete ablation.json field list with the ci/nightly profile split and the additive gpu ctest label design; (5) the cross-GPU noise-floor plan — what the banded L1 gate needs, what an IoU retune looks like, and exactly what the single RTX 3090 can and cannot measure today.

### Key Findings

#### R2-1 — Perturbation suite (oracle-of-the-oracle): two halves, one deliverable — the minimal-detectable-regression table
- What the gate can and cannot see today, from measured numbers: recovered IoU 0.9936 vs gate 0.85 (margin 0.1436, baseline.json measured block); start-pose↔label correspondence pinned empirically at IoU == 1.0 (oracle_test.cpp correspondence procedure, REQUIRE(best_iou > 0.50)); the 6.31 mm z gap passes the gate at 0.9936. So the honest pre-registration expectations, each to be confirmed by the suite: (a) z regressions up to at least the 6.31 mm gap are INVISIBLE to the gate by design (magnification <1% at ~1.1 m SID, inside the dilation-6 absorption radius — Round 1's mechanism, still derived not measured); (b) in-plane/rotation regressions become visible once the silhouette displacement exceeds the dilation-absorption radius (≈6 px at dilation 6 — the rendered image and comparison frame are both dilated by the FastImplantDilationMetric dilation argument, so overlap is preserved for sub-radius shifts); (c) structural regressions (budget/SetCallOffset, dilation-schedule, frame↔label mapping, backface, edge-config) trip the gate hard because they move the recovered pose by stage-range magnitudes (15-35 mm, settings_constants.h TRUNK_RANGE/BRANCH_RANGE/Z_SEARCH_RANGE) — far beyond any absorption radius; (d) cost-VALUE regressions (the live distance-map index bug, distance_map_metric.cu:27) are INVISIBLE to the gate — the gate compares rendered silhouette vs label, never cost values — which is exactly why Tier-0 pins (02) and ablation.json exist. [Source: repo — test/golden/baseline.json, test/oracle/oracle_test.cpp, include/domain/settings_constants.h:24-37; prior-run angle 02]
- Suite shape, half 1 — per-variant perturbation grid (the transfer function): anchor at the fem.jts golden pose (frame 0), per variant v ∈ the 7 registered (CostFunctionManager.cpp:344-423) and per axis i ∈ {x, y, z, xa, ya, za}, render + IoU at Δ ∈ {±1, ±2, ±5, ±6.31(z), ±10, ±15} mm/deg, one axis perturbed at a time (12-18 renders per (variant, axis)); record IoU(Δ) into ablation.json perturbation_calibration[]. Assertions (per-variant, executable): (m1) IoU is monotone non-increasing in |Δ| beyond the plateau (a non-monotone curve flags a render/convention bug, not a gate issue); (m2) plateau: IoU ≥ 0.99 for |Δ| ≤ dilation-absorption radius (in-plane) — pins the absorption mechanism; (m3) z-characteristic pin: IoU(Δz = 6.31) ≥ 0.99 — the measured z-blindness becomes a pinned characteristic, and if a future z remedy (SAME_Z weight, chamfer reweight) makes this assertion fail, that is the z-axis becoming visible, which the suite must report as an event, not a failure. Deliverable: per-axis minimal-detectable-regression (smallest |Δ| with IoU < 0.85) — the direct answer to "what size of regression trips the gate".
- Suite shape, half 2 — targeted injections (checked-coverage): each injection is a poisoned oracle run at the flat-3000 shape, asserting the gate's behavior: NEG (negative control, unpoisoned — MUST pass, guards against false positives); INJ-BUDGET (cost lambda capped at 100 calls — SetCallOffset/stage-loop regression proxy — MUST fail); INJ-DILATION (comparison dilated at 0 and 12 instead of 6 — MUST fail, and if 12 does not fail that itself is a finding: the gate's dilation sensitivity is asymmetric); INJ-LABEL (wrong frame's label — MUST fail, proves the empirical correspondence is load-bearing); INJ-BACKFACE (backface ON vs the oracle's OFF — expected fail or near-fail on an open/concave STL; doubles as contradiction-4's evidence check (b), recommended by angle 02); INJ-EDGE (Canny aperture/threshold altered — expected fail); INJ-VARIANT (swap to a z-blind variant — may NOT fail: a variant regression invisible to the gate is the informative case, and it is exactly what the ablation z-gap column exists to catch). Assertion philosophy per Schuler & Dallmeier checked-coverage: a gate that never fails is untested; the suite must contain at least one injection that fails, one that passes, and one whose outcome is a measurement. [Source: repo — test/oracle/oracle_test.cpp (kBudget/kIouGate/build pipeline), src/compute/CostFunctionManager.cpp:344-423, src/compute/DIRECT_DILATION.cpp:73-104; https://www.st.cs.uni-saarland.de/publications/files/schuler-stvr-2013.pdf]
- Cost and schedule: half 1 ≈ 7 variants × 6 axes × ~15 Δ ≈ 630 renders ≈ well under 10 min at the verified ~20-60 evals/s budget-3000 rate (qml_parity_check.cpp:126 "a few minutes on the RTX 3090"); half 2 ≈ 7 injected 3000-budget runs ≈ tens of minutes. Per-PR reduced shape: half 1 on DIRECT_DILATION frame 0 only; full suite nightly. Headless Tier-0 twin: the IoU-vs-shift math (dilated-overlap IoU on synthetic strips) runs in the CPU metric reference, so the transfer-function fitter is testable without the GPU; the render+metric path stays GPU-authoritative. [Source: repo — test/oracle/qml_parity_check.cpp:124-126, test/CMakeLists.txt:1253-1254; verified evals/s derivation in Round 1]
- Confidence: high on the mechanics (all seams source-verified); medium on the pre-registration expectations (they are the suite's hypotheses; the minimal-detectable-regression numbers are unmeasured until the suite runs).
- Relevance to this project: this closes the synthesis open question "What size of regression trips the IoU 0.85 gate?" — the suite is the instrument, and it simultaneously hardens the gate doctrine (appearance arbiter) by proving which regression classes the oracle can and cannot see, so the other five angles' gates are understood, not assumed.

#### R2-2 — z-profile probe as an executable spec: 31-render sweep, valley-depth metric, and the ranking hypothesis mapped to verified metric composition
- Entry point (source-verified): the RunDirectStage injected-cost lambda at optimizer_manager.cpp:1235-1246 — pose set (physical Point6D → SetCurrentPrimaryCameraPose), biplane secondary via calibration_.convert_Pose_A_to_Pose_B, then stage_manager.callActiveCostFunction(). The probe replicates exactly one of these three bodies; no production change.
- Sweep spec: anchor = fem.jts frame-0 truth (baseline.json expected_pose_per_frame frame 0, z_tran = -1027.713; note the captured baseline ran at -1022.93 — the manifest records which anchor), other 5 axes pinned at truth; Δz ∈ {-15, -14, …, +15} mm step 1 = 31 renders per (variant, dilation, frame); each point = one render + one metric call ≈ 20-60 ms ⇒ ~1-2 s per (variant, dilation), whole probe (7 × 4 × 1) ≈ 868 renders ≈ 1-3 min on the 3090; frames {0,1,2} nightly.
- Variants: all 7, with the ranking hypothesis mapped onto verified metric composition (src/compute): chamfer-heavy DIRECT_DILATION = FastImplantDilationMetric + DistanceMapMetric (DIRECT_DILATION.cpp:73-83 — note the second DistanceMapMetric call is dead-commented at :101-104); intensity DIRECT_MAHFOUZ = ImplantMahfouzMetric (gpu_metrics.cuh:45-51); pure dilated-overlap DIRECT_DILATION_T1 = FastImplantDilationMetric only (DIRECT_DILATION_T1.cpp:64-79 — caveat: the always-Trunk guard (angle 02 bug 4) means the probe scores T1's reachable trunk behavior; the probe measures exactly the reachable path and the manifest flags it). - Dilations: {6, 3, 1} per the documented schedule (baseline.json dilation_px), plus 4 as the runtime-implied branch value (settings_constants.h TRUNK_DILATION 6 + BRANCH_DILATION_DECREASE 2 → branch 4, Z_SEARCH_DILATION 1) — the probe lets the data arbitrate the 6/3/1-vs-6/4/1 contradiction (synthesis Contradiction 1) instead of the docs.
- Metrics per curve (executable): valley_depth = (max − cost(0)) / (max − min) over the 31-point sweep ∈ [0,1]; argmin_offset_mm; plateau_halfwidth_mm at 90% of max; noise_floor = spread of cost(0) over 5 repeats (rides along as a determinism check — expect 0 for the int-atomic cost path, angle 05's verified finding).
- Executable assertions: (p1) cost(0) is the sweep minimum within the noise floor — a flat or off-center curve (random argmin) classifies the variant as z-blind at that dilation (recorded, informational — this IS the measurement); (p2) z-blindness classification threshold: valley_depth < 0.05 ⇒ "z-blind at dilation d" recorded per (variant, dilation); (p3) the ranking hypothesis asserted pin-first: nightly run 1 records vd(DIRECT_DILATION) ≥ vd(DIRECT_MAHFOUZ) ≥ vd(DIRECT_DILATION_T1); subsequent runs assert it (pin-first doctrine: first measurement records, later runs enforce); (p4) instrument validation: ablation z_gap_mm should anti-correlate with valley_depth across variants — if a deep-valley variant still shows a large z gap, the probe and the ablation disagree and both are suspect.

Headless Tier-0 twin: the CPU metric reference runs the same sweep on synthetic silhouettes scaled by the magnification factor (no-GPU z-sensitivity estimate); the GPU probe remains authoritative (real render + metric path — the 05-compute-perf boundary: probe consumes timing, does not own instrumentation).
- Confidence: high on mechanics (lambda, variants, metric composition all source-verified this round); the valley-depth numbers and the ranking itself remain hypotheses until the probe runs — that is the point of the instrument.
- Relevance: this is the gate on every z remedy (synthesis recommendation 8's GO condition for polish, and the SAME_Z/chamfer calibration surface), and it converts the run's load-bearing z-weak-axis argument into measured data.

#### R2-3 — Round-1 correction: the Directive::SymTrap seam addition already exists; the remaining work is pins and the tibia-after-femur drive sequence, not code
- Source proof the seam is closed: the typed enum has SymTrap = 5 (include/coordinator/optimizer_run_controller_core.h:58-63); the shell's DirectiveToString maps it to the exact manager string "Sym_Trap" (src/coordinator/optimizer_run_controller.cpp:437-452, case at :447-448); the manager parses "Sym_Trap" → sym_trap_call = true (optimizer_manager.cpp:177-185); sym_trap_call triggers CalculateSymTrap() after the trunk stage (optimizer_manager.cpp:1125-1127), skips the leaf stage (:1130-1131), and returns via finished() (:1192-1194). Round 1's "one concrete seam gap" (and synthesis recommendation 3's "requires the small seam addition") is STALE against the current tree — the synthesis should be updated: the multi-stage oracle needs no seam addition, only pins. The manager-side implementation is also verified: CalculateSymTrap (optimizer_manager.cpp:1294+) enumerates 60 candidates via create_vector_of_poses(pose_list, pose_6D, 20), scores each with EvaluateCostFunctionAtPoint(pose, 2) ("Use leaf"), sleeps 5000/60 ms per candidate (~5 s total — must be inside the oracle's TIMEOUT budget), and emits onUpdateOrientationSymTrap per candidate (relayed by the controller with the stale-epoch guard, optimizer_run_controller.cpp:327-333, bind at :415-422).
- What breaks if SymTrap is omitted (the pin's job — this is the "what breaks" answer): DirectiveToString's default case returns "Single" (optimizer_run_controller.cpp:449-452), and OptimizerRunRequest.directive defaults to Directive::Single (optimizer_run_controller.h:54-55). An author who forgets req.directive = Directive::SymTrap gets a SILENT Single run: no sym_trap_call, no CalculateSymTrap, the leaf stage runs instead, and the tibia-ambiguity resolution is skipped. The appearance gate CANNOT see this: the mirrored/ambiguous tibia pose may project onto the same label at ≥ 0.85 IoU — that is the definition of the ambiguity. The oracle must therefore assert three things on the tibia pass: (a) the driver-recorded launch.directive == "Sym_Trap" (the fake-driver suite already records the launch by value — test/CMakeLists.txt:365-409); (b) the orientationSymTrapUpdated relay fired ≥ 1 (proves CalculateSymTrap executed; assert == 60 to also catch the silent early return at optimizer_manager.cpp:1294-1300 when the optimum's rotations are all zero); (c) stage-bookkeeping: with sym_trap_call the leaf is skipped, so costCalls() lands at the trunk cap (20000), NOT the cumulative 35000 — the flat-3000 oracle is blind to exactly this class.
- How the tibia-after-femur pass drives past SingleModelOnly: the pre-check is a QML-bridge policy only — app/experimental/OptimizerBridge.cpp:44-51 rejects selected_model_rows.size() != 1 with GateStatus::SingleModelOnly, explicitly "NOT in the shared controller" (OptimizerBridge.h:7-9; test/CMakeLists.txt:413 "the SingleModelOnly bridge policy stays in the bridge test"). The shared OptimizeIntentController gate does not enforce exactly-one-model. The oracle therefore constructs OptimizerRunRequest { directive, selected_model_rows = {0, 1}, model_count = 2, storage, launch { models = {femur, tibia}, primary_model_index = 0|1, … } } and calls OptimizerRunController::start() directly — the bridge never executes, so SingleModelOnly never fires. Drive sequence: Run 1 (femur): directive Single, primary = femur (index 0), storage from fem.jts frame 0 (tibia row pinned from tib.jts — the manager reads the non-principal pose per frame via pose_storage_.GetModelPose(name, frame) → SetCurrentPrimaryCameraPose at optimizer_manager.cpp:937-947, biplane at :967-970); read the recovered femur from the optimizedFrameRelayed relay; write it into a fresh LocationStorage as the femur row; Run 2 (tibia): directive SymTrap, primary = tibia (index 1), femur row = Run-1 recovery; trunk DIRECT around tib.jts, then sym-trap enumeration; gate = tibia silhouette IoU vs the tib label (fixtures verified present: example_studies/Kneel_1/KR_right_6_tib.stl, tib.jts, Labels/tib/AT_K1_V1_0160/0170/0180_label_tib.tif — the tibia label correspondence must be pinned empirically with the same start-pose-IoU procedure as oracle_test.cpp before the tibia gate means anything).
- Confidence: high — every link in the chain source-verified this round (enum, mapping, parse, sym-trap impl, relay, bridge policy, fixtures).
- Relevance: this removes a planned code change from the execution path (synthesis step 3), replaces it with three cheap pins, and gives the tibia-after-femur pass a concrete, assertable drive sequence — the multi-stage oracle is closer than Round 1 thought.

#### R2-5 — Cross-GPU noise-floor plan: what the banded L1 gate needs, what an IoU retune looks like, what the single 3090 can measure today
- The banded L1 gate's preconditions (from the test-infra seat, nothing is banded before these): (a) baseline per-px L1 = 0.0207 (single measurement, baseline.json measured block; silhouette_pixel_diff_threshold 0.021 informational); (b) per-GPU statistics: N ≥ 5 repeats of the golden-pose render + recovered-pose render on EACH GPU, giving μ_g and σ_g of per-px L1 per GPU; (c) pooled cross-GPU σ; band = μ_ref ± k·σ_pooled with k chosen so the band absorbs cross-GPU render-boundary variance (rasterization-boundary pixels differ across GPUs/drivers; the metrics are int reductions so within-GPU variance should be ~0) yet the known regression signature — a misaligned silhouette adds the full silhouette area to the pixel diff, i.e., per-px L1 jumps by roughly an order of magnitude from 0.0207 — lands far outside the band; (d) the band is recorded in baseline.json (a re-baseline event), never hard-coded in the test. Until GPU #2 exists, the L1 assert stays informational (Round 1's position, now with the explicit measurement protocol).
- IoU retune shape: the 0.85 gate sits 0.1436 below the measured 0.9936. It is retuned only as a re-baseline event, never as drift-following: (1) after angle 02's distance-map index fix + one oracle re-baseline, re-measure recovered IoU; (2) keep 0.85 unless the new measurement's margin to the noise floor shrinks below ~10× the cross-GPU IoU σ, or the perturbation suite shows the gate trips on perturbations smaller than the model's expected pose noise (i.e., the gate is stricter than the thing it gates); (3) a retune is a one-line baseline.json change plus the re-baseline record — the suite (R2-1) re-calibrates after any retune. The appearance-arbiter doctrine is unchanged: never gate on raw pose.
- What can be measured TODAY on the single RTX 3090 (the noise floor's single-GPU half): (a) seed/run determinism — two identical launches must produce a bit-identical recovered pose and identical cost-call counts (int-atomic path is order-independent; the ablation runner's rerun_identical twin is the vehicle); (b) run-to-run variance — N = 5 oracle runs on the flat-3000 shape, reporting spread of pose / IoU / per-px L1 (expect ≈ 0 modulo render-boundary pixels; record pose_spread_mm_deg into noise_floor); (c) the z-profile noise floor (cost(0) × 5 per variant); (d) the perturbation transfer function and the minimal-detectable-regression table (R2-1); (e) the reduced-shape data-profile measurement (budget-vs-IoU curve, Moré & Wild style) — the input to the ci profile. What CANNOT be measured today: cross-GPU variance, driver-version sensitivity, thermal/clock effects on the render path (the 3090's boost clocks vary timing but not int-atomic scores) — each needs GPU #2 or a driver matrix, and the noise_floor block is the schema slot reserved for that data when it lands.
- Confidence: high on the single-GPU protocol (determinism facts source-verified via angle 05); the cross-GPU terms are spec until a second GPU exists (Round 1's honest position, now with the exact measurement recipe).
- Relevance: this converts the two "deferred until a second GPU" items in Round 1's What-Could-Not-Be-Verified into a concrete measurement plan, and it lets the single 3090 start banking the determinism and variance data today instead of waiting.

## Round 3 — Lineage and Field Evidence from the Zotero Corpus (measurement-apparatus)

### Summary

Round 3 grounds the apparatus in the algorithm's own lineage, reading the primary texts now in the Zotero corpus. Flood & Banks 2018 (TMI 37(1), DOI 10.1109/TMI.2017.2773398) is the DIRECT-JTA paper the JTML stage loop descends from, and it documents a z-leaf budget of 50,000 evals — equal to the trunk — over a 20 mm out-of-plane range vs 5 mm in-plane, explicitly because out-of-plane translation is "the least accurate degree of freedom for single-plane fluoroscopy": the z-stage budget becomes a first-class manifest parameter and the ablation shapes gain Flood's 50k/3×15k/50k against JTML's 20k/2×5k/5k. Yamazaki 2004 (TMI 23(5), DOI 10.1109/TMI.2004.826051) is a dedicated depth-position remedy paper whose mechanism — build the z evaluation curve, fit a 4th-order polynomial, take its extremum — is the field-validated twin of the z-profile probe, with published depth RMSEs (2.6→0.9 mm simulation, 3.2→1.4 mm in vitro) that become the z-remedies question's external benchmarks and a "difficult to determine a fixed weight" analysis that bears directly on the SAME_Z weight calibration. Modern automatic-registration papers (Jensen 2023 J Arthroplasty; Arulampalam 2025 IJCARS; Burton 2023/2024) supply per-axis error tables for the ablation runner's benchmark blocks, and Flood's dilation/Canny sensitivity tables give the perturbation suite its field-mirroring shape — including the concrete finding that JTML's trunk dilation 6 sits below Flood's femur-robust band (8–12).

### Key Findings

#### R3-1 — Z-leaf budget: the lineage paper allocates 50,000 z-evals (equal to trunk); the z-stage budget becomes a first-class manifest parameter, and the ablation shapes gain Flood's 50k/3×15k/50k
- Primary-text facts (floodAutomatedRegistration3D2018.txt): DIRECT-JTA's stage loop is trunk → three branch restarts → z-translation search: "The iteration budget was 50,000 for the trunk search, 15,000 for each of the three branch searches, and 50,000 for the z-translation search" — the z (leaf-equivalent) budget EQUALS the trunk budget; total 145,000 evals/frame at ~3,000 evals/s on a GTX 970 ("approximately 3,000 iterations per second (50 seconds per frame)"). The z-stage range: "During the z-translation search phase the out-of-plane range was set to 20 mm while all other components were set to 5 mm/degrees." The rationale, verbatim: "This extra search in the out-of-plane translation is necessary because it is the least accurate degree of freedom for single-plane fluoroscopy."
- The JTML mapping (constants verified in Rounds 1–2): trunk 20,000 → 2×branch 5,000 → leaf 5,000 (35k total); leaf ranges (3,3,15,3,3,3) — z 15 mm vs Flood's 20 mm, in-plane 3 vs 5; branch (15,15,25,25,25,25) is verbatim Flood's branch-restart sizing ("15 mm for the in-plane translation, 25 mm for the out-of-plane translation, and 25° for each of the Euler angles"). The z-stage's share of budget: Flood 50k/145k = 34.5%; JTML 5k/35k = 14.3% — a 2.4× lower z-fraction, against the run's load-bearing z-weak-axis problem. Flood also pegged the budget to wall clock ("pegged to take approximately one minute of operating time") — the same pragmatics presumably behind JTML's shape, which is why the budget question must be measured, not argued.
- Spec updates (multi-stage oracle + ablation manifest): (a) budget_shapes gains "flood-direct-jta" {trunk 50000, branch 15000, number_branches 3, leaf 50000} → cumulative caps [50000, 65000, 80000, 95000, 145000], which the stage-bookkeeping gate (costCalls on the cumulative caps) extends to naturally; (b) the z-stage budget becomes an explicit ablation axis z_leaf_budget ∈ {5000 (JTML prod), 20000 (JTML trunk parity), 50000 (Flood parity)}, crossed with the z-range axis {15 mm (JTML), 20 mm (Flood)} — budget and range are separable questions; (c) the dilation schedule axis gains a third reference point: "flood-femur-10-6-1" and "flood-tibia-6-2-1" (Flood: trunk 10 femur / 6 tibia, branch = trunk − 4, z-search 1 — the "decreased by a value of four" scheme), alongside code-6-4-1 and docs-6-3-1; schedule-as-data now has three documented schemes, not two. Note the dilation finding hiding here: JTML's trunk 6 is Flood's TIBIA value — JTML's femur runs the femur at the tibia dilation (see R3-4).
- Per-eval cost context (05-compute-perf boundary): Flood's 145k evals in 50 s implies ~3,000 evals/s; JTML's derived 20–60 evals/s (Round 1, from the flat-3000 "a few minutes") is 50–150× slower per eval — Flood's metric is the GPU-cheap unnormalized L1 on edge images ("L1... can be computed by a GPU extremely efficiently"), JTML's is DRR + dilated-overlap + chamfer per eval. The 50k z-budget is therefore NOT directly transferable; the transfer question is exactly what the Moré & Wild per-stage data profile (R2-4) measures. This is the strongest external anchor yet for Cut 0's per-eval timing record.
- Flood's success-metric decision validates the apparatus's z-gate doctrine: strict success = "within 1 mm for each of the in-plane translations and 1 degree for each of the rotation angles" and "out-of-plane translation is not considered in our definition of success... single-plane, or monocular, radiographic images are extremely unreliable for determining out-of-plane position [10]; this is expected as the translation occurs along the line of sight. An orthogonal biplane comparison is likely the best resolution for this inaccuracy." — the lineage's own answer to z-inaccuracy is biplane (already supported in JTML per Round 1) or the decoupled z-remedy (R3-2); the banded-informational z gate stays correct by the lineage's own measurement convention.
- Confidence: high (primary text, direct quotes; JTML constants source-verified in Rounds 1–2).
- Relevance to this project: turns the "is 5k leaf enough?" question from an argument into a parameterized ablation axis with a lineage-anchored reference shape, and gives the stage-bookkeeping gate a second cumulative-cap vector to assert.

#### R3-2 — Z-profile probe vs the field: Yamazaki 2004's decoupled z-polish is the probe's field twin; its published depth RMSEs (2.6→0.9 mm) are the z-remedies question's benchmarks
- Primary-text facts (yamazakiImprovementDepthPosition2004.txt): the problem statement is verbatim the z-weak axis — "a change in the depth position causes only small changes in the 2-D silhouette"; field accuracy: "the accuracy of the depth position should ideally be about 1 mm, while some researchers report that absolute errors of 2–10 mm have been obtained by computer simulation tests." The mechanism: the z evaluation curve "was more jagged, and the curve peak less pointy" than the other 5 DOF, and its gradient "changed much more markedly with distance" (500/650/850 mm focus distances).
- The documented remedy (the field's z-remedy #1): independent depth optimization. After the conventional 6-DOF registration (Zuffi-style contour + Levenberg–Marquardt), build the z evaluation curve by moving the model along the focus→model-center line at "ten different points" and computing RMSD at each; fit a polynomial; "for fourth- and higher-order polynomials, the extremum error is almost saturated (about 0.5 mm)" → order 4 used; extremum found via Durand–Kerner; then a second conventional registration with the corrected depth. Results: simulation depth RMSE 2.6 mm → 0.9 mm; in vitro 3.2 mm → 1.4 mm; in vivo relative-pose consistency SD 4.9 mm → 1.5 mm; the other 5 DOF unchanged (SD ≈ 0.1 mm translations, ≈ 0.2–0.3° rotations). Residual: ~0.5 mm average z bias, "thought to be caused by slight errors in translation parallel to fluoroscopic images" — in-plane error couples INTO z.
- The field's other documented z remedies, now corpus-backed: (2) biplane — Flood "an orthogonal biplane comparison is likely the best resolution"; Yamazaki: biplane reports exist but "limited space for testing, system complexity and increased radiation exposure remain unresolved" (already supported in JTML, Round 1); (3) known-geometry prior — "conventional techniques assumed that there is no displacement between the femoral and tibial components on lateral images... depth position was ignored, and relative medio-lateral translation was set to zero" (JTML already pins the tibia relative to femur from .jts — the prior is built in); (4) penalized z — Jensen 2023: tibia optimization "included additional mediolateral translation and varus/valgus rotation penalties" (the field precedent for JTML's pole-constraint family, and its SAME_Z weight).
- Probe spec updates: (a) "yamazaki-polynomial mode" — on the SAME 31-render sweep (zero extra renders), fit a 4th-order polynomial (robust least squares) and report poly_argmin_mm + fit residual alongside the raw argmin and valley_depth; this is a drop-in, field-validated z-remedy candidate (10 points in Yamazaki, 31 here) that the polish stage (angle 06) can consume as its z-arm; (b) "fixed-weight evidence" — Yamazaki on the SAME_Z-type calibration: "a weighted optimization is generally applied to compensate for the difference of variable scale, [but] it would be difficult to determine a fixed weight value... because of the difference in gradient for each evaluation curve", and the z gradient changes with focus distance — the SAME_Z weight is fighting a distance-dependent scale; the probe must record the z-valley gradient at JTML's actual focus distance (JT_INTCALIB 1198 mm principal distance, angle-06 calibration) and the ablation should compare SAME_Z-weighted vs decoupled (Yamazaki-style) z-polish rather than SAME_Z alone; (c) "coupling mode" — re-run the sweep at ± the minimal-detectable-regression in-plane Δ (R2-1's table) to measure dz*/d(in-plane), the mechanism behind Yamazaki's residual bias; this upgrades probe assertion p4 (z_gap anti-correlates with valley_depth) from correlation to mechanism.
- The z-remedies question, answered with a band: the field's single-plane depth-position accuracy spans Yamazaki conventional 2.6–3.2 mm RMSE → remedied 0.9–1.4 mm, Jensen (DIRECT-JTA lineage) out-of-plane < 1.8 mm RMS vs human-supervised, Arulampalam depth MAE 1.8 mm (R3-3). JTML's measured 6.31 mm (frame 1, flat-3000 shape) sits at the top of Yamazaki's reported 2–10 mm range and ~3.5× above the lineage's own 1.8 mm — a candidate regression against the lineage, with two honest caveats: JTML's gap is vs the fem.jts golden (not human-supervised) at a trunk-only flat-3000 shape that NEVER runs the leaf z-stage, and the production shape may shrink it. The multi-stage oracle + probe are exactly the instruments that decide.
- Confidence: high on the Yamazaki facts (primary text); medium on the JTML-vs-field comparison (different ground-truth regimes and shapes — the caveats above are the honest framing).
- Relevance: gives the z-remedy decision (synthesis recommendation 8's GO condition) a field-validated remedy to test (decoupled polynomial z-polish), an external accuracy band to report against, and a mechanism (in-plane→z coupling) for the probe to measure.

#### R3-3 — State-of-the-art benchmarks: per-axis external error tables for the ablation runner's reports
- Corpus-sourced numbers, the applicable columns for the runner's benchmark block:
  - Jensen 2023 (jensenJointTrackMachine2023.txt — the dispatch's "jensenAutonomousMethodExtracting2021" citekey maps here; J Arthroplasty, the 2021 preprint's published form): RMS vs human-supervised — in-plane translations < 0.8 mm, out-of-plane < 1.8 mm, rotations ≤ 4° inside the tibial ambiguous zone / < 1.7° outside; external validation (45 instrumented-sawbones motion-capture frames + 260 single-plane image pairs from a biplane study): "All in-plane translation errors were submillimeter, except S/I from the biplane fluoroscopic study. All rotation errors were <1.8°"; blunder threshold = squared-sum rotation difference > 5°. Method note: CNN segmentation → NFD shape-library initial pose → DIRECT-JTA refinement, "the leaf branch served to find the optimal out-of-plane translation" — the same stage-loop family as JTML, and its out-of-plane note is the field confirming the z-weak axis inside the lineage itself: "Due to poor sensitivity for measuring out-of-plane translation with monocular vision, the medio-lateral translation had the largest RMS differences", and "the out-of-plane translation estimates were relatively poor... extremely sensitive to model projection and edge detection details".
  - Flood 2018: strict success = in-plane ≤ 1 mm AND rotations ≤ 1° (out-of-plane excluded by definition); "average out-of-plane translation around one millimeter" for femur at convergence-range trials; capture range ±55 mm/deg femur, ±25–40 tibia (tibia limited by a symmetric-trap local minimum "just over a degree along the Y Euler angle" — the sym-trap lineage).
  - Yamazaki 2004: z 2.6→0.9 mm sim / 3.2→1.4 mm in vitro; other 5 DOF SD ≈ 0.1 mm / ≈ 0.2–0.3°.
  - Arulampalam 2025 (arulampalamAccuracyNovelAutomated2025.txt, IJCARS, DOI 10.1007/s11548-025-03389-y — automated 2D-3D for THA cup from single-plane intraoperative fluoroscopy): MAE 1.9° inclination [−4.4, 4.8], 1.5° anteversion [−7.3, 4.1], 1.6 mm height [−5, 3.8], 1.8 mm depth [−7.3, 4.1]; 100% inclination within 5°, 98% anteversion within 5°, 90% height within 3 mm, 81% depth within 3 mm — depth is the weakest axis even in a 2025 automated product.
  - Burton 2023 (burtonFullyAutomaticTracking2023.txt, CBM 163:107189, DOI 10.1016/j.compbiomed.2023.107189 — biplanar native glenohumeral): median orientation 1.7° scapula / 8.6° humerus vs manual tracking.
  - Burton 2024 (burtonFullyAutomaticTracking2024.txt, J Biomech 166:112066, DOI 10.1016/j.jbiomech.2024.112066 — biplanar native knee): phantom femur MAE 0.22/0.19/0.20° rotation and 0.19/0.25/0.63 mm translation; manually-tracked femur MAE 0.24/0.49/0.75° and 1.51/0.93/0.33 mm; TF kinematics MAE 0.41/1.07/1.16° and 0.94/0.65/0.66 mm; and the z-weak-axis fact survives even in biplanar: "movement along this axis corresponds to minimal visual changes in rendered DRRs... the pose refinement loss landscape is less sensitive to changes in this DoF", femur ML consistently below 2 mm.
- Spec updates: ablation.json runs gain a "benchmarks" block: per-axis recovered-vs-golden gaps tagged with regime (single_plane_implant / biplanar_native; ground_truth_type ∈ golden|human_supervised|motion_capture|optotrak|phantom) and the applicable field column(s); the runner's summary line reports e.g. "in-plane 0.8 mm / z 6.3 mm vs Jensen 0.8/1.8 (single_plane_implant, human_supervised)". Benchmarks are context bands, never gates — the appearance gate stays the arbiter, and the regime tag prevents false equivalence (Burton's biplanar <1 mm numbers must not be compared to single-plane z gaps without the tag). Closest regime match for JTML's task: Jensen 2023 (same algorithm family, same single-plane implant task); Flood 2018 for the strict-success convention.
- Confidence: high (all numbers primary-text; regime caveats explicit in the schema).
- Relevance: the ablation runner's reports stop being bare IoU/L1/z numbers and become comparisons the run's decision-makers can read against the field — including the honest position that JTML's measured 6.31 mm z gap is ~3.5× the lineage's own out-of-plane RMS.

#### R3-4 — Perturbation suite mirrors the corpus's gate-like sensitivity analyses
- Flood 2018 Table V (dilation sensitivity) — the exact shape to mirror: perturb the trunk dilation ±1 and ±2 from the high-performance values and re-run the full capture-range experiment; result: "the femur implants are relatively robust at trunk dilations of eight to twelve, while the Group A tibial implants performed well at dilation levels of four to eight. The Group B tibial implants favored a higher dilation in the range of six to eight." Suite upgrade: the perturbation suite (R2-1) gains a dilation-robustness sub-table — trunk dilation ∈ {4, 5, 6, 7, 8} (= JTML's 6 ± 2), recording per-variant strict-success retention / IoU, with the report line "JTML trunk 6 sits BELOW the femur-robust band (8–12) and at the tibia band's low edge (4–8)". Flood's size caveat — "the ideal dilation values are likely to also depend on the size of the implant in pixels. A very small implant image (say 64 pixels across) would dilate to meaningless noise" — is the size-dependence check the sub-table must record for Kneel_1's implant pixel size at the actual SID.
- Flood 2018 Table VI (Canny sensitivity) — two directions, not one: "highly noisy" (too-sensitive thresholds, 20/65 and 30/80 per group) vs "insufficient edge detection" (too-insensitive, 40/100 and 100/140). Suite upgrade: INJ-EDGE becomes Flood's two-directional pair (one noisy-threshold config, one insensitive config), asserting the gate trips in both directions or recording which direction it is blind to.
- Jensen 2023 ambiguous-zone analysis — the tibia gate's checked-coverage anchor: "Transversely symmetric tibial implants posed problems during registration because 2 distinct poses produced roughly identical projections"; blunder = squared-sum rotation difference > 5°; and the remedy ordering "the tibial implant was always optimized after the nonsymmetric femoral implant" (the field precedent for JTML's tibia-after-femur, R2-3). Suite implication: the sym-trap injection (mirrored tibia pose) may legitimately PASS the appearance gate — identical projection ≈ identical IoU, by definition of the ambiguity — so the tibia pass's checked coverage lives in the sym-trap pins (launch directive == "Sym_Trap", relay count == 60, costCalls == 20000), not the IoU gate; the suite asserts the pins trip, not the gate.
- Yamazaki 2004 per-variable evaluation curves: the field's own gate-like sensitivity analysis is a per-DoF curve family — the z-profile probe IS the JTML mirror of this instrument; corpus confirms the instrument family, no new instrument needed.
- Flood's intro capture-range curve — context for the suite's Δ magnitudes: conventional registration success "can be around 90% when the initial guess is 4mm from the in-plane solution, and 4° from the rotation solution... [but] can drop to as low as 50% when the initial guess is within 16mm and 16°" — the ±{1,2,5,10,15} mm/deg grid of R2-1 brackets exactly the field's success-rate cliff; the minimal-detectable-regression table gains a field-anchored expectation for where the cliff should appear.
- Confidence: high (all primary-text; the suite upgrades are direct mirrors).
- Relevance: the perturbation suite's checked-coverage argument (R2-1) is no longer first-principles-only — every injection class now has a corpus-documented sensitivity experiment it mirrors, and the dilation sub-table converts a doc-contradiction (6/3/1 vs 6/4/1) into a measured robustness band with a lineage reference.
