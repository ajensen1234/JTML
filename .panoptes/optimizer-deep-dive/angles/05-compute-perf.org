#+TITLE: Compute Performance of the GPU Cost Path — Sync-Point Inventory, Streamed Pipeline, Instrumentation, Ordered Cuts
#+DATE: 2026-08-12
#+PANOPTES_ANGLE: compute-perf

* Summary

The synthesis item-8 claim (cost path is sync-bound, not kernel-bound) is *directionally confirmed by source structure but not yet measured*: every eval runs on the default stream with zero streams/events anywhere in src/, and 5 synchronous `cudaMemcpy` D2H calls per monoplane eval (`render_engine.cu:781-790` ×2, `fast_implant_dilation_metric.cu:289-290` ×1, `distance_map_metric.cu:110-119` ×2) each drain the entire device pipeline, leaving the GPU idle across 3 distinct host-block windows per eval. The existing ms/call meter (`optimizer_manager.cpp:1272-1278`) uses `clock()`, which measures CPU process time and *excludes both GPU time and sync-wait time* — so it systematically under-reads a sync-bound pipeline and cannot arbitrate the claim. The removal order that follows is: (0) instrument with nvtx3 + cudaEvent and measure; (1) async-ify the 3 terminal score copies with a single per-eval event wait (pinned buffers already exist — pure win); (2) batch the DIRECT iteration's independent evals with double-buffered eval state so one eval's tail overlaps the next's head; (3) only if the fragment-fill sync remains dominant, remove it via a device-side clamp + fixed grid (the one kernel-level change); (4) fix the meter to wall-clock/event time. Every cut is gated on the oracle (IoU ≥ 0.85) and, where possible, bit-identical cost values.

* Key Findings

** Sync-point inventory (monoplane eval = 14-15 kernel launches + 5 sync D2H)

Per-eval hot path is `CostFunctionManager::costFunctionDIRECT_DILATION` (src/compute/DIRECT_DILATION.cpp:67-106): RenderPrimaryCamera → FastImplantDilationMetric → DistanceMapMetric. Kernel/D2H count verified in source:

- Render (`RenderEngine::Render`, src/compute/render_engine.cu:711-840): `cudaMemset` (:716), ResetKernel (:722), WorldToPixelKernel (:725), BoundingBoxForTrianglesKernel (:746), BoundingBoxSizesKernel (:756), `cub::DeviceScan::ExclusiveSum` (:764), PrepareLaunchPacketKernel (:775), StridePrefixKernel (:812), FillTriangleKernel (:823) — 8 launches + cub internals.
- FastImplantDilationMetric (src/compute/fast_implant_dilation_metric.cu:169-295): ResetPixelScoreKernel (:170), EdgeKernel (:218), DilateKernel (:242), DifferenceKernel (:273) — 4 launches.
- DistanceMapMetric (src/compute/distance_map_metric.cu:71-127): 2× Reset (:72,:73) + main kernel (:99) — 3 launches.
- Total ≈ 15 launches (matches the "~15 kernel launches" figure) + 5 synchronous D2H `cudaMemcpy`.
- Biplane adds a full second Render + FastImplantDilationMetric (+11 launches, +3 D2H).
- Confidence: high
- Relevance: this is the count synthesis item 8 was built on; the per-sync *cost* is the part that needs measurement (Cut 0).

The 5 syncs, classified by removability:

| # | file:line | payload | consumer | class |
|---|-----------|---------|----------|-------|
| 1 | render_engine.cu:781-785 | bounding box, 4×int, pinned (`gpu_image.cu:21-22`) | host crop computation for metric launch grids (fast_implant_dilation_metric.cu:201-207, distance_map_metric.cu:83-89) | structural mid-eval: host needs bbox to *size* the metric launches; removable only by moving crop to device (kernel change) |
| 2 | render_engine.cu:786-790 | fragment_fill, 1×int, pinned (`render_engine.cu:248-249`) | host overflow check (:795-808) + grid dims of StridePrefix (:812-816) and FillTriangle (:823-827) | structural mid-eval: data-dependent launch; removable via device-side clamp + fixed grid (Cut 3) |
| 3 | fast_implant_dilation_metric.cu:289-290 | pixel score, 1×int, pinned (`gpu_metrics.cu:7-11`) | return value of the metric | terminal — async-able now (Cut 1) |
| 4 | distance_map_metric.cu:110-114 | distance_map_score, 1×int, pinned (`gpu_metrics.cu:52-56`) | return value | terminal — async-able now (Cut 1) |
| 5 | distance_map_metric.cu:115-119 | edge_pixels_count, 1×int, pinned (`gpu_metrics.cu:62-65`) | return value | terminal — async-able now (Cut 1) |

Cost nuance: syncs #1 and #2 are back-to-back, so the *fragment* copy (:786-790) waits on the same pipeline drain as the bbox copy and returns almost immediately — the exposed stall is the single drain before them, not two. Similarly #4+#5 share one drain. So the per-eval cost is really ~3 host-block windows (render-head drain, fast-implant drain, distance-map drain), each = GPU idle during host wake + driver launch latency, plus 5× driver round-trip overhead for the sync calls themselves. All targets are already page-locked, so `cudaMemcpyAsync` conversion needs no allocation work.

- Confidence: high
- Relevance: terminal copies (3 of 5) are trivially removable; the 2 render syncs are the structural ones — one of which (fragment_fill) has a clean kernel-level removal, the other (bbox) does not without moving crop math onto the device (which would change launch grids — interaction with 02's metric-math semantics and 04's architecture shape).

** The ms/call meter cannot see GPU time — and under-reads when sync-bound

`optimizer_manager.cpp:1272-1278`:

```cpp
if ((clock() - update_screen_clock_) > 33) {
    emit UpdateDisplay(
        static_cast<double>(clock() - start_clock_) /
            static_cast<double>(opt.GetCostFunctionCalls()),
        ...);
    update_screen_clock_ = clock();
}
```

`clock()` on Linux returns *process CPU time* (user+sys), not wall time. A thread blocked in a synchronous `cudaMemcpy` is sleeping in the driver — it accrues no CPU time. So the meter excludes not only GPU kernel time but also the sync-wait time itself: a sync-bound pipeline reads as *artificially low* ms/call. The meter therefore cannot distinguish "fast" from "GPU idle"; it is directionally misleading for exactly the hypothesis at issue. Any before/after comparison must use a wall-clock meter (std::chrono or cudaEvent), not the existing one.

- Confidence: high (semantics of clock() on Linux; meter code verified)
- Relevance: the user's requirement "a before/after ms/call meter that includes GPU time via events" is not optional polish — the existing meter would fail to show the win, and could even show a *worse* number if a cut moves work from GPU-idle time into CPU time.

** Determinism: int atomicAdd/atomicSub reductions are value-deterministic

All cost-path reductions are integer atomics on single counters:
- DifferenceKernel: `atomicAdd(&result[0], 1)` / `atomicSub(&result[0], 1)` (src/compute/fast_implant_dilation_metric.cu:145,147)
- DistanceMapMetric_Kernel: `atomicAdd(&edge_pixel_count[0], 1)`, `atomicAdd(&distance_map_score[0], distance_map[orig_loc])` (src/compute/distance_map_metric.cu:46-47)
- WhitePixelSum / IOUKernel: `atomicAdd` (src/compute/gpu_metrics.cu:129, src/compute/iou.cu:66-72)

Integer addition is commutative and associative — the final value is independent of execution order. Given identical launch configs and identical inputs, every run yields bit-identical scores. Launch configs depend only on the bounding box (a pure function of pose + model), so the same pose sequence reproduces the same grids and the same results. The known order-nondeterministic path (DRR float atomicAdd) is NOT in the DIRECT_DILATION cost path. Consequences:
1. Bit-identical results after Cuts 1-2 are achievable and verifiable by diffing a recorded pose→score sequence against baseline.
2. Cut 3 must preserve the per-thread work for threads `< fragment_fill` exactly (only add an early-exit clamp for threads `>=`), and must not change the cub scan — then rendered output stays bit-identical.
- Confidence: high
- Relevance: the user's "bit-identical if possible" bar is real; it also gives the oracle a cheap extra gate (compare per-frame optimized pose + cost value to the baseline run, not just IoU).

** Allocation hoisting verified — nothing allocates in the eval path; buffers are pinned

- GPUMetrics ctor allocates all host score buffers via `cudaHostAlloc` and all device score buffers via `cudaMalloc` once (src/compute/gpu_metrics.cu:7-65); destructor frees (same file:68-95).
- RenderEngine::InitializeCUDA allocates all triangle/bounding-box buffers once (src/compute/render_engine.cu:248-323), including CUB scan storage via the size-query idiom (:311-320) — `cub_storage_bytes_` is fixed after init, so the per-eval `cub::DeviceScan::ExclusiveSum` at :764 is a plain launch with no allocation.
- `fragment_fill_` (render_engine.cu:248-249) and `bounding_box_` (src/compute/gpu_image.cu:21-22) are pinned host memory.
- The eval path (`costFunctionDIRECT_DILATION`) performs no cudaMalloc/cudaHostAlloc/free. The per-eval churn is 5 D2H copies, not allocations.
- Confidence: high
- Relevance: Cut 1 (async copies) requires zero allocation work — the pinned targets exist. The "scratch-buffer metrics" ask is already satisfied in the GPU cost path; the per-frame churn the earlier synthesis flagged (GPUImage::UploadImageToGPU reallocating on upload) is outside the eval path.

** The DIRECT loop is sequential, but each iteration's evals are mutually independent — batchable without changing results

`DirectOptimizer::Run` (src/domain/direct_optimizer.cpp:27-58) evaluates the unit center once, then loops ConvexHull → TrisectPotentiallyOptimal. In TrisectPotentiallyOptimal (:113-163), for each potentially-optimal hyperbox, two changed-center points are evaluated sequentially:

```cpp
changed_hyperbox_a->value_ = EvaluateCostFunction(changed_hyperbox_a->GetCenter());
data_.AddHyperBox(changed_hyperbox_a);
changed_hyperbox_b->value_ = EvaluateCostFunction(changed_hyperbox_b->GetCenter());
data_.AddHyperBox(changed_hyperbox_b);
```

Both centers derive from the pre-loop snapshot (`potentially_optimal_hyperboxes_`, :116-118); B's pose does not depend on A's score; the loop does not re-enter ConvexHull until all boxes are processed. So per iteration, all 2×N_optimal evals are pairwise independent and can be enqueued back-to-back with a single terminal wait, replaying the per-eval bookkeeping (best-value update + AddHyperBox + improvement callbacks) in the original order afterward — yielding identical stored values, identical optimum, and identical callback sequences. This is the algorithm-level enabler for pipelining; it does not touch GPU code.

- Confidence: high (code path verified; replay-order preserves observable behavior)
- Relevance: this makes the cheapest big win (Cut 2) available without kernel rewrites — matching the user's "per-eval sync removal, not kernel rewrites" lean.

** In-place metric composition constrains streaming: evals must be double-buffered

FastImplantDilationMetric writes *into* the rendered buffer: EdgeKernel writes EDGE_PIXEL into `rendered_image->GetDeviceImagePointer()` (fast_implant_dilation_metric.cu:218-240), DilateKernel writes DILATED_PIXEL into it (:242-271), and DistanceMapMetric then reads that same mutated buffer for `EDGE_PIXEL` (distance_map_metric.cu:46-50). Order within an eval is fixed: Render → edge/dilate (in place) → difference (score 1) → distance-map over the edge pixels (score 2). Consequently:
- The two metrics cannot run concurrently on one buffer, and the next eval's Render (`cudaMemset` at render_engine.cu:716) cannot start until the current eval's last metric kernel finishes reading the image.
- Overlapping eval N's tail with eval N+1's head therefore requires a second GPUImage render output (+ duplicate score buffers), i.e. double-buffered eval state. This is the core of the streamed-pipeline design below and the main structural interaction with 04's architecture shape.
- The biplane path has a free overlap: secondary Render uses a different camera's buffers (gpu_model.cu:144-146), so with async terminal copies the primary metrics' D2H overlaps the secondary render kernels on the same stream with no double-buffering.
- Confidence: high
- Relevance: sets the boundary of what streams can buy; single-stream ordering is mostly sufficient once copies are async — the default stream already serializes correctly, so the minimal design needs no multi-stream complexity.

** Miscellaneous hot-path details

- `Render()` opens with `cudaGetLastError()` per eval, self-annotated "MAYBE DELETE TO SAVE TIME?" (render_engine.cu:713) — a per-eval driver round trip, cheap but pointless in a hot loop where the tail of the function already returns `cudaGetLastError()` (:839). Delete it.
- Per-eval pose upload: none. `SetPose` is host-side (render_engine.cu:354-377); WorldToPixelKernel receives pose scalars as kernel arguments (:725-744). No H2D traffic per eval.
- `WriteImage`/`GetcvMatImage` D2H copies (render_engine.cu:852-856, :880-884) are debug/visualization only — off the hot path.
- The fragment-overflow guard is `fragment_fill_[0] > maximum_stride_size * (threads_per_block - 1)` (render_engine.cu:795-808; constants in include/compute/cuda_launch_parameters.h: maximum_stride_size = 10,000,000, threads_per_block = 256) — i.e. the stride-prefix buffer (10M ints, 40 MB) bounds the algorithm at ~2.55G fragments. This check is the reason sync #2 sits mid-eval.
- Confidence: high
- Relevance: cheap wins to fold into Cut 1 (delete the stray cudaGetLastError) and context for the overflow semantics Cut 3 must preserve.

* The streamed-pipeline design

Goal: keep the GPU busy across evals by removing host-block windows, without multi-stream complexity (default-stream ordering already encodes the dependencies).

- **Phase-separated eval API.** Split the cost callback into *enqueue* (launch all kernels + `cudaMemcpyAsync` terminal copies into the existing pinned buffers + `cudaEventRecord`) and *wait* (read scores after the event). For the non-batched path the wait is immediate; for the batched path it is deferred to the end of the iteration.
- **Double-buffered eval state.** Two GPUImage render outputs (or two device images + one swapped GPUImage) plus a second set of dev score buffers (dev_pixel_score_, dev_distance_map_score_, dev_edge_pixels_count_ — either a second GPUMetrics or buffer arrays). Eval A's metric kernels read image A while eval B's Render memset+writes image B.
- **Iteration batching (DirectOptimizer).** New batch surface on the optimizer (e.g. an optional `batch_cost` callback `std::vector<double>(std::vector<Point6D>)` or a deferred-result API): TrisectPotentiallyOptimal collects the iteration's poses, the cost layer enqueues all evals back-to-back (alternating buffers A/B/A/B...), the mid-eval fragment sync of eval k waits while eval k-1's tail runs on the GPU, and one terminal event wait per iteration harvests all scores; bookkeeping replayed in original order (identical values, identical callback sequence).
- **What stays synchronous.** The fragment-fill D2H (render_engine.cu:786-790) remains mid-eval in Cuts 1-2 — but in the batched design its wait overlaps the *previous* eval's already-enqueued kernels, so it stops being an idle bubble. Only Cut 3 removes it entirely.
- **Biplane overlap for free.** Keep the primary metrics' async copies outstanding while enqueuing the secondary Render + FastImplantDilationMetric (different camera buffers, default-stream order is safe); wait once at the end. No double-buffer needed for this one.
- **Streams vs. single stream.** Two explicit streams (copy stream for the D2H + compute stream for kernels, joined by events) are an optional refinement once events exist; the default-stream version captures most of the win with less risk. 04's architecture angle owns the broader backend shape; the seam here is only "eval state is double-buffered and the cost layer can enqueue before it waits."

- **Per-stage within an eval**: `RenderEngine::Render` (render_engine.cu:711), `GPUMetrics::FastImplantDilationMetric` (fast_implant_dilation_metric.cu:169), `GPUMetrics::DistanceMapMetric` (distance_map_metric.cu:71).
- **Per-iteration**: the DirectOptimizer `Run` loop body (direct_optimizer.cpp:41-49) — this makes the batch boundary visible once Cut 2 lands.
- **Per-frame**: `OptimizerManager::Optimize` frame-loop body (optimizer_manager.cpp:970-1050 region; the frame loop sets budgets at :991-993) — name it "frame N".
- **Per-sync markers**: `nvtx3::mark` immediately before each of the 5 D2H copies (render_engine.cu:781,786; fast_implant_dilation_metric.cu:289; distance_map_metric.cu:110,115) so Nsight shows exactly which sync drains what.

* Measurement protocol (first profiling run)

1. **Event-based per-eval wall clock** in `test/oracle/oracle_test.cpp`: `cudaEventRecord` start/stop around `p.trunk->callActiveCostFunction()` inside the DirectOptimizer cost lambda (oracle_test.cpp:286-290), accumulating per-eval mean/p50/p95 across the budget. Record the same for `Render()` alone, `FastImplantDilationMetric` alone, `DistanceMapMetric` alone.
2. **Compare against the clock() meter** (optimizer_manager.cpp:1274): capture both simultaneously in a harness run; quantify the gap. Expect event-time > clock()-time whenever syncs or kernels dominate — that gap is the proof of the item-8 claim's magnitude.
3. **Nsight Systems trace** (with the nvtx ranges above): per-eval breakdown = kernel time (sum of ~15 kernel spans) vs. sync stall (gaps between the last kernel before each D2H and the first kernel after the wait) vs. driver/launch overhead. The decisive number: total GPU-active time per eval vs. total wall time per eval.
4. **Nsight Compute** on FillTriangleKernel and DilateKernel: confirm they are memory/latency-bound small kernels (no hidden fat kernel), which justifies treating kernel time as roughly irreducible and sync time as the target.
5. **Bit-identity harness**: a recorded fixed pose sequence (e.g. first 1000 evals of the oracle's frame 0) dumped as (pose → cost) pairs; re-run after each cut and diff — must be identical (int-atomic reductions make this achievable; see determinism finding).
6. **Gate structure for every cut**: (a) headless suite green (`pixi run test`), (b) oracle green (IoU ≥ 0.85 on all 3 frames, oracle_test.cpp:245,333; TIMEOUT 3600 in test/CMakeLists.txt:1253), (c) bit-identity diff empty where claimed, (d) measured per-eval event-time improvement ≥ the cut's predicted Δ (a cut that doesn't move the needle gets reverted — measure-first discipline).

* Ordered cuts with gates

** Cut 0 — Instrument (no behavior change). nvtx3 ranges + event timing + nsys/ncu capture + baseline table. Gate: baseline recorded (per-eval kernel time vs sync stall vs launch overhead; clock()-meter vs event-meter gap). Nothing to regress.

** Cut 1 — Async terminal copies + one event wait per eval (cheapest, highest win-per-risk). Convert the 3 terminal D2H (fast_implant_dilation_metric.cu:289-290; distance_map_metric.cu:110-119) to `cudaMemcpyAsync` into the existing pinned buffers + `cudaEventRecord`/`cudaEventSynchronize` at the eval boundary; fold in the stray `cudaGetLastError()` deletion (render_engine.cu:713). Net effect: 3 sync round trips become 1 event wait; the distance-map pair shares one drain with the fast-implant score; the copies overlap each other and the kernels' tails. Gate: oracle green; per-eval event-time down by measured Δ; bit-identity diff empty. Expected: removes ~2 of 3 drain windows per eval + 2-3 driver round trips — likely 10-40% of per-eval wall time, pending Cut 0 numbers.

** Cut 2 — Iteration batching + double-buffered eval state (the streamed pipeline; no kernel rewrites). DirectOptimizer batch surface (collect iteration poses → enqueue all evals back-to-back on alternating buffers → one terminal wait → replay bookkeeping in original order); second render output + duplicate dev score buffers. The mid-eval fragment sync stays but its wait now overlaps the previous eval's tail. Gate: oracle green; optimum pose + cost values bit-identical to a baseline run of the same seed/budget (callback replay order preserves behavior); per-eval event-time drops further. This is the user's "per-eval sync removal" in its strongest non-kernel form.

** Cut 3 — Remove the fragment-fill mid-eval sync (the one kernel-level change; conditional). Only if Cut 0-2 leave render_engine.cu:786-790 as the dominant remaining stall. Mechanics: clamp the guards in StridePrefixKernel (render_engine.cu:812-813) and FillTriangleKernel (:823-824) to `min(fragment_fill, SAFE_CAP)` with SAFE_CAP = maximum_stride_size * threads_per_block, so the stride-prefix buffer can never be written out of bounds; launch those two kernels with a fixed grid sized from a per-model worst-case bound; move the overflow check to a deferred async read (frame aborts at detection — the current behavior is already abort-the-frame, render_engine.cu:795-808). Bit-identity: threads `< fragment_fill` must do exactly today's work (extra threads exit at the guard; no writes, no shared-memory init change). Gate: oracle green; non-overflow renders bit-identical; overflow frames still error the frame. If the analytic worst-case grid is unacceptable (fragment count is pose-dependent and can exceed any fixed bound), keep the sync and accept it as the one structural cost.

** Cut 4 — Fix the meter (optimizer_manager.cpp:1272-1278). Replace `clock()` with a wall-clock (std::chrono::steady_clock for host-side, cudaEvent for GPU-inclusive) so ms/call includes GPU + sync time. Gate: meter tracks the event-measured per-eval time within noise. This is required before any of Cuts 1-3 can be *demonstrated* to the user via the UI meter.

** Biplane note (free win, fold into Cut 1): with async terminal copies, the primary metrics' D2H overlaps the secondary Render kernels (separate buffers, gpu_model.cu:144-146) with no double-buffering — wait once at the end of costFunctionDIRECT_DILATION's biplane branch.

** CPU fallback for Tier-0 — recommend against. The headless Tier-0 suite is already CUDA-free by construction: DirectOptimizer is pure (direct_optimizer.h:11-13 "zero Qt/VTK/CUDA/JTML dependencies") and tested with injected costs (test/CMakeLists.txt:46-63, 86-97); cost-parameter logic has deterministic twins (test/CMakeLists.txt:236-265). The GPU cost path's only gate is the `oracle` label (test/CMakeLists.txt:1150-1254), which is exactly what Cuts 0-3 make GPU-CI-tractable. A CPU rasterizer + dilation port is a separate large project with no current consumer; if CPU-side coverage of the cost *math* is wanted, that belongs to 02's metric-math tests (host-side reference implementations), not a render engine port.

* What Could Not Be Verified

- Actual per-eval kernel times, sync-stall latencies, and the kernel-vs-sync split — requires Cut 0 on the RTX 3090 (oracle machine). The item-8 claim's *magnitude* is unverified; only its structural plausibility is confirmed.
- Whether a fixed FillTriangle grid with a pose-independent worst-case bound is tractable — the fragment count is pose-dependent (per-triangle projected bbox areas), so Cut 3's grid bound needs a measurement-informed decision; the fallback (keep the sync) is safe.
- `nsys` availability on the GPU box — nsight-compute is in pixi.lock, nsight-systems is not; the profiling run may need `pixi add nsight-systems`.
- Whether `cudaEventSynchronize` per eval (Cut 1) still pays a meaningful driver wake-up latency on this driver/arch — the measurement protocol decides whether Cut 2's deeper restructuring is justified.
- The exact production image size and triangle count of KR_right_7_fem.stl at runtime (oracle uses 1024×1024, oracle_test.cpp:60-61) — affects absolute kernel times but not the sync structure.

** Key Findings (Round 2)

*** R2-1 — The clock() meter has a 1000× unit error on Linux, on top of the CPU-time blind spot

- grep of src/ for CLOCKS_PER_SEC: zero hits — the meter divides raw clock() ticks by calls with no unit conversion: `static_cast<double>(clock() - start_clock_) / static_cast<double>(cost_function_calls_)` (optimizer_manager.cpp:1198-1199) and the RunDirectStage twin (:1274-1275).
- On Linux glibc, clock() returns microseconds (CLOCKS_PER_SEC = 1e6; MSVC uses 1000). The code labels the value "ms/call"; the actual value is CPU-µs/call → 1000× unit error. The JTA codebase is a Windows-Qt origin, so this is plausibly port-induced — but on this Linux/pixi build the error is live.
- UI consumption compounds it: "Iterations Per Second: 1000.0 / iteration_speed" (view/mainscreen.cpp:4654-4655) with iteration_speed in µs/call yields calls-per-ms — 1000× understated (and further understated because CPU time excludes sync-wait). The ETA `(budget − calls) / (1000.0 / iteration_speed)` (:4598, :4659) produces remaining milliseconds displayed as mm:ss — ~1000× overstated.
- Severity: medium-high for the meter's purpose (user-facing speed/ETA are wrong by ~3 orders of magnitude; no before/after perf claim through this meter is meaningful); high as a correctness fact.
- Confidence: high (code path verified; no CLOCKS_PER_SEC anywhere; the platform unit semantics are POSIX-standard). The "port-induced" attribution is medium (original codebase not verifiable here).
- Relevance: Cut 4 must (a) switch to steady_clock wall time and (b) emit TRUE ms/call so the existing UI math (1000.0/ms_per_call) becomes correct without a UI-side change.

*** R2-3 — Cut 3's fixed grid is bounded by arithmetic: stride-prefix capacity + in-kernel guards make it a host-side change

- dev_stride_prefixes_ is allocated once at maximum_stride_size × sizeof(int) = 10M × 4 B = 40 MB (render_engine.cu InitializeCUDA, :311-312 region). StridePrefixKernel writes one entry per 256-fragment stride group (index i, guarded i < total/256, :592-593); FillTriangleKernel reads dev_stride_prefixes[blockIdx.x] with blockIdx.x < total/256. Both stay in-bounds iff total ≤ maximum_stride_size × 256 ≈ 2.56e9.
- The existing host overflow guard is `fragment_fill_[0] > maximum_stride_size × (threads_per_block − 1)` = 2.55e9 (render_engine.cu:795-800), i.e., exactly the capacity bound (threads_per_block = 256, include/compute/cuda_launch_parameters.h). SAFE_CAP = maximum_stride_size × threads_per_block is the device-capacity ceiling; nothing above it is launchable anyway.
- Bit-safety of a fixed grid: BOTH fill kernels wrap their entire body — including FillTriangleKernel's shared-memory load and __syncthreads (:636-641) — inside `if (i < total)` (:628-629); StridePrefixKernel likewise (:592-593). Threads/blocks beyond the true count execute nothing and write nothing. Therefore launching grids computed from min(fragment_fill, GRID_CAP) needs NO kernel-source change: threads < total do exactly today's work.
- The real tractability question is launch cost, not correctness: a grid at the analytic ceiling is ceil(2.55e9/256) ≈ 10M blocks of FillTriangleKernel — schedulable (gridDim.x limit 2³¹−1) but with per-block overhead that must be measured. The worst-case analytic fragment count (all 12,412 facets spanning the full 1024² image ≈ 1.3e10) exceeds capacity, so overflow is geometrically possible in the extreme → the sync-fallback is mandatory, not optional.
- Severity: high (this arithmetic is what makes Cut 3's decision procedure executable — it shrinks the cut from "kernel-level change" to a host-side grid computation + measured GRID_CAP).
- Confidence: high (all guard/alloc lines verified).

** Cut 3 — fragment-fill removal: the decision procedure (conditional)

Trigger measurement (during Cut 0): the fragment sweep (fragment_fill_[0] min/max/p99/max-ever + bbox per eval over frame-0's 3000 evals) plus the render-drain time (event gap from PrepareLaunchPacketKernel completion to the fill kernels' start).

Trigger condition (BOTH must hold; pre-registered from Cut 0's data):

(a) the render drain (bbox+fragment sync + overflow check + launch latency) is the dominant remaining per-eval stall after Cuts 1-2 — e.g., ≥ 50% of per-eval wall (number fixed from Cut 0's table);
(b) the fragment distribution is tightly bounded: max_observed × margin < SAFE_CAP = maximum_stride_size × threads_per_block = 2.55e9 (the capacity ceiling, R2-3), AND a GRID_CAP/256-block launch is affordable (measure the empty-grid launch time for the chosen GRID_CAP — the analytic ceiling would be ~10M blocks, so the practical GRID_CAP comes from the measured distribution, e.g., next power-of-two ≥ max_observed × 2).

Device-side clamp design (R2-3 makes it a host-side change): compute `fill = min(fragment_fill_[0], GRID_CAP)`; launch StridePrefixKernel and FillTriangleKernel from `fill` (ceil(fill/(256×256)) and ceil(fill/256) — the existing launch expressions at render_engine.cu:812-816/:823-826 with the value substituted). Optionally clamp on-device (PrepareLaunchPacketKernel writes min(fragment_fill, GRID_CAP) to a second device int) so the host never needs the true value to launch. NO kernel-source change: threads/blocks beyond the true total exit at the existing in-kernel guards (StridePrefixKernel :592-593; FillTriangleKernel :628-629, which wraps the whole body including the shared-mem load + __syncthreads :636-641), writing nothing. Non-overflow renders are bit-identical by construction (threads < total do exactly today's work).

Overflow semantics preserved (non-negotiable): if fragment_fill_[0] > GRID_CAP, the eval must NOT silently under-render (fragments in (GRID_CAP, total) would never be processed). Two safe behaviors: (i) per-eval fallback to the synchronous read + dynamic grid (the current path — keep the sync as the tail handler), or (ii) abort the frame exactly as today (fragment_overflow_ = true + cudaErrorMemoryAllocation, render_engine.cu:795-808). The fallback keeps bit-identity for all non-fallback evals and preserves error behavior for the tail. The bbox sync (:781-785) is NOT touched by Cut 3 (the crop/grid host math still needs it).

Safe fallback (the decision's default): if (a) or (b) fails — unbounded tail, or GRID_CAP blocks unaffordable — keep the fragment sync and accept it as the one structural cost; in the batched pipeline (Cut 2) its wait already overlaps the previous eval's tail, so the remaining exposure is small. This is a measured no-go, not a punt.

Prediction: Δ = the measured render-drain sum minus the residual fallback cost. Gate: oracle green, non-overflow bit-identity empty, overflow frames still error, event-time reduction ≥ prediction.

* Round 3

** Summary

The corpus's rendering/DRR evidence turns the cross-era throughput datum into a full, falsifiable baseline and gives the cut order its first external anchors. Flood 2018 (floodAutomatedRegistration3D2018.txt) is verified end-to-end as the sanity baseline: 145,000 evals (50k trunk + 3×15k branch + 50k z) at ~3,000 iterations/s = 333 µs per eval on a GTX 970 (the paper's own arithmetic checks: 145,000/3,000 ≈ 48 s ≈ "50 seconds per frame"), where the eval is deliberately GPU-cheap ("a simple L1 norm... can be computed by a GPU extremely efficiently" — render + one L1 pass, no chamfer, no per-eval input dilation). Abdellah 2015 measured the SAME GTX 970 rendering volumetric DRRs at 25 ms/2048² and 67 ms/4096² — so a silhouette eval is ~2 orders of magnitude cheaper than a volumetric DRR on identical silicon, and JTML's derived 16–50 ms/eval on an RTX 3090 (4.2× bandwidth, ~9× FP32) sits squarely in volumetric-DRR territory while doing silhouette work: the cross-era arithmetic implies ~95%+ of JTML's per-eval wall is host-side, a pre-registration Cut 0 can falsify (GPU-active per-eval > 1 ms inverts the cut order). The fast-DRR family licenses almost nothing for the fragment-fill rasterizer itself — bindless textures accelerate reads on volumetric cudaArrays, not the scatter-writes of a linear-memory fill (render_engine.cu:628-700); block projection (Mu 2016) and splatting are approximate-reuse techniques that break the run's bit-identity/determinism contract; CUDA/OpenGL interop is display-only. The real transfers are: Dorgham's "similarity on the GPU" doctrine — the primary-text antecedent of Cuts 1–3, with a measured ~2 ms CPU-similarity ≈ D2H-copy parity; Flood's own batch-render future-work note (L761–765) — the antecedent of Cut 2, verbatim; the field's sampled/reduced-resolution DRR evidence (registration-accuracy-preserving at 50% compression, failing at 75%) — the spec for a render-resolution ablation arm beyond the cuts; and Tornai's block-size data (10–145% swings) — a zero-semantics knob for Cut 0's ncu pass. Pre-registered evals/s on the 3090: today 20–60 (derived), Cut 1 → 60–300, Cut 2 → 1,000–5,000 with Flood's 3,000 evals/s as the cross-era parity line; Cut 4's meter fix gains a wall-clock cross-check gate.

** Key Findings (Round 3)

*** R3-1 — Flood 2018 is the sanity baseline, verified verbatim (arithmetic + cost semantics)

- Budget and speed (floodAutomatedRegistration3D2018.txt L568–574): "The iteration budget was 50,000 for the trunk search, 15,000 for each of the three branch searches, and 50,000 for the z-translation search. Using a 4GHz Intel Core i7 4790K in conjunction with a Nvidia GeForce GTX 970, a GPU based version of the registration routine achieved speeds of approximately 3,000 iterations per second (50 seconds per frame)." Arithmetic check: 145,000/3,000 = 48.3 s ≈ "50 seconds per frame" — "iteration" = cost-function eval; per-eval = 333 µs INCLUDING DIRECT bookkeeping on the host.
- Cost semantics (L157–162): "The score is a simple L1 norm that rewards matching edges and punishes overlapping black space. There is no need for normalization because we are interested in finding the global minimum... We use L1 in place of other p-norms because it can be computed by a graphics processing unit (GPU) extremely efficiently." The eval = silhouette render + one L1 pass; the input Canny frame is dilated ONCE per stage (not per eval); there is NO chamfer/distance-map term and no per-eval input dilation — JTML's extra metric stages (fast-implant edge/dilate/difference + distance-map chamfer, ~7 kernels) are the workload delta vs Flood, not the render.
- Budget-by-time design (L568): "Iteration count for the algorithm was pegged to take approximately one minute of operating time." The lineage sizes budgets by WALL TIME; JTML's are fixed eval counts (20k/5k×2/5k). If the cuts raise evals/s toward Flood's rate, each frame gets faster in wall time without changing the search — a pure win — but the lineage's time-budget framing is a flag for the budget-constants conversation (they were tuned against a slow pipeline).
- Confidence: high (verbatim quotes; arithmetic verified). Relevance: this is the baseline the dispatch requires — the first nvtx/cudaEvent record must report JTML's per-eval time against 333 µs/eval (GTX 970, 2018).

*** R3-2 — Same-GPU cross-check: a volumetric DRR costs ~2 orders more than a silhouette eval on the identical GTX 970

- Abdellah 2015 (abdellahGPUAccelerationDigitally2015.txt L14–15, L333–337): bindless-texture + ray-march volumetric DRR pipeline on "an NVIDIA GeForce 970 GTX": "the pipeline line can generate 2048² and 4096² DRRs at 40 and 15 frames per second respectively" — i.e. 25 ms and 67 ms per volumetric DRR, versus Flood's 333 µs per silhouette+L1 eval on the same GPU: a 75–200× per-frame gap. This validates that the silhouette+L1 design is the field's cheap-cost choice and that JTML's fragment-fill renderer (also silhouette-based) belongs in the µs-per-eval regime, NOT the ms-per-eval regime.
- Cross-check corroboration: Tornai 2012 (tornaiFastDRRGeneration2012.txt L21–23) ray-cast DRR of a 400×225 ROI = 2.7–5.2 ms full-ROI (0.3–7.3 ms at 1.1–9.1% sampling) on 2007–2010 GPUs; Dorgham 2012 (dorghamGPUAcceleratedGeneration2012.txt L27–30) 256³ CT DRR ≈ 24 ms (8800 GTX) / ≈ 2 ms (GTX 580); Ikebe 2023 (ikebeDRRAccelerationUsing2023.txt L195–197, L424) Siddon–Jacobs DRR ≈ 61 ms on a laptop GTX 1650 Ti; Gopalakrishnan 2022 (gopalakrishnanFastAutoDifferentiableDigitally2022.txt L135–136) 200² DRR = 72.7 ms on an RTX 2080 Ti (PyTorch-vectorized — see R3-4 item 7). Volumetric DRRs are uniformly tens-of-ms; Flood's silhouette eval is sub-ms.
- Confidence: high (all numbers verbatim; the 75–200× ratio is arithmetic). Relevance: if Cut 0 measures JTML's per-eval wall in the tens-of-ms, the magnitude of the sync-bound claim is confirmed against the field's own per-eval economics; the comparison also quantifies how much headroom a GPU-only cost would have.

*** R3-3 — Cross-era arithmetic: JTML's derived 16–50 ms/eval on a ~9×-faster GPU implies ~95%+ host-block fraction (pre-registered, falsifiable)

*** R3-4 — Fast-DRR family vs the fragment-fill rasterizer (render_engine.cu): per-technique applicability verdicts
