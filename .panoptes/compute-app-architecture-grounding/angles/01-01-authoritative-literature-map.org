* Summary
The direct answers to the user's three working beliefs, with evidence:
- Belief (a) "MVVM works great for CRUD/microservices but compute land is idiosyncratic": partly true, partly not. TRUE at the popular layer: the post-2000 bestseller canon (PoEAA, DDD, Clean Architecture, the microservices wave) and the MVVM canon (Josh Smith's MSDN article, Qt's model/view docs) are enterprise/UI-framework-shaped. ** Group 1 — The modularity/seams theory canon (why layer cuts exist)
*** On the Criteria To Be Used in Decomposing Systems into Modules — D.L. Parnas, 1972, paper
- Decomposition should follow explicit criteria — each module hides one design decision (information hiding) so change stays local. This is the origin of "choose the seams before the shapes."
- Confidence: high (ACM DOI + open PDF verified this run)
- [Source: https://dl.acm.org/doi/10.1145/361598.361623 ; open PDF: https://cw.fel.cvut.cz/old/_media/courses/a4m33sep/materialy/architecture_and_design/01-article_original_de_parnas.pdf]
- Relevance to this project: the repo's layer cuts were derived from testability seams + per-cut gates, not from a book; Parnas is the authoritative statement that decomposition criteria (seams) come first. Plan 003's mechanical reorg is a Parnas-style exercise.
*** Out of the Tar Pit — B. Moseley & P. Marks, 2006, paper
- Complexity is the dominant difficulty in large software; most is *accidental*; mutable state is a major accidental-complexity driver; argues for a functional core with data at the edge.
- Confidence: high
- [Source: https://curtclifton.net/papers/MoseleyMarks06a.pdf]
- Relevance to this project: names the tension behind R12 ("no premature abstraction"): the norm is an essential-complexity stance. Supports keeping jtml_domain pure and state confined to the coordinator.
*** The Architecture of Complexity — Herbert Simon, 1962, paper
- Complex systems are "nearly decomposable" hierarchies; evolution and repair both depend on hierarchical structure.
- Confidence: medium (URL not fetched this run; canonical citation: *Proc. American Philosophical Society* 106(6), 467–482)
- [Source: https://www.jstor.org/stable/985870 — verify the stable ID before citing]
- Relevance to this project: the theoretical justification for the layered restructure: domain/services/compute/view is a nearly-decomposable hierarchy with sealed interfaces between levels.
*** Simple Made Easy — Rich Hickey, 2011, talk
- Simplicity = no interleaving of concerns ("one thing per axis"); easiness ≠ simplicity; complexity accumulates at the seams between things.
- Confidence: high
- [Source: https://www.infoq.com/presentations/Simple-Made-Easy/]
- Relevance to this project: vocabulary for why the Qt-free domain + explicit seams are *simple* even where not *easy*; direct counter to premature abstraction (R12).

** Group 2 — Domain-neutral architecture practice and standards
*** Software Architecture in Practice, 4th ed. — Bass, Clements, Kazman, 2021, book (SEI/Addison-Wesley)
- Architecture = structure plus quality attributes; tactics for performance, modifiability, testability, etc.; architecture is evaluated against explicit scenarios.
- Confidence: high
- [Source: https://sei.cmu.edu/library/software-architecture-in-practice-fourth-edition/]
- Relevance to this project: the repo's normative constraints (R15 behavior preservation, per-cut gates, IoU gate) are quality-attribute scenarios in this vocabulary; this book shows how to make them explicit and checkable instead of implicit.
*** Documenting Software Architectures: Views and Beyond, 2nd ed. — Clements et al., 2010, book (SEI)
- Document architecture through multiple views (module views, component-and-connector views, allocation views), each chosen for its stakeholders and concerns.
- Confidence: high
- [Source: https://sei.cmu.edu/library/documenting-software-architectures-views-and-beyond-second-edition/]
- Relevance to this project: plan 003's layer diagram is a module view; V&B is the authority on what else to document — dependency rules per cut, interface contracts, and the headless-test architecture are all documentable as views.
*** Evaluating Software Architectures: Methods and Case Studies — Clements, Kazman, Klein, 2001, book (ATAM method)
- Scenario-based evaluation (ATAM): derive quality-attribute scenarios, analyze trade-offs, make risks explicit.
- Confidence: high
- [Source: https://sei.cmu.edu/library/evaluating-software-architectures-methods-and-case-studies/]
- Relevance to this project: the per-cut gates + GPU oracle are a lightweight project-specific ATAM; this is where "make your evaluation criteria explicit before you cut" is canonized.
*** ISO/IEC/IEEE 42010:2011 — Systems and software engineering — Architecture description, 2011, standard
- The international standard for architecture description; core concepts: architecture, architecture description, viewpoint, view, concern, stakeholder. Supersedes IEEE 1471-2000.
- Confidence: high
- [Source: https://www.iso.org/standard/50508.html ; community overview: http://www.iso-architecture.org/42010/]
- Relevance to this project: the standard vocabulary if the project documents its architecture formally (concerns: performance of the cost loop, testability, Rust interop, QML surface).
*** Hexagonal Architecture (Ports & Adapters) — Alistair Cockburn, 2005, essay
- "Create your application to work without either a UI or a database": the domain core sits at the center; adapters plug into ports; the app is regression-testable headless.
- Confidence: high
- [Source: https://alistair.cockburn.us/hexagonal-architecture]
- Relevance to this project: this is the literature's *name for the repo's shape*: Qt-free jtml_domain, injected std::function cost into DirectOptimizer, composition root in src/app, headless test suite. The user's architecture already is hexagonal; the map gives it a citable name.
*** The Clean Architecture — Robert C. Martin, 2012 essay (book 2017)
- The Dependency Rule: source-code dependencies point inward; UI, frameworks, and tools are peripheral; domain at the center.
- Confidence: high
- [Source: https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html]
- Relevance to this project: names the direction the repo already encodes (Qt/VTK/CUDA peripheral, jtml_domain central). Caveat: the essay's examples are enterprise-shaped — see the CRUD-bias section.
*** Presentation Domain Data Layering — Martin Fowler, bliki
- The canonical statement of the presentation/domain/data layering vocabulary, including when it does and does not apply.
- Confidence: high
- [Source: https://martinfowler.com/bliki/PresentationDomainDataLayering.html]
- Relevance to this project: the repo's layer names (view/domain/services) descend from exactly this vocabulary; the essay is the reference point for the naming debate (angle 02 territory).
*** Strangler Fig Application + Legacy Seam — Martin Fowler, bliki

- Confidence: high
- [Sources: https://martinfowler.com/bliki/StranglerFigApplication.html ; https://martinfowler.com/bliki/LegacySeam.html]

*** Design Patterns — Gamma, Helm, Johnson, Vlissides (GoF), 1994, book
- 23 OO collaboration patterns; domain-neutral catalog; the baseline vocabulary for "the objects you operate on" at the interaction level.
- Confidence: high

** Group 3 — Compute-heavy: parallel patterns, GPU, numerics (the "compute land" canon)
*** The Landscape of Parallel Computing Research: A View from Berkeley — Asanovic et al., 2006, tech report
- The "dwarfs"/motifs taxonomy of compute: dense/sparse matrix, spectral, N-body, structured/unstructured grids, Monte Carlo; parallel software must be re-thought at the algorithm-structure level.
- Confidence: high
- [Source: https://www2.eecs.berkeley.edu/Pubs/TechRpts/2006/EECS-2006-183.html ; PDF: https://www2.eecs.berkeley.edu/Pubs/TechRpts/2006/Archive/EECS-2006-183.pdf]
- Relevance to this project: 2D-3D registration over GPU renders is structured-grid + dense-matrix work; this report is the canonical classification of *why* compute kernels are shaped as they are, and it is entirely non-CRUD.
*** Structured Parallel Programming: Patterns for Efficient Computation — McCool, Robison, Reinders, 2012, book
- The pattern catalog for parallel computation: map, gather, scatter, stencil, transpose, reduction, scan, pack, partition, fork-join.
- Confidence: high
- [Source: https://shop.elsevier.com/books/structured-parallel-programming/mccool/978-0-12-415993-8]
- Relevance to this project: each of the ~15 kernel launches in the cost function is one of these named patterns; the 7 cost variants are different reductions/scans/stencils over the same geometry. Best single reference for "what pattern is my kernel?"
*** Patterns for Parallel Programming — Mattson, Sanders, Massingill, 2004, book
- A four-part pattern language: finding concurrency; algorithm structure (task, divide-and-conquer, geometric decomposition); supporting structures; implementation mechanisms.
- Confidence: high
- [Source: https://www.oreilly.com/library/view/patterns-for-parallel/0321228111/]
- Relevance to this project: the design-method complement to McCool: how to decide between task vs geometric decomposition for the optimizer's parallel cost evaluation.
*** A Philosophy of Software Design — John Ousterhout, 2018 (2nd ed. 2021), book
- Complexity is the fundamental problem; deep modules (large implementation, minimal interface); "define errors out of existence"; red flags. Written from an OS/systems background, not enterprise.
- Confidence: high
- [Source: https://www.web.stanford.edu/~ouster/cgi-bin/book.php]
- Relevance to this project: the DirectOptimizer cost-function interface and the CostFunctionManager registry are "deep module" designs in this vocabulary; a mainstream, non-CRUD authority that transfers cleanly to compute.
*** Data-Oriented Design — Richard Fabian, 2018, book; Data-Oriented Design and C++ — Mike Acton, CppCon 2014, talk
- DOD: understand the goal, the data, and the hardware before the classes; SoA over AoS; hot/cold data splitting; "data is the problem, not your objects."
- Confidence: high
- [Sources: https://www.dataorienteddesign.com/dodbook/ ; https://www.youtube.com/watch?v=rX0ItVEVjHc]
- Relevance to this project: the cost loop (~7k evals/s, ~15 launches + ~5 synchronous D2H memcpys per eval) is exactly the cache/synchronization-bound regime DOD targets; this is the authoritative counter-literature to OO-first decomposition inside the compute core, and an active debate the user should know exists.
*** What Every Computer Scientist Should Know About Floating-Point Arithmetic — David Goldberg, 1991, paper
- IEEE-754 semantics, rounding, cancellation, error analysis; the canonical numerics-semantics reference.
- Confidence: high
- [Source: https://docs.oracle.com/cd/E19957-01/806-3568/ncg_goldberg.html ; ACM: https://dl.acm.org/doi/10.1145/103162.103163]
- Relevance to this project: the determinism doctrine (int vs float atomics, ordered reductions, bit-identical reruns), IoU-gate thresholds, and oracle comparisons all live under this paper's rules.
*** Programming Massively Parallel Processors: A Hands-on Approach — Kirk & Hwu (4th ed. 2022; 5th ed. Feb 2026), textbook
- The standard GPU/CUDA textbook: memory hierarchy, occupancy, kernel design, reduction patterns.
- Confidence: high
- [Source: https://shop.elsevier.com/books/programming-massively-parallel-processors/hwu/978-0-443-43900-1]
- OVERLAP FLAG: angle 05 owns the deep CUDA treatment; here it is mapped as the compute canon's textbook.
- Relevance to this project: the reference for the kernel-level patterns (reductions, atomics, memcpy/stream overlap) behind the cost function.
*** CUDA C++ Programming Guide — NVIDIA, official documentation
- The platform's primary specification: programming model, execution model, memory model, performance guidelines.
- Confidence: high, with a recency note: the guide tracks current CUDA (13.x era as of 2026); the project pins CUDA 12.4, which predates current releases — check the guide's version notes before citing specifics.
- [Source: https://docs.nvidia.com/cuda/cuda-programming-guide/index.html]
- OVERLAP FLAG: angle 05.

* The CRUD/Microservices Bias: Where It Comes From and What Counters It
** The origin of the bias (sources for the claim)
- Patterns of Enterprise Application Architecture — Fowler, 2002 [Source: https://martinfowler.com/books/eaa.html]. By its own author's framing, this book is about *enterprise* applications (DB-backed, business-logic-heavy, web/client-server). It is the ancestor of the presentation/domain/data vocabulary the repo's layer names echo — the vocabulary carries enterprise assumptions with it.
- Domain-Driven Design — Evans, 2003 [Source: https://www.domainlanguage.com/ddd/]. "Domain" here means *business-process domain* (aggregates, entities, repositories for orders/customers). Transfer to compute requires translation: the user's domain is geometry/registration, not business transactions.
- The Clean Architecture — Martin, 2012/2017 [Source: https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html]. The Dependency Rule is domain-neutral, but the book's entities and examples are enterprise-flavored.
- The microservices wave, 2014–2018 — Fowler & Lewis's Microservices guide [Source: https://martinfowler.com/microservices/], Microservice Trade-Offs [Source: https://martinfowler.com/articles/microservice-trade-offs.html], Monolith First [Source: https://martinfowler.com/bliki/MonolithFirst.html]; Newman's *Building Microservices* (2nd ed. 2021) and Richardson's *Microservices Patterns* (2018) are the two canonical books (authoritative for microservices only; their pages were not fetched this run — see What Could Not Be Verified); Kleppmann's DDIA (2017) is server-centric by design [Source: https://dataintensive.net/]. All of these presume HTTP + databases + processes.
- Framework amplification: the MVVM canon is UI-framework-bound by construction — Josh Smith's canonical MVVM article (MSDN Magazine, Feb 2009) is explicitly about WPF line-of-business UI [Source: https://learn.microsoft.com/en-us/archive/msdn-magazine/2009/february/patterns-wpf-apps-with-the-model-view-viewmodel-design-pattern]; Qt's own model/view documentation scopes the pattern to UI data presentation [Source: https://doc.qt.io/qt-6/model-view-programming.html]. This is where "MVVM works great for CRUD apps" comes from: MVVM's home turf is the presentation tier of data-entry UIs, not the architecture of a compute core.
- Net claim: the skew the user senses is a property of the *popular* layer (2000s-2010s bestsellers + framework tutorials), and it is traceable to those sources. The repo's own layer naming is directly descended from the enterprise vocabulary (via PresentationDomainDataLayering [Source: https://martinfowler.com/bliki/PresentationDomainDataLayering.html]) — so the user is right to want a second, non-enterprise grounding.
