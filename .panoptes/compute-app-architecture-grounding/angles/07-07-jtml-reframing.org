#+TITLE: JTML Re-Framing: A Wide Menu of Architecture Options
#+DATE: 2026-08-13
#+PANOPTES_ANGLE: 07-jtml-reframing

* Summary

Read as a principal engineer doing an architecture assessment: JTML's current layering is better-grounded than the "no authoritative reference" feeling suggests — it embodies functional-core, ports-and-adapters, and characterization-testing patterns *by accident of being testability-driven* — but it is vocabulary-orphaned (plan 003's External References section is empty), data-flow-blind (no explicit map of what crosses each boundary), and the words it chose (domain/services/coordinator) collide with loaded architecture vocabulary. This report offers a wide menu of **19 named re-framing options across 6 families** (keep-and-justify, re-layer, data-shaped, language-driven, ecosystem-native, hybrid), each with what changes, what stays, what breaks (R15/R12 exposure), cost/benefit, and its external evidence base. Per the assignment, this is a menu, **not a recommendation** — the menu-at-a-glance table at the end is the decision surface. Sibling angles 01–06 are still in flight; each option notes where their findings would strengthen the evidence base.

* Current-Shape Assessment

** What works — the case for the status quo (challenging belief (a))

The current shape is *not* without authority; it converges on published architecture patterns from the testability direction:

- **The injected-cost seam is an output port.** `DirectOptimizer` takes a `std::function<double(const double*)>` cost — that is literally a ports-and-adapters "port" (adapter = `jtml_compute`). The headless suite plugs a fake cost in and runs the whole optimizer — the port is already load-bearing. [Source: local-recon.org (recon of this run), docs/plans/2026-08-07-003-refactor-layered-directory-restructure-plan.md] — Confidence: high
- **`jtml_domain` is a provable functional core.** Nine files grep-gated to zero `QObject|vtk|cuda|torch|opencv` — a pure value-and-function surface with a planned Rust FFI boundary. Gary Bernhardt's "Boundaries" thesis is exactly "use simple values as boundaries between components" (https://www.destroyallsoftware.com/talks/boundaries). The repo's purity gate is a machine-checked instantiation of that. — Confidence: high
- **Per-cut gates + R15 are the discipline external literature recommends for restructuring.** Behavior-preserving relocation verified by oracle + headless + manual-visual gates is the "characterization test before refactor" doctrine (Michael Feathers: https://michaelfeathers.silvrback.com/characterization-testing) applied as a team-wide norm — the oracle (IoU-gated golden master) is a characterization artifact. — Confidence: high
- **The dependency graph is downward-only and acyclic** (`domain ← services ← coordinator ← view ← app`, `compute` standalone) — that is the Clean Architecture Dependency Rule in miniature (https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html), even though it was derived from CMake link hygiene, not from the essay. — Confidence: high
- **R12 is doing real anti-premature-abstraction work** — no interface layer exists today; the seams that exist (injected cost, headless coordinator, stage-graph registry) were all built because a test or a feature needed them. That is the empirical sequence the literature recommends (abstraction after evidence), not the speculative one it warns about (https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rr-raii aside; see Fowler on refactoring discipline). — Confidence: medium (inference from plan docs)

** What is genuinely suspect — where belief (b) is right

- **No external grounding was ever consulted** — plan 003's "External References: None required" for the naming that shapes every file path ([plan 003, External References section](docs/plans/2026-08-07-003-refactor-layered-directory-restructure-plan.md)). The *behavior* is grounded; the *vocabulary* is not. — Confidence: high
- **The names collide with loaded vocabulary.** "services" (DDD Service Layer vs application services vs microservices — https://martinfowler.com/eaaCatalog/serviceLayer.html), "domain" (DDD rich domain model — which JTML's deliberately-anemic algorithm surface is *not*, per Fowler's critique: https://martinfowler.com/bliki/AnemicDomainModel.html), "coordinator" (MVVM coordinator vs orchestrator). A reader maps the names onto the wrong literature. — Confidence: high
- **Layers were derived from build/test seams, not data flow.** The flow UI → coordinator → optimizer → GPU cost → render is implicit; no doc maps which structs cross which boundary (this run's local-recon lists "no explicit data-flow map" as a gap). Layer placement and data movement are two different axes that have never been checked against each other. — Confidence: high
- **Hot-spot gravity:** `optimizer_manager.cpp` ~1,700 lines interleaves algorithm policy (stage sequence, budgets, dilation) with session/GPU state and signal emission ([plan 008 problem frame](docs/plans/2026-08-12-008-refactor-optimizer-graph-container-plan.md)); `mainscreen.cpp` ~5,115 lines is View + composition-adjacent code (local-recon). The layer *names* imply separation the files don't fully honor. — Confidence: high
- **Compute metrics mutate the rendered image in place** — composition works only by mutation ordering (prior-run finding: `.panoptes/optimizer-deep-dive/synthesis.org`, angle 05). That is an implicit data-flow contract that the architecture docs never state. — Confidence: high
- **"services" layer character drifted:** since plan 004 U8 the services layer links GPU/torch — its name says "headless service", its reality is "GPU-adjacent support" (local-recon). The boundary semantics need either a rename or a documented intent. — Confidence: medium

** MVVM is CRUD-tuned? — the strongest arguments both ways (belief (c))

- For the belief (MVVM is form/data-binding machinery): The pattern's mechanism is per-field property notification and command binding. Martin Fowler's Presentation Model (which MVVM renamed) is explicit: the view "synchronizes its state with Presentation Model frequently," "field or key synchronization" (https://martinfowler.com/eaaDev/PresentationModel.html). Microsoft's own framing: "The view model implements properties and commands to which the view can data bind to, and notifies the view of any state changes through change notification events" (https://learn.microsoft.com/en-us/dotnet/architecture/maui/mvvm). Wikipedia's MVVM article records the known limits: "overkill for simple user interfaces," upfront generalization is hard, and large-scale data binding degrades performance (https://en.wikipedia.org/wiki/Model%E2%80%93view%E2%80%93viewmodel). A 3D viewport's state is not fields — it is GPU buffers, camera, interactor state, render timing — precisely what binding machinery was not built for. — Confidence: high
- Against the belief (MVVM has a real role here): MVVM's testability argument is the strong one — Josh Smith's canonical case is decoupling presentation logic from the view for testability and designer/developer parallelism (https://learn.microsoft.com/en-us/archive/msdn-magazine/2009/february/patterns-wpf-apps-with-the-model-view-viewmodel-design-pattern). JTML's *actual* MVVM surface — `SettingsBridge`, the stage-graph selection VM (`stageGraphs`/`stageGraphIndex` per plan 009), `FrameListModel`/`ModelListModel` QAbstractListModel view-models — is exactly the form-like, stateful, testable territory MVVM/PM was designed for, and the fake-bridge tests already harvest that value. The error in "MVVM is CRUD-tuned" is treating the whole app as an MVVM problem: the compute core is a *pipeline* problem (VTK/CUDA-shaped), while the settings/state/UI surface is a *binding* problem (MVVM-shaped). The two have different native framings — that split, made explicit, is itself one of the options below. — Confidence: high
- Net: the belief is half-right and half-misapplied; the critique's strongest form is "MVVM names the wrong layer for the compute path," not "MVVM is useless here." — Confidence: high

* The Wide Menu

The menu spans six families. Every option states: rationale / changes / stays / breaks (R15/R12 exposure) / cost-benefit / evidence anchor. No recommendation is made; the menu-at-a-glance table is the decision surface.

** Family A — Keep-and-justify

*** A1. Status Quo, Now Authoritative (document-and-adopt)
- Rationale: The cheapest way to "reference something authoritative" is to make the *existing* shape authoritative: map each layer and seam to the external framework it already instantiates (dependency rule, ports, functional core, characterization testing), fill plan 003's empty External References, and write the compound learning into docs/solutions/. This converts "fine that it works" into "demonstrably grounded" without moving a file.
- Changes in JTML: docs only — an architecture ADR/compound learning mapping domain→functional core, injected cost→port, coordinator→use-case orchestration, services→application-layer support, compute→adapter+pipeline, view→Qt model/view; plus a boundary-contract table (see Data-Shaped Sketch). Optionally one grep-guard per claimed property so the claims stay machine-checked.
- Stays: every lib, dir, seam, test, gate.
- Breaks: nothing — R15 trivially preserved; R12 untouched (no new abstractions).
- Cost/Benefit: XS cost (days of writing); benefit is the requested "authoritative reference" plus a map for future reviewers; zero regression surface.
- Evidence: Clean Architecture dependency rule (https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html), Bernhardt boundaries (https://www.destroyallsoftware.com/talks/boundaries), Feathers characterization testing (https://michaelfeathers.silvrback.com/characterization-testing). Strengthened by angle 01 (literature map) — the authoritative mapping table is exactly its deliverable.

*** A2. Naming Alignment (rename into authoritative vocabulary)
- Rationale: The five lib names are the only thing with no external backing. Rename into vocabulary that reads correctly against the literature: e.g., `services` → `application` (Evans/application layer) or `infrastructure`; `coordinator` → `use_cases` or keep `coordinator` but document it as orchestrator; `domain` stays (it is the value surface). A reader should be able to open the repo and map names onto sources.
- Changes in JTML: directory renames + include re-pointing (the exact-string scripted rewrite precedent from plan 003 conventions), CMake target names, packaging `install(TARGETS ...)`, `golden_oracle.org` path refs, AGENTS.md + docs sweep; note `jtml_view`'s AUTOUIC PUBLIC include dir bakes the target name ([plan 003 conventions](docs/solutions/conventions/jtml-layered-lib-split-2026-08-08.md)).
- Stays: the dependency graph, lib count, test suite, all gates.
- Breaks: mechanical R15 exposure (every include site is a compile-checked rename — the zero-prefix grep guards make misses loud); R12 low. Real cost: docs churn and the baked-in target name.
- Cost/Benefit: S–M cost, one-time; benefit is vocabulary that links to literature instead of colliding with it.
- Evidence: Fowler Service Layer catalog (https://martinfowler.com/eaaCatalog/serviceLayer.html), Evans DDD layer naming (book; see angle 01 for the map). Strengthened by angle 01.

** Family B — Re-layer

*** B1. Clean Circles (align to Clean Architecture's four rings)
- Rationale: The current shape already approximates the rings: domain = entities (pure), coordinator's intent controller + stage policy = use cases, viewmodels/pose_file_io/SettingsBridge = interface adapters, Qt/VTK/CUDA/view = frameworks. Aligning explicitly means *naming* the rings in the directory structure and adding boundary interfaces only where control actually inverts (the cost port already exists; a progress port and a persistence port are the other two real ones).
- Changes in JTML: introduce `use_cases/` for OptimizeIntentController + stage-policy code (pulling the policy out of optimizer_manager toward it — plan 008 is already the vehicle); rename nothing else; formalize cost/progress/persistence as thin interfaces in domain.
- Stays: lib split, gates, kernels.
- Breaks: R12 risk is the real one — Clean Architecture's boundary interfaces, taken literally, means inventing interfaces for their own sake; R15 risk only if optimizer_manager is restructured before pins land (it is the 1,700-line hot spot). Cost M.
- Cost/Benefit: M cost; benefit = a universally recognizable map (the most-cited architecture essay in the field) for the part of the system that is genuinely policy-shaped.
- Evidence: https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html (verified: "simple data structures passed across the boundaries"). Strengthened by angle 01 and angle 02 (critique — this family is where over-abstraction risk is documented).

*** B2. Hexagonal Hinge (ports & adapters, made explicit)
- Rationale: JTML is *already hexagonal in embryo*: the injected cost is an output port, the headless coordinator is the test adapter, the oracle is a second adapter on the same port. The option: enumerate the six real ports (Cost, StageGraphRepository, Settings, PosePersistence, Render, Progress), name them in domain, and keep every existing adapter where it is.
- Changes in JTML: ~4–6 thin abstract interfaces in domain (each wrapping an existing seam, not inventing a new one); adapters stay in compute/services/view; no directory move beyond interface files.
- Stays: everything else, including libs and gates.
- Breaks: R12 exposure is bounded *if* each interface wraps an existing seam (the anti-R12 failure is interfaces with a single implementation and no consumer); R15 safe (thin wrappers).
- Cost/Benefit: S–M; benefit = the app becomes readable as a canonical ports-and-adapters diagram, which is the most testable framing the literature offers for exactly this shape of app.
- Evidence: Hexagonal architecture (https://en.wikipedia.org/wiki/Hexagonal_architecture_(software)); Cockburn's original essay is the canonical primary source but its site failed to fetch for this report (see What Could Not Be Verified). Strengthened by angle 01.

*** B3. DDD Layers (Evans vocabulary, honestly anemic)
- Rationale: Adopt Evans' layer names (domain model / application / infrastructure / interface) with the honest caveat that JTML's domain is a *value-and-algorithm surface*, not a rich DDD domain model — Fowler's anemic-domain-model critique cuts exactly here (services carrying all behavior over bags of data). If the user wants DDD vocabulary, the option is to take the vocabulary while documenting that JTML deliberately chooses the anemic shape because the domain is math, not stateful entities (and Rust interop demands plain data).
- Changes in JTML: renames per DDD (services→infrastructure, coordinator→application), plus a decision record explaining why the domain stays "anemic" by design.
- Stays: code semantics.
- Breaks: same mechanical rename exposure as A2 plus the semantic commitment — a reader will expect rich domain models and find none; the ADR must pre-empt that.
- Cost/Benefit: S–M; benefit = vocabulary that has a book behind it; cost = the mismatch must be documented or it misleads.
- Evidence: https://martinfowler.com/bliki/AnemicDomainModel.html (the critique, quoted), https://martinfowler.com/eaaCatalog/serviceLayer.html. Strengthened by angle 02 and angle 03.

** Family C — Data-shaped

*** C1. Flow Map First (document the data flow, change nothing yet)
- Rationale: The user said the framing they *want* is "the way the data is shaped, how that gets passed around, the objects/structs." That map does not exist. Producing it is itself the first re-framing move, and every other data-shaped option needs it to sequence against. Deliverable: one doc (docs/architecture/data-flow.md) with the boundary-contract table below (which structs cross which boundary, who owns them, what never crosses), plus a "hot path" section for the ~7k evals/s loop.
- Changes in JTML: docs + a small number of `static_assert`/compile-time audits (e.g., no raw device pointers outside compute includes) if desired.
- Stays: all code.
- Breaks: none. R15/R12 trivially safe.
- Cost/Benefit: S; benefit = the missing foundation for C2–C5 and for every future reviewer; it is the single cheapest option that directly answers the user's stated desire.
- Evidence: Bernhardt (values at boundaries — https://www.destroyallsoftware.com/talks/boundaries); Clean Architecture's boundary-data rule (https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html). Strengthened by angle 03 (data-centric design survey — the map should use its vocabulary).

*** C2. Value Contracts (typed value objects at every boundary)
- Rationale: Give the flow a small set of immutable value types — Pose6D, StageSpec/StageScript (already exists per plan 008), RunPayload (already passed by value via OptimizerRunLaunch), CostSample (variant, components, total, eval serial), EvalRequest/EvalResult, StateEvent — and forbid anything else from crossing a lib boundary. Concretely this means the compute metrics become pure functions over scratch buffers (killing the in-place mutation ordering), and the optimizer exchanges values, not handles.
- Changes in JTML: compute metric signatures (behavior-preserving: pin-first, then scratch-buffer version, oracle-verified); coordinator already moves payloads by value; view consumes StateEvent values instead of poking coordinator state.
- Stays: libs, gates, kernels.
- Breaks: R15 exposure is the metric purity refactor (the highest-risk single item — the in-place mutation is load-bearing); sequence behind pins + the oracle; R12 low.
- Cost/Benefit: M; benefit = every boundary becomes inspectable, mockable, and cacheable (a pure cost enables caching/CPU fallback — prior-run angle 05 called the scratch buffer "unblocks caching, reuse, and CPU fallback").
- Evidence: Bernhardt boundaries (https://www.destroyallsoftware.com/talks/boundaries), Clean Architecture boundary data (https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html), Fowler Value Object (https://martinfowler.com/eaaCatalog/valueObject.html). Strengthened by angle 03 and angle 05.

*** C3. Cache-Shaped Optimizer (data-oriented design of the hot loop)
- Rationale: The DIRECT hot loop already uses column-sorted storage (`direct_data_storage` — structurally a struct-of-arrays). DOD would make that explicit and extend it: hot/cold split of per-stage state, batch eval state as contiguous arrays, zero per-eval allocations, and document the layout as architecture rather than accident. This is the "organize data so what you process is adjacent in memory" pattern — relevant at 7k evals/s where each eval is sync-bound (prior-run angle 05) and cache misses in the DIRECT bookkeeping add real latency.
- Changes in JTML: storage internals in domain (layout reorg only, behavior-identical arithmetic), compute already hoists allocations; add a layout doc.
- Stays: all seams and APIs.
- Breaks: R15 exposure is subtle — float *order* changes can shift DIRECT's discrete trisection decisions; must be pinned by oracle + baseline tolerance before/after; R12 low.
- Cost/Benefit: S–M; benefit = faster evals/s on the existing hardware without touching kernel math, plus a documented layout that future algorithm work respects.
- Evidence: Fabian, Data-Oriented Design (https://www.dataorienteddesign.com/dodbook/), Nystrom data locality incl. hot/cold splitting (https://gameprogrammingpatterns.com/data-locality.html). Strengthened by angle 03 and angle 05 (measurement — per-eval sync cost is the dominant term, so the DOD payoff is bounded by it).

*** C4. Pipeline of Filters (VTK-style demand-driven stages)
- Rationale: The registration is naturally a dataflow pipeline: Load study → Segment → Estimate initial pose → Render silhouette/DRR → Compute cost → Optimize stage → Emit pose. VTK's canonical architecture is exactly this — algorithms as filters over typed data with lazy, dirty-flag execution (MTime/Modified), which is why scientific imaging apps are pipeline-shaped. Plan 008 already made the *run shape* data (StageScript); this option extends the same principle to the *compute path*: each stage a filter with declared inputs/outputs, the Optimize() loop a pipeline executor.
- Changes in JTML: the stage-graph container (plan 008/009) becomes the production executor (it is currently validated but "not consumed by the production run" per plan 009); Optimize()'s interleaved session/GPU/signal code is factored into stage functions with explicit data objects between them.
- Stays: kernels, cost variants, IoU gates, budgets.
- Breaks: R15 risk is the highest in the menu — this restructures the 1,700-line hot spot; must land behind the multi-stage oracle pins (prior-run angle 06 recommendation) and plan 008's bit-identical PoC discipline; R12 medium (stage abstraction must not outrun need).
- Cost/Benefit: M–L; benefit = the stage-graph selection feature (plan 009) becomes naturally expressible, biplane/tiered-dilation/polish shapes become data (plan 008 R5), and the shape matches the ecosystem's mental model (VTK, FBP).
- Evidence: AOSA VTK chapter (Geveci & Schroeder — https://aosabook.org/en/v1/vtk.html), vtkAlgorithm execution model (https://vtk.org/doc/nightly/html/classvtkAlgorithm.html), flow-based programming (https://jpaulm.github.io/fbp/). Strengthened by angle 05 (stack-native) and angle 06 (case studies — ParaView/3D Slicer are pipeline-shaped).

*** C5. CUDA-Graph Cost (one captured graph per evaluation)
- Rationale: The per-eval GPU work is ~15 kernel launches + ~5 synchronous D2H copies; NVIDIA's own data show launch overhead is the tax (2.9μs kernel vs 9.6μs observed per launch, falling to 3.4μs with a captured graph — https://developer.nvidia.com/blog/cuda-graphs/). A captured, instantiated CUDA Graph turns the whole eval into one launch; the two host-decided launch sizes in Render() become device-side upper bounds (prior-run angle 05 rec 2 called this "the single highest-leverage kernel-level change").
- Changes in JTML: compute layer internals only: capture once per stage-config, instantiate once, relaunch per eval; remove per-eval D2H syncs where they exist only for host bookkeeping.
- Stays: kernels, host cost assembly, the injected-cost port, all seams.
- Breaks: R15 exposure on the render path (pin via oracle + `ctest -L render` before/after); R12 low; CUDA-Graph capture has constraints (no host feedback mid-graph) that the scratch-buffer purity of C2 makes tractable — C5 pairs naturally with C2.
- Cost/Benefit: M; benefit = the largest concrete per-eval latency win available on this stack, and the eval loop becomes a single stream-ordered op — which is also the *data shape* the stage graph (plan 008) can express.
- Evidence: NVIDIA CUDA Graphs (https://developer.nvidia.com/blog/cuda-graphs/), CUDA C++ Programming Guide streams/graphs (https://docs.nvidia.com/cuda/cuda-c-programming-guide/index.html#streams). Strengthened by angle 05 (compute-perf measurement first: nvtx/Nsight before and after).

*** C6. Stream-Ordered Eval Loop (overlap without graphs)
- Rationale: If CUDA Graphs prove too constraining, the same direction with less machinery: run the eval loop stream-ordered — launch eval N+1's kernels on a stream while eval N's D2H drain completes — with a small bounded lookahead, keeping the worker-thread model and host meters. Determinism is preserved (int-atomic reductions are order-independent per prior-run angle 05; stream ordering is defined).
- Changes in JTML: compute per-eval API gains stream/event handles; the coordinator loop becomes a two-phase (enqueue/drain) loop.
- Stays: everything else.
- Breaks: R15 medium (concurrency surface, but same values), R12 low.
- Cost/Benefit: M; benefit = hides the ~5 D2H round-trips behind compute without kernel changes; a fallback/complement to C5.
- Evidence: CUDA C++ Programming Guide, streams section (https://docs.nvidia.com/cuda/cuda-c-programming-guide/index.html#streams). Strengthened by angle 05.

*** C7. Typed Event Flow (the UI boundary speaks events, not calls)
- Rationale: The view currently calls into coordinator state and receives coarse signals. Make the boundary an explicit typed event stream — RunStarted{stageGraph}, StageStarted{spec}, EvalCompleted{serial, cost, components}, BestPoseUpdated, RunCompleted{pose, IoU, stats} — so the view and meters are pure projections of a stream, and the coordinator's state machine is the only writer. This is the Qt-native version of "the flow, made data" and directly enables the honest meters (the current ms/call meter divides CPU clock() by count — prior-run angle 05 — which structurally excludes GPU time).
- Changes in JTML: coordinator emits richer typed signals; view/meters subscribe; SettingsBridge-style VMs already give the pattern (plan 009's `stageGraphs`/`stageGraphIndex`).
- Stays: coordinator state machine, optimizer, compute.
- Breaks: R15 medium (UI behavior — manual-visual gate + QML widget parity tests); R12 low.
- Cost/Benefit: S–M; benefit = testable UI logic, honest meters, and the event log doubles as the debugging trace (the repo already has trace-driven-debugging learnings: docs/solutions/ui-bugs/jtml-qml-trace-driven-debugging-2026-08-12.md).
- Evidence: Qt signals/slots as the native decoupling mechanism (https://doc.qt.io/qt-6/model-view-programming.html), flow-based programming (https://jpaulm.github.io/fbp/). Strengthened by angle 05 (stack-native) and angle 06.

** Family D — Language-driven

*** D1. Pure Core / Imperative Shell, made explicit
- Rationale: JTML already has the FCIS shape (pure domain + imperative shell of Qt/GPU/files). Making it explicit: the coordinator's Idle→Running→Idle state machine becomes a pure step function `(State, Event) -> (State, Effects)` in domain, and the QObject shell applies the effects (GPU launches, file writes, signal emissions). This is the highest-value *behavioral* change for testability: every transition becomes a headless assertion, and the 1,700-line manager's policy moves where the tests already live.
- Changes in JTML: OptimizeCoordinator refactored to a pure transition core + thin effect shell; optimizer_manager stage policy migrates behind plan 008's StageScript anyway; tests move from QtTest-observed to pure-function asserts (plus a thin shell test).
- Stays: libs, seams, gates, kernels.
- Breaks: R15 medium-high — the machine is live in production; sequence behind pins and the multi-stage oracle; R12 low.
- Cost/Benefit: M; benefit = the largest testability win per unit of restructure, and it is exactly the shape the planned Rust interop wants (pure core callable from either language).
- Evidence: Bernhardt "Boundaries" (https://www.destroyallsoftware.com/talks/boundaries). Strengthened by angle 04 (language affordances — functional core in C++20 and/or Rust) and angle 02.

*** D2. Rust Interop Surface (cxx on the 9 pure files)
- Rationale: The domain purity gate exists *for* a Rust boundary. This option realizes it: generate cxx bindings over the 9 pure files (Pose6D, DirectOptimizer, StageScript machinery), keep the C++ shell as-is, and give new algorithm work (DIRECT variants, cost-math experiments) a Rust home behind the same value types. The FFI is the "data-shaped" boundary par excellence — only plain data crosses it, by construction.
- Changes in JTML: build system (cxx bridge + pixi/cargo integration), domain headers annotated with cxx, new algorithm code optionally in Rust; the interop surface becomes the documented contract for what may cross out of domain.
- Stays: everything outside domain, all seams.
- Breaks: R12 if Rust arrives before a concrete algorithm need; build fragility (hegel already network-at-configure; cxx adds toolchain coupling to a pixi-only build); R15 safe (pure surface, additive).
- Cost/Benefit: M–L; benefit = the FFI surface the layout was designed for, plus a second language for experiments without contaminating the C++ core.
- Evidence: cxx — safe interop between Rust and C++ (https://cxx.rs/). Strengthened by angle 04 (language affordances survey — including whether Rust earns its place for this workload).

** Family E — Ecosystem-native

*** E1. Qt Data Layer (model/view first-class)
- Rationale: Qt's native "authoritative shape" for data on screen is Model/View — `QAbstractItemModel` roles, delegates, proxy models — and JTML already has two view-models (FrameListModel, ModelListModel) plus a VM layer (SettingsBridge). Making it first-class: the model classes become *the* canonical interface between view and state; `mainscreen.cpp` (5,115 lines) shrinks to thin projection; the QML experiment shares the same models for free (QAbstractListModel is the QML-native interface — prior-run angle 04).
- Changes in JTML: view/VM layer only; list models gain the roles the view needs; SettingsBridge/VM surface (plan 009) completes; no change below view.
- Stays: all layers below view, gates.
- Breaks: R15 medium (view behavior — manual-visual + widget/QML parity tests); R12 low.
- Cost/Benefit: M; benefit = the UI layer finally expresses the ecosystem's pattern instead of a bespoke 5k-line View, and it is the cheapest way to keep both frontends alive.
- Evidence: Qt Model/View Programming (https://doc.qt.io/qt-6/model-view-programming.html — including the convenience classes and proxy-model machinery), Fowler Presentation Model (https://martinfowler.com/eaaDev/PresentationModel.html). Strengthened by angle 05 (stack-native guidance) and angle 02 (MVVM critique).

*** E2. VTK-Native Render Path (render + cost as VTK algorithms/data)
- Rationale: The app renders STL implants and DRRs inside a QVTK window but the render/cost engine is hand-written CUDA outside VTK's pipeline. This option wraps the engine in the ecosystem's shape: implants as vtkPolyData, DRR as vtkImageData, the render engine as a vtkAlgorithm subclass with proper MTime/Modified semantics — so VTK's demand-driven execution, caching, and tooling (vtkCamera, vtkRenderWindow, Doxygen ecosystem) apply; it also forces consolidation of the stl_reader/STLReader duplicate flagged in plan 003.
- Changes in JTML: compute/render internals + services model loading; the CUDA kernels stay but are invoked from a vtkAlgorithm; camera/calibration move to vtkCamera/vtkMatrix4x4 (careful — calibration is a deferred purity decouple).
- Stays: kernels, cost variants, host loop.

* Data-Shaped Concrete Sketch (accountable question 3)

What the data-shaped framing looks like concretely — the structs, where they live, who owns them, and which boundary each crosses:

** The structs

- `Pose6D { double x,y,z; double zrot,xrot,yrot; Source source; bool valid; }` — crosses: UI ⇄ coordinator ⇄ optimizer ⇄ compute. Lives in: `domain` (value type, trivially copyable, Rust-FFI-safe). Owner: domain (immutable; copies everywhere, references nowhere).
- `StageSpec { StageKind kind; int budget; PoseRange range[6]; int dilation; CostVariantId variant; bool zSearch; }` and `StageScript = vector<StageSpec>` — already exists (plan 008). Crosses: services(settings) → coordinator → domain(optimizer). Lives in domain. Owner: the StageGraphByName registry (code-registered data).
- `RunPayload { StageGraphRef graph; CostSelection perStage; FrameSet frames; SettingsSnapshot settings; }` — already passed by value (OptimizerRunLaunch). Crosses: viewmodel → coordinator → optimizer. Owner: coordinator's caller (the view/VM side) constructs; nobody mutates after launch.
- `EvalRequest { Pose6D pose; uint64 evalSerial; }` and `EvalResult { double cost; CostComponents components; bool feasible; }` — crosses: optimizer ⇄ compute. Lives in domain (types) with compute implementing the evaluation; `CostComponents` is the *named* decomposition (overlap, chamfer, priors, sym-trap) so the meters and the z-profile probe can read it without re-deriving it.
- `CostSample { CostVariantId variant; CostComponents c; double total; uint64 evalSerial; }` — crosses: compute → coordinator → view (meters, traces). Owner: coordinator's event stream (see C7). This is the struct that replaces "the cost is a double and the meters guess".
- `GpuImage { void* devicePtr; Dims dims; PixelFormat format; cudaStream_t stream; }` — compute-internal handle type. NEVER crosses out of `jtml_compute` (grep-guarded). Owner: compute (hoisted allocations, scratch buffers). The C2 option makes the *metrics* pure consumers of GpuImage (no in-place mutation).
- `StudyFrame { FrameId id; Path stlPath, fluoroPath, calibration; }` — crosses: services → compute (for rendering) and services → view (for display). Owner: services/model layer.
- `StateEvent = Idle | Running { stageSpec, evalsDone, budget, bestCost } | Done { pose, IoU, stats } | Failed { reason }` — crosses: coordinator → view, via Qt signals (or C7's typed stream). Owner: coordinator's state machine (single writer).

** Ownership table

| Thing | Owner | May not leave |
|---|---|---|
| Value types (Pose6D, StageSpec, RunPayload, CostSample, StateEvent) | domain | — (they are the currency) |
| Run lifecycle + state machine | coordinator | — |
| GPU buffers, kernels, streams, graphs | compute | compute ⇄ nothing outside (handles only) |
| Files, torch models, settings persistence | services | raw paths only via StudyFrame |
| Widgets, list models, VMs | view | QObject pointers never cross into domain |
| Wiring (composition) | app/main.cpp | — |

** The hot path (per-eval, ~7k evals/s)

`RunPayload` (owned) → optimizer picks `EvalRequest` → compute evaluates on hoisted buffers via stream/graph → `EvalResult` value → optimizer stores in column-sorted storage → coordinator emits `EvalCompleted` events → view projects. The data-shaped discipline: *no* device pointer, *no* QObject, *no* mutable shared state crosses any of these hops — each hop is a value.
