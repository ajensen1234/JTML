#+TITLE: Stack-Native Authority: What Qt, VTK, and CUDA Officially Say About Structuring JTML
#+DATE: 2026-08-13
#+PANOPTES_ANGLE: 05-stack-native-guidance

* Summary

The stack's own official guidance is the closest-to-home authority for JTML, and it lines up with JTML's current shape more than the user may expect. Qt's official docs do NOT recommend model/view as a general data-architecture pattern: model/view is the sanctioned interface for *item views* (lists/tables/trees), explicitly designed so the data "does not have to be stored in the model" (doc.qt.io) — Qt's own best practices for complex apps say UI in QML/declarative, business logic and "complex calculations or data processing" in strongly-typed C++ (doc.qt.io/qt-6/qtquick-bestpractices.html), and long-lived compute loops in a worker QObject moved to a QThread driven by queued signals (doc.qt.io/qt-6/threads-technologies.html). VTK's pipeline is officially a *pull-based, render-triggered, acyclic* DAG whose execution is driven by Update()/Render() and cached by MTime (VTK Book Ch.4, examples.vtk.org) — it is authoritative for the rendering leaf of JTML, and explicitly unsuited (no loops, no push) to be "the model" of an iterative GPU optimizer. CUDA's official best practices say minimize and overlap host/device transfers, keep data on the device, use non-default streams for overlap, and (NVIDIA's own graphs guidance) capture the launch sequence to cut microsecond-scale launch overhead — which is exactly the shape of JTML's eval loop. Net: a stack-native JTML = thin QAbstractItemModel adapters at the view boundary only, push-based optimizer in a persistent worker (already present), CUDA streams/graphs in jtml_compute, and VTK as the lazy render leaf, with the coordinator as a headless state machine.

* Key Findings

** Qt: model/view is the canonical pattern for *item views*, not for app data architecture
- The official Model/View Programming doc defines model/view as "an architecture to manage the relationship between data and the way it is presented to the user" in item views, and states the data "does not have to be stored in the model; it can be held in a data structure or repository provided by a separate class, a file, a database, or some other application component" — i.e., Qt's own doc positions the model as a *view-facing interface*, not the app's data backbone. [Source: https://doc.qt.io/qt-6/model-view-programming.html]
- Qt recommends model/view over item-based convenience classes ("We recommend that you use a model/view approach to handling data in item views unless you strongly need an item-based set of classes" — QListWidget/QTableWidget), but this is scoped to item views. Nothing in the official docs makes model/view the canonical structure for compute/data flow in a desktop app. [Source: https://doc.qt.io/qt-6/model-view-programming.html]
- The official UI-technology comparison positions Qt Widgets as "for creating complex desktop applications" and Qt Quick as "fluid, dynamic... best on touch interfaces" — matching JTML's choice of Widgets+xcb as primary with QML experimental. [Source: https://doc.qt.io/qt-6/topics-ui.html]
- Relevance: JTML's run lists / cost-curve points are what model/view is for (thin QAbstractItemModel/QAbstractListModel adapters at the view boundary); pushing the optimizer's data flow through model/view is not sanctioned anywhere in Qt's docs. The user's belief "(a) model/view is canonical" is true only at the view seam. Confidence: high.
- Relevance to this project: jtml_view (QWidgets) + experimental QML with injected bridges matches the official frontend/backend split (below); a QAbstractItemModel adapter over run results (OptimizerRunController results) would be the stack-native view seam, not a data backbone.

** Qt: official best practices = separate UI from business logic; C++ owns computation; keep C++ unaware of QML
- "One of the key goals that most application developers want to achieve is to create a maintainable application... to separate the user interface, the frontend, from the business logic, the backend." "Strongly typed languages, such as C++, are best suited for an application's business logic... Typically, such code performs tasks such as complex calculations or data processing, which are faster in strongly typed languages than in QML." [Source: https://doc.qt.io/qt-6/qtquick-bestpractices.html]
- "we should strive to keep C++ types unaware of QML as much as possible. This can be achieved by 'pushing' references to C++ types into QML" via required properties and QQmlApplicationEngine::setInitialProperties — exactly the SettingsBridge/injected-fake-bridge seam JTML already uses. [Source: https://doc.qt.io/qt-6/qtquick-bestpractices.html]
- Larger/dynamic datasets in QML: "use a strongly typed language, such as C++, to handle the business logic" — C++ models (QAbstractItemModel subclasses) are the official mechanism for exposing them. [Source: https://doc.qt.io/qt-6/qtquick-bestpractices.html; https://doc.qt.io/qt-6/qtquick-modelviewsdata-cppmodels.html]
- Additional official QML guidance: store state in models, not delegates; prefer declarative bindings over imperative assignments; use explicit interaction signals (moved) over valueChanged to avoid event cascades. [Source: https://doc.qt.io/qt-6/qtquick-bestpractices.html]
- Relevance: JTML's layered libs (jtml_domain / jtml_services / jtml_coordinator / jtml_compute in C++; QML only at the frontend with SettingsBridge viewmodel) are already the officially-sanctioned shape for a Qt app with heavy computation. Confidence: high.
- Relevance to this project: the experimental QML app + SettingsBridge + injected fake bridges for tests is the pattern Qt's own docs describe; nothing needs to change for stack-conformance, and it gives the QML experiment an authoritative justification.

** Qt: threading — the official pattern for a long-lived compute worker is exactly OptimizeCoordinator's shape
- Threading Basics: the "main thread (also known as the 'GUI thread' in Qt applications)... The Qt GUI must run in this thread. All widgets and several related classes, for example QPixmap, don't work in secondary threads." Two use cases for threads: "Make processing faster by making use of multicore processors" and "Keep the GUI thread or other time critical threads responsive by offloading long lasting processing or blocking calls to other threads." [Source: https://doc.qt.io/qt-6.8/thread-basics.html]
- The official "Multithreading Technologies" page's use-case table gives the canonical pattern for "Permanent: Have an object living in another thread that can perform different tasks upon request and/or can receive new data to work with": "Subclass a QObject to create a worker. Instantiate this worker object and a QThread. Move the worker to the new thread. Send commands or data to the worker object over queued signal-slot connections." This is verbatim the OptimizeCoordinator + OptimizeWorker + moveToThread + RunRequested queued-connection architecture already in src/coordinator/optimize_coordinator.cpp. [Source: https://doc.qt.io/qt-6/threads-technologies.html]
- QtConcurrent is officially scoped out of this job: "QtConcurrent can't be used when communication with the running thread is needed, and it shouldn't be used to handle blocking operations" — the CUDA eval loop needs bidirectional communication, so QThread+worker (not QtConcurrent) is the stack-native choice. [Source: https://doc.qt.io/qt-6.8/thread-basics.html]
- QObject/thread rules: "QObject and all of its subclasses are not thread-safe"; "If you are calling a function on a QObject subclass that doesn't live in the current thread... you must protect all access... with a mutex"; "Calling delete on a QObject from a thread other than the one that owns the object... is unsafe... Use QObject::deleteLater()"; child objects must be created in the parent's thread; "You must ensure that all objects created in a thread are deleted before you delete the QThread." [Source: https://doc.qt.io/qt-6/threads-qobject.html]
- Relevance: the local note that per-run threads caused a dangling-pointer segfault, fixed by one persistent worker thread, is the failure mode these rules predict (deleting/owning objects across threads). The current code is the textbook-correct fix. Confidence: high.
- Relevance to this project: JTML's coordinator threading should be *preserved* under R15; the official docs are the citation that justifies it.

** Qt: state management — the coordinator's headless state machine has an official framework analog (with caveats)
- QStateMachine is "based on the concepts and notation of Statecharts" and executes the State Chart XML (SCXML) algorithm; states + transitions form a state graph; "The machine is event driven and keeps its own event loop... it executes asynchronously, and that it will not progress without a running event loop." [Source: https://doc.qt.io/qt-6/qstatemachine.html]
- Caveat for a *headless* worker: QStateMachine requires a running event loop, which the worker thread does provide (QThread::exec via moveToThread), but Qt's own framing is UI-adjacent (QEventTransition, error states, started/finished signals). The current hand-rolled enum state machine in OptimizeCoordinator is consistent with the concept; adopting QStateMachine is an option, not a requirement. Confidence: high on what the docs say; medium on whether QStateMachine fits the headless worker (no official example of that usage found).
- Relevance to this project: if the restructure plan wants an authoritative anchor for "coordinator = state machine", the Qt State Machine Framework is it; if it wants the headless variant, the SCXML/statechart literature is the anchor.

** VTK: the pipeline is officially a pull-based, render-triggered, acyclic DAG — authoritative for rendering, not for the optimizer
- Official VTK Book, Ch.4 "The Visualization Pipeline": "The pipeline consists of objects to represent data (data objects), objects to operate on data (process objects), and an indicated direction of data flow." Execution is demand-driven: "The mapper begins network execution by asking its input to update itself via the Update() operation. This causes a cascade of Update() methods as each filter in turn asks its input to update itself" — the "update" and "execution" two passes. [Source: https://examples.vtk.org/site/VTKBook/04Chapter4/]
- Invalidation is MTime-based: "Each object only need keep track of its internal modification time. When output is requested, the object compares its modification time with that of its inputs, and executes if out of date"; vtkObject's Modified() updates it, GetMTime() reads it. [Source: https://examples.vtk.org/site/VTKBook/04Chapter4/]
- Pipeline execution is triggered by rendering: "Generally the execution of the pipeline is triggered by a mapper's Render() method invocation, typically in response to a Render() method invocation on an associated vtkActor (which in turn receives it from the render window)." [Source: https://examples.vtk.org/site/VTKBook/04Chapter4/]
- Class-level confirmation: vtkAlgorithm is "the superclass for all sources, filters, and sinks in VTK"; "Pipelines are controlled by instances of vtkExecutive... The executive is responsible for data flow"; requests flow "upstream/downstream" through ProcessRequest; pipeline MTime is computed (ComputePipelineMTime). [Source: https://vtk.org/doc/nightly/html/classvtkAlgorithm.html]
- What the pipeline explicitly does NOT do: loops — "VTK 5.0 does not allow you to execute a looping visualization network"; conditional/branching execution "must supplement the visualization network with a conditional language." [Source: https://examples.vtk.org/site/VTKBook/04Chapter4/]
- Relevance: "VTK's pipeline is the model" holds only for the visualization data path. JTML's optimizer is push-based, GPU-bound, and iterative (per-eval kernel sequence) — the exact opposite of VTK's lazy, pull-based, acyclic model. Forcing the optimizer through VTK pipeline objects would fight the official execution model. Stack-native use: keep VTK pipelines at the render leaf (implant/scene geometry), mutate data objects, let Render()/Update() + MTime cache re-execute only what changed. Confidence: high.
- Relevance to this project: the existing jtml_view VTK rendering usage (e.g., QmlVtkRenderer / VTK widget in jtml_view) is the correct place; jtml_compute stays VTK-free, as the current layering already does.

** CUDA: official best practices = minimize/overlap host-device transfer, keep data on device, non-default streams, batch staged transfers
- "To use CUDA, data values must be transferred from the host to the device. These transfers are costly in terms of performance and should be minimized." "The complexity of operations should justify the cost of moving data to and from the device." "Data should be kept on the device as long as possible... programs that run multiple kernels on the same data should favor leaving the data on the device between kernel calls, rather than transferring intermediate results to the host and then sending them back." [Source: https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html]
- "The peak theoretical bandwidth between the device memory and the GPU is much higher (898 GB/s on the NVIDIA Tesla V100...) than the peak theoretical bandwidth between host memory and device memory (16 GB/s on the PCIe x16 Gen3)"; transfer overhead must be counted when deciding host vs device placement. [Source: https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html]
- Overlap requires streams: cudaMemcpyAsync is the non-blocking variant and "requires pinned host memory"; "A stream is simply a sequence of operations that are performed in order on the device. Operations in different streams can be interleaved and in some cases overlapped"; copy/kernel overlap requires "different, non-default streams" because default-stream ops serialize with all other streams. [Source: https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html]
- Staged concurrent copy/execute: chunk the data into nStreams and issue per-stream copy→kernel sequences to overlap transfer with compute; estimate tE + tT/nStreams. [Source: https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html]
- Concurrent kernel execution: non-default streams required; check concurrentKernels; kernels in different streams can run simultaneously on capable devices. [Source: https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html]
- Synchronization guidance (official tech blog): cudaDeviceSynchronize is a "heavy hammer... in most cases this is overkill, and can really hurt performance due to stalling the entire device and host thread"; prefer cudaStreamSynchronize(stream) or cudaStreamQuery/cudaEventQuery for non-blocking completion tests. [Source: https://developer.nvidia.com/blog/how-overlap-data-transfers-cuda-cc/]
- Relevance to JTML: ~15 kernel launches + ~5 *synchronous* D2H memcpys per eval, ~7k evals/s — the official guidance points at (a) moving the per-eval D2H results to cudaMemcpyAsync on a non-default stream + events (streams overlap, query is non-blocking), (b) keeping the distance map / dilation intermediates on device across evals (they already are, per jtml_compute shared-GPU design), (c) pinned host buffers for the D2H path, and (d) batching several evals' transfers into one copy when the optimizer allows. Guidance, not prescription — R12 keeps any change evidence-driven. Confidence: high.
- Relevance to this project: jtml_compute being a SHARED GPU context with render + dilation + distance-map kernels is already aligned with "keep data on device"; the sync D2H per eval is the main official-guidance tension point.

** CUDA: CUDA Graphs is the official answer to short-kernel launch overhead — directly relevant to the eval loop
- NVIDIA official blog on CUDA Graphs: "The time taken by each GPU operation (e.g. kernel or memory copy) is now measured in microseconds. However, there are overheads associated with the submission of each operation to the GPU – also at the microsecond scale – which are now becoming significant"; graphs provide "a mechanism to launch multiple GPU operations through a single CPU operation, and hence reduce overheads"; build via stream capture (cudaStreamBeginCapture/EndCapture), instantiate once, launch with cudaGraphLaunch; measured per-kernel overhead dropping from 9.6μs to 3.4μs vs 2.9μs raw kernel time in the blog's example. [Source: https://developer.nvidia.com/blog/cuda-graphs/]
- CUDA C++ Best Practices Guide confirms graphs as a recommended technique for reducing launch overhead of many short kernels (revisited in the optimization sections; the guide's overview lists overlapping transfers and fine-tuning as successive optimization levels). [Source: https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html]
- Relevance: a fixed ~15-kernel eval sequence with fixed dependency order is the canonical use case for capture-once/replay (or cudaGraphExecUpdate if params change); the D2H copies inside the graph become event-driven rather than host-blocking. This is the single most stack-native optimization the official docs suggest for the eval loop. Confidence: high on the guidance existing; medium on JTML's specific gain without profiling (the docs themselves mandate profiling first — "profile the application to determine hotspots and bottlenecks").
- Relevance to this project: a CUDA-Graphs experiment is a natural compute-side follow-up (jtml_compute), orthogonal to the architecture restructure; flags it as an option for the menu, not a prescription.

** Stack-native JTML shape (guidance distilled from the above — not prescription)
- GUI thread: jtml_view widgets + VTK render window (xcb). Zero compute, zero CUDA API calls on this thread except rendering-triggered VTK Update()/Render(). Qt's docs: widgets "can only be used from the main thread"; KDAB rule 2. [Sources: https://doc.qt.io/qt-6.8/thread-basics.html; https://www.kdab.com/the-eight-rules-of-multithreaded-qt/]
- OptimizeCoordinator: keep the persistent QThread + worker QObject + queued signals (this is the officially documented pattern for a permanent command-driven worker), keep the headless enum state machine (or adopt QStateMachine on the worker's event loop — both stack-native, QStateMachine needs a running event loop). [Sources: https://doc.qt.io/qt-6/threads-technologies.html; https://doc.qt.io/qt-6/qstatemachine.html]
- jtml_compute: owns CUDA context, one (or a small set of) non-default stream(s), pinned host buffers for results; per-eval D2H via cudaMemcpyAsync + events, completion reported to the worker via polling cudaStreamQuery or events → queued signal to coordinator; CUDA Graphs capture of the fixed eval sequence as an experiment. [Sources: https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html; https://developer.nvidia.com/blog/cuda-graphs/]
- VTK: only as the render leaf. Feed updated pose/geometry into vtk data objects; the MTime cache makes re-render incremental; do not thread VTK pipeline execution into the optimizer's loop. [Source: https://examples.vtk.org/site/VTKBook/04Chapter4/]
- View seam: thin QAbstractItemModel/QAbstractListModel adapters over results for lists/plots; SettingsBridge-style pushed references for QML; C++ stays QML-unaware. [Sources: https://doc.qt.io/qt-6/model-view-programming.html; https://doc.qt.io/qt-6/qtquick-bestpractices.html]
- Confidence: high (each element is a direct mapping of an official statement); the assembly is interpretation, flagged as guidance.
