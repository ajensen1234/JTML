#+TITLE: Production Case Studies: How Compute-Heavy Desktop Apps Are Actually Structured (Slicer, MITK, ParaView, Blender)
#+DATE: 2026-08-13
#+PANOPTES_ANGLE: 06-case-studies

* Summary

Across 3D Slicer, MITK, ParaView, and Blender — four of the most successful compute-heavy desktop applications in production — the recurring architecture is NOT layered "domain/services". It is a combination of (1) a central data registry with events (MRML scene, MITK DataStorage, Blender Main/ID datablocks, ParaView proxy state), (2) a plugin/module registry (Slicer module factory, BlueBerry bundles + extension points, ParaView plugins, Blender operators/IDTypeInfo), (3) a demand-driven or dependency-graph execution model with explicit invalidation (VTK pipeline with MTime, Blender depsgraph with copy-on-write, ParaView update-driven pipelines), and (4) a command/observer or operator pattern for mutation, often with undo. None of the four uses MVVM; all keep long-running compute away from the UI thread — Slicer via a worker thread with a queued-result contract, ParaView via a *separate process* (pvserver), Blender via thread-pool evaluation on CoW copies, and MITK via Qt plugin threads with a singleton progress bar. For JTML, the closest production analogs to the existing OptimizeCoordinator + stage-graph + CostFunctionManager seams are Slicer's module/logic/widget split, VTK's invalidation-cached pipeline, Blender's depsgraph invalidation flags for GPU-resident data, and MITK's micro-service registry for the 7 cost variants.

* Key Findings

** 3D Slicer — MRML scene + module factory + logic/widget split

*** Structure: three module types, one data model, one factory
- Slicer's functional units are modules, of three kinds: CLI (standalone executables driven via an XML interface description, GUI generated automatically), Loadable (C++ plugins built against Slicer, distributed as shared libraries, full control of Qt UI and internals), and Scripted (Python). The developer guide's guidance: CLI is "recommended for implementing computational algorithms", Loadable for "complex, performance-critical, interactive components". [Source: https://github.com/Slicer/Slicer/blob/main/Docs/developer_guide/module_overview.md]
- Module loading is a factory pipeline: register module factories into the factory manager, point it at directories, scan and register (not instantiate), then instantiate and connect each module to the scene and the application (qSlicerAbstractModuleFactoryManager). [Source: https://github.com/Slicer/Slicer/blob/main/Docs/developer_guide/module_overview.md]
- Modules come in three parts: the module, the logic, and the module widget; MRML is the shared data model underneath. [Source: https://slicer.readthedocs.io/en/latest/developer_guide/mrml_overview.html]
- Confidence: high. Relevance: JTML's stage-graph container and module seams are one-product instances of this pattern; the factory-with-scan-and-register step is the production-grade version of the StageGraphByName registry.

*** Data model: MRML scene = graph of nodes with events, display/storage separated from data
- All data lives in an MRML scene, a list of MRML nodes; nodes have unique IDs, names, key:value attributes, and references to other nodes (role-addressed: "a node may reference multiple nodes, each performing a distinct role, and each addressed by a unique string"). [Source: https://slicer.readthedocs.io/en/latest/developer_guide/mrml_overview.html]
- Nodes invoke events on change (most commonly "Modified"); observers are callbacks registered by other nodes, application logic objects, or widgets. The scene is the shared spine: "Other Slicer components (Logic and Qt Widget) observe changes in MRML scene and individual nodes and process change MRML events." [Source: https://slicer.readthedocs.io/en/latest/developer_guide/mrml_overview.html]
- Presentation is deliberately separated from data: display nodes and storage nodes are distinct node classes attached by reference, so the same dataset can be shown differently in different views without touching the data node. [Source: https://slicer.readthedocs.io/en/latest/developer_guide/mrml_overview.html]
- Scene-level undo/redo exists as an advanced topic on the MRML scene itself, not as an app-level service. [Source: https://slicer.readthedocs.io/en/latest/developer_guide/index.html (MRML overview TOC: "Scene undo/redo" under Advanced topics)]
- Confidence: high. Relevance: this is the mature form of what JTML's stage-graph container + persistent run state approximate: one event-emitting registry with node references, not objects spread across "domain" layers.

*** Documented architecture: official developer guide names the layers it actually has
- The MRML library itself is "kept fully independent from 3D Slicer" and based on VTK, with Qt only as an optional dependency for GUI widgets. MRML's own docs describe the observer wiring via vtkSetAndObserve* macros, EventBroker, and vtkObserverManager. [Source: https://slicer.readthedocs.io/en/latest/developer_guide/mrml_overview.html]
- Slicer's GUI is Qt, adopted in a deliberate port (Slicer 4) from the old Tk-based UI; the Qt port wiki cites "signals and slots", designer tooling, and modularity as reasons, and Slicer shares the CTK (Common Toolkit) with other medical apps. [Source: https://www.slicer.org/wiki/Slicer4:QtPort]
- Confidence: high. Relevance: even a Qt-based medical platform keeps its data + logic core Qt-free and puts Qt at the widget boundary — exactly JTML's jtml_domain/compute Qt-free split. Slicer uses Qt Widgets, not QML; JTML's QML front is a deviation these case studies do not validate.

*** Threading / long-running compute: CLI runs in a separate thread; results queued to the GUI thread
- "Command Line Modules run in a separate execution thread from the main GUI. This thread is not allowed to modify the Slicer GUI, so any results from the module that need to be read back into Slicer and displayed are queued for the main thread"; vtkSlicerApplicationLogic::ProcessReadData() drains the queue. [Source: https://www.slicer.org/wiki/Documentation/Nightly/Developers/SlicerExecutionModel]
- Progress/abort is a shared C struct, ModuleProcessInformation: inputs from app to module = `unsigned char Abort`; outputs = `float Progress`, `char ProgressMessage[1024]`, a progress callback pointer, `double ElapsedTime`. Progress reporting composes over multiple filters via watchers with fraction + start offsets (vtkPluginFilterWatcher / itk::PluginFilterWatcher wrapping VTK/ITK observer events). [Source: https://www.slicer.org/wiki/Documentation/Nightly/Developers/SlicerExecutionModel]
- CLI scheduling is non-blocking: vtkSlicerCLIModuleLogic::Schedule "schedules the CLI to be run in a separate thread ... returns immediately". [Source: https://apidocs.slicer.org/main/classvtkSlicerCLIModuleLogic.html]
- Confidence: high. Relevance: JTML's OptimizeCoordinator with a persistent worker thread and D2H sync results is the same shape; the missing piece Slicer formalizes is an explicit progress+abort struct crossing the thread boundary, and the "no GUI mutation from the worker" rule.

*** Lessons for JTML
- The optimizer run is best modeled as a scene-like state registry (run state, stage graph, results) that emits Modified events, with views/logic subscribing as observers — MRML's proven shape — rather than as a layered object graph.
- Add an explicit cancellation + progress contract to the worker thread (Slicer's ModuleProcessInformation struct is the reference shape; JTML's ~7k evals/s DIRECT loop can report progress as fraction + elapsed + message).
- CLI-style "compute in isolated unit, results marshalled across a boundary" is the pattern Slicer recommends for computational algorithms; JTML's direct optimizer over GPU kernels fits the Loadable+CLI hybrid: computation unit is Qt-free and steerable only via parameters, not via mid-run UI.

** MITK — BlueBerry plugin framework + DataStorage tree + micro services

*** Structure: explicit modularization hierarchy micro service < module < view < plugin < perspective < application
- MITK's official modularization ladder: "micro service, module, view, plug-in, perspective and finally application". Modules are shared libraries providing algorithms and data structures, mostly GUI-independent, built only when required. Views are the smallest UI unit, "usually contain any code which communicates with the user, performs input checking and similar, but no advanced algorithms". Plugins (bundles) provide views and other contributions and can be switched on/off at CMake configure time; perspectives arrange views for a workflow; an application is a selection of plugins + configuration. [Source: https://docs.mitk.org/2016.11/ModularizationPage.html]
- BlueBerry is the application framework: "creating modular and extensible end-user applications", with workbench concepts (views, editors, perspectives) and an extension-point registry, Eclipse-RCP-style. [Source: https://docs.mitk.org/nightly/BlueBerryIntro.html]
- Confidence: high. Relevance: MITK is the strongest production precedent for a capability layering where algorithm libs are GUI-independent and UI units are thin — the "domain/services" shape JTML has today is closest to MITK's module/plugin split, but MITK's ordering is compute-libs first, UI units last, with no coordinator layer; the workbench/perspective layer is where composition happens.

*** Data model: mitk::DataStorage — a directed graph keyed on provenance
- DataStorage holds data nodes in a "noncyclical directed graph data structure" via a 'was created by' relation: "It handles a 'was created by' relation by associating each data object with a set of source objects, that this object was created from"; adding a node emits AddNodeEvent; subsets can be queried with predicates (GetSubset). [Source: https://www.mitk.org/docs/2022.04/classmitk_1_1DataStorage.html]
- A DataNode wraps data + a property list and sits in the tree; Qt tree models (QmitkDataStorageTreeModel) present the storage as a tree reflecting parent-child source relationships. [Source: https://docs.mitk.org/2025.08/classmitk_1_1DataNode.html]
- Confidence: high. Relevance: provenance edges ("was created by") and event emission on add are exactly what an optimizer run graph needs (which stage produced which result); JTML's stage graph is a special case of this directed provenance graph.

*** Services: CppMicroServices registry with declared interfaces
- "A micro service is a reusable component provided by MITK modules. It can be accessed by other MITK modules or MITK plug-ins via its declared interface" (CppMicroServices-based). [Source: https://docs.mitk.org/2016.11/ModularizationPage.html]
- Confidence: medium (featured in modularization overview; deeper micro-service docs not re-verified this pass). Relevance: the CostFunctionManager registry (7 cost variants) is a micro-service registry in miniature — MITK shows the mature form: register by interface, resolve by interface at runtime, modules never hard-wire implementations.

*** Threading / long-running compute
- Progress is a global singleton with a GUI-independent interface: mitk::ProgressBar::GetInstance() implemented by QmitkProgressBar (Qt), with mitk::ProgressBarImplementation as the GUI-independent abstraction ("GUI-independent interface for all GUI-dependent implementations of a progress bar. Subclasses implement the actual rendering ... using the platform's GUI toolkit (e.g., Qt)"). [Source: https://docs.mitk.org/latest/classmitk_1_1ProgressBarImplementation.html, https://docs.mitk.org/latest/classQmitkProgressBar.html]
- Confidence: medium-high (class docs verified; the threading-per-plugin behavior is by construction of BlueBerry/Qt but not documented in one page this pass). Relevance: progress UI behind an interface (not a concrete Qt widget) matches JTML's headless-testable progress reporting and SettingsBridge-style viewmodel seam.

*** Lessons for JTML
- Provenance-aware data graph (stage graph with "was created by" edges) gives free lineage for debugging optimizer runs and for selective invalidation.
- Registry-of-services by declared interface is the production pattern behind CostFunctionManager's 7 variants.
- "Views contain no advanced algorithms" is MITK's explicit rule — a useful wording for JTML's view/VM boundary (SettingsBridge + QML must stay thin).

** ParaView — client/server + proxy pattern + VTK pipelines; compute in a separate process

*** Structure: two processes, proxy objects, ServerManager state
- ParaView's signature structure is process separation: a `paraview`/`pvpython` client connects over sockets to `pvserver`; all data processing happens on pvserver, and rendering can be remote (server renders images, ships them to client) or local (geometry shipped to client). pvbatch runs parallel without a client. "The pipelines themselves, however, are created remotely on the pvserver process." [Source: https://docs.paraview.org/en/latest/ReferenceManual/parallelDataVisualization.html]
- Client-side proxies represent server-side VTK objects; the client/server boundary marshals commands via vtkClientServerStream ("messages are used to represent both commands and results for vtkClientServerInterpreter"), and the Python servermanager module exposes the proxy manager: "Returns an iterator that can be used to iterate over all groups and types of proxies that the proxy manager can create" / "Creates a new proxy of given group and name". [Source: https://www.paraview.org/paraview-docs/latest/cxx/classvtkClientServerStream.html, https://www.paraview.org/paraview-docs/latest/python/paraview.servermanager.html]
- Confidence: high. Relevance: this is the strongest form of the "compute never touches UI thread" idea: a whole process boundary with a serialized command/result protocol. JTML's persistent worker thread is the in-process version; ParaView is the existence proof that the boundary can be hardened to process level if GPU-reset/crash isolation ever matters (CUDA context resets).

*** Data flow: VTK demand-driven pipeline underneath
- ParaView is built on VTK's dataflow pipeline; ParaView's own user guide describes the data model as VTK's (vtkDataObject hierarchies, pipeline of readers/filters/mappers). [Source: https://docs.paraview.org/en/latest/UsersGuide/understandingData.html]
- VTK's pipeline (AOSA chapter): three object classes — vtkDataObject (data), vtkAlgorithm (processing), vtkExecutive (execution control over the connected graph); execution is demand-driven ("the actual pipeline execution occurs when the Write method is invoked ... upon demand for the data") with per-filter caching keyed on modification time: re-execution only propagates to stale filters after a change (e.g., SetValue on a contour filter invalidates only upstream of the change). [Source: https://aosabook.org/en/v1/vtk.html]
- Request passes allow streaming: filters can request pieces/extents/time steps/ghost layers, and each filter can modify downstream requests; the pipeline caches outputs plus ComputeTime metadata. [Source: https://aosabook.org/en/v1/vtk.html]
- Confidence: high. Relevance: the DIRECT optimizer loop (render engine → dilation → distance map → cost) is a pipeline; VTK shows how to make it lazy and invalidation-driven instead of re-evaluating everything each iteration — directly applicable to JTML's ~15 kernels/eval budget.

*** Plugins and Qt: pq* objects wrap proxies; plugins extend both client and server
- The Qt client is built on pq classes; pqApplicationCore "creates and manages various managers which are necessary for the ParaView-based client to work with the ServerManager" and must be instantiated after QApplication. [Source: https://www.paraview.org/paraview-docs/v5.13.0/cxx/classpqApplicationCore.html]
- Plugins can be loaded client-side or server-side (paraview.simple.plugin: "the remote keyword ... specify whether the plugin will be loaded on client (remote=False) or on server (remote=True)"), and plugin XML can register new proxy types, property widgets, decorators (pqPropertyWidgetDecorator subclasses). [Source: https://www.paraview.org/paraview-docs/latest/python/paraview.simple.plugin.html, https://www.paraview.org/paraview-docs/latest/cxx/PluginHowto.html]
- Undo/redo is captured from the client-server state stream itself: "The UndoRedo manager now can listen to state changes are they are being pushed around and capture them as undo-sets. Since this state is exactly how the client is communicating with the server, it won't be fragile." [Source: https://www.paraview.org/ParaView/index.php/ServerManager_2.0]
- Confidence: high (class docs + plugin howto + wiki). Relevance: "state as the undo unit" is a strong precedent for JTML's full-run payloads by value — undo/redo becomes replay of immutable run payloads.

*** Lessons for JTML
- The proxy pattern shows the value of a serializable command/result surface between interactive UI and compute; JTML's OptimizeRunDriver payloads + injected cost already approximate it — consider formalizing the boundary as a protocol (even in-process) so a future pvserver-style split is a deployment option, not a rewrite.
- Undo from the command stream (ParaView) or from scene state (Slicer/Blender) beats command-stack bookkeeping; JTML's by-value run payloads fit this.
- VTK's MTime-style invalidation should inform the stage-graph: cache per-stage outputs and re-execute only the invalidated subgraph each evaluation.

** Blender — DNA/RNA/ID datablocks + operators + dependency graph (CoW), no Qt

*** Structure: data-centric core with an explicit data model trilogy
- Blender's core is data-model-driven: DNA (the struct layout persisted to .blend files, "reproducible, forward- and backward-compatible"), RNA (generated reflection/API layer over DNA with getter/setter callbacks, computed properties, update flags that notify the UI and dependency graph; generated at compile time by makesrna), and ID datablocks in the Main database. [Source: https://developer.blender.org/docs/features/core/dna/, https://developer.blender.org/docs/features/core/rna/, https://developer.blender.org/docs/features/]
- Mutation goes through operators — the extensibility proposal notes operators "was designed to be extensible from the start" and Python add-ons "can define their own operators that behave just like built-in operators", while adding a new datablock historically required changes across dozens of files; the fix is an IDTypeInfo struct with callback functions (landed as T73719). [Source: https://developer.blender.org/docs/features/core/proposals/extensibility/]
- Blender does not use Qt; the UI is Blender's own widget toolkit on its own platform abstraction (GHOST — Generic Handy Operating System Toolkit) for windowing/input/drawing contexts. [Source: https://developer.blender.org/docs/features/interface/ (official UI docs); GHOST naming/detail: DeepWiki-derived, https://deepwiki.com/blender/blender/3.2-ghost-and-window-management]
- Confidence: high for DNA/RNA/operators; medium for the GHOST attribution (official docs page is under construction; naming cross-checked via DeepWiki only).
- Relevance: Blender is the counter-example proving Qt is not required for a world-class compute+interactive app, and that the deepest architecture investment can be in the *data model + update graph*, not the UI framework.

*** Data flow: dependency graph with copy-on-write, window-owned
- The depsgraph (Blender 2.8 design): "the dependency graph only updates what was dependent on the modified value and will not update anything which was not changed"; nodes are scene entities, edges are relations. Evaluation runs on CoW copies of DNA data ("dependency graph applies all the required changes ... on a copy of DNA data. Such data we call generated"); original data is never mutated by evaluation, which solves threading conflicts between viewport and render threads ("low-res character in the rest pose in one viewport and hi-res animation playing back in the other viewport"). [Source: https://developer.blender.org/docs/features/core/depsgraph/]
- Ownership: the window owns the depsgraph for interactive use (re-created when workspace/render engine/scene layer changes); the Render structure owns it for final renders. Evaluation is threaded (shallow copies created at graph construction, contents filled from evaluation threads via DEG_create_shallow_copy / DEG_finish_copy). [Source: https://developer.blender.org/docs/features/core/depsgraph/]
- Render engines consume only generated data and get engine-specific storage with invalidation bitflags: `struct DEGRenderEngineData { int flag; }` with DEG_RE_MATERIALS_UPDATE / DEG_RE_GEOMETRY_UPDATE bits stored per-object, "so render engine can keep VBOs for geometry when only material changes". [Source: https://developer.blender.org/docs/features/core/depsgraph/]
- Confidence: high. Relevance: this is the closest production analog to JTML's GPU-resident state: per-stage invalidation flags on GPU resources (VBOs/rendered images) instead of recomputing everything; CoW for run results so the UI can keep rendering the previous state while the next evaluation runs.

*** Undo and long-running compute
- Undo is state-snapshot based, not command-list based: "The undo system in Blender is currently fully relative, which means to reach a given undo step, you also need to load all those in-between"; steps have types with callbacks implementing storage/loading; global undo with step count and memory limits. [Source: https://developer.blender.org/docs/features/core/undo/]
- Confidence: high. Relevance: full-state-snapshot undo matches JTML's by-value full-run payloads (OptimizerRunLaunch "full run payload by value") — a natural fit, and evidence that state-snapshot undo is production-proven even for huge scenes.

*** Lessons for JTML
- Model the optimizer as a depsgraph: stage graph nodes = kernels/transforms, edges = dependencies, each stage's GPU output tagged with invalidation flags (Blender's DEGRenderEngineData), re-evaluating only dirty stages per DIRECT iteration.
- Consider CoW "evaluated copies" for optimizer state so the UI renders the previous pose while the GPU computes the next — Blender solved exactly the "viewport vs compute thread" conflict this way.
- Data model first, UI second: RNA-style generated accessors over the pose/run state would give JTML a stable API surface (also the documented Rust-interop surface candidate for jtml_domain) decoupled from both compute and Qt.

** Cross-project recurring patterns (the shared vocabulary)

*** Pattern 1 — A central event-emitting data registry is the spine of every app
- MRML scene (Slicer), mitk::DataStorage (MITK), Main/ID datablocks (Blender), ServerManager proxy state (ParaView). In every case, structure is defined by *where data lives and how change is announced*, not by layer boundaries. [Sources: https://slicer.readthedocs.io/en/latest/developer_guide/mrml_overview.html, https://www.mitk.org/docs/2022.04/classmitk_1_1DataStorage.html, https://developer.blender.org/docs/features/core/dna/, https://www.paraview.org/paraview-docs/latest/python/paraview.servermanager.html]
- Confidence: high. Relevance: JTML's stage-graph container + OptimizeCoordinator already lean this way; the case studies say *make it the center*, with nodes/state emitting Modified-type events that views and logic observe.

*** Pattern 2 — Plugin/module registry with factories and extension points
- Slicer module factory (scan → register → instantiate → connect to scene), MITK BlueBerry bundles + extension points + perspectives, ParaView plugins with client/server-side loading, Blender operators + IDTypeInfo. [Sources: https://github.com/Slicer/Slicer/blob/main/Docs/developer_guide/module_overview.md, https://docs.mitk.org/nightly/BlueBerryIntro.html, https://www.paraview.org/paraview-docs/latest/cxx/PluginHowto.html, https://developer.blender.org/docs/features/core/proposals/extensibility/]
- Confidence: high. Relevance: registers-by-name (StageGraphByName, CostFunctionManager) are the thin end of this wedge; the production form adds scan-at-startup, instantiate-lazily, and connect-to-context steps.

*** Pattern 3 — Demand-driven / dependency-graph execution with explicit invalidation
- VTK pipeline (MTime + ComputeTime caching, request passes, demand-driven execution), ParaView (pipeline executes on update; state changes pushed to server), Blender depsgraph (CoW + per-component invalidation bits). All three treat recomputation as something to minimize and make correctness depend on invalidation, not on eager re-run. [Sources: https://aosabook.org/en/v1/vtk.html, https://developer.blender.org/docs/features/core/depsgraph/, https://docs.paraview.org/en/latest/ReferenceManual/parallelDataVisualization.html]
- Confidence: high. Relevance: DIRECT at ~7k evals/s with ~15 kernels/eval is exactly where eager re-evaluation is wasteful; per-stage dirty flags on GPU-resident intermediates is the proven answer.

*** Pattern 4 — Mutation via commands/operators, undo from state or command stream
- Blender operators (extensible, Python-registrable, with undo steps), ParaView UndoRedo manager capturing the client-server state stream, Slicer scene undo/redo, VTK command/observer (StartEvent/ProgressEvent/EndEvent). [Sources: https://developer.blender.org/docs/features/core/proposals/extensibility/, https://developer.blender.org/docs/features/core/undo/, https://www.paraview.org/ParaView/index.php/ServerManager_2.0, https://aosabook.org/en/v1/vtk.html]
- Confidence: high. Relevance: JTML's injected-cost DirectOptimizer and by-value run payloads map cleanly: "run = operator; undo/redo = state snapshots of the run registry".

*** Pattern 5 — Compute is walled off from UI; results cross a boundary
- Slicer CLI thread + queued results; ParaView separate process + serialized stream; Blender depsgraph evaluation on CoW copies in worker threads; MITK GUI-independent algorithm modules. In every case the rule is: worker code cannot touch UI, and communication is by explicit message/state, not shared mutation. [Sources: https://www.slicer.org/wiki/Documentation/Nightly/Developers/SlicerExecutionModel, https://docs.paraview.org/en/latest/ReferenceManual/parallelDataVisualization.html, https://developer.blender.org/docs/features/core/depsgraph/, https://docs.mitk.org/2016.11/ModularizationPage.html]
- Confidence: high. Relevance: JTML's persistent worker thread + D2H sync results is the in-process version of a universal pattern; add progress+abort contract and (optionally) a serializable protocol to keep the process-isolation option open.

*** Pattern 6 — Qt is the UI toolkit, not the architecture
- Slicer (Qt widgets via CTK, data core Qt-independent), ParaView (Qt client above ServerManager), MITK (Qt views + progress, GUI-independent algorithm modules). Blender shows the alternative (own toolkit). None of them use QML, and none use MVVM: Slicer is model(MRML)/view(widgets)/logic(controllers) with observer glue; ParaView is proxy+observer; MITK is workbench views + services; Blender is data-model + operators. [Sources: https://www.slicer.org/wiki/Slicer4:QtPort, https://www.paraview.org/paraview-docs/v5.13.0/cxx/classpqApplicationCore.html, https://docs.mitk.org/nightly/BlueBerryIntro.html, https://developer.blender.org/docs/features/interface/]
- Confidence: high for "Qt not MVVM" across Slicer/ParaView/MITK; medium for Blender toolkit attribution.
- Relevance: directly answers the user's belief (b): MVVM is not the production pattern in this class of app; the recurring vocabulary is scene/data graph + observers + commands/operators + pipeline/depsgraph. JTML's QML app has no direct case-study precedent in these four — closest relatives are thin widget layers observing a model.

*** AOSA coverage note
- The Architecture of Open Source Applications covers VTK (v1, by Geveci & Schroeder) and ITK (v2, by Ibanez & King); there is NO AOSA chapter for 3D Slicer, ParaView, MITK, or Blender. [Source: https://aosabook.org/en/index.html]
- Confidence: high. Relevance: the authoritative written architectures for this space are VTK/ITK (libraries, not apps) plus each project's own developer docs — which is what this angle used.

* What Could Not Be Verified

- Blender's GHOST toolkit: the official developer UI docs page exists but is flagged "under construction"; the GHOST name and role were verified only through a derived DeepWiki page. Blender's non-use of Qt is well established, but the internal toolkit details are lower-confidence.
- Slicer scene undo/redo coverage: the MRML overview lists "Scene undo/redo" as an advanced topic, but per-node-type undo semantics were not verified in depth.
- ParaView's claim that proxies "minimize network communication" (DeepWiki phrasing) was not used; only the class-reference-level marshalling (vtkClientServerStream) and official docs were treated as evidence.
- MITK micro-service usage depth and BlueBerry's current deprecation status: the modularization page is from 2016.11 docs; current BlueBerry status (still documented on nightly docs, fetched OK) was not deeply verified.
- Exact depsgraph scheduler/thread-pool internals of Blender (documents threaded evaluation and CoW; exact scheduling policies not documented in the fetched pages).
- Whether any production Qt/CUDA/VTK app in this class uses QML at its core: none of the four do; no claim about QML viability beyond "no case-study precedent found".
- Game-engine specifics beyond Godot (nodes/scenes + signals) and Unreal (modules/plugins/subsystems): Unity DOTS/ECS claims were not verified this pass.
