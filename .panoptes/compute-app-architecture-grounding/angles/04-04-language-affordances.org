#+TITLE: Language Affordances — Language Semantics as Architecture for Compute-Heavy Desktop Apps
#+DATE: 2026-08-13
#+PANOPTES_ANGLE: 04-language-affordances

* Summary

Language features are architecture levers: immutability, ownership, value-vs-reference
semantics, ADTs, and purity each *force or forbid* data shapes and data-flow topologies,
and on SIMT hardware those shapes are performance semantics, not style. The evidence shows
(a) functional purity is a proven correctness/testability instrument for numerical code
(QuickCheck, JAX's purity requirement, Futhark/Accelerate), (b) SIMT/SIMD makes data
layout (SoA vs AoS, coalescing, divergence avoidance) a first-class design axis with
authoritative CUDA/NVIDIA references, (c) Rust ownership is compiler-checked data-flow
topology — an architecture-enforcing mechanism, not just memory safety, and (d) C++ is the
incumbent but not the only credible option: Rust↔C++ interop (cxx/autocxx, cxx-qt) and
Rust-to-CUDA paths (rust-cuda, NVIDIA's experimental cuda-oxide) are credible, with
mixed-language production precedent (Firefox, Android). For JTML this grounds the
jtml_domain boundary: a thin, C-ABI-shaped, single-ownership seam between pure-domain code
and the CUDA/Qt layers is the defensible target.

* Key Findings

convenient. This is the core framing for the project's re-framing menu.

** F2: Functional purity is a compute correctness/testing lever — not a web/CRUD-only tool

The belief "functional purity is for web/CRUD" fails against three verified bodies of
evidence: testing technology, pure GPU languages, and the purity requirements of
mainstream compute frameworks.

- Property-based testing was *invented* in a pure language precisely because purity makes
  properties testable: "QuickCheck is a library for random testing of program properties.
  The programmer provides a specification of the program, in the form of properties which
  functions should satisfy, and QuickCheck then tests that the properties hold in a large
  number of randomly generated cases."
  [https://www.cse.chalmers.se/~rjmh/QuickCheck/manual.html] — This is the same testing
  family as the project's hegel PBT tests; purity makes the properties meaningful.
- The canonical argument that functional languages are about *modularity and glue* (not
  just elegance) is Hughes' "Why Functional Programming Matters", which uses numerical
  algorithms (alpha-beta, numerical methods) as worked examples: "since modularity is the
  key to successful programming, functional programming offers important advantages for
  software development." [https://www.cs.kent.ac.uk/people/staff/dat/miranda/whyfp90.pdf]
- Pure data-parallel languages for GPU exist and are performant: Futhark is "a statically
  typed, data-parallel, and purely functional array language in the ML family" with "a
  heavily optimising ahead-of-time compiler that presently generates either GPU code via
  CUDA, HIP, or OpenCL, or multi-threaded CPU code"; it supports nested data-parallelism,
  automatic differentiation, and in-place updates *while preserving purity via a
  uniqueness type system* — and explicitly targets "relatively small but compute-intensive
  parts of an application" with FFI-able C output. [https://futhark-lang.org/]
  Peer-reviewed: "Futhark: purely functional GPU-programming with nested parallelism and
  in-place array updates" (ICFP 2017). [https://dl.acm.org/doi/10.1145/3062341.3062354]
- Haskell's embedded GPU DSL Accelerate expresses array computations via collective
  operations (maps, reductions, permutations) and compiles to LLVM CPU and CUDA backends;
  programs are "declarative, statically-typed, pure, functional".
  [https://www.acceleratehs.org/] [https://hackage.haskell.org/package/accelerate]
- JAX — one of the most-used compute frameworks — *requires* the functions it transforms
  (jit/vmap/grad) to be pure: "JAX transformations like jit(), vmap(), grad(), require the
  functions they wrap to be pure: that is, functions whose outputs depend solely on the
  inputs, and which have no side effects."
  [https://docs.jax.dev/en/latest/stateful-computations.html] This is functional semantics
  doing real architectural work in production ML.
- Haskell's scientific-computing ecosystem is niche but real (resources collected on the
  Haskell wiki). [https://wiki.haskell.org/Scientific_computing]
- Confidence: high (primary sources for QuickCheck, JAX, Futhark, Accelerate, Hughes)
- Relevance: the project's R15 behavior preservation + PBT norm is exactly where purity
  pays: a pure jtml_domain means the optimizer's cost abstraction can be tested
  property-style headlessly (no GPU/Qt), and a future Rust port of the domain layer
  inherits the same guarantee (Rust functions are pure-by-convention, and Rust enforces
  immutability where C++ only advises const).

** F3: The SIMT/SIMD model dictates data shape — SoA, coalescing, divergence

"CUDA is just kernels" misses that the SIMT execution model is an architectural force on
*data design*; the authoritative references converge on the same structural rules.

- Execution model: threads execute in warps of 32, one common instruction at a time —
  NVIDIA's official guide covers SIMT kernel writing.
  [https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html]
- Coalescing definition (official + academic): "Coalesced memory access or memory
  coalescing refers to combining the global-memory accesses from some or all of the
  threads in a warp into a single memory operation"; "consecutive threads within a warp
  access consecutive memory locations" for efficient bandwidth. NVIDIA splits each
  128-byte cache line into four 32-byte sectors, so a warp accessing 32 consecutive words
  on an L2 miss needs a minimum of four transactions.
  [https://developer.nvidia.com/blog/unlock-gpu-performance-global-memory-access-in-cuda/]
  [https://cvw.cac.cornell.edu/cuda-intro/gpu-performance-topics/coalesced]
- SoA vs AoS: the classic, widely-cited guidance is that Structure-of-Arrays favors
  coalescing (why it is preferred "for parallel implementations like CUDA" is a canonical
  Stack Overflow question with sustained expert discussion)
  [https://stackoverflow.com/questions/17924705/structure-of-arrays-vs-array-of-structures];
  an academic treatment of abstracting AoS/SoA layout in C++ (Strzodka) states "the choice
  between an array-of-structures (AoS) data layout and a structure-of-arrays (SoA) layout
  has a large impact on overall program performance."
  [https://asc.ziti.uni-heidelberg.de/Files/St11ASX_CUDA.pdf]
- Nuance verified in this run: the current CUDA C++ Best Practices Guide (13.3) *does not*
  contain an explicit SoA/AoS section by name; its framing is coalesced vs strided access
  patterns and memory-optimization structure (pinned memory, async/overlapping transfers,
  zero-copy). The SoA guidance lives in the programming guide's coalescing discussion, the
  textbook literature, and NVIDIA's newer blog material.
  [https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html]
- Canonical textbook: "Programming Massively Parallel Processors" (Kirk & Hwu, 5th
  ed., 2023) is the standard hands-on treatment; the publisher's description notes
  "various techniques for constructing and optimizing parallel programs are explored in
  detail" (data layout and memory-coalescing among them, per its long-standing
  curriculum).
  [https://www.sciencedirect.com/book/monograph/9780443439001/programming-massively-parallel-processors]
- Structural consequence for global optimizers: when every evaluation is a GPU cost pass
  over a *population* of parameter vectors, the layout of that population (SoA fields per
  parameter dimension vs AoS per member) is decided by coalescing, not by the domain
  model. This is a data-shape decision the language/host layer must make first-class.
- Confidence: high (NVIDIA docs, Cornell HPC course, textbook record); medium for the
  specific SoA-over-AoS performance multiplier claims in third-party blogs
  (architecture-dependent, unverified here)
- Relevance: the DIRECT optimizer's ~15 kernels + ~5 sync D2H memcpys per evaluation mean
  both (a) kernel-side population layout and (b) the transfer budget are the real
  architecture; the domain layer's parameter-vector representation should map losslessly
  onto the SoA GPU buffers.

** F4: Host/device marshalling is a first-class architectural seam

- NVIDIA's authoritative guidance: "minimizing data transfers between the host and the
  device is crucial because the peak bandwidth between device memory and the GPU is much
  higher than between host memory and device memory"; pinned (page-locked) memory raises
  host↔device bandwidth; transfers should be batched and overlapped with computation.
  [https://developer.nvidia.com/blog/how-optimize-data-transfers-cuda-cc/]
- cudaMemcpy transfers are blocking: "control is returned to the host thread only after
  the data transfer is complete" (Best Practices Guide, Data Transfer Between Host and
  Device; async/overlap and zero-copy variants exist).
  [https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html]
- Confidence: high
- Relevance: ~5 synchronous D2H copies per evaluation is the structural bottleneck to
  shape around: language features that make copies explicit and transfer ownership (Rust
  moves; C++ move semantics; pure functions returning fresh buffers) keep this seam
  legible instead of buried in mutable shared state.

** F5: Rust ownership is an architecture-enforcing mechanism — "not just memory safety"

- The CACM article "Safe Systems Programming in Rust" frames Rust as "the first
  industry-supported programming language to overcome the longstanding tradeoff between
  the safety guarantees of higher-level languages... and the control over resource
  management provided by lower-level 'systems programming' languages (like C and C++)" —
  i.e., the ownership system is the *mechanism* that makes safety and control coexist.
  [https://cacm.acm.org/research/safe-systems-programming-in-rust/]
- The Rust Book is explicit that ownership is compiler-checked *rules*, not runtime
  machinery: "Memory is managed through a system of ownership with a set of rules that the
  compiler checks. If any of the rules are violated, the program won't compile. None of
  the features of ownership will slow down your program while it's running."
  [https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html]
- Architectural reading: with single-owner + move semantics, the *data-flow topology of
  the program* (who creates, who owns, who borrows, when destruction happens) is enforced
  by the type checker. That is exactly the property an FFI boundary into C++/Qt/CUDA
  needs: ownership contracts at the seam cannot silently diverge.
- ADTs add to this: enums encode "a value is one of a possible set of values" and "the
  compiler can check whether you've handled all the cases" — invalid states (e.g., an
  unconfigured cost function) become unrepresentable.
  [https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html]
- Confidence: high
- Relevance: jtml_domain is planned as the "Qt/GPU-free Rust-interop surface". If Rust is
  adopted there, ownership becomes the enforcement mechanism for who owns cost-function
  state, parameter buffers, and evaluation results across the C++/GPU seam — precisely the
  boundary where C++ currently relies on convention.

** F6: Rust↔C++ FFI for compute — credible guidance exists, and the boundary must be thin and C-ABI-shaped

- cxx (dtolnay) is the mainstream safe-interop mechanism: "This library provides a safe
  mechanism for calling C++ code from Rust and Rust code from C++, not subject to the many
  ways that things can go wrong when using bindgen or cbindgen to generate unsafe C-style
  bindings. This doesn't change the fact that 100% of C++ code is unsafe."
  [https://github.com/dtolnay/cxx] Google's autocxx automates generation of such
  interfaces from existing C++ headers (bindgen-variant plugged into cxx).
  [https://github.com/google/autocxx]
- The Rustonomicon's FFI chapter is the authoritative danger map: foreign functions are
  *assumed unsafe*; "C libraries often expose interfaces that aren't thread-safe, and
  almost any function that takes a pointer argument isn't valid for all possible inputs
  since the pointer could be dangling, and raw pointers fall outside of Rust's safe memory
  model"; the compiler cannot check that a declaration matches the C side. Practical rules
  it documents: wrap raw C APIs in safe Rust interfaces with unsafe confined internally;
  use #[repr(C)] for layout; prefer raw pointers over references across the boundary; use
  the C-unwind ABI when exceptions/panics can cross; catch_unwind at the seam.
  [https://doc.rust-lang.org/nomicon/ffi.html]
- Firefox's production interop doctrine: "the more complicated is the data you want to
  transfer, the harder it'll be to transfer across the FFI boundary. Booleans, integers,
  and pointers cause little trouble."
  [https://firefox-source-docs.mozilla.org/writing-rust-code/cpp-interop.html]
- Qt+Rust paths exist and are production-oriented: KDAB's cxx-qt provides "safe interop
  between Rust and Qt" with code generators exposing QObject/signals-slots/properties to
  Rust ("an ideal solution for incorporating some Rust into an existing C++ project");
  woboq's qmetaobject provides QML bindings from Rust. [https://github.com/KDAB/cxx-qt]
  [https://github.com/woboq/qmetaobject-rs]
- Rust-native CUDA is real but young: the rust-cuda project (Rust-GPU org) rebooted in
  2025 after dormancy, aiming to write CUDA kernels in Rust via NVVM IR/PTX with
  "significant improvements landing regularly" (status: active, not yet tier-1
  production). [https://github.com/Rust-GPU/Rust-CUDA]
  [https://rust-gpu.github.io/blog/2025/03/18/rust-cuda-update/] NVIDIA Labs' cuda-oxide
  is an "experimental Rust-to-CUDA compiler that lets you write (SIMT) GPU kernels in
  safe(ish), idiomatic Rust. It compiles standard Rust code directly to PTX — no DSLs, no
  foreign language bindings." (explicitly experimental).
  [https://nvlabs.github.io/cuda-oxide/]
- Confidence: high for cxx/autocxx/Rustonomicon/Firefox guidance (primary docs); high for
  existence-and-status of Rust-CUDA paths; low-to-medium for production readiness of
  Rust-to-CUDA kernels
- Relevance (FFI guidance headline): for the jtml_domain seam, the credible shape is (1) a
  C-ABI-compatible interface (plain data structs, opaque handles, explicit ownership
  transfer in/out — no Qt objects, no STL containers across the boundary), (2) Rust/C++
  interop only at that seam via cxx or autocxx if Rust is introduced, (3) unsafe confined
  to a thin adapter layer per Rustonomicon, (4) the GPU layer stays CUDA (or SYCL) on the
  C++ side; Rust-to-CUDA remains an option to re-evaluate, not a near-term dependency.

** F7: GPU host-language / DSL landscape — credible options and when they are credible

- Futhark: credible when the compute core is expressible as data-parallel array
  computation and you want machine-neutral purity + AD; it is explicitly *not* a
  replacement for general-purpose languages — "the intended use case is that Futhark is
  only used for relatively small but compute-intensive parts of an application," with
  FFI-able C output. Ongoing research project, but "quite usable for real programming."
  [https://futhark-lang.org/]
- Halide: credible for image/array *pipelines* where algorithm and schedule separation
  pays; embedded in C++; targets CUDA, OpenCL, Metal, DX12 and CPU architectures;
  MIT-licensed; the decoupling idea is peer-reviewed (PLDI 2013, CACM research highlight).
  [https://halide-lang.org/] — less natural fit for irregular global-optimizer control
  flow.
- Taichi: Python-embedded DSL with JIT to GPU/CPU, automatic parallelization, a flexible
  memory-layout system (SNode: "quick experimentation with different memory layouts to
  maximize performance without rewriting computation code"), AD, and AOT deployment
  without Python; adoption listed at OPPO, Kuaishou, ETH, Utah. Vendor claim "approach or
  even outrun the speed of C++ or CUDA" is a claim, not independently verified here.
  [https://www.taichi-lang.org/]
- JAX: credible when the cost function is JIT-able and you want autodiff over it
  (grad/vmap/jit composition, XLA), and when purity is acceptable; it is Python-hosted and
  its transformations require pure functions.
  [https://docs.jax.dev/en/latest/stateful-computations.html]
- SYCL: open Khronos standard — "code for heterogeneous and offload processors... written
  using modern ISO C++"; explicitly does *not* guarantee automatic performance portability
  ("optimized kernel code may differ across the architectures"); implementations: Intel
  oneAPI DPC++, AdaptiveCpp, etc.; a SYCL SC working group is aligning with safety
  standards including IEC 62304 (medical software). [https://www.khronos.org/sycl/]
- Kokkos: performance-portable C++ parallel programming model aimed at HPC (C++
  applications across GPU platforms). [https://kokkos.org/] Independent 2024 research
  across CUDA/HIP/Kokkos/RAJA/OpenMP/OpenACC/SYCL concludes such models "don't make any
  guarantees about performance portability" — consistency across NVIDIA/AMD GPUs is
  hard-won. [https://arxiv.org/abs/2402.08950]
- Credibility assessment: for a *tight host-controlled optimizer loop* (sequential stages,
  ~15 bespoke kernels, ~5 sync memcpys per eval), the DSL layer most likely to help is the
  one that stays on the C++ side (SYCL/CUDA) or that matches the kernel shape exactly
  (Futhark for pure data-parallel kernels; Halide for imaging-like stages). JAX/Taichi are
  credible when you would otherwise hand-write autodiff or Python orchestration — neither
  matches a Qt6/C++20 desktop host today.
- Confidence: high for each tool's self-description and peer-reviewed anchors; medium for
  performance-portability and productivity comparisons (benchmark-dependent)

** F8: Mixed-language architectures are production-normal in scientific software

- Firefox is the canonical long-running mixed C++/Rust production codebase: "Rust support
  has been required on all platforms since Firefox 54, and the first major Rust components
  were shipped in Firefox 56 (encoding_rs) and 57 (Stylo)"; the model is per-component
  ownership — "The C++ components are written in C++, and the Rust components are written
  in Rust." [https://wiki.mozilla.org/Oxidation]
- Google reports on Android: Rust adoption yielded "a 1000x reduction in memory safety
  vulnerability density compared to Android's C and C++ code," plus "a 4x lower rollback
  rate and spending 25% less time in code review."
  [https://blog.google/security/rust-in-android-move-fast-fix-things/]
- In scientific software, Python+C++ hybrid is the default architecture (e.g., pybind11
  integration tutorials; university coursework on "mixed-language programming" treating
  C++-core/Python-front as standard practice).
  [https://finsberg.github.io/IN1910/docs/lectures/optimization/optimization_and_mixed_programming.html]
  [https://medium.com/sissa-mathlab/integrating-c-and-python-for-scientific-computing-2dda79b0da73]
- The "two-language problem" (prototype in a high-level language, rewrite in C++ for
  production) is a recognized failure mode; Julia markets itself as its solution.
  [https://juliahub.com/white-papers/why-julia-solving-the-two-language-problem-for-high-performance-computing]
  [https://www.wired.com/story/python-is-so-slow-can-julia-solve-the-two-language-problem/]
- Confidence: high for Firefox/Android primary sources; medium for the
  two-language-problem framing (marketing-adjacent)
- Relevance: the project is already a mixed-language architecture (C++20 + CUDA + QML);
  the evidence says the risk is not *whether* to mix languages but whether the seams (data
  contracts, ownership, transfer budget) are explicit. A Rust jtml_domain adds one more
  seam of a now well-trodden kind.

* What Could Not Be Verified

- Production readiness of Rust-native CUDA kernels (rust-cuda, cuda-oxide): both are
  confirmed active/experimental, but no evidence of large production deployments was found
  in this run; treat as horizon options, not near-term dependencies.
- Taichi's "approach or outrun C++/CUDA" performance claim: vendor-published, not
  independently benchmarked here.
- The exact performance multiplier of coalesced vs scattered access (third-party guides
  cite 10-20x; authoritative docs describe the mechanism but not a universal constant — it
  is architecture- and access-pattern-dependent).
- Whether the current CUDA C++ Best Practices Guide (13.3) covers SoA/AoS by name:
  verified *negative* (it frames memory optimization as coalesced/strided patterns, pinned
  memory, async transfers); older editions and textbooks carry the SoA/AoS guidance.
- Specific production deployments of cxx-qt in medical/registration-class desktop
  software: cxx-qt's interop claims are verified, its deployment footprint in this
  application class is not.
- Whether Futhark-generated CUDA would integrate cleanly with this project's CUDA 12.4
  toolkit and bespoke cost kernels: Futhark targets CUDA generally, but version-specific
  compatibility with this toolchain was not verified.
- Haskell/Accelerate in industrial-scale production compute (vs research/niche): ecosystem
  exists, production-scale usage not verified.

** R2.3 What problem is Rust solving? — sharpened verdict (problem definition)

- The repo's documented GPU failure is **one corruption incident**: the grid→pixel index
  formula at src/compute/distance_map_metric.cu:27 was `(blockIdx.y + gridDim.x +
  blockIdx.x) * blockDim.x` instead of the row-major `(blockIdx.y * gridDim.x +
  blockIdx.x) * blockDim.x`. The in-file comment (:27-34) and the deep-dive run's Finding
  1 both classify it: deterministic mis-mapping (top crop rows never visited, middle band
  visited with multiplicity), single reader (DistanceMapMetric_Kernel, called only from
  costFunctionDIRECT_DILATION at src/compute/DIRECT_DILATION.cpp:80), found by review
  against the CPU reference (CropIndexToGlobal in test/unit/test_metric_semantics.cpp),
  fixed by arithmetic correction + pins. **This is an index-logic bug, not a memory-safety
  defect.** [Source: src/compute/distance_map_metric.cu:27-34;
  .panoptes/optimizer-deep-dive/synthesis.org Finding 1]
- **Verdict on reach**: Rust cannot reach this class of bug. A wrong operator in a kernel
  is invisible to ownership/borrow-checking; a Rust rewrite of the kernel
  (rust-cuda/cuda-oxide) changes the language, not the arithmetic. The buffer-ownership
  hazard at the C-ABI seam (R2.2 layer correction 2) is real but is preserved, not fixed,
  by a C-ABI seam: raw pointers crossing a seam keep raw-pointer semantics on both sides —
  ownership there must be fixed by seam design (opaque handles, explicit transfer in/out),
  in any language. The deep-dive run already assigns ownership the same way: compute owns
  buffer state, manager owns the object graph, coordinator registers callbacks only
  (synthesis.org Finding 5, Round 2 seam contract). [Source:
  .panoptes/optimizer-deep-dive/synthesis.org Finding 5 R2;
  src/compute/CostFunctionManager.cpp:100-134]
- **What Rust would actually buy at jtml_domain** (honest framing): (a) compiler-checked
  initialization — of the 7 documented cost-path bugs, DD_NEW_POLE_CONSTRAINT.cpp:134 is a
  genuine uninitialized read (UB, "can be a signalling NaN", synthesis.org Finding 1 R3)
  that Rust's init rules would reject if that code were Rust; (b) exhaustive ADTs for the
  variant slots (DirectOptimizer::Options selection/ties/split_rule enum classes,
  direct_optimizer.h:47-72; StageKind); (c) single-owner buffer discipline in the pure
  algorithm layer. But the 7-bug corpus is predominantly *logic* (Y_dist≡X_dist no-op,
  always-Trunk tautology, sym_trap x→z swap, the index formula) — caught by review +
  CPU-reference pins, not by the type system. **Net verdict: Rust is a
  correctness-instrument and testability play for the pure algorithm layer (fits the
  R15/PBT norm and the planned pure-core shape), NOT a GPU-safety play, NOT a fix for the
  documented failure history.** The one hardware corruption was index arithmetic; the
  ownership risk lives below the seam where Rust would sit. [Source:
  .panoptes/optimizer-deep-dive/synthesis.org Finding 1, R3 wave-1;
  include/domain/direct_optimizer.h:47-72]

** R2.4 SIMT/coalescing is a latent lever — CONFIRMED (single-pose sequential eval, no batching)

- Verified: per-eval dispatch is one cost call per pose — callActiveCostFunction()
  switches on the active cost name and calls the per-eval function
  (src/compute/CostFunctionManager.cpp:281-299, costFunctionDIRECT_DILATION at
  DIRECT_DILATION.cpp:58 "called every time the optimizer wants to query the cost function
  at a given point"); biplane_mode_ defaults false (CostFunctionManager.cpp:95) and is a
  constructor/UploadData parameter (CostFunctionManager.cpp:111,133). No batching exists
  anywhere in the cost path. [Source:
  src/compute/CostFunctionManager.cpp:95,111,133,281-299;
  src/compute/DIRECT_DILATION.cpp:58-62]
- The DIRECT loop is sequential, but each iteration's evaluations are pairwise independent
  (TrisectPotentiallyOptimal evaluates 2×N centers from a pre-loop snapshot) — **batchable
  with replay-ordered bookkeeping, no kernel rewrite**; constraint:
  FastImplantDilationMetric writes into the rendered buffer, so batches need
  double-buffered render output + duplicate score buffers (deep-dive Finding 5). [Source:
  .panoptes/optimizer-deep-dive/synthesis.org Finding 5 R2]
- Language consequence (the sharp finding): **the batching decision and the seam-shape
  decision are the same decision.** The deep-dive contract pins DirectOptimizer's
  injection as std::function<double(const Point6D&)> single-eval, with an optional batch
  sibling std::function<std::vector<double>(const std::vector<Point6D>&)> (synthesis.org
  Finding 5 R2). If Rust takes the domain layer, the batch seam is where Rust's
  Vec/ownership ergonomics and SoA population layout (round-1 F3: coalescing favors SoA)
  actually pay; the coalescing lever is exercised by making the batch population SoA in
  the kernel-facing buffers, which is a data-shape contract the language layer must
  expose. Decide the batched-seam shape before locking the language — the two decisions
  are coupled. [Source: .panoptes/optimizer-deep-dive/synthesis.org Finding 5 R2; round-1
  F3 sources]
