#+TITLE: Data-Centric Design: When the Shape and Flow of Data Drives the Architecture
#+DATE: 2026-08-13
#+PANOPTES_ANGLE: 03-data-centric-design

* Summary

There is a large, well-documented, language-agnostic body of work — not folklore — on making the shape and flow of data the primary axis of architecture: dataflow / pipes-and-filters / blackboard / implicit-invocation as architectural styles (Garlan & Shaw 1994, POSA), data-oriented design as a mindset (Acton, Fabian, Llopis, Nystrom), data-oriented programming as a value/immutability discipline (Sharvit), and functional-core-imperative-shell as the canonical boundary rule for compute systems (Bernhardt). The user's instincts are grounded: "the way the data is shaped, how that gets passed around, the objects/structs I operate on" is precisely the vocabulary these sources use. But the sources also say the opposite of the user's three beliefs: (a) layering-by-responsibility is one *code-ownership* scheme, not the natural default — data-flow styles decompose by *data transformation* instead; (b) structs/objects are not the natural unit of design — layout (SoA vs AoS), value semantics, and ownership discipline are; (c) "my layers are fine, they lack authority" is a category error — data-centric architecture doesn't give the existing layer stack authority, it replaces the decomposition axis, which is why a data-shaped structure would look visibly different (hot/cold splits, batch-shaped evaluation data, value payloads at boundaries, no object graphs in the hot path).

* Key Findings

** A named family of data-centric architecture styles exists, with authoritative primary sources

- Dataflow programming: the program is a directed graph of operations with data flowing along edges; execution is driven by availability of data inputs, not control flow. [Source: https://en.wikipedia.org/wiki/Dataflow_programming ; https://devopedia.org/dataflow-programming]
- Pipes and filters: incremental transformation of a data stream by independent filters connected by pipes; components are data source / filter / pipe / sink. [Source: https://www.tutorialspoint.com/software_architecture_design/data_flow_architecture.htm ; https://learn.microsoft.com/en-us/azure/architecture/patterns/pipes-and-filters ; Garlan & Shaw, "An Introduction to Software Architecture" (1994): https://ia800801.us.archive.org/17/items/DTIC_ADA288356/DTIC_ADA288356_text.pdf]
- Blackboard: a shared structured memory (the blackboard, with levels/panels) that independent knowledge sources read from and write to, coordinated by a scheduler; originated in the Hearsay-II speech-understanding system. [Source: https://en.wikipedia.org/wiki/Blackboard_(design_pattern) ; https://architectural-patterns.net/blackboard ; https://dev.to/lovestaco/the-blackboard-pattern-a-framework-for-complex-problem-solving-4o1p]
- Implicit invocation / event-driven: components communicate by announcing events; other modules are invoked implicitly without direct coupling — "an event announcement implicitly causes the invocation of procedures in other modules." [Source: https://en.wikipedia.org/wiki/Implicit_invocation ; Garlan & Shaw 1994: https://ia800801.us.archive.org/17/items/DTIC_ADA288356/DTIC_ADA288356_text.pdf]
- Repository / data-centered styles (shared data store with independent processes) are a separate SEI-recognized family alongside data-flow styles. [Source: https://softwareresearch.net/fileadmin/user_upload/Teaching/SS06/SE2_02_ArchStyles.pdf]
- The authoritative catalog is Pattern-Oriented Software Architecture, Vol. 1 (Buschmann, Meunier, Rohnert, Sommerlad, Stal), which defines Pipes-and-Filters, Blackboard, and the rest as named patterns. [Source: https://www.amazon.com/Pattern-Oriented-Software-Architecture-System-Patterns/dp/0471958697 ; https://en.wikipedia.org/wiki/Pattern-Oriented_Software_Architecture]
- Confidence: high (all primary/canonical sources).
- Relevance to this project: these styles are exactly the "external grounding" the user asked for; they decompose systems by *data transformation* (pipes/filters), *shared state* (blackboard/repository), or *event flow* (implicit invocation) — none by responsibility-based layering. The existing jtml stage-graph container and injected-cost seams are primitive instances of this family (a dataflow of registration stages feeding a cost consumer) but were derived from testability, not from a documented style.

** Data-oriented design (DOD): two core principles with named proponents

- Mike Acton (CppCon 2014 keynote, "Data-Oriented Design and C++"): "The purpose of all programs, and all parts of those programs, is to transform data from one form to another. If you don't understand the data, you don't understand the problem." [Source: https://cppcon.org/third-keynote-2014/ ; video: https://www.youtube.com/watch?v=rX0ItVEVjHc ; lecture notes: https://calpoly-iandunn.github.io/csc476/lectures/09-data-oriented-design]
- Two core principles distilled from the talk: (1) understand the data first, design around it; (2) "there is never 'one' of anything important — design around the 'multiple' case, not the single case." [Source: https://calpoly-iandunn.github.io/csc476/lectures/09-data-oriented-design]
- DOD contrasts with OOP: OOP "organises source code around data types rather than physically grouping individual fields and arrays in an efficient format for access by specific functions," and often hides layout under abstraction layers, while a data-oriented programmer "wants to consider this first and foremost." [Source: https://en.wikipedia.org/wiki/Data-oriented_design]
- The canonical book is Richard Fabian, *Data-Oriented Design* (2018): "Understand the goal, understand the data, understand the hardware, develop the solution"; the full text is available free. [Source: https://www.dataorienteddesign.com/dodbook/ ; PDF: https://www.dataorienteddesign.com/dodbook.pdf ; Amazon: https://www.amazon.com/Data-oriented-design-engineering-resources-schedules/dp/1916478700]
- The early articulation is Noel Llopis, "Data-Oriented Design (Or Why You Might Be Shooting Yourself in The Foot With OOP)" (2009). [Source: http://gamesfromwithin.com/data-oriented-design (canonical URL, cited by Wikipedia: https://en.wikipedia.org/wiki/Data-oriented_design)]
- Data locality as a mechanical basis: modern CPUs load 64–128-byte cache lines; organizing data contiguously in processing order produced a 50x speedup in Nystrom's controlled benchmark (same computation, different layout). [Source: https://gameprogrammingpatterns.com/data-locality.html]
- A 2025 measurement study (A* search, OOD vs DOD, single- and multi-threaded) found DOD had fewer cache misses and faster execution in multi-threaded runs, though thread-management overhead made single-threaded faster for that fine-grained task. [Source: https://arxiv.org/abs/2512.07841]
- Confidence: high for principles and sources; medium for the specific 50x and arXiv numbers (single benchmarks, different workloads).
- Relevance to this project: the user's belief (b) "objects/structs are the natural unit of design" is precisely the claim DOD rejects. The GPU cost function (poses in, costs out) is literally "transforming data from one form to another"; "design around the multiple case" points straight at batching evaluations rather than modeling single evaluations.

** Data-oriented programming (DOP): immutability and separation of code from data (complementary, not the same as DOD)

- Sharvit's four language-agnostic principles: (1) separate code from data; (2) represent data with generic structures (maps/arrays); (3) treat data as immutable — changes are new versions of data, references may change but values never do; (4) separate data schema from data representation. [Source: https://blog.klipse.tech/dop/2022/06/22/principles-of-dop.html]
- Motivation: data as a first-class citizen — "manipulate data inside a program with the same simplicity as numbers or strings"; benefits include predictable behavior, simpler testing, and easier concurrency (immutable data is safe to share). [Source: https://blog.klipse.tech/dop/2022/06/22/principles-of-dop.html]
- Immutability is achievable in any paradigm; cost is structural sharing or copying, so it must be applied where it pays (boundaries, shared state) rather than inside hot loops. [Source: https://deepwiki.com/viebel/data-oriented-programming/6.1-immutability-and-structural-sharing]
- Confidence: high (author's own published principles; primary).
- Relevance to this project: this is the language-agnostic frame for "value-semantic snapshots": a pose, a cost vector, a run payload are data; whether they are `struct Point6D` passed by value (as the local OptimizerRunDriver/launch payloads already do) or reference-tracked objects is a DOP-style design decision. It gives authority to the user's instinct that the "structs I'd be operating on" matter more than which layer owns the code.

** Boundary-crossing patterns in production compute apps center on data ownership and transfer — not code layering

- The canonical boundary rule is functional-core / imperative-shell (Gary Bernhardt, "Boundaries"): a pure, side-effect-free core that transforms values; an imperative shell that handles I/O, threads, GPU, UI; data crosses the boundary only as simple values ("simple values as the boundaries between components and subsystems"). [Source: https://www.destroyallsoftware.com/talks/boundaries ; https://www.destroyallsoftware.com/screencasts/catalog/functional-core-imperative-shell ; https://functional-architecture.org/functional_core_imperative_shell/]
- Value-copied immutable payloads across thread boundaries: Qt's implicit sharing gives value semantics with copy-on-write — objects passed by value share data until a write detaches (QPen::setCapStyle → detach(); QPixmap p2 = p1 shares until p2 is painted). This is the framework-native way to pass data-shaped values across QML/QObject boundaries without manual deep copies. [Source: https://doc.qt.io/qt-6/implicit-sharing.html]
- Double buffering / producer–consumer: decouple production from consumption so both sides run at their own pace on alternating buffers; "underlies the rendering system of just about every game." [Source: https://gameprogrammingpatterns.com/double-buffer.html ; https://en.wikipedia.org/wiki/Producer%E2%80%93consumer_problem]
- Message passing / actor model: interaction only through asynchronous message passing, no shared mutable state — "eliminates shared mutable state at the architectural level." [Source: https://en.wikipedia.org/wiki/Actor_model ; Hewitt: https://arxiv.org/pdf/1008.1459v1]
- CPU↔GPU boundary: data residence is the design fact. "Performance is best when data is resident in the memory of the processor accessing it"; CUDA offers explicit placement (cudaMemcpy), pinned host memory for asynchronous transfers (DMA cannot chase pageable pages), zero-copy mapped memory, and unified/managed memory. [Source: https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/understanding-memory.html ; https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html ; https://arpanpathak.github.io/gpu-parallel-book/chapters/part2_cuda_cpp_kernels/ch04_memory_management_data_movement.html ; https://stackoverflow.com/questions/5209214/default-pinned-memory-vs-zero-copy-memory]
- How this differs from layering-by-responsibility: layers answer "which module's code does this work"; boundary patterns answer "what crosses, in what shape, at what cadence, with what synchronization." The architecture of a compute app is mostly the second question — which is why a layer diagram is silent on the things that make or break it (e.g., 5 synchronous D2H memcpys per evaluation, per the local context).
- Confidence: high (primary docs: Qt, NVIDIA; canonical texts: Bernhardt, Nystrom, Hewitt).
- Relevance to this project: local context reports ~15 kernel launches and ~5 sync D2H memcpys per evaluation at ~7k evals/s — a data-flow description, not a layer description. The GPU cost function is a shared-data boundary (device buffers owned by jtml_compute), and per NVIDIA guidance the design question is "where is the data resident and how often does it move," not "which layer is responsible."

** Struct/object design principles for compute-heavy code (layout, semantics, ownership)

- Value semantics for compute: objects that behave like values (copies are independent, assignment is cheap via shared data) are the Qt-endorsed pattern and the C++ move-semantics idiom; sinks use rvalues to avoid hidden copies. [Source: https://doc.qt.io/qt-6/implicit-sharing.html ; https://stackoverflow.com/questions/29927808/performance-with-value-semantics]
- Views/spans: std::span is a non-owning view over contiguous elements with static or dynamic extent — "describes an object that can refer to a contiguous sequence of objects"; passing views instead of owning containers keeps ownership at one site. [Source: https://en.cppreference.com/cpp/container/span ; https://johnfarrier.com/exploring-c-stdspan-part-5-performance-and-practicality/]
- Ownership discipline: "Ownership is the defining discipline of high-performance C++"; smart pointers, views, and value semantics provide zero-overhead abstractions when used correctly. [Source: https://gist.github.com/wyattgill9/d29aa9551177e2113d8dfd19a7bece8d]
- SoA vs AoS: "array of structures (AoS), structure of arrays (SoA) ... are contrasting ways to arrange a sequence of records in memory" of "interest in SIMD and SIMT programming"; SoA is the canonical parallel-array layout, contrasted with the AoS typical of OO designs; a 40–60% improvement from layout alone is reported in one C++ study, and layout choice is a first-class CUDA optimization (coalescing). [Source: https://en.wikipedia.org/wiki/AOS_and_SOA ; https://en.wikipedia.org/wiki/Data-oriented_design ; https://azad2171.github.io/soa_vs_aos_memory_layout_cpp/ ; https://asc.ziti.uni-heidelberg.de/Files/St11ASX_CUDA.pdf ; https://cuda.live/tutorials/optimization]
- Hot/cold splitting: split data into a "hot" piece touched every pass and a "cold" piece used rarely, so cache lines carry only hot data; Nystrom warns it is "somewhere between a black art and a rathole" — apply where hot paths justify it. [Source: https://gameprogrammingpatterns.com/data-locality.html]
- Packed contiguous arrays over pointer graphs: arrays of components (not pointers to components) removed pointer-chasing and made the update loop 50x faster; keep conceptual entities as views *into* the arrays rather than owning graphs. [Source: https://gameprogrammingpatterns.com/data-locality.html]
- Arena/region allocation: arena allocators give "rapid allocation and bulk deallocation" with reduced fragmentation — "we don't have to fear allocating and freeing memory during frames"; the standard technique for per-frame or per-iteration scratch. [Source: https://www.bytesbeneath.com/p/the-arena-custom-memory-allocators ; https://medium.com/@sgn00/high-performance-memory-management-arena-allocators-c685c81ee338 ; https://medium.com/@ramogh2404/arena-and-memory-pool-allocators-the-50-100x-performance-secret-behind-game-engines-and-browsers-1e491cb40b49]
- Structural vs nominal typing: C++ is nominal (types are identified by name/declaration), while structural typing checks shape — relevant because "shape" of data is a first-class concept in data-centric design, and generic data structures (DOP principle #2) deliberately keep shape in the data rather than in the type graph. [Source: https://medium.com/@thejameskyle/type-systems-structural-vs-nominal-typing-explained-56511dd969f4]
- Confidence: high on canonical references (cppreference, Qt, NVIDIA, Nystrom, Wikipedia); medium on the specific blog benchmarks (40–60%, 50x, 50–100x are workload-dependent).
- Relevance to this project: Point6D poses are the natural SoA/AoS question (a batch of poses as a flat `float/double*` of 6×N is the GPU-friendly shape; a vector of 6-field structs is the OO shape), and the optimizer loop is the archetypal hot/cold case (rectangles/costs hot; provenance/metadata cold). Value-copy payloads (OptimizerRunLaunch) already embody value semantics — the missing piece is a stated ownership model for the shared GPU buffers.

** Where data lives and who owns it (CPU vs GPU, heap vs arena, one owner vs shared)

- CPU vs GPU: "Performance is best when data is resident in the memory of the processor accessing it" — residence should follow access pattern, with explicit placement APIs; managed/unified memory is a convenience with data-migration costs. [Source: https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/understanding-memory.html]
- Heap vs arena: general-purpose allocators are "complex, spanning thousands of lines"; arenas trade generality for speed and locality where lifetime is scoped (per frame / per optimization iteration). [Source: https://medium.com/@sgn00/high-performance-memory-management-arena-allocators-c685c81ee338 ; https://www.bytesbeneath.com/p/the-arena-custom-memory-allocators]
- One owner vs shared: shared-mutable is the failure mode; the options are (1) one owner + views (spans), (2) copy-on-write value semantics (Qt implicit sharing detaches on write), or (3) message passing with immutable payloads (actor model) — never shared mutable state without a synchronization protocol. [Source: https://doc.qt.io/qt-6/implicit-sharing.html ; https://en.wikipedia.org/wiki/Actor_model ; https://gist.github.com/wyattgill9/d29aa9551177e2113d8dfd19a7bece8d]
- Decision rule that falls out of the sources: data residence and ownership are decided by *who touches the data, how often, and from which execution context* — the inverse of deciding by which layer is "responsible" for it.
- Confidence: high (primary NVIDIA and Qt docs).
- Relevance to this project: the shared GPU state in jtml_compute is exactly the "one owner vs shared" decision: NVIDIA's guidance implies device-resident buffers owned by the compute module, with only small value-shaped results crossing back per evaluation — which is a data-flow contract the current layering documents only implicitly.

** What "design around the data" means concretely for an optimizer loop that consumes poses and produces costs

- The optimizer's own literature is data-centric: DIRECT (Jones, Perttunen, Stuckman 1993) is "a modification of the standard Lipschitzian approach" that "carries out simultaneous searches using all possible constants from zero to infinity" — its working state is a set of hyperrectangles with sampled center values, diameters, and a potentially-optimal set derived from those values. [Source: https://link.springer.com/article/10.1007/BF00941892]
- There is an entire paper on DIRECT's *data structures* (Gablonsky & Kelley, "Dynamic Data Structures for a Direct Search Algorithm"): the algorithm's performance "depends on the characteristics of the objective function, the problem dimension, and the desired solution accuracy," and the paper designs the hyperrectangle storage/sampling/subdivision data structures explicitly — i.e., the reference DIRECT implementations (Fortran 1998–2001, C port) are built around data layouts, not around an object model of rectangles. [Source: https://link.springer.com/article/10.1023/A:1019992822938 ; https://people.cs.vt.edu/~shaffer/Papers/COAP02.pdf ; https://github.com/DataReportRe/FPCC/blob/main/DiRect/README.md]
- A data-shaped framing of "consume poses, produce costs": (1) pose batch = flat array of N×6 parameters (the "multiple case" — Acton's second principle); (2) cost evaluation = transformation of that array into a flat array of N costs, ideally one device-resident pass (batch), not N separate launches; (3) DIRECT bookkeeping = hyperrectangle metadata (center, diameter, index) as packed records; (4) selection step = sorting/partitioning by value+diameter — a data transformation; (5) the GPU cost function itself is a pipes-and-filters pipeline (preprocessing → kernels → reduction → D2H result). Each stage's output is the next stage's input type; the architecture is the type pipeline.
- FCIS maps onto this directly: the pure core (DIRECT's rectangle math, selection, iteration bookkeeping) consumes and produces values; the imperative shell (kernel launches, D2H copies, stream sync, UI reporting) exists only at the edges. [Source: https://www.destroyallsoftware.com/talks/boundaries ; https://functional-architecture.org/functional_core_imperative_shell/]
- The DOD lens predicts the dominant cost is data movement, not arithmetic: cache lines (CPU side) and host↔device transfers (GPU side) — matching the local context where ~5 sync memcpys per eval are the suspicious seam. [Source: https://gameprogrammingpatterns.com/data-locality.html ; https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html]
- Confidence: high for the DIRECT algorithm/data-structure facts (primary papers); the JTML-shaped mapping is this angle's synthesis, marked as such.
- Relevance to this project: this is the answer to "what would a data-shaped structure look like": stage graph = dataflow of transforms on pose/cost arrays; DIRECT state = packed rectangle records; cost function = a batch transform with a documented device-residence contract; the injected `std::function` cost seam is the filter boundary in pipes-and-filters vocabulary. Angle 07 turns this into concrete JTML options.

** Failure modes of data-centric design (and the sources' own warnings)

- Premature optimization: Nystrom's explicit "when to use it" for data-locality work is *when you have a performance problem* — "don't waste time applying this to some infrequently executed corner of your codebase"; the result of unneeded optimization "is almost always more complex and less flexible." [Source: https://gameprogrammingpatterns.com/data-locality.html]
- Premature layout coupling: hot/cold splitting and layout tuning are "somewhere between a black art and a rathole" — easy to get sucked into endless data rearranging for unknown gains. [Source: https://gameprogrammingpatterns.com/data-locality.html]
- Paradigm tension: Llopis/Wikipedia note DOD "is also incompatible with most other paradigms" due to its layout emphasis, and Fabian argues it is not inherently exclusive — the dispute itself is a warning that data-centric and OO structures coexist badly inside the same hot path. [Source: https://en.wikipedia.org/wiki/Data-oriented_design ; https://www.dataorienteddesign.com/dodbook/]
- Over-abstraction of the style itself: "a big misunderstanding ... is that we can design a static library or set of templates to provide generic solutions to everything" — DOD resists generic container-of-everything solutions. [Source: https://www.dataorienteddesign.com/dodbook/ (text hosted at https://i.warosu.org/data/sci/img/0147/04/1660532961271699.pdf)]
- Blackboard overkill: architectural-patterns.net's own problems note — the architecture "may be overkill" unless you have real scheduling heuristics; if simple selection works, the shared-repository machinery adds complexity without benefit. [Source: https://architectural-patterns.net/blackboard]
- Immutability costs: DOP's immutability requires structural sharing or copies — cheap for boundaries, wrong for hot loops. [Source: https://blog.klipse.tech/dop/2022/06/22/principles-of-dop.html ; https://deepwiki.com/viebel/data-oriented-programming/6.1-immutability-and-structural-sharing]
- Loss of polymorphism/flexibility: data-locality patterns push away inheritance, interfaces, and dynamic dispatch; Nystrom keeps the friendly object model for non-hot paths and reserves packed arrays for the hot loop ("This doesn't mean we need to get rid of GameEntity"). The design lesson: apply data-centric structure where the data flow is real; keep abstraction where it is. [Source: https://gameprogrammingpatterns.com/data-locality.html]
- Confidence: high (all warnings are from the canonical sources themselves).
- Relevance to this project: the local R12 "no premature abstraction" norm is the mirror image of this failure-mode list — the sources do not license unfettered layout churn; they license a data-flow map of the real seams (pose/cost pipeline, GPU boundary, DIRECT state) before any restructuring. R15 behavior preservation constrains any reshuffle.

* What Could Not Be Verified

- The magnitude claims (50x, 40–60%, 50–100x) come from single-author benchmarks/blogs with different workloads and machines; direction is consistent, magnitudes are not transferable to this project's kernel mix.
- Whether the arXiv DOD-vs-OOD study (a student journal paper on A*) generalizes beyond A*-like workloads — treat as weak supporting evidence only.
- The exact internal data layout of the current local DIRECT implementation, its cost-evaluation batching, and whether the ~5 sync D2H memcpys per evaluation are individually necessary — the local context states the numbers but not the per-memcpy justification; verifying requires reading jtml_compute (outside this angle's scope).
- Whether Llopis's 2009 gamesfromwithin.com article is still reachable at its canonical URL (Wikipedia cites it; the site is legacy).
- Fabian's book PDF is the author's free full-text version; pagination/edition of the print book may differ from the free text.
- No sensitive data encountered; nothing redacted. All fetched pages were treated as source material only.

** DIRECT storage — pointer-chasing AoS with per-insert new (CONFIRMED; angle-07 C3 SoA claim CORRECTED)
- Actual layout (direct_data_storage.h:54-65 + direct_data_storage.cpp:16-44, 80-133):
