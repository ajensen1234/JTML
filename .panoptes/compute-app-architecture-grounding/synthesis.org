* Executive Summary
The deepen pass changed the headline but did not overturn it: **JTML's layering is grounded-by-accident, and the round-2 re-anchor confirms that its seams map to the production classes once the mapping is pointed at the right objects.** What was mislabeled in round 1 was the *class cast*: the production worker is not the persistent-thread OptimizeCoordinator — it is MainScreen → OptimizerRunController → OptimizerManagerRunDriver, a fresh-thread-per-run driver with the H3 bounded-wait destructor contract, and OptimizeCoordinator is a test-only state machine. Once re-anchored, every external-framework mapping round 1 drew still holds: Qt-free jtml_domain (10 .cpp TUs, purity real but unenforced) = functional core; injected `std::function<double(const Point6D&)>` cost = hexagon output port; per-cut gates + GPU oracle = characterization testing + fitness functions; the H3 thread contract = Qt's deleteLater-on-owning-thread rules implemented faithfully (with one knowingly-bent DirectConnection flag-flip). The round-1 MVVM verdict survives and sharpens: binding-centric MVVM remains unsupported as the organizing principle for the compute path (and production doesn't do it), while the VM layer JTML actually built — SettingsBridge, a bounded 36-property form-state VM at user frequency with no worker writes and no bloat — is the *correct* Presentation-Model-for-form-state deployment; the new structural nuance is that all five QML bridges ride the slower QV8Bindings binding path (setContextProperty objects), so the bridge surface should stay small and per-frame data should stay off Q_PROPERTYs.

The other headline correction is quantitative. The measured baseline is ~7,000 evals/s ≈ 143 μs/eval wall (RTX 3090 Ti), refuting the derived 20-60 evals/s by ~2 orders. The per-eval D2H boundary is 24-32 bytes across 3-5 pinned int copies — which is a *latency* story (5 synchronous default-stream pipeline drains per eval), not a transfer-budget story (224 KB/s aggregate is nothing on PCIe). Consequently the highest-leverage compute-side levers are the launch/drain structure (C5 CUDA-graph, C6 stream-ordering — upside band [7%, 50%] of wall, unmeasured) and honest instrumentation (Cut 0), not byte-counting; the host-side data shape (C3) is real hygiene (pointer-chasing AoS confirmed) but bounded by the GPU/sync term until a profile says otherwise. No C-option dies at the measured baseline; C3 and C5 convert from "premised wins" into "framed hypotheses with a defined measurement step."

The user's three working beliefs resolve as follows. (a) "MVVM works great for CRUD, compute land is idiosyncratic": TRUE about the binding machinery (frequency mismatch — view-driven low-frequency bindings vs data-driven high-frequency streams — not "CRUD-ness"), FALSE if extended to the whole pattern family: separated presentation + the dependency rule are exactly what a compute core needs, and the case studies plus Qt's own docs confirm it. (b) "The authoritative material skews CRUD/web": the popular layer does, but a substantive compute/scientific canon exists (Carver et al., Wilson et al., AOSA VTK/ITK by the frameworks' creators, Mattson/McCool, Berkeley dwarfs, BSSw) and the neutral theory canon (Parnas, POSA, Cockburn, ISO 42010, Ousterhout) transfers directly. (c) "No external grounding for data shaping": strong frameworks exist — Bernhardt's functional-core/imperative-shell, Wlaschin's type-driven domain modeling, Kleppmann's encoding/evolution, Kent's data-model-as-choice, DOD's layout-first doctrine — and the repo's actual hot path is now a *measured* data-flow story.

**Recommended course of action** (full trade-off surface in the Options Menu): (1) document the existing shape as authoritative against the *production* classes — A1 + F3, XS cost, mapping OptimizerRunController/Core/Driver, the `std::function<double(const Point6D&)>` port, the H3 contract, and the 10-TU domain; (2) produce the data-flow map including the per-eval hot path against the measured numbers — C1, S cost — which directly answers the user's stated desire for "how the data is shaped, how it gets passed around, the objects/structs"; (3) run the Cut 0 instrumentation (cudaEvent/nvtx3 + Nsight) before any compute-side change — the kernel-vs-sync breakdown is the single most decision-relevant missing measurement, and NVIDIA's own APOD mandate is profile-first; (4) fix the honest meter (optimizer_manager.cpp:1199 + mainscreen.cpp:4598) whenever a UI touch happens — it is a real unit bug, small, and evidence-anchored; (5) then choose among C5/C6/C3/C4 on the measured breakdown, and treat the Rust surface (D2) as a correctness-instrument play for the pure algorithm layer — version-compatible with CUDA 12.4 (both rust-cuda ≥12.0 and cuda-oxide 12.x+), maturity is the blocker, and it is NOT a GPU-safety play (the documented failure history is index-logic bugs Rust cannot reach).
